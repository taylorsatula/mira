# web/ — browser UI: four vanilla-HTML pages plus static assets, served directly by FastAPI file routes in `main.py`

## Rules

- **Serving contract lives in `main.py`, not here.** Page routes (`/chat`, `/memories`, `/domaindocs`, `/settings`, each with trailing-slash twins) are defined inside the `if Path("web").exists():` block in `main.py` and gate behind `auth_api.get_current_user_for_pages` — an unauthenticated visit round-trips through the session cookie (`single` mode) or gets the 401 envelope (`multi`). `/`, `favicon.ico`, `apple-touch-icon.png`, `manifest.json`, and the `/assets` StaticFiles mount carry no auth so a gated page can still load its own JS/CSS. A new page needs both an HTML file here and a route there; adding only one leaves it 404 or unserved.
- **No bundler, globals-only JS.** All client JS is plain `<script>`-tag vanilla JS communicating through `window.*` exports; ownership of that convention and the module set belongs to `web/assets/javascript/AGENTS.md`. Consequence for this directory: any new script must be added to a page's load manifest by hand (see Wiring) — there is no import graph to discover it.
- **Cache-busting is a manual `?v=` query string.** Every `<script src>` and `<link rel="stylesheet">` in the page manifests carries a `?v=<tag>` query; when an asset's content changes, its `?v=` value must be bumped in every page that references it or browsers keep the stale copy. There is no build step to do this for you. The four `<img src="...?v=8SSMG8w">` icon references follow the same convention.
- **Vendored libs bump together.** `web/assets/javascript/marked.min.js` (marked v12.0.0) and `web/assets/javascript/purify.min.js` (DOMPurify 3.0.9) are loaded as a pair, before any renderer, and only by `web/chat/index.html`; their `?v=` query must change with a version bump. Never load one without the other — the sanitize allowlists in `messaging.js`/`history.js` assume both globals exist.
- **Only `web/chat/index.html` loads the full app chain.** `settings/`, `domaindocs/`, and `memories/` load a minimal manifest (`theme.js` + `style.css` in `<head>`, then `api-client.js`, a page feature module, `sidebar.js`) and bootstrap `window.miraAPI` themselves in an inline script. They never load `core.js`, so anything shared out of those inline scripts must not depend on `AppState`, `elements`, or any `core.js` export — hoist such code into `assets/javascript/` per the child map instead.
- **Page logic lives inline in the HTML.** `web/settings/index.html` and `web/memories/index.html` carry their entire page controller as an inline `DOMContentLoaded` script (tab router, API calls, DOM wiring), and `web/domaindocs/index.html` defines the whole `DomaindocsCompanion` class inline. This is deliberate: page-specific logic stays out of the shared `assets/javascript/` module set. Only promote code there when a second page needs it.
- **Dead assets — do not wire or rely on them.** `sw.js` (service worker, network-first cache) is registered by nothing and loaded by no page. `web/assets/base.css`, `web/assets/forms.css`, `web/assets/prose.css`, and `web/assets/neon-cyberpunk-elements.css` are loaded by no page (`doc.css` even references `/learn/*.html` pages that do not exist in this tree); every page loads only `web/assets/style.css`. `web/assets/javascript/segment-timeout.js` is orphaned per the child map. Fixing any of these means wiring them deliberately, not assuming they are live.

## Files

- `chat/index.html` — the main chat page and the only consumer of the full app chain: loading screen, sidebar, notifications/announcement banner, inline-history container, compose bar with attachment/thinking/repulsion/tool/queue/domain popovers, repulsion-feedback and location-consent modals. Owns the full script load-order manifest (see Wiring). Also carries the inline pre-paint theme bootstrap that all four pages copy.
- `settings/index.html` — settings page with hash-tab router (`#profile`, `#general`, `#credentials`, `#tools`, `#automations`) driven by an inline `pageLoaders` registry; inline script implements profile/portrait/LoRA user-model CRUD via `actions.executeAction('user'|'portrait'|'lora', ...)`, trigger-rule management against `/v0/api/triggers/rules` (`cns/api/trigger_rules.py`), HTTP-credential management (`user` domain `list/store/delete_http_credential`), and API-token management via raw `fetch` to `/v0/auth/api-tokens*` with CSRF headers (`auth/api.py` owns that contract). Gotchas: `btn-delete-history` calls `window.miraAPI.search.clearSearchContinuum` — no `search` service exists on `MiraAPIClient`, so the guard alerts "not available yet" (dead path, guarded); `performLogout` redirects to `/login`, which has no page in mira-OSS. `Calls: cns/api/actions.py`, `cns/api/trigger_rules.py`, `auth/api.py`
- `domaindocs/index.html` — domain-knowledge editor. Inline `DomaindocsCompanion` class wraps `DomainKnowledgeManager` (from `domain-knowledge.js`) with 1s change polling, idle-gated re-render (skips while the user typed within 5s, preserves focus/cursor), edit-conflict detection against section `updated_at` with a keep-mine/keep-MIRA modal, drag-and-drop reorder within a parent level, and archive/unarchive via `?archived=true`. Initialization is event-driven: `apiClient.auth.onAuthChange` login event constructs the companion; `initPage()` validates the session and redirects to `/login` otherwise. `Calls: cns/api/actions.py` (via `domain-knowledge.js`), `cns/api/data.py`
- `memories/index.html` — memory browser: server-paginated list via `miraAPI.data.getData('memories', {limit, offset, search})` with client-side filtering/sorting on the loaded page (not server-side), single/bulk delete plus create via `actions.executeAction('memory', ...)`, per-row link counts (inbound/outbound), and a second `#domain-knowledge` tab whose four textareas just create memories at importance 0.7 — they do not write domain docs, despite the heading. `Calls: cns/api/data.py`, `cns/api/actions.py`
- `manifest.json` — PWA manifest: `start_url: "./chat/"`, standalone display, single icon `apple-touch-icon.png`. Served unauthenticated from the repo root route.
- `favicon.ico`, `apple-touch-icon.png` — browser-expected root files served by dedicated unauthenticated `FileResponse` routes in `main.py` (the apple-touch icon additionally lives in `chat/` for the manifest's relative icon path; pages reference it as `../chat/apple-touch-icon.png`).
- `sw.js` — network-first service worker skipping `/v0/` and WebSocket URLs; never registered by any page (see Rules). Treat as dead code.
- `assets/` — static tree mounted at `/assets` by `main.py`. JavaScript modules are documented in `web/assets/javascript/AGENTS.md`.
- `assets/style.css` — the single stylesheet every page loads; owns the full visual system including the light/dark themes keyed off `<html data-theme>` (set by the inline theme bootstrap; `theme.js` only maintains it afterward — no `@media` interaction). Large (4.5k lines) because the four pages share one sheet; page-specific styles are inline `<style>` blocks or inline `style=` attributes in the HTML.
- `assets/fonts/` — four self-hosted woff2 fonts (IBM Plex Mono, Roboto, Noto Emoji, Minni), preloaded by every page's `<head>` with `/assets/fonts/...` absolute paths. `web/chat/index.html` additionally pulls one Google Fonts family (Bagel Fat One) for the Repulsed! indicator — the only external font dependency.
- `assets/images/` — UI icons (`icons/`, `icons/toolicons/` per-tool), logo variants, and arrows; referenced with `?v=` cache-bust queries from the page manifests.

## Wiring

- **Script load manifests (order is the contract; JS ownership is the child map's).** Each page lists what it loads, in order:
  - `web/chat/index.html`: inline theme bootstrap → `theme.js` (head) → `style.css` → body → `marked.min.js` + `purify.min.js` → `api-client.js` → `core.js` → `ui.js`, `sidebar.js`, `messaging.js`, `history.js`, `events.js` → `settings.js`, `domain-knowledge.js`, `collapse-animation.js`, `location.js`, `repulsion-feedback.js`. The dependency-correct insertion rules for new scripts are owned by `web/assets/javascript/AGENTS.md` (Rules: load order); this HTML is where they are enforced.
  - `web/settings/index.html`: theme bootstrap → `api-client.js` → `tool-config.js` → `sidebar.js` → inline page script. No `core.js`, no markdown libs.
  - `web/domaindocs/index.html`: theme bootstrap → `api-client.js` → `sidebar.js` → `domain-knowledge.js` → inline `DomaindocsCompanion` script. No `core.js`, no markdown libs.
  - `web/memories/index.html`: theme bootstrap → `api-client.js` → `sidebar.js` → inline page script. No `core.js`, no markdown libs.
  Adding a script to a page means editing that page's manifest at a dependency-correct position; reordering breaks the `window.*` contract the same way it does inside the child directory.
- **Per-page auth bootstrap.** Non-chat pages do their own session validation: `settings/` and `memories/` instantiate `MiraAPIClient` inline and call `auth.validateToken()`; `domaindocs/` gates all functionality on the `onAuthChange` login event and hard-redirects to `/login` on failure. The WS/chat session contract itself is owned by `auth/` and `cns/api/` — this directory only consumes it through `api-client.js`.
- **Sidebar is shared chrome.** `sidebar.js` is loaded by all four pages and marks the active nav item per page via `aria-current`; chat-only sidebar actions no-op off the chat page per the child map's contract.
- **Cross-page navigation:** `web/settings/index.html` "Edit Memories" → `/memories`; chat's domain popover "Manage Domains" → `/domaindocs` (new tab); domaindocs unarchive → redirect to `/domaindocs`; all logout paths redirect to `/login`, which does not exist in mira-OSS.
