## Rules

- `export_user_bundle.py` hand-rolls the per-user crypto instead of importing it: `hmac.new(get_service_config("userdata_encryption_key").encode(), uid.encode(), hashlib.sha256).digest()` → `Fernet(base64.urlsafe_b64encode(session_key[:32]))` duplicates `utils/userdata_manager.py`'s `derive_session_key` + `_create_fernet` exactly, and must keep doing so — a derivation change lands in both the same commit, or every exported `encrypted__` value decrypts to None under an `UNDECRYPTABLE__*` flag while the bundle still passes its own manifest: the loss surfaces only in use, on the receiving install.
- The import procedure lives in two twin texts that change together: the `AGENTS_MD` template inside `export_user_bundle.py` (shipped in the zip, addressed to the receiving install's agent) and `import_user_bundle.py`'s docstring (the implementation spec). Both pin: manifest sha256 verification before any write, the account question (never guess), import order (profile → continuums → messages → entities → memories; original UUIDs kept so cross-links resolve, `user_id` remapped only), embeddings regenerated on the receiving install's model, row-count re-verification, and the hosting-gap acknowledgment on first conversation. Drift → an import done per one text fails the other's verification.
- The exporter's run legs, beyond its docstring's list: `requirements.txt` pins psycopg v3 only, so the script's `import psycopg2` is a hand-install obligation — a venv built from requirements dies at import until you install psycopg2 into it (`cryptography` is pinned; psycopg2 is not). The AppRole env vars and `PYTHONPATH` at the hosted app root carry the rest (AppRole story owned by root `AGENTS.md`, Commands). Every leg fails before the first query — a misrun never yields a partial bundle; only the `db_path` hardcode (Files card) fails silently, after.

## Files

- `__init__.py` — docstring only, no re-exports.
- `export_user_bundle.py` — hosted-instance per-user exporter: builds the migration zip — `messagesmemories.json` (users row + six Postgres tables, embedding/search-vector columns dropped at export), `userdb.json` (per-user SQLite, `encrypted__` prefixes stripped on decrypt), `manifest.json` (sha256 + row counts), and the embedded `AGENTS.md` import contract (twin Rule above). Entry: `EMAIL`/`OUT` (argv; default output `/tmp/<email>.zip`), `PG_TABLES` (table → dropped-columns spec), `AGENTS_MD`, `write_json`; the module runs top-to-bottom, `write_json` its only function. Gotcha: `db_path` hardcodes the deployed root `/opt/mira/app/data/users/<uid>/userdata.db` — on any other tree the `os.path.exists` guard silently skips the whole SQLite half: a valid zip with empty `userdb.json` tables and a self-consistent manifest, so receiving-side verification passes with the tool data gone.
- `import_user_bundle.py` — fresh-install importer: SPEC ONLY — the body is `print(__doc__)`; the docstring is the contract (the seven steps the twin Rule pins). Kept as the import-side twin of the zip's embedded `AGENTS.md`; implementing the docstring re-activates the file — until then an import runs by hand per the zip's `AGENTS.md`, and the printed text is not a working import. Usage names `<bundle.zip> [--account <email>]`.
- `migrate.py` — the database step runner CLI (`migrate [--plan|--dry-run] [--report-marker] [--elevation] [--stamp] [--adopt-drifted]`, `restore <STAMP>`, `backup [--output DIR]` (a full snapshot into an operator-chosen directory — read-only against the install, no steps/BASELINE/classification, destination never swept or retention-counted), `status [--json]`, `lint`, `reconcile` (drops undeclared `MIRA_*` lines from the settings file — `utils/env_reconcile.py`; no Vault, no database), `generate`), argparse and rendering only over `utils/schema_migrations.py` (no SQL, no psycopg). Exit codes: 0 ok, 1 a step failed after the backup, 2 refusal (nothing changed), 3 blocked (database or Vault unreachable, no superuser access, no terminal for typed input, backup failed). `main` attaches a TOAST-level filter to the `clients.vault_client` logger (`_DropVaultToast`), so the operator's update transcript carries no Vault lifecycle lines. `--plan --report-marker` prints the plain-English plan, then JSON between `MIRA_PLAN_BEGIN`/`MIRA_PLAN_END` (read by `deploy/update.sh`). Callers: `deploy/update.sh` (plan, phase 6.5, restore, status), `deploy/postgresql.sh` (fresh install), `deploy/docker/scripts/mira-migrate.sh` (every container start), `ui/tui/migrate.py` (`mira migrate`/`restore`/`backup`/`status`). Needs `PYTHONPATH` = install root and the AppRole env; `lint` opens no connection and reads no Vault. Gotcha: `main(argv, resolve_conninfo=…)` is the probe seam — production binds `vault_admin_conninfo` (the `mira_admin` URL through `clients/postgres_client.py:PostgresClient._parse_database_url`); never add a conninfo flag or env var. `generate` is the one exception, maintainer-only: `--superuser/--host/--port` name a local superuser for throwaway databases; it reads no Vault and never touches `mira_service`.
- `post_server_post.py` — the post-server POST CLI: thin shim, `raise SystemExit(post_server_cli())`, imported from `utils/power_on_self_test.py` — the stable operator surface for the post-server phase; the module's own two-phase `main()` stays with `utils/AGENTS.md`. Args: `--base-url` (default `default_post_server_base_url()`: configured host, `0.0.0.0`/`::` folded to `127.0.0.1`), `--deadline-seconds`, `--json`; exit 0 iff `required_passed`, else 1; two required checks, `http_health` + `http_diagnostics`. Gotcha: the checks read as plain HTTP, but `_check_http_diagnostics` pulls `diagnostics_token` from Vault (`get_service_config`) for `/v0/api/health/threads` — run with the mira-app AppRole env vars or a healthy server reports FAIL on the diagnostics check.

## Wiring

- Exporter reads: `clients.vault_client.get_database_url("mira_service", admin=True)` → direct psycopg2 connection on the BYPASSRLS `mira_admin` role (sanctioned for this operator script: explicit email/`user_id` WHERE clauses, no RLS contextvar) + `get_service_config("userdata_encryption_key")` for the twin derivation (Rule above). Vault contracts owned by `clients/AGENTS.md` (`vault_client.py`).
- Consumers (reverse-edge sweep, not recall): `rg 'export_user_bundle|import_user_bundle'` → this directory only, plus map text; `rg 'post_server_cli'` → `utils/power_on_self_test.py` (defines it; its docstring names this shim) + the shim. The scripts' consumers are the operator and, for the zip, the receiving install's agent reading the embedded `AGENTS.md`.
- Schema edge: the exporter's fixed 12-column `users` SELECT couples to `deploy/mira_service_schema.sql` (schema owned by `deploy/AGENTS.md`) — the SELECT names 12 of the table's 22 columns today; the ten outside (`is_active`, `webauthn_credentials`, `memory_manipulation_enabled`, `daily_manipulation_last_run`, `subject_kind`, `deletion_requested_at`, `soft_deleted_at`, `purge_deadline`, `demo_start_at`, `demo_expires_at`) already vanish from every exported profile, no exclusion rationale documented anywhere, while the `PG_TABLES` side (`SELECT *`) auto-includes growth. `users` gains a column → same commit here; a deliberately dropped column needs the exclusion stated at the SELECT, or the profile silently loses person-state a migration wants.
