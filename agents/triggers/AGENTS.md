# agents/triggers/ — what makes a sidebar work item exist, and the rule surface over it

## Files

- `__init__.py` — the re-export only; nothing in the repo imports the package root, and a class in `__all__` alone is unreachable by both the dispatcher and the rules API.
- `registry.py` — the one trigger registry, read by dispatch and by the rules API. Open it before adding, removing, or reordering a trigger.
- `rule_filter.py` — the dispatch-time reader of a user's `trigger_rules` rows. Open it when a user reports work items missing rather than skipped, or when a stored rule looks inert.
- `heartbeat_trigger.py` — due-brief discovery for the HeartbeatAgent, plus the device-wake publishing job. Open it before changing when a brief wakes, what its work item carries, or when a device is told to sleep.
- `memory_floor_trigger.py` — floor-mode curation discovery: a bounded random sample of low-value un-tended memories, pre-fetched with texts and scores. Open it before changing floor cadence, sample shape, or what the curator is handed.

## Wiring

- Registration: `utils/sidebar_jobs.py:register_sidebar_jobs` → `TRIGGER_CLASSES` loop → `dispatcher.register_trigger` → the `sidebar_dispatcher_poll` job → `register_device_wake_job` → the `heartbeat_device_wake_aggregate` job. The wake job is skipped when `config.sidebar_dispatcher.enabled` is false (the early return above it) and also when `config.heartbeat.enabled` is false (its own guard), and it always borrows `config.sidebar_dispatcher.poll_interval_minutes` — one cadence knob, not two. Counterparts: `utils/AGENTS.md`, `agents/AGENTS.md`.
- Eligibility: `agents/sidebar.py:_get_eligible_users` unions `heartbeat_armed_users` into the pollable user set, a table written by `tools/implementations/heartbeat_tool.py:upsert_armed_user` and `refresh_armed_marker`. A trigger whose users are dormant and unarmed is never polled, so it must ride that table or widen the union. Counterpart: `agents/AGENTS.md`.
- Rules protocol: `cns/api/trigger_rules.py` writes `trigger_rules` rows, validating `trigger_id` and `field` against `registered_trigger_specs()` and compiling `pattern` at write time → `rule_filter.apply_trigger_rules` as the last step of each discovery → a matching rule's `prompt` rides `context['rule_prompt']` → `agents/base.py:SidebarAgent._build_system_prompt`, the single consumption point, so no agent wires rule prompts itself; it appends the rule prompt after the agent rubric and before the iteration-status line. The table's DDL is `utils/userdata_manager.py:_init_trigger_rules_schema`, created at every user-DB open. Counterparts: `cns/api/AGENTS.md`, `agents/AGENTS.md`.
- Floor sample: `MemoryFloorTrigger.check_for_new_items` → `lt_memory/db_access.py:LTMemoryDB.get_floor_candidates` (below the importance threshold, stale or never tended, `ORDER BY random()`, RLS-scoped) → `get_memories_by_ids` pre-fetch → the agent → `update_last_tended`, which is what closes the loop through the candidate query's NULL-and-age branch. Costs come from `config.memory_curator.floor_*`. Counterpart: `lt_memory/AGENTS.md`.
- Briefs: discovery calls `tools/implementations/heartbeat_tool.py:ensure_briefs_table` at poll time and reads `state = 'armed'` rows; brief storage, the `encrypted__` columns arriving already decrypted, and the `heartbeat_armed_users` writes all live there. Counterpart: `tools/implementations/AGENTS.md`.
- Device binding: `publish_device_wake_aggregate` → `utils/device_binding.py:notify_heartbeat_sleep`, its sole caller. An empty `heartbeat_armed_users` publishes nothing and `notify` never raises, so a shim failure leaves the device at full power — the unbound behavior. Counterpart: `utils/AGENTS.md`.
- Agent handoffs, both through the lazy `agent_class` property: heartbeat hands a `briefs` list of full decrypted payloads each carrying its own `dispatch_stamp`; the floor hands `FloorContext`. The class then reaches its agent through the spec hop — `trigger.agent_class` → `agents/specs.py:spec_for_agent_class` (keyed on the class's `agent_id`, raising `KeyError` when `SUBAGENT_SPECS` holds no row for it) → `agents/spawn.py:spawn_subagent`. Counterparts: `agents/implementations/AGENTS.md`, `agents/AGENTS.md`.

## Rules

- Adding a trigger is a coordinated edit in this order: the class in a new module here (with `trigger_id`, `interface_name`, `check_for_new_items`, `on_dispatched`, `FILTERABLE_FIELDS`, a lazy `agent_class`), its member in `registry.py:TRIGGER_CLASSES`, its re-export in `__init__.py`, the consuming agent class, its row in `agents/specs.py:SUBAGENT_SPECS`, and its config block in `config/config.py`. Registration anywhere else is dead code. Skip the registry member and the trigger never dispatches while the rules API rejects its `trigger_id`; skip the spec row and every spawn of that agent raises `KeyError` inside `agents/sidebar.py:_spawn_agent`, caught per user, so the trigger reports success and silently discovers nothing; skip `on_dispatched` and every dispatch raises `AttributeError` after the agent has already spawned; skip `FILTERABLE_FIELDS` and the trigger registers with zero addressable fields and no error. Protocol depth and `item_id` keying doctrine: `agents/HOW_TO_BUILD_AN_AGENT.md`.
- The module level of a trigger file imports only `WorkItem` and `rule_filter`; agent class, config, DB managers, timezone helpers and `heartbeat_tool` all resolve inside the method or the property. `registry.py` imports both trigger modules at module level and `register_sidebar_jobs` walks that chain at boot, so a module-level agent import drags the agent's own tool module into scheduler registration — the boot cost the lazy properties exist to prevent. Anything constructed once per process (`MemoryFloorTrigger._db`) belongs in `__init__`, never in a poll.
- Every `check_for_new_items` ends with `return apply_trigger_rules(user_id, self.trigger_id, items)`; a trigger that returns items without it silently ignores the user's rules. The filter is opt-in per trigger (no enabled rows → every item passes) and exclusive per item (rows present → only a regex-matching item survives; drops are logged, not raised). Renaming a context key silently drops every discovered item for every user holding a rule on it, and `rule_filter.py`'s docstring carries why a missing key and a non-matching value are indistinguishable there.
- A work-item context key is a three-way same-commit contract: the trigger builds it, `FILTERABLE_FIELDS` declares it (the API validates rule fields against that declaration), and the consuming agent renders it — `FloorContext` for the floor, the `briefs` keys for heartbeat. Rename one side and the agent renders nothing, rules match a dead field, or the API accepts a field no item carries. `registered_trigger_specs` reads the declaration with `getattr(cls, "FILTERABLE_FIELDS", ())`, so a missing attribute is zero fields with no error; heartbeat's empty tuple is a declaration that its payload is a list, not an omission. Non-string context values never match a pattern, so lists stay undeclared.
- Every trigger class defines `on_dispatched` because `agents/sidebar.py:_poll_user` calls it unconditionally after a successful spawn, inside the per-user trigger loop. The live violation is `HeartbeatTrigger`, which has no such method: each heartbeat dispatch raises `AttributeError` after the agent thread starts, caught per user, so the run survives and a later trigger in `TRIGGER_CLASSES` would be skipped for that tick — heartbeat is last in the list today, which is the only reason nothing else is lost.
- The floor's use-day gate stays the inline per-user modular check, `get_user_cumulative_activity_days() % cfg.floor_use_days` inside `check_for_new_items`. It is the sanctioned spelling of `get_users_due_for_job`'s MOD condition for a caller that already holds the user; converge it back and the trigger re-queries the whole users table every poll. Never add a last-ran column to make the gate stateful — the drift defect `utils/AGENTS.md` names.
- The dispatch stamp is twin code with the agent's failure accounting: discovery writes `last_wake_at = format_utc_iso(now)` on every dispatched brief and carries that string as each brief's `dispatch_stamp`; `agents/implementations/heartbeat_agent.py` reads `state = 'armed'` with `last_wake_at == dispatch_stamp` as carried-but-never-reported, and every `heartbeat_tool` report outcome overwrites `last_wake_at`. Move any one of the three and unreported briefs wedge armed behind a stale stamp until the completion sweep is their only exit.

Elsewhere: this directory owns what makes a work item exist, not the decision to run one or what the agent does with it. The add-a-trigger walkthrough — protocol shape, `item_id` keying doctrine, the opt-in double gate, pre-fetch cost shape — is `agents/HOW_TO_BUILD_AN_AGENT.md`; why a bullet on this page reads as it does is `git log`. Every other destination this directory reaches is an edge — see `## Wiring` above.

## The wake cycle, poll to re-arm

The case that decides most of the Rules above: one armed brief goes from due to re-armed.

1. `utils/sidebar_jobs.py:register_sidebar_jobs` instantiates each `TRIGGER_CLASSES` member on the dispatcher, skipping `HeartbeatTrigger` when `config.heartbeat.enabled` is false. That is the registration half of the double gate; `check_for_new_items` re-checks the same flag at poll time. Only the disable direction lands without a restart — an enable flip waits for one, because the class never joined the dispatcher.
2. A poll tick sets the user contextvar from the dispatcher's eligibility union, `heartbeat_armed_users` included — the edge under `## Wiring` that keeps an armed user pollable while dormant.
3. Discovery re-checks the flag, runs `ensure_briefs_table`, selects `state = 'armed'` ordered by `next_wake_at`, and keeps the rows whose parsed wake time has passed. An unparseable `next_wake_at` logs a warning and skips that brief, so one corrupt row never fails the poll.
4. All due briefs collapse into ONE work item whose `item_id` is the earliest due brief's wake time truncated to the minute. Batching exists because briefs cluster — a morning's re-arms — and one agent run beats N. A re-arm writes a new `next_wake_at`, so the next due window is a genuinely new item and the same window never double-dispatches.
5. Before returning, discovery stamps every dispatched brief and puts that stamp in its context entry. The stamp precedes the return: stamp afterwards and the agent's comparison reads a pre-dispatch value.
6. `apply_trigger_rules` shapes the item, then the dispatcher's dedup decides whether to spawn. Every run that enters `SidebarAgent.run` exits through `_exit`, which writes the `sidebar_activity` row before `on_completion`, and `max_retries` is the base default 0 — a failed window is never re-dispatched.
7. Each report outcome (fired, false, bailed) overwrites `last_wake_at`. `on_completion` then finds briefs still `armed` with `last_wake_at` equal to the stamp and hands them to `apply_run_failure`, which either re-arms with backoff (a NEW `next_wake_at`, so a new window) or marks `failed_permanently` at `max_failures`. That report-overwrite is what makes stamp equality mean "unreported": a new outcome that skips the overwrite counts a reported brief as a straggler, and this sweep is the only unwedge path, which is why it runs on every terminal status — rejected and the iteration-cap failure included — and not only success.
8. Every state transition refreshes `heartbeat_armed_users`; the wake job reads the earliest `earliest_wake_at` across users and publishes it to the device binding.
