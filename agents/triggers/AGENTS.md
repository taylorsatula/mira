# agents/triggers/ — dispatcher work-item discovery triggers

## Rules

- Triggers are pure discovery: `check_for_new_items(user_id)` returns `WorkItem`s or `[]`, makes no judgment calls, and performs no dedup — the dispatcher owns dedup via `sidebar_activity`. This contract is declared on the `SidebarTrigger` protocol in `agents/sidebar.py`; the one-home statement lives in `agents/sidebar.py`'s docs (protocol docstrings). `on_dispatched()` is for side effects only; `MemoryFloorTrigger.on_dispatched()` is a no-op.
- The floor cadence gate is an inline per-user modular check (`activity_days % cfg.floor_use_days`) using `get_user_cumulative_activity_days()`, not a call to `get_users_due_for_job()` — the dispatcher already iterates users, so re-querying all users per poll is both wasteful and wrong for this shape.
- `item_id` must stay stable per activity-day cycle (`floor_{user_id}_{activity_days}`) — the dispatcher's `sidebar_activity` dedup depends on the same key reproducing within a cycle; changing the key format silently breaks dedup.
- `agent_class` is a lazy `@property` that imports `MemoryCuratorAgent` at access time (`agents/triggers/memory_floor_trigger.py`). There is no import cycle: `memory_curator_agent` → `tools.implementations.memory_tool` → `lt_memory` terminates — `lt_memory` never imports from `agents/` (the `on_memories_stored` callback in `lt_memory/factory.py` is the seam, not an import). The laziness defers heavy infra-client initialization (`memory_tool` pulls `clients/hybrid_embeddings_provider.py` and `clients/valkey_client.py` at module load) out of `utils/sidebar_jobs.py`'s import path; the dispatcher reads `trigger.agent_class` per dispatch (`agents/sidebar.py` `_spawn_agent`), so a module-level import in the trigger would work but eagerly initialize those clients at registration time.
- Failed floor runs are not retried: `max_retries=0` by dispatcher policy; the next due activity day re-samples. A retry path here would double-process the same sample.

## Wiring

- Dispatch contract (this directory imposes on `agents/sidebar.py`): the dispatcher keys each `WorkItem` as `{interface_name}:{item_id}` for both its in-flight thread map and the `sidebar_activity` SQLite dedup row — `interface_name` and `thread_id` are the UPSERT conflict key written by `_write_activity_record` (`agents/base.py`). Therefore `interface_name` must be globally unique per trigger and `item_id` stable per dedup cycle (see Rules); changing either silently re-dispatches already-processed work or suppresses new work.
- `agents/sidebar.py` imports nothing from this directory; the import is one-way: `memory_floor_trigger.py` imports `WorkItem` from `agents.sidebar`, and `utils/sidebar_jobs.py:register_sidebar_jobs` imports and registers `MemoryFloorTrigger` (lazily, after `agents.sidebar` is fully loaded). `WorkItem`'s position in `agents/sidebar.py` is boot-irrelevant.
- Lazily injected dependencies: `LTMemoryDB(get_shared_session_manager())` at `__init__` time (`lt_memory/db_access.py`, `utils/database_session_manager.py`); `MemoryCuratorAgent` at `agent_class` access time, which the dispatcher reads per dispatch (`agents/sidebar.py` `_spawn_agent`). RLS user context is ambient during `check_for_new_items` — the dispatcher sets it per user via `set_current_user_id()` in `poll()`; the trigger's per-user modular gate relies on `get_user_cumulative_activity_days()` (`utils/user_context.py`) reading that contextvar.
- Ordering constraint: the use-day gate must run before `get_floor_candidates()` — after the gate, the query is the only cost per poll; reversing them pays the SQL scan for users not due.

## Files

- `__init__.py` — re-exports `MemoryFloorTrigger` only.
- `memory_floor_trigger.py` — `MemoryFloorTrigger` (`trigger_id = "memory_floor"`, `interface_name = "memory_curator_floor"`). No-LLM SQL discovery: `LTMemoryDB.get_floor_candidates()` (`lt_memory/db_access.py`) selects un-archived memories with `importance_score` strictly below `cfg.floor_threshold` and untended past the `cfg.floor_unseen_days` cutoff (or never tended but old), `ORDER BY random()` capped at `cfg.floor_sample_size` (`config.config.MemoryCuratorConfig`), then `get_memories_by_ids()` fetches texts/scores so the agent judges without a read round-trip. The sampling is random, not deterministic — only the *eligibility* predicate is deterministic SQL. Emits a single floor-mode `WorkItem` whose context matches `FloorContext` (owned by `agents/implementations/memory_curator_agent.py`). Consumers: `agents/sidebar.py` (SidebarDispatcher poll loop) → spawns `MemoryCuratorAgent` in floor mode.
