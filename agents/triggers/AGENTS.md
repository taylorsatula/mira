# agents/triggers/ — dispatcher work-item discovery triggers

## Rules

- The trigger registry is one list: `registry.py:TRIGGER_CLASSES`. `utils/sidebar_jobs.py:register_sidebar_jobs` instantiates and registers every class in it on the dispatcher, and `cns/api/trigger_rules.py` derives its valid trigger/field set from `registered_trigger_specs()` at request time — what dispatches is exactly what is rule-addressable. A trigger class not in the list is unreachable by the dispatcher AND rejected by the rules API; a second hand-maintained trigger table anywhere is a defect (the API's old `_TRIGGER_FIELDS` drifted into exactly that and was deleted).
- Each trigger class declares `FILTERABLE_FIELDS` — the regex-matchable scalar keys of its work-item context, derived from that context's shape. `MemoryFloorTrigger.FILTERABLE_FIELDS = ("mode",)` (`FloorContext`: `mode` is the only scalar string key; `memories` is a list, not matchable). A trigger with no scalar context fields declares an empty tuple — the API then lists it with an empty field set; names are never invented.
- User filter rules are applied at the end of discovery via `rule_filter.py:apply_trigger_rules(user_id, trigger_id, items)` — discovery shaping, not a dispatch judgment (dedup/retry/terminal decisions stay dispatcher-owned). No enabled rules → every item passes (filtering is opt-in); with rules, an item passes only when an enabled rule's pattern case-insensitively regex-matches its context value for the rule's field (non-string values never match); a matching rule's `prompt` is attached as `context['rule_prompt']`, which `SidebarAgent._build_system_prompt` (`agents/base.py`, owned by `agents/AGENTS.md`) appends to the system prompt after the agent rubric — the single consumption point, so every agent honors rule prompts without per-agent wiring. The `scope` column is trigger-specific stored metadata — no registered trigger has a scoped surface, so nothing matches on it today.
- Triggers are pure discovery: `check_for_new_items(user_id)` returns `WorkItem`s or `[]`, makes no dispatch judgment calls, and performs no dedup — the dispatcher owns dedup via `sidebar_activity`. This contract is declared on the `SidebarTrigger` protocol in `agents/sidebar.py`; the one-home statement lives in `agents/sidebar.py`'s docs (protocol docstrings). `on_dispatched()` is for side effects only; `MemoryFloorTrigger.on_dispatched()` is a no-op.
- The floor cadence gate is an inline per-user modular check (`activity_days % cfg.floor_use_days`) using `get_user_cumulative_activity_days()`, not a call to `get_users_due_for_job()` — the dispatcher already iterates users, so re-querying all users per poll is both wasteful and wrong for this shape.
- `item_id` must stay stable per activity-day cycle (`floor_{user_id}_{activity_days}`) — the dispatcher's `sidebar_activity` dedup depends on the same key reproducing within a cycle; changing the key format silently breaks dedup.
- `agent_class` is a lazy `@property` that imports `MemoryCuratorAgent` at access time (`agents/triggers/memory_floor_trigger.py`). There is no import cycle: `memory_curator_agent` → `tools.implementations.memory_tool` → `lt_memory` terminates — `lt_memory` never imports from `agents/` (the `on_memories_stored` callback in `lt_memory/factory.py` is the seam, not an import). The laziness defers heavy infra-client initialization (`memory_tool` pulls `clients/embeddings_provider.py` and `clients/valkey_client.py` at module load) out of `utils/sidebar_jobs.py`'s import path; the dispatcher reads `trigger.agent_class` per dispatch (`agents/sidebar.py` `_spawn_agent`), so a module-level import in the trigger would work but eagerly initialize those clients at registration time.
- Failed floor runs are not retried: `max_retries=0` by dispatcher policy; the next due activity day re-samples. A retry path here would double-process the same sample.

## Wiring

- Dispatch contract (this directory imposes on `agents/sidebar.py`): the dispatcher keys each `WorkItem` as `{interface_name}:{item_id}` for both its in-flight thread map and the `sidebar_activity` SQLite dedup row — `interface_name` and `thread_id` are the UPSERT conflict key written by `_write_activity_record` (`agents/base.py`). Therefore `interface_name` must be globally unique per trigger and `item_id` stable per dedup cycle (see Rules); changing either silently re-dispatches already-processed work or suppresses new work.
- `agents/sidebar.py` imports nothing from this directory; the import is one-way: `memory_floor_trigger.py` and `rule_filter.py` import from `agents.sidebar` (`WorkItem`), and `utils/sidebar_jobs.py:register_sidebar_jobs` imports `TRIGGER_CLASSES` from `registry.py` and registers an instance of every class (lazily, after `agents.sidebar` is fully loaded). `WorkItem`'s position in `agents/sidebar.py` is boot-irrelevant.
- Lazily injected dependencies: `LTMemoryDB(get_shared_session_manager())` at `__init__` time (`lt_memory/db_access.py`, `utils/database_session_manager.py`); `MemoryCuratorAgent` at `agent_class` access time, which the dispatcher reads per dispatch (`agents/sidebar.py` `_spawn_agent`). RLS user context is ambient during `check_for_new_items` — the dispatcher sets it per user via `set_current_user_id()` in `poll()`; the trigger's per-user modular gate relies on `get_user_cumulative_activity_days()` (`utils/user_context.py`) reading that contextvar.
- Ordering constraint: the use-day gate must run before `get_floor_candidates()` — after the gate, the query is the only cost per poll; reversing them pays the SQL scan for users not due.

## Files

- `__init__.py` — re-exports `MemoryFloorTrigger` only.
- `registry.py` — the single trigger registry: `TRIGGER_CLASSES` (the list the dispatcher registers from and the rules API derives its valid trigger/field set from), `TriggerSpec` (trigger_id / interface_name / filterable_fields, class-level metadata — no instantiation), `registered_trigger_specs()`, and an import-time duplicate `trigger_id`/`interface_name` check that fails loud rather than letting one trigger silently shadow another.
- `rule_filter.py` — `apply_trigger_rules(user_id, trigger_id, items)`: the dispatch-time consumer of `trigger_rules` rows (per-user SQLite via `get_user_data_manager`). Semantics owned by this directory's Rules; an uncompilable stored pattern raises (the API validates patterns at write time, so stored garbage is corruption, not user error).
- `memory_floor_trigger.py` — `MemoryFloorTrigger` (`trigger_id = "memory_floor"`, `interface_name = "memory_curator_floor"`, `FILTERABLE_FIELDS = ("mode",)` derived from `FloorContext`). No-LLM SQL discovery: `LTMemoryDB.get_floor_candidates()` (`lt_memory/db_access.py`) selects un-archived memories with `importance_score` strictly below `cfg.floor_threshold` and untended past the `cfg.floor_unseen_days` cutoff (or never tended but old), `ORDER BY random()` capped at `cfg.floor_sample_size` (`config.config.MemoryCuratorConfig`), then `get_memories_by_ids()` fetches texts/scores so the agent judges without a read round-trip. The sampling is random, not deterministic — only the *eligibility* predicate is deterministic SQL. Emits a single floor-mode `WorkItem` whose context matches `FloorContext` (owned by `agents/implementations/memory_curator_agent.py`), then applies the user's trigger rules via `apply_trigger_rules` before returning. Consumers: `agents/sidebar.py` (SidebarDispatcher poll loop) → spawns `MemoryCuratorAgent` in floor mode; `cns/api/trigger_rules.py` (validates against this class's `trigger_id`/`FILTERABLE_FIELDS` via `registry.py`).
