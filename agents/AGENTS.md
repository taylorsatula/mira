# agents/ — the autonomous sidebar-agent runtime: base-class loop mechanics and dispatcher

*Same deal when the idea involves MIRA acting on its own — watching something, tending something, digesting something while you're not around. Hand the spec to your pair-programming assistant with `HOW_TO_BUILD_AN_AGENT.md` and a new sidebar worker exists by the end of the session, no core-loop archaeology required.*

## Rules

- `SidebarAgent` (`base.py`) owns all loop mechanics; implementations define only `agent_id`, `model_config_name`, `available_tools`, `get_agent_prompt(work_item)`, `build_initial_message(work_item)`. Do not override `run()` — all termination cases (success, failure, timeout, sentry skip, input rejection, iteration cap) must flow through `_exit()`, which writes the `sidebar_activity` record and calls `on_completion()`. A subclass that bypasses `_exit()` leaves no dedup record and the dispatcher will re-dispatch the item forever. `complete_task` is terminal within its block: a successful `complete_task` mid-block breaks execution, trailing calls in that block are skipped (their side effects never commit), and `tool_results[-1]` is always its envelope. After `max_iterations` wind-down nudge there is one grace pass (`range(1, max_iterations + 2)`) where the model actually responds to the nudge; it renders as "N (grace)" — never "N+1/N" — in the overwatch header and any `_iteration_status()` addendum. No completion there → `_exit('failed')` as before.
- `thread_id` is a system concern, never an LLM decision: `_execute_tool_calls()` injects it (= `work_item.item_id`) into every `sidebar_tool` call, and `complete_task` additionally gets `interface_name`, `agent_id`, `run_count`. Tool schemas for agents must not expose these as LLM-fillable parameters.
- The `sidebar_activity` / `scratchpad` SQLite contract: DDL constants (`ACTIVITY_TABLE_DDL`, `SCRATCHPAD_TABLE_DDL`) are owned by `utils/userdata_manager.py` with the other per-user schemas (which also creates `sidebar_activity` at every user-DB open); `ensure_activity_schema()` in `base.py` runs them; writes go through the UPSERT in `_write_activity_record()` with `UNIQUE(interface_name, thread_id)`. Both the base class (failure records) and `tools/implementations/sidebar_tool.py` (`complete_task` records) create the same tables through `ensure_activity_schema()` — schema changes update the one DDL site plus `SidebarDispatcher` queries. **Both also write the same row for a completed run**: `complete_task` writes its terminal status (`handled`/`escalated`) first, then the completion path in `base.py:run()` routes that status into `_exit(activity_status=...)`. If `_exit` is ever called on the completion path without the tool's status, its `'failed'` default overwrites the terminal record — `AsyncActivityTrinket` then shows successes as failures, and at `max_retries > 0` the dispatcher re-dispatches every successfully completed item.
- Dedup and retry belong to the dispatcher (`sidebar.py`), never to triggers: `_dispatch_decision()` returns `dispatch` (no prior run), `retry` (`status == 'failed'` and `run_count <= agent_class.max_retries`), or `skip` (any terminal status in `_TERMINAL_STATUSES`). On retry it sets `work_item.context['prior_run']`; the base class prepends `build_recovery_context(prior_run)` to the initial message (default: `None`). Trigger-side dedup logic is forbidden — see `agents/triggers/AGENTS.md`.
- Sentry gate (`sentry_model_config_name`) and overwatch (`overwatch_model_config_name`) are opt-in per-class attributes, both resolved against existing `model_configs` routes (`clients/llm/AGENTS.md` owns the route set — never invent a route name). The sentry fails open (any LLM or parse error → proceed) and its response format is the `<decision>proceed|skip</decision>` / `<reason>` XML parsed by `parse_sentry_response()`. `sentry_max_tokens` / `overwatch_max_tokens` are per-request ceilings so a route change cannot widen them.
- Overwatch runs in a daemon thread per non-terminal iteration with `contextvars.copy_context()` so user context propagates; the agent loop is never blocked by it and overwatch failures log at `debug` and vanish. Late-arriving summaries must not downgrade terminal trinket states — that invariant is owned by `working_memory/trinkets/AGENTS.md`.
- Wall-clock timeouts come from `config.sidebar_dispatcher` (`SidebarDispatcherConfig` in `config/config.py`): `agent_timeout_overrides` is keyed by class name minus the `Agent` suffix, lowercased (`ForageAgent` → `"forage"`), falling back to `agent_timeout_seconds`; `agent_iteration_timeout_seconds` bounds a single iteration. Adding an override key that doesn't match this derivation silently uses the shared default.
- Trace capture is automatic: `AgentTrace` (with per-iteration `IterationTrace`/`ToolCallTrace`, optional `SentryTrace`) is finalized in `run()`'s `finally` and written to sidebar_agent/<item_id>.json under the user's tool-data dir. Traces are observability — write failures are swallowed at `warning` and must not affect the run.

## Files

- `base.py` — `SidebarAgent` ABC plus module-level helpers (`_get_tool_schemas`, `_execute_tool_call`, `_write_activity_record`, `_save_trace`, `_publish_trinket_refresh`). Entry points: `run()`, `load_agent_prompt()`, `ensure_activity_schema()`, the sentry/overwatch hook family (`build_sentry_message`, `parse_sentry_response`, `get_overwatch_context`, `on_overwatch_update`), and the completion hooks `_get_completion_trinket()` / `_build_completion_context()`. `_sanitize_work_item` truncates `raw_content` to 8000 chars, then runs `utils.untrusted_content.screen_untrusted` (two-tier screen, fail closed): `InjectionRejected` exits through `_exit('rejected')`; any other error — screen outage, missing credential, unparseable escalation verdict — propagates to `run()` and exits `'failed'`, never passing content through unscreened. `sidebar_tool` is always first in the assembled tool list (`_get_all_tool_names()`); `tool_schema_overrides` swaps a tool's schema wholesale. When `inherit_base_prompt=True` (default), `base_system.txt` from `config/prompts/agents/` is prepended — the prompt file inventory is owned by `config/prompts/AGENTS.md`. Consumers: everything in `agents/implementations/`, `tools/implementations/forage_tool.py`, `tools/implementations/sidebaragents_tool.py` (imports `_publish_trinket_refresh`).
- `sidebar.py` — `WorkItem` model, `SidebarTrigger` protocol (`check_for_new_items` returns ALL candidates; `on_dispatched` is idempotent side effects only), `SidebarDispatcher` poll loop. Entry points: `register_trigger()`, `poll()`, `_dispatch_decision()`, `_spawn_agent()`, `_maybe_cleanup()`. Per-poll cap `MAX_ITEMS_PER_USER_PER_POLL = 5`; in-flight tracking keyed `interface_name:item_id` against `max_concurrent_agents`; cleanup deletes `sidebar_activity` + cascade-deletes `scratchpad` notes past `_CLEANUP_RETENTION_DAYS` (30d), rate-limited to once per 24h per user. Consumer: `utils/sidebar_jobs.py`.
- `HOW_TO_BUILD_AN_AGENT.md` — agent-authoring walkthrough: agent-vs-tool-vs-trinket decision, architecture diagram, symbol-anchored pattern index, nine-step subclass walkthrough (class, prompt file, tool restriction, completion hooks, per-iteration hooks, overwatch, trigger, config, retries, sentry), direct-invocation alternative, security guardrails, the `run()` loop order, a grouped checklist, live verification, and reference implementations for all three agents. Trust: CURRENT — signatures verified against `base.py` (`get_agent_prompt(work_item)`, `__init__(tool_repo)`, `run(work_item, event_bus)`).
- `implementations/` — concrete agents (forage, whilethecatsaway, memory_curator). See `agents/implementations/AGENTS.md`.
- `triggers/` — dispatcher work-item discovery. See `agents/triggers/AGENTS.md`.
- `__init__.py` — empty marker, no re-exports.

## Wiring

- Scheduler path (registration chain, stated from this directory's side): the root boot sequence calls `utils/scheduled_tasks.py:register_sidebar_dispatcher_job`, which calls `utils/sidebar_jobs.py:register_sidebar_jobs` — that constructor is the only sanctioned registration point. It constructs `SidebarDispatcher(tool_repo, event_bus, max_concurrent_agents)` from `agents/sidebar.py`, registers `MemoryFloorTrigger` as the sole trigger, and binds `dispatcher.poll` to an APScheduler `IntervalTrigger` at `config.sidebar_dispatcher.poll_interval_minutes`. `poll()` iterates users active within 2 days (`sidebar.py:_get_eligible_users`) and sets/clears `set_current_user_id()`/`clear_user_context()` per user. Registering a trigger anywhere else is dead code.
- Spawn paths: (1) dispatcher `_spawn_agent()` — daemon thread running `agent.run(item, event_bus)` under `copy_context()`; (2) direct invocation — a tool creates a `WorkItem` and runs the agent itself (e.g. `tools/implementations/forage_tool.py`, integration-mode memory curation at the segment-collapse hook). Both paths end at the same `_exit()` → `sidebar_activity` → `on_completion()` chain.
- Tool boundary: agents call `sidebar_tool` (scratchpad + `complete_task`) and their declared `available_tools`; both tools are owned by `tools/implementations/AGENTS.md`, as are the agent-spawning tools themselves. `agents/base.py` only assembles schemas and injects identity.
- Completion publishing goes through `cns.core.events.UpdateTrinketEvent` on `continuum_id='sidebar'`; which trinket receives it is decided by the agent's `_get_completion_trinket()` override — trinket contracts are owned by `working_memory/trinkets/AGENTS.md`.
- Adding a sidebar agent end-to-end requires: agent class in `agents/implementations/` (child map), prompt file in `config/prompts/agents/` (`config/prompts/AGENTS.md`), completion trinket (`working_memory/trinkets/AGENTS.md`), and a discovery path (trigger here in `agents/triggers/` or a direct-invocation tool in `tools/implementations/`). Skipping the prompt file fails at first `get_agent_prompt()` call, not at import.
