# cns/infrastructure/ — durable conversation persistence and the hot Valkey cache every turn passes through

## Files

- `__init__.py` — docstring plus a `ContinuumRepository` re-export.
- `continuum_pool.py` — the `UnitOfWork` that stages and commits one turn, and the per-user-locked pool over it; `UnitOfWork._get_real_messages` is dead, with no in-repo caller. Open it before changing what a turn persists, in what order, or when the cache write is skipped.
- `continuum_repository.py` — the `messages` and `continuums` statement surface this package owns, and the segment sentinel status vocabulary, behind a module singleton; `load_messages_with_metadata` is dead, with no in-repo caller. Open it before changing a save path, a sentinel lookup, or a reload.
- `feedback_repository.py` — writes and reads the assessment signals the user-model pipeline synthesizes from. Open it before changing what synthesis is fed.
- `feedback_tracker.py` — synthesis timing and the stored user-model text with its pending check-in feedback. Open it before changing when synthesis runs or how check-in feedback is consumed.
- `persona_repository.py` — append-only Persona revisions, the current-revision pointer, and the evidence rows behind them. Open it before adding a writer to Persona history or a reader of its evidence.
- `valkey_message_cache.py` — the cached message list and the collapse-epoch counter. Open it before changing a cache read, write, or invalidation.

## Wiring

- Construction and boot: `cns/integration/factory.py:_initialize_session_cache` builds the session-cache loader, then calls `initialize_continuum_pool` with the repository `main.py` already resolved; `utils/power_on_self_test.py:_check_dependency_initialization` requires both singletons live. A pool built over a second repository instance commits through a different per-user connection pool than the one the API layer resolved. Counterpart: `cns/integration/AGENTS.md`.
- Turn: `get_or_create` → `increment_segment_turn` → the orchestrator stages into the `UnitOfWork` → `commit()` → post-commit callbacks publish. The epoch is captured before the message read, so a collapse anywhere after the read skips the commit's cache write instead of overwriting it. Counterparts: `cns/api/AGENTS.md`, `cns/services/AGENTS.md`.
- Collapse: `cns/services/segment_collapse_handler.py` rewrites the sentinel through `save_message`'s `ON CONFLICT (id) DO UPDATE`, then calls `continuum_pool.invalidate()`. Invalidation follows every sentinel write; skip it and the next `get_or_create` serves the pre-collapse segment from cache. Counterpart: `cns/services/AGENTS.md`.
- Extraction failure budget: `find_failed_extraction_segments` and `EXTRACTION_MAX_CONTENT_FAILURES` are defined here, and `lt_memory/processing/orchestrator.py:extract_unprocessed_segments` writes the two metadata keys this query's predicate tests, through `get_user_db_client` on this directory's repository. A freshly collapsed segment carries neither mark and must pass the filter; the sweep's writes must be what stops it passing. Rename either key or loosen the strict `<` on one side alone and the segment either re-enters the sweep on every pass or is excluded before its first attempt. Counterpart: `lt_memory/processing/AGENTS.md`.
- Assessment signals: `feedback_repository.py` imports `AssessmentSignal` from `cns/services/assessment_extractor.py` — this package's one upward import — so a field that type stops declaring is a field the repository keeps persisting as absent. Counterpart: `cns/services/AGENTS.md`.
- Session cache: a pool miss sends `cns/core/segment_cache_loader.py:load_session_cache` through `find_active_segment`, `find_collapsed_segments`, `load_segment_messages` and `load_continuity_messages`. Those finders' status filters are this directory's contract, so a filter changed here changes what the client sees as its next session. Counterpart: `cns/core/AGENTS.md`.
- Segment-content exclusion twin: `tools/implementations/continuum_tool.py:_fetch_context_messages` repeats `load_segment_messages`' boundary and notification predicates as its own SQL. Both change in one commit, or a tool-expanded window disagrees with the segment the cache loaded. Counterpart: `tools/implementations/AGENTS.md`.
- Cross-directory lender: `get_user_db_client` hands a per-user `PostgresClient` outside this package, and the singleton repository object crosses the same way — `cns/services/manifest_query_service.py` calls `find_all_segments`, `summary_generator.py` and `live_context_compaction_service.py` hold it from `main.py`'s construction path, and `segment_timeout_service.py` types its sweep on `ActiveSegmentRow`. A signature change on any of them reaches a consumer that never reads this directory; `rg 'get_user_db_client'` and `rg 'ContinuumRepository'` name them.
- Consumer sets: `rg 'FeedbackTracker'` and `rg 'PersonaRepository'` name every caller of the two tracking repositories. A new method on either lands with its caller's contract, since neither repository documents who owns the surrounding policy. Counterparts: `cns/services/AGENTS.md`, `auth/AGENTS.md`, `working_memory/trinkets/AGENTS.md` — which renders `get_lora_content`'s `synthesis_xml`/`needs_checkin` and `get_current_revision().directives` into prompt sections.
- Signup: `auth/database.py` must call `create_continuum` at account creation, because `get_or_create` raises `RuntimeError` for a user with no continuum, and `auth/seed_lora.py` then calls `FeedbackTracker.initialize_user` — a user without that row never synthesizes. Counterpart: `auth/AGENTS.md`.
- Operator docs: `docs/SEGMENT_SYSTEM.md` states these sentinel, pause and collapse mechanics at operator level, so a sentinel-behavior change verifies it against source in the same commit. Counterpart: `docs/AGENTS.md`.

## Rules

- Invalidation is one atomic operation, `delete_and_increment`, never a delete followed by a separate epoch bump. A writer holding the pre-collapse epoch lands its stale list in the gap between the two calls, and no later read can tell the copy is stale.
- One live sentinel per continuum — status `active` or `paused`, both live — enforced by the partial index `idx_messages_live_segment_unique` (`deploy/mira_service_schema.sql`). Every new sentinel query matches both statuses; the sanctioned active-only exception is `find_all_active_segments_admin`, whose timeout sweep must not treat a paused user as segment-less. An active-only match makes a paused user look segment-less, and the caller mints an id no persisted row carries.
- A sentinel is one message row for its whole life: `save_message`'s `ON CONFLICT (id) DO UPDATE` is how collapse rewrites it (`cns/services/segment_helpers.py:collapse_segment_sentinel` copies the row and flips status). Delete and reinsert instead and `find_segment_by_id` loses the segment's history while the collapse handler's pre-save re-read guard sees a different row than the one it claimed.
- Events that must observe durable state ride `UnitOfWork.add_post_commit_callback`; `cns/services/orchestrator.py` stages `TurnCompletedEvent` there. The callback list is cleared before it runs, so a callback may commit new work, and a callback exception propagates with the turn already durable. Publishing at build time instead makes subscribers observe a turn whose commit can still fail.
- `increment_user_activity_day` is called from exactly two places, both here: `save_message` and `save_messages_batch`, and only when the batch carries a `role == "user"` message. Its failure is logged, never raised. A third persistence path that skips the call makes every use-day job skip that user — the chain is owned by `utils/AGENTS.md` (`utils/user_activity.py`), and the call site is this directory's to keep.
- A new table lands in three places in one commit: its DDL and RLS policy in `deploy/mira_service_schema.sql`, a grant, and an entry in `clients/postgres_client.py:_RLS_COVERED_TABLES`, which is what arms the canary. A table missing from that tuple can be queried without user scope and nothing remarks on it — the silent cross-user read the canary exists to catch.

Elsewhere: this directory owns how conversation state is stored and cached, not the policy deciding when a segment ends or what a turn does with one. The schema's own column comments are `deploy/mira_service_schema.sql`; why a mechanism has its present shape is `git log`; signatures and per-method contracts are each file's docstring. Every other destination this directory reaches is an edge — see `## Wiring` above.

## Sentinel and epoch lifecycle, turn to collapse

1. Load: `get_or_create` takes the per-user lock and captures the epoch before reading anything. A hit serves the cached messages; a miss composes the session from `load_session_cache` and caches the result under the epoch it captured.
2. Turn entry: `increment_segment_turn` runs one subquery-pinned UPDATE against the live sentinel — turn count incremented, `paused_at` dropped, status back to `active`, `last_turn_at` stamped with arrival time. That stamp is the crash grace: a turn dying before its commit leaves fresh activity for the timeout sweep's lock probe to read once the request lock expires. No live sentinel means a fresh id allocated in memory and exposed through the `current_segment_id` contextvar, with nothing persisted yet.
3. Turn body: the orchestrator stages every durable message of the turn, tool results included, and `add_messages` trims oversized content in place so the in-memory copy matches the row about to be written.
4. Commit: the sentinel INSERT autocommits before the message transaction opens, then all messages land in one `execute_transaction`. A user-role message ticks the activity day; the cache write is a compare-and-set against the epoch from step 1. A batch failure invalidates the cache and re-raises.
5. Idle → claim: the timeout sweep publishes a timeout event for a live sentinel with no turn in flight; `_claim_collapse` then flips status to `collapsing` in one conditional UPDATE that also admits a claim older than its stale window, so a process death between claim and save does not strand the segment. Every racing claimant gets zero rows and aborts.
6. Collapse: the handler re-reads the sentinel, aborts if `last_turn_at` moved or the status left the claimable set, rewrites that same row through `save_message`, and invalidates — the delete and the epoch bump are one operation, so no writer holding the pre-collapse epoch can land stale content after it. The next load misses, reloads from the database, and the bumped counter agrees with the empty cache.
