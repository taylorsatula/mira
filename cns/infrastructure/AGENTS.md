# cns/infrastructure/ — persistence and caching for the CNS conversation graph

## Rules

- DB access splits two ways, and the split is per-repository, not per-call: `continuum_repository.py` builds per-user `PostgresClient` instances (RLS via `app.current_user_id`), while `feedback_repository.py`, `feedback_tracker.py`, and `persona_repository.py` go through `utils.database_session_manager.get_shared_session_manager().get_session(user_id)`. Cross-user sweeps use `get_shared_session_manager().get_admin_session()` (BYPASSRLS) — see `find_all_active_segments_admin()`, which must keep its `users.is_active = TRUE` join or the timeout sweep collapses segments of deactivated accounts.
- Never construct a `PostgresClient` per call. `ContinuumRepository` caches one client per user in `_db_cache`; the public accessor is `get_user_db_client(user_id)` — external modules use that, never reach into privates.
- `ContinuumRepository` is a module-level lazy singleton via `get_continuum_repository()`; `ContinuumPool` is initialized once at startup via `initialize_continuum_pool()` in `cns/integration/factory.py` and read via `get_continuum_pool()`. Both raise at first use if uninitialized — never construct them directly.
- The Valkey continuum cache has no TTL. Every continuum-cache write is epoch-guarded (`set_continuum_if_epoch()`, unconditional `set_continuum()` no longer exists); the only invalidation is `invalidate_continuum()`, which also INCREMENTs the per-user collapse-epoch key `continuum:{user_id}:epoch` (missing epoch reads as 0). A cache miss in `ContinuumPool.get_or_create()` means new session, not stale data — do not add TTL-based expiry or you break session-boundary detection.
- During a turn, `UnitOfWork` is the only message-persist path: queue with `uow.add_messages()`, commit once with `uow.commit()`. Bypassing it with direct `save_messages_batch()` calls skips the Valkey cache sync that `commit()` performs.
- `FeedbackTracker.should_synthesize()` is stateless by design: `cumulative_activity_days % threshold == 0` plus a dedup guard against the `activity_days_at_last_synthesis` snapshot. Never add a separate counter or "last ran" table; the snapshot column is the whole mechanism.

## Files

- `__init__.py` — docstring only; re-exports `ContinuumRepository` but other modules import from the submodule paths directly.
- `continuum_repository.py` — All PostgreSQL persistence for continuums, messages, and segment sentinels. Exports `HistoryResult`, `FailedSegment`, `ActiveSegmentRow` TypedDicts and `IncrementSegmentTurnResult`. `get_history()` pages backwards on an exclusive `(created_at, id)` keyset cursor — no offset; `created_at` alone ties within a turn, so `id` is part of the boundary. Segment lifecycle: `find_active_segment()` matches both `active` and `paused` (a paused segment is still the current segment); `pause_segment()` / `unpause_segment()` toggle status; `increment_segment_turn()` is called at API entry and auto-resumes paused segments, stamping `last_turn_at` to close the timeout-service race window; `set_heartbeat_wake_at()` (heartbeat service only) stamps the next wake time on the active sentinel — consumed by the heartbeat dispatcher (skip sleeping users) and the timeout service (defer collapse), both of which ignore stale/past stamps, so no cleanup path exists. `set_heartbeat_retry_at()` (heartbeat failure path only) stamps the retry backoff and increments `heartbeat_failures` on the same sentinel — the dispatcher honors it for pacing but the timeout service ignores it by design, so persistent heartbeat failure cannot starve the collapse sweep; `reset_heartbeat_failures()` zeroes the counter after a heartbeat turn with a usable outcome — a valid confirm record or an exempted external cancel (failure-form semantics owned by `cns/services/AGENTS.md`) — re-arming the liveness stamp the failure streak had suspended. `load_messages_for_live_compaction_range()` excludes segment boundaries, system notifications, and compaction synopses. `load_segment_messages()` and `get_history()` additionally exclude keepsleeping heartbeat turns (`cns/services/heartbeat_service.py` metadata predicate; breakout turns stay visible). Both `save_message()` and `save_messages_batch()` increment user activity days only for genuine user messages — the gate is `role == "user" AND metadata.heartbeat != "true"` — so machine-sourced heartbeat stimuli never advance `cumulative_activity_days`. `load_tool_result_by_id()` returns raw persisted tool-result text only when user, active session, and retrieval ID all match; ambiguous IDs raise. `find_failed_extraction_segments()` feeds extraction retry with a content-failure budget (`EXTRACTION_MAX_CONTENT_FAILURES`): only failures caused by the segment's own data consume it — infrastructure/LLM outages are classified and excluded — and exhausting the budget writes an `extraction_abandoned` marker so the exclusion is operator-visible, never silent. Collapsed segments are final — no method in this file reverses a collapse. Consumers: `cns/services/orchestrator.py`, `cns/services/segment_timeout_service.py`, `cns/services/segment_collapse_handler.py`, `cns/api/data.py`, `cns/api/actions.py`, `tools/implementations/continuum_tool.py`.
- `continuum_pool.py` — Owns `ContinuumPool` (Valkey-backed session cache) and `UnitOfWork`. `get_or_create()` is the entry point for all continuum session resolution: DB continuum must already exist from signup (RuntimeError otherwise); on Valkey miss it delegates to `SegmentCacheLoader.load_session_cache()` and re-caches via the epoch-guarded `set_continuum_if_epoch()` — a collapse landing mid-load bumps the epoch past the captured value and the stale write is skipped, not clobbered. `UnitOfWork.add_messages()` truncates any single message over a hardcoded 150k-character limit before persistence. `add_post_commit_callback()` defers work until after both persistence layers succeed. Consumers: `cns/integration/factory.py` (construction and `initialize_continuum_pool()`), `cns/api/chat.py`, `cns/api/actions.py`, `cns/services/orchestrator.py`.
- `valkey_message_cache.py` — Owns `Message` ↔ Valkey JSON serialization, the collapse-epoch counter, and compare-and-set tool-result compaction. Key formats: `continuum:{user_id}:messages`, `continuum:{user_id}:epoch`. `set_continuum_if_epoch()` is the epoch-guarded write (Lua `set_if_counter_matches` in `clients/valkey_client.py`: SET only when the epoch equals the provided value, missing epoch = 0); `invalidate_continuum()` DELs the messages key and INCREMENTs the epoch in ONE atomic `delete_and_increment` Lua op (a stale writer can never re-enter between the two). `apply_tool_result_patches()` rewrites only still-current tool messages (content must equal `expected_content`, not already `tool_result_compacted`), retrying the CAS up to `CACHE_PATCH_MAX_ATTEMPTS` (3) before raising. No constructor DI — calls `clients/valkey_client.py:get_valkey_client()` directly. Consumers: `continuum_pool.py` (internal), `cns/integration/factory.py` (reaches the pool's instance via `get_continuum_pool().valkey_cache`), `cns/services/tool_result_summarizer.py` (runtime-imports `ToolResultCachePatch`, holds the cache via TYPE_CHECKING-typed `ValkeyMessageCache`).
- `feedback_repository.py` — CRUD for the `feedback_signals` table (user-model evidence). Exports `FeedbackSignalRow`. `save_signals()` / `get_unsynthesized_signals()` / `mark_signals_synthesized()` drive the synthesis input queue. Consumers: `cns/services/user_model_synthesizer.py`, `cns/services/segment_collapse_handler.py`.
- `feedback_tracker.py` — Owns synthesis lifecycle state in `feedback_synthesis_tracking`. Exports `LoraContent`, `TrackingStatus`. `get_and_clear_checkin_response()` atomically consumes and nulls stored check-in feedback via `UPDATE ... RETURNING`; `set_synthesis_output()` is the persistence endpoint for user-initiated LoRA refinement. `reset_synthesis()` restores the row to the fresh-install `initialize_user()` baseline for every field it owns — output NULL, `last_synthesis_at` NULL, `needs_checkin` FALSE, `checkin_response` NULL, `activity_days_at_last_synthesis` 0 — so a reset user's countdown and `use_days_since_synthesis` read exactly as a fresh install (reset does NOT re-stamp the snapshot). Consumers: `working_memory/trinkets/lora_trinket.py` (via `get_lora_content()`), `cns/services/lora_service.py`, `cns/api/data.py`, `cns/api/actions.py`, `cns/services/orchestrator.py`.
- `persona_repository.py` — `PersonaRepository`: append-only Persona revisions and per-segment evaluation signals (`persona_revisions`, `persona_signals`, `persona_state`). Exports `PersonaSignal`, `PersonaRevision`. `append_revision()` takes a `FOR UPDATE` lock on `persona_state`, enforces `expected_parent_revision_id` (concurrent edit raises "generate a new preview" instead of silently losing one), logs a structured `PERSONA REVISION` line in place of an audit journal, and marks consumed signals. `refinement_due()` applies the use-day cadence (default interval 7) against `refinement_checkpoint_activity_day`; `mark_refinement_attempt()` advances that checkpoint on failed/no-evidence attempts so the same day does not retry forever. `get_current_revision()` raises if the baseline is missing. Consumers: `cns/services/persona_service.py`, `working_memory/trinkets/persona_trinket.py` (constructs `PersonaRepository` directly, not via the service).

## Wiring

`UnitOfWork.commit()` calls `repository.save_messages_batch()` then `valkey_cache.set_continuum_if_epoch()`, in that order — DB write always precedes cache write, and a cache-write failure must never fail the request after the DB write landed: `commit()` logs `error` and calls `invalidate_continuum()` (forcing the next `get_or_create()` to reload from DB); if that invalidation also fails it logs `critical` and a stale cache may serve until the next collapse. The UnitOfWork carries `cache_epoch`, captured in `get_or_create()` BEFORE the message read (so any collapse invalidating those messages bumps the epoch past it) and threaded through `begin_work()`. `set_continuum_if_epoch()` is a Lua compare-and-set against the live `continuum:{user_id}:epoch`: on mismatch (a collapse invalidated the cache between load and commit) the write is SKIPPED, not an error — the cache stays empty and the next `get_or_create()` misses and rebuilds collapse-correct state via `SegmentCacheLoader` (owned by `cns/core/AGENTS.md`, defined in `cns/core/segment_cache_loader.py`). A crash between the two writes leaves DB authoritative with the same reconstruction path. Post-commit callbacks run only after both writes and metadata persistence succeed. (Tool-result compaction — the former consumer of this hook — is DEADHEADED pending redesign; see `cns/services/AGENTS.md`.)

New-segment sentinel ordering spans this directory and the API layer: `increment_segment_turn()` (API entry) allocates `segment_id` and publishes it via the `current_segment_id` contextvar (`utils.user_context.set_current_segment_id`); `_ensure_active_segment()` reads that contextvar when the sentinel is finally persisted inside `save_messages_batch()`, so the ID tools saw this turn matches the persisted sentinel — the sentinel INSERT autocommits on the pooled connection in a separate commit before the message-batch transaction opens, so the orphan-sentinel window is residual, not eliminated — but a stale contextvar ID (it outlives the segment it named) is collision-checked against existing sentinels of that segment_id in the continuum first, with `str(uuid4())` allocated on collision, so no segment_id is ever persisted twice. `find_segment_by_id()` orders `created_at DESC` so any residual duplicate resolves to the newest row deterministically. The active-sentinel INSERT conflicts on a unique partial index and `DO NOTHING` — concurrent creators race-lose silently.

Pipeline boundaries owned by this directory: `FeedbackRepository.save_signals()` takes `AssessmentSignal` from `cns/services/assessment_extractor.py` (imported at module top — the boundary is a type import, not an HTTP/event edge); `FeedbackTracker.get_lora_content()` feeds `LoraTrinket` (map: `working_memory/trinkets/AGENTS.md`); `PersonaRepository` is the parallel boundary for the Persona pipeline — `cns/services/persona_service.py` reads/writes revisions and signals there, and `PersonaTrinket` renders `get_current_revision().directives`. Persona never touches `FeedbackTracker`; the two evidence stores share no table (`persona_signals` vs `feedback_signals`).

Cache write/delete edge owned here: the key `continuum:{user_id}:messages` has exactly three writers, all in `valkey_message_cache.py` — `set_continuum_if_epoch()` (epoch-guarded; called from `UnitOfWork.commit()` AND the `ContinuumPool.get_or_create()` cache-miss re-cache), `apply_tool_result_patches()` (compare-and-set rewrite driven by `cns/services/tool_result_summarizer.py` on `ToolResultHistoryCommittedEvent`), and `invalidate_continuum()` (key delete + epoch INCREMENT). Collapse is the only DELETE trigger: `cns/services/segment_collapse_handler.py` calls `ContinuumPool.invalidate()` → `invalidate_continuum()` (scoped by the `user_id` contextvar). There is no TTL. The summarizer/collapse race is benign by CAS construction: `apply_tool_result_patches()` reads the key first and no-ops when it is missing (a collapse delete landing mid-compaction yields 0 applied, never a partial key), and `clients/valkey_client.py:compare_and_set()` is a Lua get-compare-set that fails closed when the value changed between read and write — a retry against a fresh copy patches the same still-current message content, which is data-correct. Exhausted retries raise `RuntimeError`, which the summarizer logs and swallows; worst case is lost compaction, not corruption. The commit-vs-collapse race is closed by the epoch CAS: a turn that loaded its continuum before collapse and commits after it carries a stale epoch, its `set_continuum_if_epoch()` skips the write, and no stale pre-collapse copy ever re-enters the cache.

Inbound call edges: both API transports drive the whole turn through `ContinuumPool.get_or_create()` → `continuum_pool.repository.increment_segment_turn()` → `begin_work()` → `UnitOfWork.commit()` — `cns/api/chat.py` (sync `POST /chat`) and `cns/api/websocket_chat.py` (streaming WS); neither is the sole entry. `cns/services/orchestrator.py` holds `ContinuumRepository` and `UnitOfWork` (DI from `cns/integration/factory.py`, which constructs both the repository singleton and the pool via `initialize_continuum_pool()`).

## Segment sentinel lifecycle

Segment state lives in message-row metadata (`is_segment_boundary`, `status`, `segment_id`, `segment_turn_count`), not in a segments table. The full cycle, with the invariants that are invisible from any single file:

1. **Allocation** — `increment_segment_turn()` at API entry. Existing active/paused sentinel: atomic `UPDATE ... RETURNING` bumps `segment_turn_count`, forces `status='active'`, stamps `last_turn_at`, and publishes the returned `segment_id` via contextvar. No sentinel: allocate a fresh UUID in memory only.
2. **Deferred persistence** — on the first real message of a session, `_ensure_active_segment()` (called from `save_message()` / `save_messages_batch()`) creates the sentinel using the contextvar ID (collision-checked, fresh UUID on collision — see Wiring). Sentinel creation is time-bounded by the last collapsed segment's `segment_end_time`, so a segment's first message is correct even when saved long after `increment_segment_turn()` ran.
3. **Pause/resume** — `pause_segment()` sets `status='paused'` + `paused_at`; the timeout service cannot see paused segments. Resume paths: `increment_segment_turn()` (next user message) or explicit `unpause_segment()` (UI action), which clears `paused_at`.
4. **Collapse** — external chain (`cns/services/segment_collapse_handler.py` → `summary_generator` → LT_Memory extraction) marks the sentinel `status='collapsed'` with summary/precis/complexity metadata. The handler re-reads the sentinel immediately before the collapsed save and aborts (RuntimeError, segment stays active) unless it is still active/paused with an unchanged `last_turn_at` — an interleaved turn or a concurrent claim wins the save instead. `stamp_segment_liveness()` (heartbeat service, at wake-turn dispatch) stamps `last_turn_at` on the active sentinel so the timeout service's liveness guard covers a hung wake turn for one threshold window. Terminal state; subsequent cache loads read these sentinels via `find_collapsed_segments()`.

Breaking the ordering rules produces specific failures: persisting a sentinel with a fresh UUID instead of the contextvar ID orphans the ID tools already used; collapsing a paused segment (the `users.is_active` guard exists for the analogous admin case) collapses sessions the user intentionally froze; reading `find_active_segment()` without the paused match makes the pool treat a paused session as brand new on every request.
