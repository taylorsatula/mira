# cns/infrastructure/ — persistence and caching for the CNS conversation graph

## Rules

- DB access splits two ways, and the split is per-repository, not per-call: `continuum_repository.py` builds per-user `PostgresClient` instances (RLS via `app.current_user_id`), while `feedback_repository.py`, `feedback_tracker.py`, and `persona_repository.py` go through `utils.database_session_manager.get_shared_session_manager().get_session(user_id)`. Cross-user sweeps use `get_shared_session_manager().get_admin_session()` (BYPASSRLS) — see `find_all_active_segments_admin()`, which must keep its `users.is_active = TRUE` join or the timeout sweep collapses segments of deactivated accounts.
- Never construct a `PostgresClient` per call. `ContinuumRepository` caches one client per user in `_db_cache`; the public accessor is `get_user_db_client(user_id)` — external modules use that, never reach into privates.
- `ContinuumRepository` is a module-level lazy singleton via `get_continuum_repository()`; `ContinuumPool` is initialized once at startup via `initialize_continuum_pool()` in `cns/integration/factory.py` and read via `get_continuum_pool()`. Both raise at first use if uninitialized — never construct them directly.
- The Valkey continuum cache has no TTL. `ValkeyMessageCache.set_continuum()` stores without expiry; the only invalidation is `invalidate_continuum()` (called by `ContinuumPool.invalidate()`, invoked from `cns/services/segment_collapse_handler.py` on segment collapse). A cache miss in `ContinuumPool.get_or_create()` means new session, not stale data — do not add TTL-based expiry or you break session-boundary detection.
- During a turn, `UnitOfWork` is the only message-persist path: queue with `uow.add_messages()`, commit once with `uow.commit()`. Bypassing it with direct `save_messages_batch()` calls skips the Valkey cache sync that `commit()` performs.
- `FeedbackTracker.should_synthesize()` is stateless by design: `cumulative_activity_days % threshold == 0` plus a dedup guard against the `activity_days_at_last_synthesis` snapshot. Never add a separate counter or "last ran" table; the snapshot column is the whole mechanism.

## Files

- `__init__.py` — docstring only; re-exports `ContinuumRepository` but other modules import from the submodule paths directly.
- `continuum_repository.py` — All PostgreSQL persistence for continuums, messages, and segment sentinels. Exports `HistoryResult`, `FailedSegment`, `ActiveSegmentRow` TypedDicts and `IncrementSegmentTurnResult`. `get_history()` pages backwards on an exclusive `(created_at, id)` keyset cursor — no offset; `created_at` alone ties within a turn, so `id` is part of the boundary. Segment lifecycle: `find_active_segment()` matches both `active` and `paused` (a paused segment is still the current segment); `pause_segment()` / `unpause_segment()` toggle status; `increment_segment_turn()` is called at API entry and auto-resumes paused segments, stamping `last_turn_at` to close the timeout-service race window. `load_messages_for_live_compaction_range()` excludes segment boundaries, system notifications, and compaction synopses. `load_tool_result_by_id()` returns raw persisted tool-result text only when user, active session, and retrieval ID all match; ambiguous IDs raise. `find_failed_extraction_segments()` feeds extraction retry with a `max_attempts` ceiling. Collapsed segments are final — no method in this file reverses a collapse. Consumers: `cns/services/orchestrator.py`, `cns/services/segment_timeout_service.py`, `cns/services/segment_collapse_handler.py`, `cns/api/data.py`, `cns/api/actions.py`, `tools/implementations/continuum_tool.py`.
- `continuum_pool.py` — Owns `ContinuumPool` (Valkey-backed session cache) and `UnitOfWork`. `get_or_create()` is the entry point for all continuum session resolution: DB continuum must already exist from signup (RuntimeError otherwise); on Valkey miss it delegates to `SegmentCacheLoader.load_session_cache()` and re-caches. `UnitOfWork.add_messages()` truncates any single message over a hardcoded 150k-character limit before persistence. `add_post_commit_callback()` defers work until after both persistence layers succeed. Consumers: `cns/integration/factory.py` (construction and `initialize_continuum_pool()`), `cns/api/chat.py`, `cns/api/actions.py`, `cns/services/orchestrator.py`.
- `valkey_message_cache.py` — Owns `Message` ↔ Valkey JSON serialization and compare-and-set tool-result compaction. Key format: `continuum:{user_id}:messages`. `apply_tool_result_patches()` rewrites only still-current tool messages (content must equal `expected_content`, not already `tool_result_compacted`), retrying the CAS up to `CACHE_PATCH_MAX_ATTEMPTS` (3) before raising. No constructor DI — calls `clients/valkey_client.py:get_valkey_client()` directly. Consumers: `continuum_pool.py` (internal), `cns/integration/factory.py` (reaches the pool's instance via `get_continuum_pool().valkey_cache`), `cns/services/tool_result_summarizer.py` (runtime-imports `ToolResultCachePatch`, holds the cache via TYPE_CHECKING-typed `ValkeyMessageCache`).
- `feedback_repository.py` — CRUD for the `feedback_signals` table (user-model evidence). Exports `FeedbackSignalRow`. `save_signals()` / `get_unsynthesized_signals()` / `mark_signals_synthesized()` drive the synthesis input queue. Consumers: `cns/services/user_model_synthesizer.py`, `cns/services/segment_collapse_handler.py`.
- `feedback_tracker.py` — Owns synthesis lifecycle state in `feedback_synthesis_tracking`. Exports `LoraContent`, `TrackingStatus`. `get_and_clear_checkin_response()` atomically consumes and nulls stored check-in feedback via `UPDATE ... RETURNING`; `set_synthesis_output()` is the persistence endpoint for user-initiated LoRA refinement. Consumers: `working_memory/trinkets/lora_trinket.py` (via `get_lora_content()`), `cns/services/lora_service.py`, `cns/api/data.py`, `cns/api/actions.py`, `cns/services/orchestrator.py`.
- `persona_repository.py` — `PersonaRepository`: append-only Persona revisions and per-segment evaluation signals (`persona_revisions`, `persona_signals`, `persona_state`). Exports `PersonaSignal`, `PersonaRevision`. `append_revision()` takes a `FOR UPDATE` lock on `persona_state`, enforces `expected_parent_revision_id` (concurrent edit raises "generate a new preview" instead of silently losing one), logs a structured `PERSONA REVISION` line in place of an audit journal, and marks consumed signals. `refinement_due()` applies the use-day cadence (default interval 7) against `refinement_checkpoint_activity_day`; `mark_refinement_attempt()` advances that checkpoint on failed/no-evidence attempts so the same day does not retry forever. `get_current_revision()` raises if the baseline is missing. Consumers: `cns/services/persona_service.py`, `working_memory/trinkets/persona_trinket.py` (constructs `PersonaRepository` directly, not via the service).

## Wiring

`UnitOfWork.commit()` calls `repository.save_messages_batch()` then `valkey_cache.set_continuum()`, in that order — DB write always precedes cache write. A crash between the two leaves DB authoritative; the next Valkey miss reconstructs via `SegmentCacheLoader` (owned by `cns/core/AGENTS.md`, defined in `cns/core/segment_cache_loader.py`). Post-commit callbacks run only after both writes and metadata persistence succeed; tool-result compaction uses this hook so the exact original is durable before its hot-cache copy is shortened.

New-segment sentinel ordering spans this directory and the API layer: `increment_segment_turn()` (API entry) allocates `segment_id` and publishes it via the `current_segment_id` contextvar (`utils.user_context.set_current_segment_id`); `_ensure_active_segment()` reads that contextvar when the sentinel is finally persisted inside `save_messages_batch()`, so the ID tools saw this turn matches the persisted sentinel and sentinel + first message land in one commit. The active-sentinel INSERT conflicts on a unique partial index and `DO NOTHING` — concurrent creators race-lose silently.

Pipeline boundaries owned by this directory: `FeedbackRepository.save_signals()` takes `AssessmentSignal` from `cns/services/assessment_extractor.py` (imported at module top — the boundary is a type import, not an HTTP/event edge); `FeedbackTracker.get_lora_content()` feeds `LoraTrinket` (map: `working_memory/trinkets/AGENTS.md`); `PersonaRepository` is the parallel boundary for the Persona pipeline — `cns/services/persona_service.py` reads/writes revisions and signals there, and `PersonaTrinket` renders `get_current_revision().directives`. Persona never touches `FeedbackTracker`; the two evidence stores share no table (`persona_signals` vs `feedback_signals`).

Cache write/delete edge owned here: the key `continuum:{user_id}:messages` has exactly three writers, all in `valkey_message_cache.py` — `set_continuum()` (called from `UnitOfWork.commit()` and from the `ContinuumPool.get_or_create()` cache-miss re-cache), `apply_tool_result_patches()` (compare-and-set rewrite driven by `cns/services/tool_result_summarizer.py` on `ToolResultHistoryCommittedEvent`), and `invalidate_continuum()` (key delete). Collapse is the only DELETE trigger: `cns/services/segment_collapse_handler.py` calls `ContinuumPool.invalidate()` → `invalidate_continuum()` (scoped by the `user_id` contextvar). There is no TTL. The summarizer/collapse race is benign by CAS construction: `apply_tool_result_patches()` reads the key first and no-ops when it is missing (a collapse delete landing mid-compaction yields 0 applied, never a partial key), and `clients/valkey_client.py:compare_and_set()` is a Lua get-compare-set that fails closed when the value changed between read and write — a retry against a fresh copy patches the same still-current message content, which is data-correct. Exhausted retries raise `RuntimeError`, which the summarizer logs and swallows; worst case is lost compaction, not corruption. The unguarded writer is `UnitOfWork.commit()` itself: a turn that loaded its continuum before collapse and commits after it re-writes a pre-collapse message set, and the next `get_or_create()` cache-hits that stale copy until the next collapse.

Inbound call edges: both API transports drive the whole turn through `ContinuumPool.get_or_create()` → `continuum_pool.repository.increment_segment_turn()` → `begin_work()` → `UnitOfWork.commit()` — `cns/api/chat.py` (sync `POST /chat`) and `cns/api/websocket_chat.py` (streaming WS); neither is the sole entry. `cns/services/orchestrator.py` holds `ContinuumRepository` and `UnitOfWork` (DI from `cns/integration/factory.py`, which constructs both the repository singleton and the pool via `initialize_continuum_pool()`).

## Segment sentinel lifecycle

Segment state lives in message-row metadata (`is_segment_boundary`, `status`, `segment_id`, `segment_turn_count`), not in a segments table. The full cycle, with the invariants that are invisible from any single file:

1. **Allocation** — `increment_segment_turn()` at API entry. Existing active/paused sentinel: atomic `UPDATE ... RETURNING` bumps `segment_turn_count`, forces `status='active'`, stamps `last_turn_at`, and publishes the returned `segment_id` via contextvar. No sentinel: allocate a fresh UUID in memory only.
2. **Deferred persistence** — on the first real message of a session, `_ensure_active_segment()` (called from `save_message()` / `save_messages_batch()`) creates the sentinel using the contextvar ID. Sentinel creation is time-bounded by the last collapsed segment's `segment_end_time`, so a segment's first message is correct even when saved long after `increment_segment_turn()` ran.
3. **Pause/resume** — `pause_segment()` sets `status='paused'` + `paused_at`; the timeout service cannot see paused segments. Resume paths: `increment_segment_turn()` (next user message) or explicit `unpause_segment()` (UI action), which clears `paused_at`.
4. **Collapse** — external chain (`cns/services/segment_collapse_handler.py` → `summary_generator` → LT_Memory extraction) marks the sentinel `status='collapsed'` with summary/precis/complexity metadata. Terminal state; subsequent cache loads read these sentinels via `find_collapsed_segments()`.

Breaking the ordering rules produces specific failures: persisting a sentinel with a fresh UUID instead of the contextvar ID orphans the ID tools already used; collapsing a paused segment (the `users.is_active` guard exists for the analogous admin case) collapses sessions the user intentionally froze; reading `find_active_segment()` without the paused match makes the pool treat a paused session as brand new on every request.
