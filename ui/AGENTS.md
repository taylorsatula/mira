# ui/ — the two MIRA chat clients and the contracts that hold them to one another

## Files

- `__init__.py` — docstring only; no re-exports.
- `browser/` — the browser client: four served page documents, the asset tree, the client half of the turn protocol; `ui/browser/AGENTS.md` indexes it.
- `tui/` — the terminal client: the strict frame mirror, the turn state machine, the single-writer screen, the install's maintenance commands; `ui/tui/AGENTS.md` indexes it.

## Wiring

- Turn frames: `cns/api/websocket_chat.py` defines the frame, `ui/browser/assets/javascript/api-client.js` with `ui/browser/assets/javascript/messaging.js` consumes it leniently, `ui/tui/protocol.py` with `ui/tui/client.py` mirrors it strictly. Both client sides change in the same commit as the server frame; each side's own file list and frame-handling table are its map's. Counterpart: `cns/api/AGENTS.md`.
- History envelope: `cns/api/data.py` returns the row set both clients render, and `ui/tui/protocol.py` mirrors the envelope and its paging fields. A field added or renamed on the server reaches the mirror in the same commit, or every history fetch raises `ProtocolError`. Counterpart: `cns/api/AGENTS.md`.
- Package boundary: nothing outside `ui/` imports this package. The server reaches the browser client only by serving `ui/browser/` as static files, and never reaches the terminal client at all — both talk to it over the wire. Counterpart: `AGENTS.md`.

## Rules

- A server frame change lands in one commit across `cns/api/websocket_chat.py`, the browser's `api-client.js:_handleFrame` and `messaging.js:handleTurnFrame`, and the terminal client's `ui/tui/protocol.py` plus `ui/tui/client.py:_frame_to_event`. The drift is asymmetric by design: the browser logs `Unknown server frame type` and drops what it cannot classify, while the TUI's `extra="forbid"` mirror raises `ProtocolError`. A client left behind therefore misbehaves with no shared check behind it, and the browser's half of that is silent.
- `messaging.js:ReplyFilter` and `ui/tui/text.py:ReplyStream` are one display filter implemented twice (grep `rg 'class ReplyFilter|class ReplyStream' ui`). A change to what a reply shows lands in both in the same commit, or one conversation renders differently per client. Counterpart: `ui/tui/AGENTS.md`. The two are not meant to be identical: the TUI sanitizes every delta because Rich passes ESC through to the terminal and renders a live pending tail, while the browser renders completed blocks only and rests reply-body safety on `renderMarkdown`'s DOMPurify pass — porting one side's step to the other as a consistency fix breaks the client it was copied into.
- `api-client.js`'s `TURN_BUSY_RETRY_DELAYS_MS`, `TURN_BUSY_POLL_MS`, `TURN_BUSY_MAX_WAIT_MS`, `RECONNECT_DELAYS_MS` and `RECONNECT_POLL_MS` and `ui/tui/chat.py`'s `TURN_BUSY_RETRY_DELAYS`, `TURN_BUSY_POLL_SECONDS`, `TURN_BUSY_MAX_WAIT_SECONDS`, `AUTO_RECONNECT_DELAYS` and `AUTO_RECONNECT_POLL_SECONDS` are one cadence in two units of time (grep `rg 'TURN_BUSY_RETRY|RECONNECT_DELAYS' ui`), both measuring the wait from the first bounce or loss. Move one client's schedule alone and the two retry a busy server, or come back after a restart, on different clocks. Counterpart: `ui/tui/AGENTS.md`.
- `ui/browser/assets/javascript/history.js:renderHistoryRows` and `ui/tui/history.py:replay_blocks` are one grouping vocabulary in two renderers (grep `rg 'renderHistoryRows|replay_blocks' ui`): a user row opens a pair, assistant and tool rows sharing a `turn_id` form one reply, and a sentinel renders only once collapsed. Both accept `is_segment_boundary` as boolean `true` or as the string `"true"` (`messaging.js:isSegmentSentinel`, `ui/tui/client.py:_is_sentinel`), and neither may be tightened to one spelling: `ui/tui/protocol.py`'s docstring records the string as historical server output while `_is_sentinel`'s records it as a plan artifact never observed live, so dropping either spelling rests on an unresolved claim and strands every sentinel on history that used it. One renderer edited alone makes the same history group differently per client. Counterpart: `ui/tui/AGENTS.md`.
- `ui/__init__.py` stays import-free: `python3 -m ui.tui` resolves the package first, inside the TUI venv built from `ui/tui/requirements.txt`, which overlaps the server's pins on `httpx` and `pydantic` alone. An import added here, or a new server-tree import from `ui/tui/`, breaks the `mira` command on every install whose environment lacks the transitive dependency, and it breaks at launch rather than at first use.
- Undelivered text is disposed of deliberately differently per client. The browser queues to Retry Send in localStorage under `mira-queue`, for the three codes in `UNSENT_TURN_CODES`, of which only `TURN_BUSY` is proof the server never took the frame. `CONNECTION_LOST` is rejected at two sites: `api-client.js:_startConnectWait` fires it under `!send.transmitted` with "the message was not sent", a send the server provably never received, while the `send.transmitted` branch of the drop handler fires the copy that says check history before resending, and only that one marks a possible duplicate. `NOT_AUTHENTICATED` carries the same risk, because `auth.clearToken` rejects the in-flight send whether or not it reached the server. The TUI returns in-flight and queued text to the input box through `ChatSession._restore_unsent`. A turn the user stopped queues in neither, because its partial reply persists server-side. Do not port one client's disposal to the other.

Elsewhere: this map owns what the two clients must agree on, not what either one does inside itself. How a component came to be shaped as it is is `ui/tui/BUILD_PLAN.md`, `ui/tui/FRONTEND_PLAN.md`, and `git log` — the code wins over all three. Every other destination this directory reaches is an edge — see `## Wiring` above.
