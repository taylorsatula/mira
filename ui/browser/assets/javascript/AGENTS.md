# ui/browser/assets/javascript/ — the browser client's shared module tree: the one transport, the client half of the turn protocol, and the per-page controllers' helpers

## Files

- `api-client.js` — the one transport: WebSocket lifecycle and the single HTTP path. Open it before changing a request, the CSRF or 401 handling, reconnect, or how a server frame is classified.
- `core.js` — shared page state, the DOM element cache, and the client's turn-independent listener set, plus startup and segment collapse. Open it before adding page-wide state or a listener that must outlive one turn.
- `ui.js` — the visual layer for indicators, badges, popovers, send animations and the loading wave. Open it before changing anything the user sees move or any toolbar indicator.
- `messaging.js` — the turn's client half and the display filter. Open it before changing how a reply is displayed or how a turn settles.
- `history.js` — the inline paged history above the response box. Open it before changing paging, row grouping, or the collapsed-segment summaries.
- `events.js` — the chat page's DOM wiring: send and stop, keyboard, file picker and image paste, popover open/close, Retry Send buttons. Open it before adding a control to the chat page.
- `sidebar.js` — navigation chrome on all four pages. Open it before changing sidebar state, the History/Pause/Wrap Up buttons, or mobile drawer behaviour.
- `inactivity-warning.js` — the session status bar and the `get_segment_status` poll behind it. Open it before changing session-state display, the countdown, or pause and resume.
- `domain-knowledge.js` — the domaindoc client plus the chat page's domain popover. Open it before changing domaindoc or section CRUD, or the enabled-domain indicator.
- `tool-config.js` — the settings page's tool-config forms over the tools API. Open it before changing how a tool's config form is built, validated, or saved.
- `repulsion-feedback.js` — the AI-tell bank and the "Repulsed!" popover. Open it before editing a tell pattern or the feedback payload.
- `location.js` — the consent modal and the geolocation POST. Open it before changing consent state, the permission gate, or the location request.
- `theme.js` — the runtime half of the appearance preference. Open it before changing how a theme mode is stored, resolved, or applied.
- `collapse-animation.js` — the segment-collapse effect. Open it before changing the conversion or fall timing, or the CSS classes it needs.
- `marked.min.js` — vendored marked v12.0.0, stock build; its own license header is its docstring, and it is never edited. Open it only to confirm the pinned version.
- `purify.min.js` — vendored DOMPurify 3.0.9, stock build, same terms. Open it only to confirm the pinned version.

## Wiring

- Turn: `events.js` submit → `messaging.js:sendMessage` → `runTurn` → `api-client.js:_sendMessage` → `_handleFrame` → `messaging.js:handleTurnFrame` for stream frames. The terminal frames never reach `handleTurnFrame`: `_handleFrame` routes `turn_complete`/`turn_stopped`/`turn_error` to `_onTurnEnd`, which resolves or rejects the send promise, and `runTurn` dispatches the settled `status` to `completeTurn`/`stopTurn` while its own catch calls `failTurn`. The promise settles once and `runTurn` is its only consumer; `endTurn` then parks the display settle in `streamingState.pendingSettle` until `beginTurn`'s container callback sets `containerReady` — run that settle any earlier and the container reset wipes the reply it just rendered, then releases the send button over the previous turn's HTML. A terminal frame added to `messaging.js:TURN_FRAME_TYPES` instead of to `_handleFrame` is handled by nothing.
- Frames: `api-client.js:_handleFrame` classifies every inbound frame, and `messaging.js:TURN_FRAME_TYPES`/`handleTurnFrame` dispose of the turn-scoped subset; the table at the end of this section is the settlement map. A frame added in `cns/api/websocket_chat.py` must land in both in the same commit — the browser logs `Unknown server frame type` and drops what it does not know, so a missed frame is silent. The wire-shape set is wider than the frame types: `api-client.js:MAX_CONTENT_LENGTH` mirrors the content bound of `MessageFrame`, and `IMAGE_MIME_TYPES` mirrors the image types it accepts. A server that widens the content bound leaves the browser refusing locally, as `MESSAGE_TOO_LONG`, a message the server would have taken — no server record of the refusal, nothing in the operator's view — and a server that accepts an image type this set lacks gets that attachment back as a `document`, never as an image. The both-clients same-commit rule and its lenient-browser-versus-strict-TUI asymmetry belong to `ui/AGENTS.md`. Counterpart: `cns/api/AGENTS.md`.
- Routes: every action, data, history, tool-config and location call is a `/v1/api/...` route whose envelope, contract and query rules `cns/api/AGENTS.md` owns. `_httpRequest` unwraps `{success, data|error, meta}`: a 2xx body without `success: true` fails as `BAD_ENVELOPE`, while a non-2xx body keeps the server's own `error.code`, or falls back to `HTTP_<status>` for a string `detail` and `REQUEST_VALIDATION_ERROR` for a list one. A handler returning a bare body therefore breaks every caller on the success path, and only there does the error read as a client bug. Counterpart: `cns/api/AGENTS.md`.
- CSRF and session: `_ensureCsrfToken` single-flights `POST /v1/auth/csrf`, and `_httpRequest` retries a cookie-bearing write exactly once, only when the failure code is in `CSRF_RETRY_CODES`. That retry exists because the server keeps one token per session and every mint replaces it; an auth side that makes the mint get-or-create leaves the retry in place but harmless, whereas a mint that stops naming the new token in the response strands every concurrent write with a silent retry loop. The other half of the edge is the 401 branch: `_httpRequest` and `_onProtocolError` both call `auth.clearToken`, so a session contract that stops answering 401 on an expired cookie leaves the browser holding a token the server rejects. Counterpart: `auth/AGENTS.md`, which owns both sides and does not yet carry the reciprocal line.
- Twins: `messaging.js:ReplyFilter` with `ui/tui/text.py:ReplyStream`; the `api-client.js` retry and reconnect constants with `ui/tui/chat.py`; and `history.js:renderHistoryRows` with `ui/tui/history.py:replay_blocks`, one row-grouping vocabulary in two renderers. Both of those renderers must keep accepting `is_segment_boundary` as boolean `true` and as the string `"true"`, because the server has sent both spellings — tighten `messaging.js:isSegmentSentinel` to one spelling and every sentinel stored under the other disappears from the browser's history while the TUI still draws it. `ui/AGENTS.md` states all three pairings and their same-commit rule. Counterpart: `ui/AGENTS.md`.
- Cache-bust and theme: `ui.js:ASSET_VERSION` must equal the `?v=` tag every page repeats, and `theme.js` is the runtime half of each page's inline pre-paint boot script. Counterpart: `ui/browser/AGENTS.md`, which owns the page side of both.
- Collapse: `core.js:Functions.collapseSegment` starts the `continuum/collapse_segment` action and `window.collapseAnimation` together, and renders the outcome only from `onFallComplete`, after both have finished. `onFallComplete` and `scrollContainer` are `collapse-animation.js`'s entire option contract, so one without the other either leaves the outcome unrendered or lets the fall write over the result; and a `collapsed: false` result is a deferral behind an in-flight turn whose `message` explains it — rendering the success HTML there claims a collapse that did not happen.
- Load order: `sidebar.js` reads `window.inactivityWarningManager` and `window.InlineHistory` inside a `DOMContentLoaded` handler because both are defined by later scripts, and reads `window.Functions.collapseSegment` at click time for the same reason. Move either read to eval time and it throws, ending `sidebar.js` there — the desktop collapse, the mobile drawer and the segment button all go quiet on every page, with no compile step to catch it.

### Every inbound frame

`_handleFrame` is the whole classifier: nothing else in the tree sees a raw frame. Three outcomes exist — a frame settles the in-flight send, a frame is emitted to `eventHandlers.onMessage`, or a frame is logged and dropped.

| frame | branch | what it does | what consumes it |
|---|---|---|---|
| `auth_success` | `_onAuthSuccess` | clears the auth timer, starts the keepalive, emits `onAuthChange` once, emits `onConnect`, flushes the frame waiting on the connection | page logout handlers; the turn-independent listeners |
| `pong` | `_handleFrame` | clears `_awaitingPong`; a second ping without a pong reconnects | nothing |
| `server_shutdown` | `_handleFrame` | logs the code and message; the close path reconnects | nothing |
| `protocol_error` | `_onProtocolError` | an auth code clears the token; `AUTH_UNAVAILABLE` reconnects; a frame attributed to the in-flight send rejects it, `TURN_BUSY` through `_onTurnBusy` | the send promise, when attributed |
| `proactive_message` | `_handleFrame` | emits `onMessage` | `core.js`'s turn-independent listener, which calls `messaging.js:handleProactiveMessage` |
| `turn_complete`, `turn_stopped`, `turn_error` | `_onTurnEnd` | resolves the send `complete` or `stopped`, or rejects it with the frame's `code` | `messaging.js:runTurn`, through the promise |
| `turn_started` | `_onTurnStream` | binds `turn_id`/`segment_id` to the in-flight send, then emits `onMessage` | `messaging.js:handleTurnFrame` |
| `assistant_delta` | `_onTurnStream` | appends `content` to the send's `streamedText`, then emits | `handleTurnFrame` |
| `context_reset` | `_onTurnStream` | clears `streamedText`, then emits | `handleTurnFrame` |
| `thinking`, `tool`, `model_error` | `_onTurnStream` | emits | `handleTurnFrame`; `tool` also reaches `core.js`'s badge listener, which is why that listener outlives a turn |
| anything else | default | logs `Unknown server frame type` and drops it | nothing |

## Rules

- Script tags are the whole build: each file's top level runs in the order its page lists it, and top-level `const`/`let`/`class` land in one shared lexical scope that later scripts read but `window` does not expose. An eval-time reference to a binding from a later script throws and ends that file there — `history.js` binds `elements.toastScrollBtn` at eval time and so must load after `core.js`, while a reference inside a function body only fails when called. Moving a tag above the module it depends on leaves a page that stops executing mid-file, with no compile step to catch it.
- Every server call goes through a `MiraAPIClient` instance: HTTP through `_httpRequest`, frames through the socket it opens. `location.js` and `tool-config.js` call `_httpRequest` directly rather than through a wrapper — the same machinery, sanctioned. A new `fetch` or `WebSocket` skips the single-flight CSRF fetch and its one retry (a second concurrent token fetch rotates the session token and 403s every other tab's in-flight write) and skips the 401 → `clearToken` path.
- `eventHandlers.onMessage` is one shared array: `core.js:initializeAPIClient` pushes the listeners that outlive a turn, and `messaging.js:runTurn` pushes `handleTurnFrame` for exactly one send and splices it in `finally`. A handler left behind receives the next turn's frames and renders them twice; a turn-scoped listener registered at startup accumulates one per send.
- Every page's controller registers a logout handler — grep `rg 'onAuthChange' ui/browser`. `MiraAPIClient` emits the event and stops; nothing navigates on its own, so a page without a handler keeps a dead session and fails every later write with 401.
- Adding a tool icon is two edits: the PNG in `ui/browser/assets/images/icons/toolicons/` and its stem in `ui.js:TOOL_ICONS`. The lookup drops the `_tool` suffix, `reminder_tool` → `reminders` is the one override, and an unlisted stem renders `default.png` without complaint.

Elsewhere: this map does not own the pages that load these modules, nor the stylesheet whose class names they toggle. The ids, class selectors and `data-indicator` attributes that `core.js:elements` captures live in the page files under `ui/browser/`, and every class these modules add or remove by name (`.active`, `.hidden`, `.converted`/`.falling`, the session-status states) is declared in `ui/browser/assets/style.css`. Every other destination this directory reaches is an edge — see `## Wiring` above.

## How an exchange leaves the response box for history

The one path that crosses three modules and decides what the history view shows.

1. `messaging.js:beginTurn` calls `archiveDisplayedExchange`: whatever was in the response box goes to `window.InlineHistory.appendExchange`, and `streamingState.displayedExchange` is cleared. `history.js:appendExchange` returns without rendering while the first page has not been fetched — that first fetch includes the exchange, so rendering it here as well would double it.
2. The turn settles and records a new `displayedExchange`. `completeTurn` marks it `persisted: true`, and so does `stopTurn`, because a stopped turn's partial reply is committed server-side. `failTurn` records one with `persisted: false` when text or a tool row reached the screen: that content never reached the server, so no history page holds it.
3. Expanding the view runs `history.js:loadInlineHistory`, which awaits `messaging.js`'s `sessionRestored` before its first fetch. `loadLastSessionResponse` resolves that promise in a `finally`, so a failed restore still releases the pager instead of leaving it waiting forever.
4. That first page passes through `withoutDisplayedExchange`, which drops every row at or after the last user row except segment sentinels, while the exchange on screen is marked persisted. `persisted` is what keeps the exclusion honest in both directions: treating a failed turn's on-screen text as persisted would make the first page drop the newest rows the server actually holds, and treating a completed exchange as virtual would render the same reply twice.
5. An interrupted reply re-enters at the same place: `api-client.js:_handleClose` settles the send `stopped` with reason `disconnect`, `stopTurn` sets `AppState.responseInterrupted`, and `core.js` restores the reply from history through `assembleTurnContent` and `showResponse`, which records a fresh persisted exchange for the first page to exclude.

Ordering invariant behind all five: a recorded exchange always describes what the response box shows, so the screen and the history pager never disagree about which rows are already displayed.
