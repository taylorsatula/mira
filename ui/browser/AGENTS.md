# ui/browser/ — the pages the server itself serves and the stylesheet and asset tree behind them

## Files

- `chat/index.html` — the chat page's document, and the source of the element ids `core.js:elements` captures at load and of the `data-indicator` values the toolbar modules query. Open it before renaming or dropping either. The five toolbar buttons carry a `data-priority` ordering nothing reads.
- `memories/index.html` — the memories page and its inline controller. Open it before changing how memories are listed, filtered, or deleted.
- `domaindocs/index.html` — the domaindocs companion and its inline controller: live polling, inline section editing under a debounced save, conflict resolution, same-level drag reorder, the archived view. Open it before changing domaindoc editing or the poll.
- `settings/index.html` — the settings hub and its inline controller; the tab roster and each tab's loader are the controller's header comment. Open it before adding or changing a settings tab.
- `favicon.ico` — site icon served at `/favicon.ico`, linked by every page.
- `apple-touch-icon.png` — home-screen icon served at `/apple-touch-icon.png`, and the manifest's only icon.
- `manifest.json` — the PWA manifest served at `/manifest.json`; start URL `/chat`, standalone display, no comments possible in it.
- `assets/style.css` — the one stylesheet for all four pages: theme tokens, chat chrome, the supporting-page primitives scoped under `.page-main` and `.modal-dialog--form`, and every class the modules toggle by name. Open it before changing a token, a colour, or a class a module adds or removes.
- `assets/javascript/` — the modules, the one transport, the client half of the turn protocol; its own map.
- `assets/fonts/` — the four `.woff2` faces behind the `@font-face` srcs in `ui/browser/assets/style.css` and behind the pages' preloads. Open it before renaming a face.
- `assets/images/` — the logo, the nav and toolbar icons, and the per-tool icons the toolbar swaps. Open it before adding an icon the pages reference by path; the `TOOL_ICONS` stem-and-filename contract is the child map's.

## Wiring

- Serving: `main.py:create_app` → `page_dependencies` → `FileResponse`. Each of the four pages registers both `/name` and `/name/`, and every one carries `page_dependencies`; the three root meta files and the `/assets` mount carry none, so a gated page can still fetch its own CSS and JS. Gating an asset route bricks every page at its stylesheet. Counterpart: root `AGENTS.md` owns the route bodies, `UI_BROWSER_DIR`, and the boot check over `UI_BROWSER_FILES`.
- Page gate: route dependency `auth_api.get_current_user_for_pages` → `auth/api.py:_page_auth_failure` → `/v1/auth/local/session`. The failure is mode-dependent, so nothing in this tree may assume a redirect exists: under `multi` the gate answers with the 401 envelope and a client-side bounce to the session endpoint would land on a 404. Counterpart: `auth/AGENTS.md` owns both routes.
- Cache-bust: `ui/browser/assets/javascript/ui.js:ASSET_VERSION` ↔ the `?v=` tag every page repeats on every asset URL. One side bumped alone splits HTML-referenced and JS-injected assets into different cache generations, so a deploy pairs stale modules with fresh markup. The four font URLs are the one untagged exception on both the preload and the `@font-face` side. Counterpart: `ui/browser/assets/javascript/AGENTS.md` owns the constant.
- Theme: each page's pre-paint boot script ↔ `theme.js` ↔ `html[data-theme="light"]` in `ui/browser/assets/style.css`, and `theme.js`'s `window.miraGetTheme()`/`window.miraSetTheme()` setters bind `#appearance-theme` in `ui/browser/settings/index.html`. `:root` holds the dark defaults, so a page whose boot script never runs renders dark and stays dark, and Auto resolves in `theme.js` at runtime and never in CSS. Renaming the attribute, either `window` function, or the `mira-theme` storage key is one commit across all four pages, the CSS selector, `theme.js`, and the settings page. Counterpart: `ui/browser/assets/javascript/AGENTS.md` owns the runtime half.
- Sidebar: `sidebar.js` wires the `#app-sidebar` markup by id, and that markup is duplicated in all four pages with only `active`/`aria-current` differing. A nav item, a pill, or a reorder lands in all four files in one commit; a page skipped keeps serving its old navigation with no error. Counterpart: `ui/browser/assets/javascript/AGENTS.md`.
- Page ids: `core.js:elements` captures `loading-screen`, `ascii-container`, `response_box` and `response_content` from `ui/browser/chat/index.html` once at eval time, and `ui.js` finds the toolbar buttons by `data-indicator`. An id or `data-indicator` renamed or dropped in the page leaves a module holding `null` that fails on first use, and an id added after `core.js` runs is invisible to every module. Counterpart: `ui/browser/assets/javascript/AGENTS.md` owns the capture.
- Trigger rules: `ui/browser/settings/index.html` is the only in-tree caller of `/v1/api/triggers/rules…` and `/v1/api/triggers/conflicts`, so a rule-shape change reaches this page in the same commit. Counterpart: `cns/api/AGENTS.md`.
- Actions: the settings inline controller drives the `user`, `portrait` and `lora` action domains through `POST /v1/api/actions`, and the memories controller drives `memory` — both inside `ui/browser/*/index.html`, where a grep over `ui/browser/assets/javascript` does not reach. Renaming an action argument or the `preview_id` field fails at the call, rendering a rejected request in the page, never at load. Counterpart: `cns/api/AGENTS.md`.
- API tokens: the settings developer tab drives `/v1/auth/api-tokens`, the same route the TUI bootstrap and `deploy/vm/talktomira.sh` mint through. Counterpart: `auth/AGENTS.md`.
- CSP: the "What must change before strict can become the default" section of `auth/security_middleware.py`'s module docstring names this tree's inline scripts and handlers as strict mode's blocker. Counterpart: `auth/AGENTS.md`.

## Rules

- Add a page in this order: (1) create the page directory and its `index.html`, copying the head block from an existing page — boot script, `theme.js`, `style.css`, font preloads, cache-bust tags; (2) add the page's path to `main.py:UI_BROWSER_FILES` — skip it and the boot fails with `RuntimeError`, not the first request; (3) add the route in `main.py:create_app` with `dependencies=page_dependencies` and both `/name` and `/name/` — skip it and the page 404s; (4) copy the `#app-sidebar` block and the `api-client.js` and `sidebar.js` tags into the new page, and add its `<li>` to the `#app-sidebar` block of all four existing pages — `sidebar.js` returns early when `#app-sidebar` or `#sidebar-toggle` is missing, so a page built from the head block alone renders an inert sidebar with no error, and a page left out of the four keeps serving its old navigation.
- Only the four pages sit behind the gate. The icons, the manifest, and everything under `/assets` are served publicly so a gated page can still fetch its own stylesheet and scripts. A `.html` reading user data served without `page_dependencies` is readable by anyone who reaches the port; an asset moved behind the gate makes every page that references it fail to load.
- Every page controller registers a logout handler that navigates to `/` — the three inline controllers here and, by the child map's rule, the chat page's modules (grep `rg 'onAuthChange' ui/browser`). `MiraAPIClient` announces the event and stops; a page without a handler keeps a dead session and fails every later write with a 401, with no visible cause.
- Do not add inline `<script>` or inline `onclick=`-style handlers. `MIRA_CSP` stays off by default because this tree runs both and `script-src 'self'` rejects them; the strict flip is blocked until every inline block moves into files under `assets/`, so widening the inline surface here pushes that flip further away and a premature flip kills every controller at load.

Elsewhere: this map does not own the server's routing, the auth gate, or any module's behavior — `## Wiring` routes all three. The images are binaries with no authority beyond their names, and how a page came to look the way it does is `git log`.

## The page gate, anonymous GET to interactive

The chain that makes a page reachable, and the reason no page here holds a login form.

1. An anonymous GET `/chat` reaches the route's `page_dependencies` and therefore `auth_api.get_current_user_for_pages`, which looks for a Bearer header and then a `session` cookie.
2. With neither validating, it raises `_page_auth_failure`, and the auth mode decides the outcome: under `single` a 302 to `/v1/auth/local/session`; under `multi` the standard 401 envelope, which is the whole story for that install — MIRA ships no `/login/` page, so the operator's own sign-in surface is the entry point.
3. `/v1/auth/local/session` provisions or adopts the install's original member account, mints the `session` cookie, and 303s back to `/chat`. Which account that is, and why the local fixture identity is not it, is `auth/api.py:create_local_session`'s docstring.
4. The account row exists before the cookie is minted, and the cookie rides the second GET before any page JS runs — so the `MiraAPIClient` constructed at DOMContentLoaded opens a socket that authenticates on the first try.
5. Expiry re-runs the same chain and never shows a form: a 401 clears the token, the controller's logout handler navigates to `/`, the root route redirects to `/chat`, and the gate mints again. The handlers navigate to `/` rather than to the session endpoint because the client cannot know the auth mode, and the gate is the one mode-aware seam on both the first visit and every recovery.
