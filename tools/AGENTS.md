# tools/ — Tool framework: base class, repository, and config registry

## Rules

- Adding a tool requires exactly four coordinated pieces, in order: (1) a `XxxToolConfig(BaseModel)` with an `enabled` field registered via `registry.register("xxx_tool", XxxToolConfig)` at module level in the implementation file, (2) a `Tool` subclass with `name`, `simple_description`, and `tool_schema` class attributes, (3) a `run()` dispatching on `params.pop("operation")` (or equivalent), (4) the file inside `implementations/`. If no config is registered, `Tool.__init__` auto-generates a default config class (`XxxToolConfig`, `enabled=True`) via `registry.create_default` — so a tool with custom config fields must register explicitly or those fields silently do not exist. Skipping module-level registration with a custom config means the auto-generated one wins only if the module was imported before the config read; the reliable contract is always register-your-own.
- Discovery is import-driven: `ToolRepository.discover_tools(package_path="tools.implementations")` imports every module in `implementations/` (skipping `_`-prefixed and `repo`) and registers every concrete `Tool` subclass found in it (`_process_module`). A subclass defined in a module that is never imported there does not exist. Set `_is_abstract_base_class = True` on shared abstract bases in `implementations/` to keep them out of the catalog.
- Startup tool set is `ESSENTIAL_TOOLS` in `repo.py` (web, invokeother, continuum, reminder, memory, domaindoc, forage, sidebaragents, email, phoneafriend), enabled by `enable_tools_from_config` — which additionally honors each tool's per-config `enabled` flag from `config/config.py` and logs a warning while skipping a disabled essential tool. Everything else loads on demand via `invokeother_tool`. Editing `ESSENTIAL_TOOLS` is an edit to `repo.py`, not to `implementations/`.
- `invoke_tool` filters and coerces LLM params before `run()`: keys not present in `tool_schema.input_schema.properties` are dropped (debug-logged), and values are coerced to each property's declared type by `_coerce_to_schema_type` (repairable mutations like `"10"` → 10 or `[10]` → 10 apply with a logged warning; irreparable values raise `ValueError`). Consequence: schema-declared params reach every operation of a tool even when that operation ignores them — each `run()` must tolerate extra kwargs. A `params` string is JSON-decoded, falling back to `{"query": ...}`.
- Tool availability has three states, checked in `invoke_tool`/`get_all_tool_definitions`: enabled (`enabled_tools`), gated (`gated_tools` — availability decided per-call by the instance's `is_available()`; cannot be force-enabled, `enable_tool` raises), and unloaded. Ephemeral on-demand loads are cleared per turn by `cleanup_ephemeral_tools(essential_tools)` on `TurnCompletedEvent`; `_pinned_tools` (set by `invokeother_tool`'s `load_for_rest_of_session`) survive it.
- Tool instances are never cached: `get_tool` constructs a fresh instance per call with the current user context (user-scoping comes from `utils/user_context` contextvar, not from the repo). Constructor DI is signature-driven: unset required params annotated `LLMBridge`/`LLMProvider`, `ToolRepository`, or `WorkingMemory` are injected automatically when the repo can supply them.
- `HOW_TO_BUILD_A_TOOL.md` is stale: its line-number anchors (e.g. tools/repo.py lines 40-143 for the Tool base class, actually at ~line 98) no longer match the code. Use its pattern index to find *which* implementation demonstrates a pattern, then read the current file; never trust its line ranges.

## Files

- `repo.py` — `Tool` base class (user scoping via `user_id`/`user_data_path`/`db` properties, user-scoped file helpers `make_dir`/`get_file_path`/`open_file`/`file_exists`, `validate_config` hook for the validate endpoint, `parallel_safe` + `is_call_parallel_safe` for scheduling) and `ToolRepository` (registration, discovery, lazy instantiation with DI, `invoke_tool` with param filtering/coercion, enable/disable/gated lifecycle, `get_tool_definition(s)` producing `ToolDefinition`s for LLM context). Also holds `ESSENTIAL_TOOLS` and `_coerce_to_schema_type`. `get_metadata` parses the `run()` docstring's Google-style Args section for parameter descriptions. Consumers: instantiated once per app by `cns/services/tool_loop.py` and `agents/` code; `implementations/` subclasses extend `Tool`.
- `registry.py` — `ConfigRegistry` singleton (`registry`): name → Pydantic config class mapping, deliberately independent of `Tool` to avoid circular imports. `get_or_create`/`create_default` fabricate `{Name}ToolConfig` with `enabled=True` for unregistered tools. Consumers: read by `config/config.py` when building tool config sections and by `repo.py:Tool.__init__`.
- `HOW_TO_BUILD_A_TOOL.md` — Authoritative-in-substance guide for writing tools: four-piece registration flow, encrypted__ schema conventions, deferred table creation, credential storage/injection (web_tool pattern), timezone handling, tool_schema parameter-description standards, quick-start and API-tool templates, common failure patterns. Trust status: STALE — pattern catalog is valid, all line-number anchors are wrong (see Rules).
- `__init__.py` — Empty file, no re-exports; registration happens in module-level `registry.register` calls inside `implementations/`.
- `implementations/` — All concrete tools. See `tools/implementations/AGENTS.md`.

## Wiring

- Startup order: modules in `implementations/` call `registry.register(...)` at import → `discover_tools("tools.implementations")` imports them and registers tool classes → `enable_tools_from_config` enables `ESSENTIAL_TOOLS` whose config `enabled` flag is true. Reordering breaks: discovery must precede enabling (enabling looks up `tool_classes`), and config registration must precede any read of a tool's config class.
- Per-turn flow owned by `cns/services/tool_loop.py`: schemas from `get_all_tool_definitions` reach the LLM; the LLM's tool calls return through `invoke_tool`; `cleanup_ephemeral_tools` fires on `TurnCompletedEvent`.
- Outbound edges: `repo.py` pulls user identity from `utils/user_context` and data access from `utils/userdata_manager`; per-tool config models live in `config/config.py`; sidebar agents fetch tools by name via `get_tool` (works for config-disabled tools) — see `agents/AGENTS.md`; tool result envelopes (list-of-blocks, `success: False`, `_image_artifact`) are interpreted by `cns/services/` — see `tools/implementations/AGENTS.md` for the envelope contract.
