# tools/ — Tool framework: base class, repository, and config registry

*Want a new capability? You don't need to surgery the framework — describe the tool you're imagining to your pair-programming assistant and point it at `HOW_TO_BUILD_A_TOOL.md`. It handles the base class, the schema, the per-user storage; restart MIRA and the tool is live. Dreamed at lunch, running by dinner.*

## Rules

- Adding a tool requires exactly four coordinated pieces, in order: (1) a `XxxToolConfig(BaseModel)` with an `enabled` field registered via `registry.register("xxx_tool", XxxToolConfig)` at module level in the implementation file, (2) a `Tool` subclass with `name`, `simple_description`, and `tool_schema` class attributes, (3) a `run()` dispatching on `params.pop("operation")` (or equivalent), (4) the file inside `implementations/`. If no config is registered, `Tool.__init__` fabricates and registers an `enabled=True`-only default config class via `create_model` (the same shape `registry.create_default` produces, but built inline in `repo.py`) — so a tool with custom config fields must register explicitly or those fields silently do not exist. Skipping module-level registration with a custom config means the auto-generated one wins only if the module was imported before the config read; the reliable contract is always register-your-own.
- Discovery is import-driven: `ToolRepository.discover_tools(package_path="tools.implementations")` imports every module in `implementations/` (skipping `_`-prefixed and `repo`) and registers every concrete `Tool` subclass found in it (`_process_module`). A subclass defined in a module that is never imported there does not exist. Set `_is_abstract_base_class = True` on shared abstract bases in `implementations/` to keep them out of the catalog.
- Startup tool set is `ESSENTIAL_TOOLS` in `repo.py` (web, invokeother, continuum, reminder, memory, domaindoc, forage, sidebaragents, email, phoneafriend, bash_tool, heartbeat), enabled by `enable_tools_from_config` — which additionally honors each tool's per-config `enabled` flag from `config/config.py` and logs a warning while skipping a disabled essential tool. Everything else loads on demand via `invokeother_tool`, though `invoke_tool` auto-enables any non-gated tool on first invocation. `resolve_dependencies` returns `[]` without user context, so startup enabling skips dependency validation — dependency failures surface on the first per-user enable. Editing `ESSENTIAL_TOOLS` is an edit to `repo.py`, not to `implementations/`.
- `invoke_tool` filters and coerces LLM params before `run()`: keys not present in `tool_schema.input_schema.properties` are dropped (debug-logged), and values are coerced to each property's declared type by `_coerce_to_schema_type` (repairable mutations like `"10"` → 10 or `[10]` → 10 apply with a logged warning; irreparable values raise `ValueError`). Consequence: schema-declared params reach every operation of a tool even when that operation ignores them — each `run()` must tolerate extra kwargs. A `params` string is JSON-decoded — a decoded dict replaces it, any other JSON value wraps as `{"value": ...}`, undecodable text falls back to `{"query": ...}` — and a non-string, non-mapping `params` raises `TypeError`.
- Tool availability has three states, checked in `invoke_tool`/`get_all_tool_definitions`: enabled (`enabled_tools`), gated (`gated_tools` — availability decided per-call by the instance's `is_available()`; cannot be force-enabled, `enable_tool` raises), and unloaded. Ephemeral on-demand loads are cleared per turn by `cleanup_ephemeral_tools(essential_tools)` on `TurnCompletedEvent`; `_pinned_tools` (set by `invokeother_tool`'s `load_for_rest_of_session`) survive it — keyed per-user on the contextvar (a process-global map of per-user sets, never a bare shared set), and cleared for the current user at `SegmentCollapsedEvent` (mirroring stateful-trinket flush). The only gated registration site is `cns/integration/factory.py:_register_gated_tools`, currently an empty `pass` — the mechanism is dormant, no live gated tools.
- Tool instances are never cached: `get_tool` constructs a fresh instance per call with the current user context (user-scoping comes from `utils/user_context` contextvar, not from the repo). Constructor DI is signature-driven: unset required params annotated `LLMBridge`/`LLMProvider`, `ToolRepository`, or `WorkingMemory` are injected automatically when the repo can supply them; an annotated param **with a default is never injected** — an `Optional[X] = None` dependency stays `None` for the instance's lifetime (use a required param to receive DI). `WorkingMemory` is injected only when the repository itself was constructed with one.
- `HOW_TO_BUILD_A_TOOL.md` uses `file.py:symbol` anchors only — no line ranges, which go stale on the next edit of the target file. When adding a pattern to its index, cite the symbol that owns it.

## Files

- `repo.py` — `Tool` base class (user scoping via `user_id`/`user_data_path`/`db` properties, user-scoped file helpers `make_dir`/`get_file_path`/`open_file`/`file_exists`, `validate_config` hook for the validate endpoint, `parallel_safe` + `is_call_parallel_safe` for scheduling) and `ToolRepository` (registration, discovery, lazy instantiation with DI, `invoke_tool` with param filtering/coercion, enable/disable/gated lifecycle, `get_tool_definition(s)` producing `ToolDefinition`s for LLM context). Also holds `ESSENTIAL_TOOLS` and `_coerce_to_schema_type`. `get_metadata` parses the `run()` docstring's Google-style Args section for parameter descriptions. Consumers: instantiated once per app by `cns/integration/factory.py` and `utils/power_on_self_test.py`; called per turn by `cns/services/tool_loop.py`; `implementations/` subclasses extend `Tool`.
- `registry.py` — `ConfigRegistry` singleton (`registry`): name → Pydantic config class mapping, deliberately independent of `Tool` to avoid circular imports. `get_or_create`/`create_default` fabricate `{Name}ToolConfig` with `enabled=True` for unregistered tools. Consumers: read by `config/config_manager.py` (per-user `config.<tool_name>` access via `get_or_create`) and by `repo.py:Tool.__init__`.
- `HOW_TO_BUILD_A_TOOL.md` — Authoritative walkthrough for writing tools: pattern index (symbol anchors), four-piece registration flow with the availability-tier table, `run()` param-filtering contract, return-envelope contract, encrypted__ schema conventions, deferred table creation, Vault-vs-`UserCredentialService` credential split and injection, the two-clocks timezone rule (model input is user-local wall time, storage is UTC), signature-driven DI, tool_schema parameter-description standards, quick-start and API-tool templates, verification tiers, and the full checklist. Trust status: CURRENT (the 2025 auto-config wording and credential-injection-template drifts were corrected: auto-config section names `Tool.__init__`'s inline `create_model` + `registry.register` fabrication; credential templates use the annotation-injected `ToolRepository` constructor param).
- `__init__.py` — Empty file, no re-exports; registration happens in module-level `registry.register` calls inside `implementations/`.
- `implementations/` — All concrete tools. See `tools/implementations/AGENTS.md`.

## Wiring

- Construction and startup: `cns/integration/factory.py:_get_tool_repository` builds the process-singleton repository as `ToolRepository(working_memory=working_memory)`, then in order `discover_tools()` → `enable_tools_from_config()` → `_register_gated_tools()`; the boot gate (`utils/power_on_self_test.py`) constructs its own independent repository for discovery and tier checks. Reordering breaks: discovery must precede enabling (`enable_tool` raises `KeyError` on an unregistered name), and config registration must precede any read of a tool's config class.
- Per-turn flow: `cns/services/orchestrator.py` calls `get_all_tool_definitions` to build LLM tool context; `cns/services/tool_loop.py` delivers the LLM's tool calls through `invoke_tool`; `cleanup_ephemeral_tools` fires on `TurnCompletedEvent` via a synchronous subscription lambda in `cns/integration/factory.py`.
- On-demand loading indirection: the LLM reaches non-startup tools only through `invokeother_tool` (itself essential), whose `load`/`load_for_rest_of_session` operations call back into this repo's `enable_tool`/`_pinned_tools` — the tool-side contract is owned by `tools/implementations/AGENTS.md`.
- Sidebar agents fetch tool instances by name via `get_tool` (`agents/base.py`), which succeeds for config-disabled tools because it bypasses `enabled_tools` entirely.
- Outbound edges: `repo.py` pulls user identity from `utils/user_context`, data access from `utils/userdata_manager`, and the `ToolDefinition` type from `clients/llm/types.py`; tool config classes are registered into `tools/registry.py` by the implementation modules themselves and surfaced as `config.<tool_name>` through `config/config_manager.py`. Tool result envelopes (list-of-blocks, `success: False`, `_image_artifact`) are interpreted by `cns/services/` — the envelope contract is owned by `tools/implementations/AGENTS.md`.
