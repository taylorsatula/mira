# tools/ — the tool framework: `Tool` base class, config registry, and the repository owning discovery, availability, and the invocation pipeline

Elsewhere: per-tool contracts (credentials, parallel-safe opt-outs, return envelopes, per-tool naming) — `tools/implementations/AGENTS.md` · authoring-walkthrough detail (pattern index, templates, param-description standard, verification tiers) — `HOW_TO_BUILD_A_TOOL.md` · per-user config merge and the `*_tool` access path — `config/AGENTS.md` · the redaction sentinel state machine — `utils/AGENTS.md` (`tool_config_store.py`) · tool-config HTTP endpoints — `cns/api/AGENTS.md` · route names for tool-issued LLM calls — `clients/llm/AGENTS.md` · event taxonomy — `cns/core/events.py`; bus mechanics — `cns/integration/AGENTS.md` · tool-loop scheduling and result interpretation — `cns/services/AGENTS.md` · how a contract came to read as it does — `git log`.

## Rules

- Adding a tool is exactly four coordinated pieces: (1) `XxxToolConfig(BaseModel)` with an `enabled` field, registered at module level via `registry.register("xxx_tool", XxxToolConfig)`; (2) a `Tool` subclass with `name`, `simple_description`, `tool_schema`; (3) `run()` dispatching on `operation`; (4) the module inside `tools/implementations/` — `discover_tools` imports every non-`_`, non-`repo` module there and registers each concrete `Tool` subclass carrying `name` (duplicate name raises `ValueError` at registration; a shared base needs `_is_abstract_base_class = True` to stay out of the catalog). Skip (1): `Tool.__init__` fabricates an `enabled=True`-only default and registers it — the tool is silently auto-ENABLED, its custom fields do not exist, and a `secret`-marked field loses redaction entirely (sentinel machine owned by `utils/AGENTS.md`). Skip (2): nothing registers — the tool is absent from the catalog and from `enable_tool`; an `ESSENTIAL_TOOLS` entry for it then raises `KeyError` at boot (essential membership rescues nothing). Skip (4): the class does not exist. Availability tier is a separate decision — `ESSENTIAL_TOOLS` membership (upstream's, not a contributor's) is the only startup enablement; `enabled=True` on a non-essential tool never loads at boot, it only makes the tool catalog-eligible; `enabled=False` keeps it out of the catalog until config flips; gated (`register_gated_tool`, only from `cns/integration/factory.py:_register_gated_tools` — an empty `pass` today) never enters enabled sets.
- Repository state is per-user, never bare: `_enabled_tools`/`_pinned_tools` are dicts keyed by contextvar user id; `_BOOT_ENABLED_KEY` (`"__boot__"`) is the reserved key for pre-context startup enablement — an `enable_tool` call outside user context (a probe) writes the boot key, i.e. every user's baseline. A bare set on this process-global singleton publishes one user's loads into every user's `get_all_tool_definitions()`.
- The config gate precedes every enablement decision: `invoke_tool` and `get_all_tool_definitions` both drop a tool whose `config.<name>.enabled` is falsy even while it sits in the enabled set (pinned before the flip) — advertising a tool invoke must reject invites an unrecoverable model loop. Lookup rides `AppConfig.__getattr__`, which routes only `*_tool` names (naming rule owned by `tools/implementations/AGENTS.md`); any other spelling silently loses the gate and the per-user overrides.
- `invoke_tool` fixes what reaches `run()`: a string param JSON-decodes (fallback `{"query": …}`); a non-mapping raises `ParameterError`; keys outside `tool_schema.input_schema.properties` drop (debug-logged); survivors coerce per-property via `_coerce_to_schema_type` (single-element lists unwrap; `"10"`→10, `"true"`→True; every mutation warns; irreparable raises `ParameterError`); `inspect.signature(run).bind` then classifies arity/keyword mismatch as `ParameterError` before dispatch. `cns/services/tool_loop.py:_schema_hint` matches `ParameterError` by type and cannot tell a repairable argument error from the signature-drift kind `inspect.signature(run).bind` raises — the CORRECT PARAMETERS hint reaches both, so a schema param missing from `run()`'s signature loops with the hint echoing the drifted schema (schema/signature drift; fix code-side). Schema-declared params reach every operation — the tolerance rule is `tools/implementations/AGENTS.md`'s.
- A non-gated tool absent from the user's enabled set auto-enables at first invocation — the load-bearing cross-turn reload path, since turn-end cleanup removed it at the last boundary. Config-disabled tools never reach the branch (gate first); gated tools never (availability is `is_available()`'s). Deleting the auto-enable breaks every `invokeother_tool` reload.
- `get_tool` constructs a fresh instance per call under the current user — never cached (caching leaks one user's data into another's call); `__init__` therefore runs per invocation: no schema creation, no network, no LLM calls. Injection is signature-driven, required-params-only, by annotation name: `LLMProvider`/`LLMBridge` ← `clients/llm_provider.get_llm_provider()`, `ToolRepository` ← itself, `WorkingMemory` ← the factory-supplied instance. `Optional[X] = None` is not injected — expecting injection through it yields a permanently `None` attribute and a tool that silently never refreshes anything.
- `tools/registry.py` imports nothing from `config`, `clients`, or `utils` — it exists to break the cycle: `config/__init__.py` imports `tools.registry` at package level, and `repo.py` defers `from config import config` into `get_config()`. A top-level config import here breaks `import config` at boot.
- Config validation is write-strict, read-tolerant: `registry.validate_config_data` rejects unknown fields (`UnknownToolConfigFields`; `validation_entries()` is the API error shape) because Pydantic's default `extra='ignore'` drops a typo'd field while the PUT still looks accepted. Strictness lives in the registry, not `extra='forbid'` on the classes — `config_manager.get_tool_config` instantiates from stored rows that pre-strict writes may pollute, and a blanket forbid fails every such read.
- Every static `tool_schema` must survive `clients/llm/types.py:ToolDefinition.from_mapping` — envelope (known keys, non-empty name and description) plus `input_schema` internals: `type` must be `"object"`, `properties` a mapping, `required` a list of non-empty strings — `utils/power_on_self_test.py:_check_tools` runs it before the server binds, so a malformed input_schema parks the boot gate. `@property` schemas are reported as `dynamic_schema_tools`, not boot-verified — a schema that boots is not thereby a correct schema; a dynamic schema needs an explicit live read.
- Consumerless surfaces, kept as API, not to build on: the docstring-parsing metadata trio `get_metadata`/`get_formatted_description`/`get_tool_metadata` (dead — `tool_schema` is the model-facing contract, and `usage_examples` on tools feeds only this chain); `disable_tool` (zero production callers — `config.<name>.enabled=false` is the disable path); `resolve_dependencies`/`get_dependencies` (machinery present, no live overrides); `registry.list_registered`; `enable_all_tools` (probe convenience). Re-activation: a runtime disable path, or a tool that declares dependencies.
- A change to `Tool`, `ToolRepository`, or registry contracts updates `HOW_TO_BUILD_A_TOOL.md` in the same commit — its pattern index and templates are copied verbatim by new tools, and drift ships malformed registrations.

## Files

- `__init__.py` — empty; no re-exports; import `tools.repo`/`tools.registry` directly.
- `registry.py` — the config-class registry (tool name → Pydantic config class), import-free by design. Entry: module-level `registry` singleton, `ConfigRegistry.register`/`get`/`get_or_create`/`validate_config_data`, `UnknownToolConfigFields`. Gotcha: `get_or_create` returns the config class, never an instance — callers construct it.
- `repo.py` — `Tool` (user-scoped `user_id`/`db`/`user_data_path` accessors, file helpers, abstract `run`, `is_call_parallel_safe`, `validate_config`) and `ToolRepository` (`ESSENTIAL_TOOLS`, `ParameterError`, `_coerce_to_schema_type`, discovery, enablement, `invoke_tool`). Entry: `invoke_tool`, `get_tool`, `get_all_tool_definitions`, `enable_tools_from_config`, `pin_tool`, `cleanup_ephemeral_tools`. Gotcha: `enabled_tools` is the cross-user union — a boot-gate read surface only; per-user visibility is `is_tool_enabled`/`get_all_tool_definitions`, never the union.
- `HOW_TO_BUILD_A_TOOL.md` — the authoring walkthrough: pattern index (anchors `file.py:symbol`), four-piece flow with per-piece skip failures, credential/timezone/param-description standards, two full templates, verification tiers, the upstream-PR process. Trust: framework-contract claims defer to this map and the code (its own doctrine-owners paragraph); one verified drift — the availability-tier table claims `enabled=True` loads a tool at startup, but `enable_tools_from_config` iterates `ESSENTIAL_TOOLS` only (Rule above states the code truth).
- `implementations/` — every concrete LLM-callable tool; per-tool contracts, credentials, return envelopes — `tools/implementations/AGENTS.md`.

## Wiring

- Startup: `cns/integration/factory.py:_get_tool_repository` — `ToolRepository(working_memory=…)` → `discover_tools()` → `enable_tools_from_config()` → `_register_gated_tools()`, plus the `TurnCompletedEvent` subscription calling `cleanup_ephemeral_tools(set(ESSENTIAL_TOOLS))`. Counterpart: `cns/integration/AGENTS.md`.
- Execution: `cns/services/tool_loop.py` reads `tool_classes[name].is_call_parallel_safe(input)` to split calls (sequential batch first, then the parallel pool), calls `invoke_tool`, matches `ParameterError` by type for the CORRECT PARAMETERS hint (rendering `get_tool_definition`), and interprets return envelopes. Counterpart: `cns/services/AGENTS.md`.
- Advertising: `cns/services/orchestrator.py` reads `get_all_tool_definitions()` per turn. Counterpart: `cns/services/AGENTS.md`.
- Sidebar bypass: `agents/base.py` fetches tools via `get_tool` and calls `run()` directly — param filtering, coercion, the config gate, and the enabled-set check never reach sidebar-agent tool calls; a framework change to `invoke_tool` must account for this second dispatch path. Counterpart: `agents/AGENTS.md`.
- Direct construction: `cns/api/actions.py` (`ReminderTool()`/`ContactsTool()` in the reminder/contacts actions and `_get_tool_instance`), `cns/api/federation.py:PagerTool()`, `cns/api/heartbeat_api.py:HeartbeatTool()`, `working_memory/trinkets/reminder_manager.py:ReminderTool()` (cached on the trinket) call `run()` (or a public method) on bare instances — DI, param filtering, coercion, the config gate, and the enabled-set check never reach them, while `Tool.__init__`'s config auto-registration still runs; a framework change to `run()` or `Tool.__init__` contracts must account for these paths alongside `invoke_tool` and the sidebar bypass.
- Config seam: `rg 'from tools\.registry import'` → `config/__init__.py` (package-level import, the cycle-break), `config/config_manager.py` (`AppConfig.__getattr__` → `registry.get_or_create`), `cns/api/tool_config.py`, `utils/tool_config_store.py` (secret-field discovery over registered classes). Merge semantics owned by `config/AGENTS.md`; sentinel machine by `utils/AGENTS.md`.
- Tool-config API: `cns/api/tool_config.py` PUT and POST `/actions/tools/{tool}/validate` consume `registry.get`/`validate_config_data`/`UnknownToolConfigFields.validation_entries`, enforce the essential-cannot-disable guard over `ESSENTIAL_TOOLS`, and run `Tool.validate_config` overrides. Counterpart: `cns/api/AGENTS.md`.
- Boot gate: `utils/power_on_self_test.py:_check_tools` constructs a bare `ToolRepository()` (no working_memory — DI-dependent tools cannot instantiate there), discovers, verifies `ESSENTIAL_TOOLS` registered/config-enabled/enabled, reads the `enabled_tools` union, and envelope-validates static schemas via `clients/llm/types.py:ToolDefinition.from_mapping`. Counterparts: `utils/AGENTS.md`, `clients/llm/AGENTS.md`.
- Collapse teardown: `ToolRepository.__init__` subscribes `_clear_pinned_tools_on_segment_collapse` to `SegmentCollapsedEvent` (`cns/core/events.py`) through the injected `working_memory.event_bus`, mirroring `working_memory/core.py:_flush_stateful_trinkets`; the bus is owned by `cns/integration/AGENTS.md`.
- Up from implementations: modules register their config classes into `registry` at import (every one except `invokeother_tool.py`, whose `Tool.__init__` fabricates the default) and instantiate tools only through `get_tool` (`rg 'get_tool\('` → `tools/implementations/invokeother_tool.py`, `agents/base.py`); per-user loads and pins arrive from `invokeother_tool`'s `load`/`load_for_rest_of_session`. Counterpart: `tools/implementations/AGENTS.md`.
- User scoping: `Tool.user_id` ← `utils/user_context.get_current_user_id`; `Tool.db`/`user_data_path` ← `utils/userdata_manager.get_user_data_manager` (contextvar-resolved per-user store; contracts owned by `utils/AGENTS.md`).

## Availability lifecycle, boot to reload

An opt-in tool (`enabled=False`, non-essential) travels this path from process start to a second-turn call; no single file shows the whole machine.

1. Boot: `cns/integration/factory.py` constructs `ToolRepository(working_memory)`; `discover_tools()` imports every `tools/implementations` module — config classes register at import, tool classes land in `tool_classes`.
2. `enable_tools_from_config()` enables `ESSENTIAL_TOOLS` only, under `_BOOT_ENABLED_KEY` — everyone's baseline. A config-disabled essential logs a warning and is skipped; the boot gate later refuses the bind.
3. Each turn, `get_all_tool_definitions()` offers the boot set ∪ the current user's set, minus config-disabled, plus available gated tools. The opt-in tool is absent.
4. The model loads it via `invokeother_tool`: `load` → `enable_tool` (this turn only); `load_for_rest_of_session` → additionally `pin_tool`.
5. Turn end: `TurnCompletedEvent` → `cleanup_ephemeral_tools` subtracts the user's enabled-minus-essential-minus-pinned tools. A `load` dies here; pins persist.
6. Segment collapse: `SegmentCollapsedEvent` → `_clear_pinned_tools_on_segment_collapse` pops the user's pins and `_enabled_tools[user_id]` together — "rest of session" means until collapse, and per-user enablement never crosses a segment boundary. The boot key survives.
7. Next turn the model calls the now-unenabled tool: `invoke_tool` config-gates first, then on the enabled-set miss auto-enables it back — the cross-turn reload. A pinned tool whose config has since flipped off is refused at the same gate, never auto-enabled.

Ordering invariants: the config gate precedes every enabled-set decision in both `invoke_tool` and `get_all_tool_definitions` — hoisted below the set check, a config-off tool becomes an auto-enabled one; cleanup subtracts only from the completing user's set; collapse deletes pins and enablement together — pins surviving enablement's death leave the tool pinned but unadvertised (`get_all_tool_definitions` omits it until a direct call auto-enables it back, so the model must already know the name).
