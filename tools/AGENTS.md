# tools/ — the tool framework: the `Tool` base class, the config registry, and the repository owning discovery, availability, and invocation

## Files

- `__init__.py` — docstring only; no re-exports, no import-time side effects.
- `registry.py` — the tool-name-to-config-class registry, and the one strict validation seam over it. Open it before changing how a tool's config is registered or how incoming config data is rejected.
- `repo.py` — the `Tool` base class and the `ToolRepository` owning discovery, availability, and the call pipeline. Open it before changing what a tool call can reach or what makes a tool available.
- `HOW_TO_BUILD_A_TOOL.md` — the authoring walkthrough. Open it before writing a tool, and before changing what a tool must declare.
- `implementations/` — every concrete LLM-callable tool, with per-tool contracts, credentials, and return envelopes; its own map.

## Wiring

- Startup: `cns/integration/factory.py:_get_tool_repository` → `ToolRepository(working_memory=…)` → `discover_tools` → `enable_tools_from_config` → `_register_gated_tools`. Working memory is constructed first because `ToolRepository.__init__` reads the bus off it and skips its collapse subscription when that bus is absent — a repository built without one never clears pinned tools, and nothing raises. Counterpart: `cns/integration/AGENTS.md`.
- Turn end and collapse: the factory subscribes `TurnCompletedEvent` to a lambda closed over `essential_set`, which calls `cleanup_ephemeral_tools`; `_clear_pinned_tools_on_segment_collapse` is subscribed inside `ToolRepository.__init__` through `working_memory.event_bus`, which is why the construction order in the Startup bullet decides whether collapse ever clears a pin. Both resolve the user from the contextvar at event time, so a completion or collapse touches only its own user's set. Counterpart: `cns/services/AGENTS.md`.
- Execution: `cns/services/tool_loop.py` reads `is_call_parallel_safe` per call to split the sequential batch from the parallel pool, calls `invoke_tool`, and matches `ParameterError` by type to decide whether to append the CORRECT PARAMETERS hint. Because the match is by type rather than by message, a `TypeError` raised inside `run()` is not relabelled a parameter error. Counterpart: `cns/services/AGENTS.md`.
- Advertising: `cns/services/orchestrator.py` reads `get_all_tool_definitions()` per turn. For enabled-set tools the config gate and the per-user set apply on both that path and `invoke_tool`, so what the model is offered and what it may call cannot diverge. The `gated_tools` loop is the one path that skips the gate: it advertises a name on `is_available()` alone, so wiring a gated tool means adding the gate to that loop first, or the model is offered a tool `invoke_tool` must refuse. Counterpart: `cns/services/AGENTS.md`.
- Bypass doors, and no gate runs on either: repository-free instantiation — `cns/api/actions.py:_get_tool_instance` and the routes calling it, `cns/api/heartbeat_api.py:cancel_brief`, `working_memory/trinkets/reminder_manager.py` build the class themselves and call `run()` — and `ToolRepository.get_tool` from `agents/base.py:_execute_tool_call`, which injects constructor dependencies but applies nothing else. Neither filters params to the schema, coerces types, checks the config gate, or checks the enabled set, so a change to the pipeline changes nothing there. `invokeother_tool`'s `get_tool` sites only read `simple_description` and `is_available()`, and the tool loop's hint rendering goes through `get_tool_definition`; neither reaches `run()`. Counterpart: `agents/AGENTS.md`.
- Config seam: `rg 'from tools\.registry import'` — `config/__init__.py` imports the registry at package level (the cycle-break), `config/config_manager.py:AppConfig.__getattr__` resolves a `*_tool` name through `registry.get_or_create`, `cns/api/tool_config.py` validates writes through `registry.validate_config_data`, `utils/tool_config_store.py` discovers secret fields off registered classes. Counterpart: `config/AGENTS.md`.
- Validation seam: `cns/api/tool_config.py:_call_tool_validation` is the repository-free consumer of the tool contract — it imports the tool module directly and re-implements the discovery predicate (`issubclass` of `Tool`, `attr.__module__ == module.__name__`, `attr.name == tool_name`) to reach `Tool.validate_config`. A change to `discover_tools`'s predicate or to `Tool.validate_config`'s contract updates it in the same commit: drift there does not raise, it turns the endpoint's `live_validation` to False and the operator reads a schema check as a connection test that never ran.
- Boot gate: `utils/power_on_self_test.py:_check_tools` constructs a bare `ToolRepository()` (no working memory, so DI-dependent tools cannot instantiate there), discovers, checks `ESSENTIAL_TOOLS` registered and config-enabled and enabled, and envelope-validates each static schema through `clients/llm/types.py:ToolDefinition.from_mapping`. Counterparts: `utils/AGENTS.md`, `clients/llm/AGENTS.md`.
- Up from `implementations/`: modules register their config class at import and reach other tools through `get_tool`; per-user loads and pins arrive from `invokeother_tool`'s `load`/`load_for_rest_of_session`. Counterpart: `tools/implementations/AGENTS.md`.

## Rules

- Adding a tool is four coordinated pieces: a `XxxToolConfig` with an `enabled` field registered at module level via `registry.register("xxx_tool", …)`; a `Tool` subclass carrying `name`, `simple_description`, and `tool_schema`; a `run()` dispatching on `operation`; and the file itself inside `implementations/`. Skip the registration and `Tool.__init__` fabricates an `enabled=True`-only default — the tool ships ON with none of its declared fields, and any `secret`-marked field loses redaction (sentinel machine owned by `utils/AGENTS.md`). Skip `simple_description` and the tool never enters the `invokeother_tool` catalog, so no path loads it.
- Availability is a separate decision from enablement, and exactly one thing loads a tool at boot: `ESSENTIAL_TOOLS` membership, which is an edit to `repo.py` and an upstream call rather than a contributor's. Two switches, not one: the config field `config.<name>.enabled` is a refusal no load path overrides — `invoke_tool` raises at the gate, and `invokeother_tool` both omits the name from its catalog and refuses it by name — while runtime presence is the per-user enabled set, written only by `invokeother_tool`'s `load`/`load_for_rest_of_session` and by `invoke_tool`'s auto-enable. `register_gated_tool` — called only from `cns/integration/factory.py:_register_gated_tools`, an empty `pass` today — hands availability to `is_available()` and makes `enable_tool` raise on that name.
- `registry.py` imports nothing from `config`, `clients`, or `utils`, and `repo.py` defers `from config import config` into `get_config()`. `config/__init__.py` imports `tools.registry` at package level, so a top-level config import in `registry.py` closes the cycle and `import config` fails at boot. `repo.py`'s `get_config()` deferral is a different constraint — nothing in `config/` imports `tools.repo` — it keeps the singleton's construction ahead of the repository that reads it.
- A `tool_schema` is boot-verified as an envelope only: `ToolDefinition.from_mapping` checks the known top-level keys and a non-empty name and description, while `input_schema` internals — enums, `required`, `additionalProperties` — pass through unvalidated and surface as model-side call failures instead. A `@property` schema is reported as a dynamic schema and skipped entirely, so it needs an explicit live read. A schema that boots is not thereby a correct schema.
- A change to `Tool`, `ToolRepository`, or the registry contract updates `HOW_TO_BUILD_A_TOOL.md` in the same commit. Its templates are copied verbatim by whoever writes the next tool, so drift ships malformed registrations.

Elsewhere: this map owns the framework those tools run on and the contract for authoring one, not what any one tool does — its operations, parameters, or stored data, which is `utils.userdata_manager`'s. Why a contract reads as it does is `git log`. Every other destination this directory reaches is an edge — see `## Wiring`.

## Availability lifecycle, boot to reload

An opt-in tool — `enabled=False`, non-essential — travels this path from process start to a second-turn call; no single file shows the whole machine.

1. Boot: `cns/integration/factory.py` constructs `ToolRepository(working_memory)`. `discover_tools()` imports every module in `tools/implementations/`, so config classes register into `registry` at import and tool classes land in `tool_classes`.
2. `enable_tools_from_config()` enables `ESSENTIAL_TOOLS` only. It runs with no user context, so the whole set lands under `_BOOT_ENABLED_KEY`: everyone's baseline. A config-disabled essential logs a warning and is skipped, and the boot gate later refuses to bind.
3. Each turn, `get_all_tool_definitions()` offers the boot set ∪ the current user's set, minus config-disabled tools, plus gated tools whose `is_available()` is true. The opt-in tool is absent.
4. The model loads it through `invokeother_tool`: `load` → `enable_tool`, which lasts the turn; `load_for_rest_of_session` → the same, plus `pin_tool`.
5. Turn end: `TurnCompletedEvent` → `cleanup_ephemeral_tools` subtracts the user's enabled-minus-essential-minus-pinned tools. A `load` dies here; a pin survives.
6. Segment collapse: `SegmentCollapsedEvent` → `_clear_pinned_tools_on_segment_collapse` pops that user's pins and their `_enabled_tools` entry together. "Rest of session" therefore ends at collapse, and no per-user enablement crosses a segment boundary. The boot key survives both steps.
7. On the next turn the model calls the now-unenabled tool: `invoke_tool` applies the config gate first, then auto-enables on the enabled-set miss. That auto-enable is the cross-turn reload. A pinned tool whose config has since flipped off is refused at the gate and never reaches the branch.

Two orderings hold the machine together. In `invoke_tool` the config gate precedes the enabled-set check — moved below it, a config-off tool becomes an auto-enabled tool and the disable contract fails; `get_all_tool_definitions` gates the enabled set after the boot-union and has no auto-enable branch at all, which is why the two paths agree for enabled-set tools and disagree only in the `gated_tools` loop. And collapse deletes pins and enablement in the same step: pins outliving their enablement leave a tool pinned but unadvertised, since `get_all_tool_definitions` omits it until a direct call auto-enables it back — a call the model has no way to know to make.
