# utils/ — the process-wide primitives the rest of the tree shares, and the boot and upgrade machinery around them

## Files

- `__init__.py` — package marker; docstring only, no re-exports. Import the submodules by full path.
- `user_context.py` — identity and the request-scoped contextvars. Open it before reading or writing anything request-scoped that other code fetches from a contextvar.
- `database_session_manager.py` — the shared Postgres pool and the session types it hands out. Open it before adding a query that must see exactly one user, or every user.
- `distributed_lock.py` — Valkey locks whose every mutation is token-scoped. Open it before guarding something that spans processes.
- `scheduler_service.py` — the APScheduler wrapper every scheduled job is registered through. Open it before adding a job or changing registration order.
- `scheduled_tasks.py` — the startup registration orchestration, and the use-day gate the lt_memory jobs ask. Open it before adding a scheduled job or deciding whether some user is due.
- `lt_memory_jobs.py` — the memory-maintenance jobs and their cadences. Open it before changing when memory maintenance runs.
- `sidebar_jobs.py` — sidebar dispatcher poll registration and trigger instantiation. Open it before changing which triggers get dispatched.
- `failover_jobs.py` — the provider recovery probe, registered only when failover is enabled. Open it before touching flip-back behaviour.
- `update_check.py` — the cached release verdict and its 24-hour job. Open it before changing the update notice or when its value is computed.
- `scheduled_task_monitor.py` — the job wrapper that times, accounts for, and dumps stuck runs. Open it before wrapping a job with a timeout.
- `thread_monitor.py` — the operation registry, per-thread stack capture and the thread dump. Open it before diagnosing a hang.
- `power_on_self_test.py` — the boot gate and the live-server checks. Open it before adding a startup requirement or a check that should fail boot.
- `schema_migrations.py` — the versioned database step runner and its backup and restore path. Open it before anything that changes MIRA's schema or its upgrade path.
- `self_restart.py` — the in-process restart latch, the in-flight turn gauge, and the SIGTERM that fires it. Open it before changing how a restart is requested or when it fires.
- `release_identity.py` — this tree's version, release-name ordering, and artifact-versus-tag verification. Open it before comparing versions or adding a consumer that runs outside the server; the one consumer today is `ui/tui/update.py`, which imports it from a venv holding none of this tree's dependencies.
- `env_reconcile.py` — the settings-file pass of `mira update`. Open it before changing which environment names survive an update.
- `device_binding.py` — the heartbeat low-power publisher into a deployer-supplied device shim. Open it before changing what crosses to the device.
- `user_activity.py` — the first-message-of-day hook and the activity counters. Open it before reading or maintaining a user's activity-day count.
- `userdata_manager.py` — per-user encrypted SQLite: the connection, the encryption, and every tool table's DDL. Open it before adding a table or a column to a tool's per-user store.
- `userdata_migrations.py` — the versioned step chain for existing per-user files. Open it before changing the shape of a per-user table that already exists on disk.
- `user_credentials.py` — the per-user credential store over that SQLite file. Open it before storing or reading a user's secret.
- `tool_config_store.py` — per-user tool configuration with server-side secret fields. Open it before changing how a tool's config or its secrets round-trip.
- `skill_files.py` — the skill catalog, its parser, and the per-user write path. Open it before changing when an edited skill takes effect.
- `domaindoc_shares.py` — cross-user domaindoc resolution through the `_shared` label suffix. Open it before touching shared-document visibility.
- `untrusted_content.py` — the external-content boundary: the wrap and the screen in front of it. Open it before letting outside text into a model context.
- `url_safety.py` — public-URL validation, and the IP a caller must pin its connection to. Open it before requesting a URL a model or a user supplied.
- `http_client.py` — retrying httpx clients and the IP-pinned transport. Open it before adding an outbound call or changing retry behaviour.
- `playwright_service.py` — the singleton headless Chromium and the per-request interception that constrains it. Open it before changing how a JavaScript page is rendered or which requests it may make.
- `nominatim_client.py` — OpenStreetMap geocoding over Nominatim and Overpass; unwired, with no in-tree consumer. Open it only when giving it one.
- `mcp_client.py` — the MCP client surface; no in-tree consumer today. Open it before building the first one.
- `artifact_store.py` — user-scoped artifact files on disk. Open it before changing where a generated file is written or read back.
- `document_processing.py` — document to text extraction, with zip-bomb guards and a text cap. Open it before adding a document format.
- `image_compression.py` — image compression at validation time. Open it before changing an image's size or storage format.
- `tag_parser.py` — response tag parsing, and the memory short-ID family. Open it before adding a tag MIRA emits or changing how one is stripped.
- `text_sanitizer.py` — the minimal message sanitizer. Open it before changing what the API layer accepts as message content.
- `perf.py` — all database and request instrumentation. Open it before adding an `execute_*` method, a perf route, or a slow-path probe.
- `logging_config.py` — the TOAST level, the log filters, colored output, and the opt-in SDK tracing. Open it before adding a log level, a filter or a handler.
- `llm_tap.py` — the USR1-toggleable LLM traffic firehose. Open it before working out which call produced a payload.
- `cost_accumulator.py` — per-request LLM cost accounting and the pricing fallback chain. Open it before changing what a turn reports as its cost.
- `timezone_utils.py` — the time vocabulary: UTC storage, local wall-time parsing, daylight-saving strictness. Open it before formatting, parsing or converting any timestamp.
- `profile_validation.py` — the gate for a user-typed profile name. Open it before accepting one.

## Wiring

- Identity into RLS: `user_context.get_current_user_id` → `LTMemorySessionManager.get_session(user_id)` → `LTMemorySession._setup_connection`, which sets `app.current_user_id` on the connection. The id must be read from the contextvar before the session exists; a session built from any other value is a second identity path, and the query succeeds against whichever user that value names.
- Restart: `bash_tool.request_restart` → `self_restart.enter_turn`/`exit_turn` → `trigger_restart_if_pending` → `main.py` exiting `RESTART_EXIT_CODE`. `enter_turn` runs before the turn body and `exit_turn` plus the trigger after its output is delivered; an unpaired or reordered pair either leaves the gauge above zero so the restart never fires, or fires it under a live turn. Counterpart: `cns/api/AGENTS.md`.
- Outbound URL to socket: `url_safety.validate_public_http_url` → `http_client.pinned_request`, which connects to `ValidatedURL.resolved_ip` and refuses any other hostname. Connecting by hostname instead re-resolves DNS after validation and reopens the rebinding window. `playwright_service.validate_browser_request_url` is the sanctioned exception: Chromium resolves its own connections, so the browser tier is not rebinding-proof. Counterpart: `tools/implementations/AGENTS.md`.
- Boot gate against job registration: `power_on_self_test._check_scheduler_registration` requires by name the jobs that `scheduled_tasks`, `lt_memory_jobs` and `auth.service` register, and `_check_http_diagnostics` re-checks four of them on the live server. A renamed job id fails the boot gate with no compile error anywhere. Counterpart: `auth/AGENTS.md`.
- Activity counter: `user_activity.increment_user_activity_day` maintains the column `scheduled_tasks.get_users_due_for_job` selects on. Skipping the increment makes every use-day job skip that user: the job runs, selects nobody, and reports success. Counterpart: `cns/infrastructure/AGENTS.md`.
- Tool secrets: `tool_config_store` asks `tools/registry.py` which fields of a tool's config class are secret. A config class the registry does not hold has no known secret fields, so redaction returns it untouched and the secrets reach the client. Counterpart: `tools/AGENTS.md`.
- Cost of a turn: `clients/llm/lifecycle.py` calls `cost_accumulator.record` per completed provider call, and the request handler calls `start`/`drain`. A provider call path that skips `record` under-reports the turn's cost with no visible failure. Counterpart: `clients/llm/AGENTS.md`.
- Sidebar activity table: the DDL in `userdata_manager` runs at every user-database open and again from `agents/base.py:ensure_activity_schema`, so the dispatcher's dedup reads a table that exists before any agent has run. Counterpart: `agents/AGENTS.md`.
- Per-user cache lifetime: `userdata_manager.UserDataManagerCleanupHandler` subscribes to `SegmentCollapsedEvent` and calls `clear_manager_cache(user_id)`; `cns/integration/factory.py` constructs it into the subscription assembly. A per-user manager cache or connection the handler does not clear survives segment collapse and pins one SQLite connection per user until the process restarts. Counterpart: `cns/integration/AGENTS.md`.
- External text into a prompt section: `untrusted_content.wrap_untrusted` is applied once per section, around the whole external listing, by the trinkets that render it (`working_memory/trinkets/email_trinket.py:generate_content` is the shape). Which sections wrap and which escape per field is owned by `working_memory/trinkets/AGENTS.md`.
- Trinket hash deletions: `domaindoc_shares.py` drops the `domaindoc` field of the `trinkets:{user_id}` hash after a share changes visibility. The field names in that hash are owned by `working_memory/trinkets/AGENTS.md`.
- Lock release and renew: `distributed_lock` releases through `compare_and_delete` and renews through `compare_and_expire`, both against the token it wrote at acquire. A plain `delete` releases a lock another holder has since taken, and a plain expire renews it on that holder's behalf. Counterpart: `clients/AGENTS.md`.
- Keys that survive a flush: the step runner's `StepContext.invalidate_valkey` flushes through the same `BOOT_FLUSH_PRESERVE_PREFIXES` tuple `main.py` uses at startup, so there is no per-step exemption. A key a step or a feature must keep across an upgrade is added to that tuple in `clients/valkey_client.py`; exempted anywhere else, it is flushed on the next boot. Counterpart: `clients/AGENTS.md`.
- Secret hydration for a config consumer: `tool_config_store.load_user_tool_config(..., hydrate_secrets=True)` derives the fields it fills from `get_secret_field_names(registry.get(tool_name))`, so the tool's config class is registered in `tools/registry.py` and each secret field marked `json_schema_extra={"secret": True}` before a caller asks for hydration — both are import-time, and the load has no later correction step. An unregistered class or an unmarked field returns the stored config with that key absent and no error: `cns/services/pollers/inbox_poller.py:_try_load_config` then finds `password` missing and reports the user as unconfigured, so the poller never starts and the prompt slot stays empty while the credential sits in the store. Counterpart: `cns/services/pollers/AGENTS.md`.
- Probe identity and the user directory layout: `tests/fixtures/probe_user.py` sets and clears the contextvar through `set_current_user_id`/`clear_user_context`, and hardcodes `<repo>/data/users/<id>` — the path `userdata_manager.base_dir` builds. The clear runs after the last user-scoped write and before the next identity is set; a probe that skips it leaves `_user_context` holding the previous user, so the next probe's writes land under that identity. Moving `base_dir`'s layout leaves the fixture's hardcoded path pointing nowhere, so its `rmtree` deletes nothing and `residue.assert_user_removed` witnesses a path that never exists, passing with the debris on disk. Counterpart: `tests/fixtures/AGENTS.md`.

## Rules

- A new `execute_*` method on `PostgresClient`, `LTMemorySession` or `AdminSession` must be added to `perf.install_db_instrumentation`'s target list, which patches by method name. An unlisted method runs un-instrumented, so its time vanishes from every request summary; timing added inside the method instead is counted twice by the wrapper.
- A new `UserPreferences` field must land in both the SELECT list and the constructor call inside `get_user_preferences`, or the field serves its default on every cache miss. Any writer of a preference must call `invalidate_user_preferences_cache(user_id)` once it has persisted, or every other context serves the stale Valkey entry for up to 5 minutes.
- The use-day gate is one stateless function, `scheduled_tasks.get_users_due_for_job`: `MOD(cumulative_activity_days, interval) = 0` over recently active users with memory manipulation enabled. A tracking table or a last-ran column is a defect, and re-selecting a user whose counter sits on a multiple is expected behaviour rather than a bug. A job body wraps each user's work in `set_current_user_id()` and clears it in a `finally` (`lt_memory_jobs.py` is the pattern); without the clear, the next user's work runs under the previous user's identity.
- Add a scheduled job as three coordinated edits: a `register_*` function in this directory, a call to it from `main.py`'s startup block before `scheduler_service.start()`, and — when the job must always exist — its job id in the boot gate's required set. Skipping the `main.py` call ships a job that never runs; adding the id without the registration parks boot on a job that does not exist.
- `schema_migrations` takes `conninfo` as a required parameter on every database entry and resolves no database credential of its own: only `scripts/migrate.py` resolves the conninfo, from Vault as `mira_admin`. A default or fallback conninfo is a second credential path, and production would then run steps against whatever the default names. Backup and restore do read and patch MIRA's Vault secrets through `VaultAdapter`, so an AppRole failure surfaces inside `take_backup` even on a host whose database credentials are fine.
- `schema_migrations.migrate` runs one fixed order: every refusal before anything is touched, the ownership bootstrap before the backup (pg_dump as `mira_admin` cannot read an object another role owns), and the backup before any ledger write or step. A mutation inserted before the backup is unrecoverable on failure; a refusal moved after the bootstrap reports that nothing was changed when the ownership of every object just changed.
- `schema_migrations.superuser_prefix` and `deploy/lib/services.sh:seam_mode` answer the same question — how this host runs a command as the PostgreSQL superuser — and change together in one commit. The two are not a translation: the shell folds every arm into one of four mode words while the Python returns the argv prefix, so Darwin and a container's root both resolve to `none` in the shell while Python returns no prefix and `sudo -u postgres` respectively. A one-sided edit leaves the shell and the Python disagreeing about how this host elevates, and the disagreement surfaces only on a host that takes the edited arm, as a refused backup. Counterpart: `deploy/lib/AGENTS.md`.
- The injection screen's band edges, `PASS_CEILING` and `REJECT_FLOOR`, and the wording of the six `SCREEN_QUESTIONS` are calibrated against `tests/protected/injection_defense_probe.py`. Move an edge only with that battery's numbers; a hand-tuned edge silently reclassifies content that battery measured. This directory owns the `SCREEN_QUESTIONS` name tuple; the question wording is `config/prompts/injection_screen/`'s. Counterparts: `tests/protected/AGENTS.md`, `config/prompts/AGENTS.md`.
- Only `screen_untrusted` applies the semantic screen; `wrap_untrusted` applies the structural wrap and nothing else. Whether a piece of external text is screened at all is therefore decided by each caller's choice of entry point, not by the screen's config: `agents/base.py:_sanitize_work_item` screens a work item's `raw_content` for every agent that leaves `sanitize_untrusted_input` on, while a tool result reaches a model context on whatever entry point its tool picked. A tool returning outside text for a model to read calls `screen_untrusted` before returning. With the screen enabled, every failure that is not a rejection raises `InjectionScreenUnavailable` — fail closed, because passing unscreened content as screened is the one outcome the screen exists to prevent.

Elsewhere: this map does not own the design of the systems these primitives and the upgrade path reach — that is each counterpart directory's map — and it does not own the step files that path runs; each file's docstring carries its own mechanism, so nothing here restates one. The contextvar and external-content doctrine is root `AGENTS.md`; config fields and use-day interval semantics are `config/AGENTS.md`; probe doctrine is `tests/AGENTS.md`; pool sizing and the Vault client's own contract belong to the infrastructure clients' maps, reached through the edges above; the step-authoring contract is `deploy/migrations/AGENTS.md`; supervisor layouts and release mechanics belong to the deploy tree's own maps. Why any rule here reads as it does is `git log`. Every other destination this directory reaches is an edge — see `## Wiring` above.

## One upgrade from a pre-mechanism install

The case that decides most of the `schema_migrations` rules and the boot guard's shape. An install built by release `v2026.10.03-2.0` has MIRA's tables and no ledger; the operator runs `mira update`.

1. Starting that install refuses at the boot gate first: `_check_schema_revision` finds no `schema_migrations` relation, asks whether any public table exists, answers yes, and refuses with S-BOOT-UNPREPARED naming `mira update`.
2. `discover_steps` reads every `V<NNNN>__<slug>` and `R__<slug>` file, then `order_steps` requires the numbered ones to be dense from 0001. A duplicate or a gap is a refusal raised before any connection is opened.
3. `migrate` takes the advisory lock, then `classify_database` finds tables with no ledger and fingerprints the live structure. `Baseline.match` returns `0000` for a known origin. No match means ADOPTION_DRIFT: the run renders the differences against `HEAD_FINGERPRINT.json` and stops unless `--adopt-drifted` was given.
4. `validate` runs before anything is touched. With nothing in the ledger, only lint findings can refuse here.
5. `objects_not_owned_by_admin` is non-zero on this database, so `bootstrap_ownership` runs `deploy/bootstrap_adopt.sql` through the superuser seam — before the backup, because pg_dump as `mira_admin` cannot read an object owned by another role.
6. `take_backup` writes the stamp and finishes with `manifest.json`. That manifest is the completeness signal: `restore`, `list_backups` and retention all read the same predicate, so a stamp whose manifest does not validate is never listed, never retained, and refused at restore with its own message instead of being guessed at.
7. Each step runs in its own transaction with its ledger row, so an interrupted run leaves the file at the last completed step. The `applied_by` value carries a `+adopt-drifted` suffix when the override was used, which is how `status` reports the choice afterwards.
8. After the last step the structure is compared against `HEAD_FINGERPRINT.json`. A mismatch reports S-POSTDRIFT and still exits 0, because the steps have committed and a nonzero exit would make the updater re-run a finished upgrade.
9. A step that raises reports S-STEP-FAILED naming the stamp and exits 1. The rollback is `restore` of that stamp, which drops and recreates the database through the same superuser seam, so `mira_admin` never needs CREATEDB.
