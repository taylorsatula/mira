# auth/ — Passwordless identity, sessions, and account lifecycle

Auth behavior is owned here: modes, magic links, sessions, CSRF, API tokens, WebAuthn, rate limits, security logging, and security headers. Two strict env parsers live here (`MIRA_AUTH_MODE`, `MIRA_CSP`) and both fail closed by design.

## Rules

- `MIRA_AUTH_MODE` (`single` default, `multi`) is parsed strictly in `mode.py` — an invalid value raises rather than coercing, because a typo would silently change the process's security model. `auth_mode()` reads the environment on every call; never capture it at import time.
- Under `single` mode identity is fixed to the auto-provisioned local account (`user@localhost`, constants `LOCAL_SESSION_*` in `service.py`), created lazily by `GET /v0/auth/local/session` on first visit. `/signup`, `/magic-link`, `/verify`, and `/local/session` itself all 404 outside their intended mode: a stray second row would split data across identities. Do not re-open any of them under `single`.
- All Vault-backed auth configuration resolves lazily on first attribute access through `AuthConfig` (`config.py`); importing it performs no I/O. Non-Vault constants stay plain module values so `auth.session`/`auth.rate_limiter` can import the module in installs with no email transport. Failed Vault lookups are not cached — a transiently broken Vault is retried rather than pinning failure into the process.
- Raw auth tokens (session tokens, magic-link tokens, API tokens) are returned only at issuance. PostgreSQL and Valkey store SHA-256 hashes (`_hash_token`, `_token_digest`); a token can never be read back.
- `get_current_user()` (`api.py`) is the single FastAPI auth dependency and the place that calls `set_current_user_id()` / `set_current_user_data()`, establishing the context PostgreSQL RLS enforces downstream. Its credential ladder is a hard contract (see `### Credential ladder` below); `cns/api/AGENTS.md` cites this map for it.
- Session cookies are `SameSite=Lax` (`get_cookie_settings`) so cross-site magic-link clicks carry the session; browser writes rely on explicit CSRF tokens instead. `Secure` follows the mode: off under `single` (plain localhost HTTP where browsers reject Secure cookies), on under `multi`.
- Session discipline in `database.py` is the security contract: pre-authentication reads (user lookup, magic-link CRUD, API-token hash validation) run on the BYPASSRLS admin session because no user context exists yet; post-authentication per-user token operations run on `get_session(user_id)` so RLS on `api_tokens` enforces ownership. With RLS on `users`/`magic_links`/`api_tokens`, using the wrong side does not error — the fail-closed `NULLIF` predicate yields silent zero-row results.
- `AccountProvisioner` (`provisioning.py`) is the minimal excision seam between account lifecycle inside `auth` and sidecar state outside it. `NullProvisioner` is the default and only implementation; its `delete` reaches `local_teardown` (revoke sessions → clear `UserDataManager` cache → rmtree `data/users/{id}` → DELETE on the admin session — ordering matters, each step depends on the previous). Do not extend the seam with hooks, priorities, ordering, events, or registration.
- Email delivery goes through the `MailSender` seam (`email_service.py`); the only shipped backend is stdlib SMTP (`SmtpMailSender`). SMTP settings resolve environment-first then Vault, at send time only — nothing in `auth` may import an HTTP email gateway client, and `single`/`dev` installs boot and serve with no mailer at all (`get_mail_sender()` returns None; the send raises `email_not_configured`).
- The CSP header is gated behind `MIRA_CSP` (`security_middleware.py`) and off by default: `script-src 'self'` is not satisfiable by the retained `web/` UI (inline script blocks and `onclick=` handlers remain), and hard-enabling would serve a blank page. The other five security headers are always sent. Parsing is strict like `mode.py` — any value other than `off`/`strict` (including empty string) raises when the middleware stack is built, before the first response.

### Credential ladder

`get_current_user` resolves exactly one credential per request:

1. `Authorization: Bearer` header, when present (`HTTPBearer(auto_error=False)`) — never extends session TTL (`extend_activity=False`).
2. Otherwise the `session` cookie — extends TTL on validation.

A header token is validated first against Valkey sessions (`SessionData`), then against hashed API tokens in PostgreSQL (`APITokenContext`). A cookie token is session-only. Cookie-authenticated unsafe methods (`POST`/`PUT`/`PATCH`/`DELETE`, except paths ending `/auth/csrf`) must carry an `x-csrf-token` header validated against the session's Valkey CSRF record; missing/invalid is 403, everything else auth-failing is 401. On success the dependency sets the user context; `websocket_chat.py` reuses the same ladder for its first auth frame but implements it itself, since WebSockets cannot use FastAPI HTTP dependencies.

`get_current_session_user` sits on top: API-token contexts are rejected (403 `SESSION_REQUIRED`) for endpoints that manage sessions, tokens, and WebAuthn credentials. `get_current_user_for_pages` is the HTML-page variant: under `single` an unauthenticated page request 302-redirects to `/v0/auth/local/session` (which bootstraps the account), under `multi` it fails with the standard 401 envelope — mira-OSS ships no `/login/` page.

## Files

- `__init__.py` — Re-exports `get_current_user` only; no registration happens here (`main.py` imports `auth.api` directly and mounts the router).
- `api.py` — `/v0/auth` routes plus the `get_current_user` dependency (see `### Credential ladder`) and the page-redirect variant `get_current_user_for_pages`; `GET /local/session` bootstraps the single-mode local account. Response envelopes come from `cns/api/base.py` helpers wrapped by `create_auth_success_response`/`create_auth_error_response`. Consumers: every protected `cns/api/` route (`Depends(get_current_user)`), page dependencies in `main.py`.
- `service.py` — Magic-link request/verify, signup, session orchestration, API-token issue/validate/revoke, logout variants, cookie settings, and the single-mode bootstrap (`create_local_session`). Anti-enumeration is behavioral: a magic-link request for an unknown email sleeps a Gaussian-delayed fake send and returns success. `get_auth_service()` is the process-wide lazy singleton — deliberately no module-level instance, so importing `auth.service` never constructs it. Consumers: `api.py`, `main.py` (via `get_auth_service`).
- `database.py` — `AuthDatabase`: user records, magic-link CRUD, API-token storage, and user creation (`create_user` inserts the user plus four seed memories in one transaction; `initialize_mira_account` creates the Continuum and welcome content). Session discipline per Rules. `create_user` performs no input-policy checks — public signup validation lives in `service.py`, and the local bootstrap depends on being able to provision the non-routable `user@localhost`.
- `session.py` — `SessionManager`: hashed Valkey sessions (`session:<sha256>`) with idle timeout and absolute max lifetime, demo-subject expiry enforcement, CSRF tokens (`csrf:<sha256>`), and SCAN-based revoke-all / revoke-all-except-current traversal.
- `mode.py` — `auth_mode()`: the strict `MIRA_AUTH_MODE` parser described in Rules.
- `provisioning.py` — `AccountProvisioner` Protocol, `NullProvisioner`, and `local_teardown` (see Rules).
- `seed_lora.py` — `seed_lora_postgres(user_id)`: initializes `feedback_synthesis_tracking` via `FeedbackTracker` during account creation so the user-model pipeline has its state row.
- `account_gc.py` — Daily 03:00 UTC job deleting accounts that never logged in within 24h and expired demo subjects; the demo branch stays inert while nothing can mint a `subject_kind='demo'` row. The cross-user scan runs on the admin session (BYPASSRLS); deletion goes through the provisioner's `delete`. Registered by `service.py:register_cleanup_jobs`.
- `config.py` — Lazy Vault-backed `AuthConfig` plus hot-path constants (`MAGIC_LINK_EXPIRY`, session timeouts, rate-limit defaults). Import-time I/O-free by design (see Rules).
- `email_service.py` — `MailSender` Protocol + `SmtpMailSender` (stdlib `smtplib`). SMTP settings resolve env-first then Vault `mira/services` fields (`MIRA_SMTP_*`/`smtp_*`); `MIRA_SMTP_STARTTLS` is strictly parsed. Used by magic-link delivery in `multi` mode.
- `rate_limiter.py` — `RateLimiter`: dual Valkey counters, email-keyed (5 per 5 min) and IP-keyed (10 per 5 min); raises on Valkey unavailability. Shared by signup, magic-link, and WebAuthn login (which rate-limits discoverable ceremonies per-IP under a `discoverable:{ip}` key).
- `webauthn_service.py` — Platform passkey (Touch ID / Face ID) challenges and credential management. Registration requests resident (discoverable) credentials; login supports an email-keyed ceremony and a discoverable ceremony (no email typed; user resolved from the credential's userHandle via an opaque one-time `challenge_id` stored in Valkey). Credentials live in `users.webauthn_credentials` JSONB keyed by their base64url credential ID — the exact encoding browsers return in ceremonies. Challenges are single-use and deleted on retrieval.
- `security_logger.py` — `security_logger` singleton: structured auth audit events with sanitized emails (partial-mask, never raw) and truncated user agents.
- `security_middleware.py` — `SecurityHeadersMiddleware`: five always-on headers, HTTPS-only HSTS, and the `MIRA_CSP`-gated CSP (see Rules). Consumed by `main.py` at middleware-stack construction.
- `types.py` — Shared Pydantic contracts: `UserRecord`, `UserProfile`, `SessionData`, `MagicLinkRecord`, `CookieSettings`, `APITokenContext`, `SubjectKind` (`member`/`demo`).
- `exceptions.py` — `AuthError(code, message, details)`; `api.py` maps codes to HTTP statuses (`rate_limit_exceeded`→429, `expired_token`→410, CSRF→403, else 401/400).

## Wiring

`main.py` mounts this router under `/v0/auth` and adds `SecurityHeadersMiddleware` when building the stack. Account creation flows through `_initialize_account` (`service.py`): `initialize_mira_account` (continuum + welcome content) → `seed_lora_postgres` → provisioner — every path (signup, local-session bootstrap) takes it, so skipping `seed_lora_postgres` there breaks the user-model pipeline for that account. Signup failure after user creation triggers provisioner cleanup; `account_gc` provides teardown symmetry for abandoned signups. `cns/api/` consumes `get_current_user` per its own map; the client side of these endpoints is covered in `web/assets/javascript/AGENTS.md` (which cites this file's `api.py` as `Calls:` target). `AuthService.register_cleanup_jobs` registers the hourly magic-link cleanup and the daily account GC job.
