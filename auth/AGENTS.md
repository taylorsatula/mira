# auth/ — passwordless identity, sessions, CSRF, API tokens, WebAuthn, and the account lifecycle

Elsewhere: the WS-side credential ladder and per-router dependency wiring — `cns/api/AGENTS.md` · browser client halves (page-gate bootstrap story, CSRF rotate/retry) — `ui/browser/AGENTS.md`, `ui/browser/assets/javascript/AGENTS.md` · TUI token bootstrap — `ui/tui/AGENTS.md` · table DDL + RLS policies — `deploy/mira_service_schema.sql` (`deploy/AGENTS.md`) · Valkey client method contracts — `clients/AGENTS.md` · scheduler registry, job-ID boot gate — `utils/AGENTS.md` · system config (timezone, local first name, token cap) — `config/AGENTS.md` · per-route envelopes and signatures — the files · history — `git log`.

## Rules

- Identity surfaces are mode-gated at the handler with a bare 404: `/signup`, `/magic-link`, `/verify` under `single`; `/local/session` under `multi` (`auth_mode()` check per handler). 404, not 403 — an install without the surface must not advertise it to anonymous probes. Ungated, one unauthenticated GET creates a stray account row on a `multi` install; one signup under `single` splits identity data across rows.
- Credential ladder (`api.py:get_current_user`): Bearer header first, else the `session` cookie; session validation first; the API-token rung (`validate_api_token`) runs only when `token_source == "header"`; `extend_activity` only for cookie tokens. Reversing either makes API tokens rolling sessions or accepts an auto-attached cookie string as a deliberately-presented bearer credential. `get_current_session_user` rejects `APITokenContext` (403 `SESSION_REQUIRED`) for browser-session-only surfaces — API-token holders must not mint tokens or manage passkeys. WS ladder counterpart: `cns/api/AGENTS.md` (`websocket_chat.py:authenticate`); MCP sub-app mirror: `cns/api/mcp.py:_AuthGate` (header rung only).
- Every cookie-authenticated unsafe method (the `UNSAFE_HTTP_METHODS` set, minus paths ending `/auth/csrf`) requires `x-csrf-token`, compared with `hmac.compare_digest` against the `csrf:` store (`_requires_cookie_csrf`/`_validate_cookie_csrf`). One live token per session — `POST /v1/auth/csrf` rotates it. Twin: the browser client single-flights token fetches and retries exactly once on 403 `CSRF_INVALID`/`CSRF_REQUIRED`; two concurrent rotations 403 every other in-flight write (client half owned by `ui/browser/assets/javascript/AGENTS.md`). A new cookie-write route skipping the check is cross-site forgeable — SameSite=lax is not a CSRF defense: legacy browsers ignore it, fresh cookies ride Chrome's Lax+POST grace window, and a same-site (registrable-domain) attacker forges the request regardless.
- Async auth handlers cross every sync Valkey/Postgres call through `run_in_threadpool` — the shared event loop also schedules WS frame sends, and sync IO on it freezes the whole single-worker server under one infra stall. Plain-`def` handlers are the sanctioned alternative (FastAPI's threadpool). `get_current_user` must stay async: converted to `def`, its ContextVar writes (`set_current_user_id`/`set_current_user_data`) run in a worker thread and do not propagate back — user context silently drops on every request. The trap is live in `get_current_user_for_pages` (already `def`; its writes are discarded), harmless only while the gated page routes (`main.py`) return `FileResponse` and touch no user-scoped data — a gated page doing server-side RLS work reads zero rows, no error.
- One canonical email identity: `normalize_email()` (lowercase) at every entry seam — signup, magic-link request — so the rate-limit key, the stored row, and the WHERE lookup share one form. A caller passing a raw mixed-case address to `AuthDatabase.get_user_by_email` finds no row; a case-variant address is one mailbox, never two accounts.
- RLS session split (`database.py`): pre-authentication reads (user lookup, magic-link CRUD, token-hash validation) run on the admin BYPASSRLS session; post-authentication token operations run on `get_session(user_id)` so `api_tokens` RLS enforces ownership. Wrong side fails closed — zero rows, no error (the NULLIF predicate, `deploy/mira_service_schema.sql`): a token write moved to the admin session loses ownership enforcement; a pre-auth read on a user session reads as "no such user".
- `webauthn_credentials` mutations are single-statement guarded UPDATEs (`add_webauthn_credential`, `remove_webauthn_credential`, `update_credential_sign_count`) — never read-modify-write the JSONB column: concurrent ceremonies lose writes. Zero rows → False → `AuthError`; a vanished user or duplicate credential ID is never reported success.
- WebAuthn error taxonomy: `WebAuthnException` means client-supplied input failed validation → 4xx `invalid_credential`, specifics server-side only; origin/RP-ID mismatch (`_is_server_config_validation_error`, matched on library message text) means server misconfiguration → `internal_error` 5xx. A new ceremony handler reusing only the first half reports a broken `APP_URL` as every user's client error.
- Demo expiry is enforced at every authentication surface, not one: `get_api_token_by_hash` JOINs users requiring member-or-unexpired-demo; `validate_session` deletes expired demo sessions; magic-link request refuses demo accounts (same envelope as unknown email); GC collects expired demos. A new surface that forgets the check lets an expired demo keep access.
- GC eligibility twin: `local_teardown`'s DELETE guard re-verifies only the mutable legs of `cleanup_unactivated_accounts`' scan predicate (member + `last_login_at IS NULL`; demo + `demo_expires_at <= NOW()`); the `created_at < 24h` term stays scan-side — `created_at` is fixed at the snapshot, and the same guarded DELETE serves `create_user`'s provisioning-failure teardown (`service.py` → `provisioner.delete`) for rows created seconds earlier. Carrying `created_at` in the guard turns those teardowns into zero-row deletes that report success (the became-ineligible branch returns True), leaving the failed-signup row to linger. The guard runs before every destructive step, so an account that activates between GC snapshot and teardown survives intact; dropping a mutable leg deletes ineligible accounts or never deletes.
- Cookie attributes flow only through `get_cookie_settings()`: samesite=lax (magic-link top-level GET navigations carry the session; writes are CSRF-guarded, not SameSite-guarded), secure follows mode (`single` serves plain HTTP on localhost, where browsers reject Secure cookies), httponly, max_age = `SESSION_MAX_LIFETIME`. Every set and delete site uses it — logout's `delete_cookie` mirrors all attributes; under single-mode plain HTTP a deletion carrying `Secure` is dropped (RFC 6265) and the revoked cookie survives.
- `create_local_session` pins the browser session to the install's ORIGINAL member account — the oldest `subject_kind='member'` row (`database.get_original_member_account`), whatever its email: the installer-created operator account on current installs, the seeded `user@localhost` row on upgraded pre-multi-user ones. The fixture identity (`LOCAL_SESSION_EMAIL`) is provisioned only when no member account exists at all. Consequence: keying the bootstrap on the fixture email instead re-splits identity at the first browser visit on any install whose operator account carries a real email — the operator lands in an empty fixture account while their history and memory stay on the real one (witnessed live, 2026-10-16).
- `MIRA_AUTH_MODE` (`mode.py`) and `MIRA_CSP` (`security_middleware.py`) parse strictly: exact case-sensitive literals, unset → default, set-but-malformed (typo, empty string) raises — mode at each call, CSP at middleware construction, before the first response. Truthy coercion would let `MIRA_AUTH_MODE=Sinlge` quietly select the single-user security model or `MIRA_CSP=strcit` run with no policy.
- Runtime mail config reads only `get_service_config` from Vault `secret/mira/services` (`email_service._vault_config`); the `MIRA_SMTP_*` environment variables are deploy-script inputs persisted into Vault at provision time (`deploy/AGENTS.md`). Unset host = no mailer (None, both modes boot); present-but-invalid raises — degrading to "no mailer configured" would turn operator error into magic links that silently never send.
- Pre-auth surfaces reveal nothing: `request_magic_link` returns the same generic success for unknown email and demo refusal as for a real send, padding with a randomized delay (`gauss(0.5, 0.07)` clamped 0.35–0.65 s) that simulates send time; no-user is logged, never returned. A divergent envelope or timing in a new pre-auth surface is a user-enumeration oracle.
- `AuthError.code` strings are the HTTP interface, mapped per handler with no shared default: the ladder (`get_current_user`) raises 401 directly for every non-CSRF code (`CSRF_*`→403) — no envelope; `logout` maps `UNAUTHORIZED`→401, `SESSION_NOT_FOUND`→404, else the 400 envelope of `create_auth_error_response`; `logout_other_devices` maps `SESSION_REQUIRED`→403 else 401; `logout_all_devices`/`webauthn_list_credentials` carry no AuthError branch, so any code they raise lands in the 500 fallback; the remaining handlers map locally over the envelope (`expired_token`→410, `rate_limit_exceeded`→429, `internal_error`→500 on the webauthn complete paths). A new code without its per-handler mapping ships as that handler's fallback — 401 on the ladder, 500 on the branch-less pair; check every handler that can raise it.

## Files

- `__init__.py` — re-exports `auth.api.get_current_user` as the package surface; no in-tree consumer imports the name from the package (`rg 'from auth import'` → only `main.py` importing the `api` submodule). Gotcha: any `auth.*` import runs this file first, so `from auth.mode import auth_mode` transitively loads the whole api→service→database stack.
- `account_gc.py` — GC of unactivated members and expired demos; admin-session scan, deletion through the provisioner, `False` deletes return as `cleanup_pending_emails` for retry. Entry: `cleanup_unactivated_accounts`, `get_account_gc_service`, `register_account_gc_job` (job id `account_garbage_collection`, daily 03:00 UTC — a POST boot-gate contract name, counterpart `utils/AGENTS.md`). Gotcha: the demo branch is inert (no code mints demo rows) — kept so a hand-created or future demo row is still collected; do not remove it for lack of a caller.
- `api.py` — the router mounted at `/v1/auth` and the HTTP auth dependencies: `get_current_user` (ladder), `get_current_session_user` (session-only), `get_current_user_for_pages` (page gate: 302 to `/v1/auth/local/session` under `single`, 401 envelope under `multi`). Entry: the dependency trio, `_requires_cookie_csrf`/`_validate_cookie_csrf`, `create_auth_success_response`/`create_auth_error_response`, `_page_auth_failure`. Gotcha: the census comment above `get_current_user` predates the threadpool crossing of its validation calls — the comment's live content is the def-conversion trap (Rules); the calls themselves now all cross.
- `config.py` — lazy auth config: Vault-backed `APP_URL` as a `@property` resolving to canonical origin form (scheme + host[:port], no path, no trailing slash — the basis for WebAuthn rp_id/origin and the magic-link URL) plus import-safe constants (`MAGIC_LINK_EXPIRY` 600, `SESSION_IDLE_TIMEOUT` 14d, `SESSION_MAX_LIFETIME` 45d, rate 5/300). Gotcha: constructing reads nothing — a new Vault-backed field must stay a lazy `@property`, or every auth import (single-mode installs included) requires a reachable, seeded Vault.
- `database.py` — the auth repository: user rows (`_USER_RECORD_COLUMNS`, id cast to text), magic links (`consume_magic_link` = one guarded UPDATE), API-token CRUD, the atomic WebAuthn JSONB mutations (Rules), and account bootstrap: `initialize_mira_account` + `_prepopulate_welcome_content` writing the continuum and welcome content through the CNS pool. Entry: `create_user`, `get_user_by_email`, `consume_magic_link`, `get_api_token_by_hash`, `add_webauthn_credential`. Gotcha: `_prepopulate_welcome_content` sets user context (message saves increment the activity day) and commits one UnitOfWork per message with a 0.1 s sleep between — batching trips duplicate-key errors; pool/UoW mechanics owned by `cns/infrastructure/AGENTS.md`.
- `email_service.py` — the `MailSender` seam and the stdlib SMTP backend: `SmtpSettings.from_vault` (unset host → no mailer; bad port/missing `smtp_from` → raise), `_parse_starttls` strict, `SmtpMailSender.send` raising a generic `RuntimeError` (relay errors can carry the credential exchange; recipient logged as a sha256[:16] digest). Entry: `get_mail_sender` (cheap per send — Vault reads cache). Gotcha: an HTTP backend is added by structural implementation + injection at the composition root (`AuthService(mailer=...)`) — no vendor implementation ships in-tree; nothing here changes.
- `exceptions.py` — `AuthError(code, message, details)`; the `code` string is the cross-file interface api.py maps to HTTP status (Rules). No gotchas.
- `mode.py` — `auth_mode()`: strict `MIRA_AUTH_MODE` parse (`single`|`multi`, default `single`), re-read from the environment on every call — no import-time capture, so a process may set it before `create_app()`. Entry: `auth_mode`, `AUTH_MODES`.
- `provisioning.py` — the account-lifecycle seam: `AccountProvisioner` Protocol (provision/ensure/delete; implementations idempotent because creation retries), `NullProvisioner` (OSS default: provisioning is nothing), `local_teardown` (guarded DELETE → revoke sessions → `clear_manager_cache` → rmtree). Entry: `local_teardown`, `DATA_USERS_ROOT`. Gotcha: `DATA_USERS_ROOT` is path arithmetic twin-anchored to `utils/userdata_manager.py`'s `base_dir` — one moving without the other deletes the wrong tree or nothing.
- `rate_limiter.py` — Valkey fixed-window dual limiter: email 5 per 300 s + IP 10 per 300 s, keys `rate_limit:email:`/`rate_limit:ip:`. Entry: `is_allowed`. Gotcha: `reset()` has no caller repo-wide — dead; do not build on it.
- `security_logger.py` — `SecurityLogger.log_event`: structured security events, email sanitized through `_sanitize_email`, user_agent truncated at 100, None fields dropped; success → info, failure → warning. The `auth.*` event names are the review surface: `rg 'log_event\('`. No gotchas.
- `security_middleware.py` — `SecurityHeadersMiddleware`: five always-on headers (nosniff, frame DENY, XSS-Protection, strict-origin-when-cross-origin referrer, camera/microphone denied + geolocation self) plus HSTS on HTTPS; CSP gated by `MIRA_CSP`, parsed once at construction. Entry: `csp_mode`, `STRICT_CONTENT_SECURITY_POLICY`. Gotcha: strict's `script-src 'self'` rejects the in-tree browser client's inline scripts — the why-off story and the preconditions for flipping the default are owned by `ui/browser/AGENTS.md`.
- `seed_lora.py` — `seed_lora_postgres`: creates the `feedback_synthesis_tracking` row via `cns.infrastructure.feedback_tracker.FeedbackTracker.initialize_user`; sole caller `service.py:_initialize_account`, so every provisioning path (signup, local bootstrap) seeds it. Gotcha: the name says LoRA, the code seeds feedback tracking — `rg 'lora'` also hits the browser settings' `lora` tab, a different surface; do not rename piecemeal.
- `service.py` — `AuthService`: magic-link lifecycle, API tokens, session/CSRF facade, local bootstrap, cleanup-job registration. Entry: `create_user`, `request_magic_link`, `verify_magic_link`, `create_local_session`, `create_api_token`, `get_cookie_settings`, `register_cleanup_jobs`, `get_auth_service`, `normalize_email`, `LOCAL_SESSION_EMAIL`. Gotcha: `get_auth_service()` is the lazy singleton — no module-level instance; construction must stay side-effect-free or every importer (the scheduler registry among them) gains an import-time construction requirement.
- `session.py` — Valkey session store: raw tokens never stored — keys are sha256 digests (`session:<digest>`, `csrf:<digest>`); the idle timeout IS the Valkey TTL; `validate_session` checks demo expiry and `max_expiry`, deleting expired pairs; revoke single / all-user (SCAN over `session:*`) / except-current; CSRF mint + `hmac.compare_digest` validation. Entry: `create_session`, `validate_session`, `revoke_user_sessions`, `revoke_user_sessions_except`.
- `types.py` — the pydantic records: `UserRecord` (full DB row), `UserProfile` (client-facing), `SessionData` (Valkey session payload), `MagicLinkRecord`, `CookieSettings`, `APITokenContext`, `SubjectKind` (`member`|`demo`). `SessionData` vs `APITokenContext` is the type-level ladder distinction `cns/api` and `utils/perf.py` import. Gotcha: `_USER_RECORD_COLUMNS` (database.py) and `UserRecord` change together — a SELECT column the model lacks is silently dropped (pydantic ignores extras); a model field the SELECT lacks raises at row construction.
- `webauthn_service.py` — passkey ceremonies over the `webauthn` package: registration (session-user keyed), email-keyed login, discoverable login (the credential's userHandle identifies the user; the client echoes back the `challenge_id`). Challenges live in Valkey TTL 300 s, consumed one-shot via `getdel_json` — a replay is `invalid_challenge`. rp_id/origin from `config.APP_URL` (localhost special-cased). Entry: `generate_registration_options`, `verify_registration`, `generate_authentication_options`, `generate_discoverable_authentication_options`, `verify_discoverable_authentication`, `_verify_credential_response`. Gotcha: login begin/complete look users up with the raw request email — no `normalize_email` — so a case-variant local part (signup stores lowercased) misses the row and the ceremony dies as `WEBAUTHN_UNAVAILABLE`/`user_not_found`.

## Wiring

- Mount and gate: `main.py` mounts `router` at `/v1/auth`, registers `SecurityHeadersMiddleware`, and gates browser pages on `get_current_user_for_pages` (wiring owned by root `AGENTS.md`; the handlers and the middleware live here).
- Response envelope: `api.py` imports `SuccessResponse`/`ErrorResponse`/`APIError`/`create_success_response`/`create_error_response`/`generate_request_id` from `cns.api.base` — an envelope-contract change reaches every handler here (counterpart `cns/api/AGENTS.md`).
- Dependency consumers: `rg 'from auth.api import get_current_user'` → the `cns/api` routers (chat, data, actions, files, location, tool_config, trigger_rules, update, heartbeat_api) plus `utils/perf.py` perf routes; the typed contexts `SessionData`/`APITokenContext` come from `auth.types` — counterparts `cns/api/AGENTS.md`, `utils/AGENTS.md`.
- Jobs and boot gate: `utils/scheduled_tasks.py:SCHEDULED_TASK_MODULES` registers `auth.service:get_auth_service` → `register_cleanup_jobs` — `auth_cleanup` hourly at :15, `account_garbage_collection` daily 03:00 UTC; both job IDs are POST boot-gate contract names, and POST additionally requires a configured email transport under `multi` only (`utils/power_on_self_test.py` → `get_mail_sender`). Counterpart: `utils/AGENTS.md`.
- Valkey keyspace: this directory writes `session:`, `csrf:`, `rate_limit:`, `webauthn_challenge:`; main.py's flush preserve-list keeps the first three, so session/CSRF/rate state survives a Valkey flush (flush list owned by root `AGENTS.md`); client method contracts owned by `clients/AGENTS.md`.
- Account bootstrap crosses out: `initialize_mira_account` creates the continuum and welcome content through `cns.infrastructure.continuum_repository`/`continuum_pool`; `seed_lora.py` seeds `cns.infrastructure.feedback_tracker`; `local_teardown` clears `utils.userdata_manager.clear_manager_cache` and removes the same `data/users/{id}` root `UserDataManager.base_dir` builds. Counterparts: `cns/infrastructure/AGENTS.md`, `utils/AGENTS.md`.
- Schema and RLS: `users`, `magic_links`, `api_tokens` DDL and the NULLIF fail-closed policies live in `deploy/mira_service_schema.sql` (counterpart `deploy/AGENTS.md`); the admin/user session split (Rules) is the code-side answer to those policies.
- Config: token cap is `config.auth.max_api_tokens_per_user` (`config/config.py:AuthConfig` — a different class from `auth/config.py:AuthConfig`); the local account's timezone and first name come from system config (`MIRA_LOCAL_SESSION_FIRST_NAME`, deploy-collected); `app_url` and the SMTP settings are seeded into Vault by the deploy scripts. Counterparts: `config/AGENTS.md`, `deploy/AGENTS.md`.
- Client twins, same-commit on drift: CSRF rotate/retry ↔ `ui/browser/assets/javascript/AGENTS.md`; page-gate bootstrap ↔ `ui/browser/AGENTS.md`; TUI token bootstrap (`GET /v1/auth/local/session` → `POST /v1/auth/csrf` → `POST /v1/auth/api-tokens`) ↔ `ui/tui/AGENTS.md`.
- Counterparts: signup bootstrap writes into the continuum message cache via a private attribute ↔ `cns/core/AGENTS.md`; the scripted auth chain in the VM tooling mirrors these routes ↔ `deploy/vm/AGENTS.md`.

## Account creation, signup to first message

1. Multi mode: `POST /v1/auth/signup` (mode-gated) → `AuthService.create_user` — `normalize_email`, format/profile-name/ZoneInfo validation, dual rate limit, then `AuthDatabase.create_user` on the admin session in one transaction: the users row plus four seed memories (name, timezone, focus, email — importance 0.9/0.8/0.8/0.7, stored without embeddings, so they surface in keyword search only). `UniqueViolation` → `user_already_exists`.
2. `_initialize_account`: `initialize_mira_account` gets-or-creates the Continuum and prepopulates five welcome messages through the CNS pool — user context is set for the writes because message saves increment the activity day; one UnitOfWork per message with a 0.1 s sleep between (sequential timestamps; batched inserts hit duplicate-key errors); the boundary segment metadata rides message two. Then `seed_lora_postgres` seeds feedback tracking and `provisioner.provision` runs (nothing in the OSS default).
3. Failure ordering: any raise in `_initialize_account` → `provisioner.delete` → `local_teardown`, whose eligibility-guarded DELETE runs first — an account that activated between the GC snapshot and teardown survives (zero-row delete reports gone-from-candidate-set); a failed teardown propagates (the row stands, pending GC), never swallowed, and no destructive step ran.
4. The row is committed; `request_magic_link` then rate-limits on the same key. Unknown email or demo account → the generic success envelope plus the randomized delay (enumeration-safe; logged server-side). A real user → `_resolve_mailer` (no mailer configured → the same `service_error` envelope a failed send returns — whether a deployment has a mailer is server configuration, not the caller's business) → send BEFORE store, so a failed send stores no link → `create_magic_link` stores only the sha256 hash; the raw token exists in the sent email and nowhere else.
5. Delivery failure is not creation failure: signup maps `magic_link_delivery_failed` to a 201 success envelope telling the user their account exists and to request a link — the committed row is never torn down for a mail failure; only provisioning failures tear down.
6. Single mode: `GET /v1/auth/local/session` → `create_local_session` — adopt the `user@localhost` row verbatim when it exists (an upgraded install keeps its data), else provision it through the same `create_user` + `_initialize_account` chain; an existing account additionally runs `provisioner.ensure`. Then `update_user_login`, session mint, 303 to `/chat` with the cookie. No rate limit — the surface exists only under `single`.

Ordering invariants: the guarded DELETE precedes every destructive teardown step; send precedes store; `_initialize_account` failure tears the account down while delivery failure keeps it; the local row is adopted, never re-provisioned around.
