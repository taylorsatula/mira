# auth/ — Passwordless identity, sessions, and account lifecycle

Auth behavior is owned here: modes, magic links, sessions, CSRF, API tokens, WebAuthn, rate limits, security logging, and security headers. Two strict env parsers live here (`MIRA_AUTH_MODE`, `MIRA_CSP`) and both fail closed by design.

## Rules

- `MIRA_AUTH_MODE` (`single` default, `multi`) is parsed strictly in `mode.py` — an invalid value raises rather than coercing, because a typo would silently change the process's security model. `auth_mode()` reads the environment on every call; never capture it at import time.
- Under `single` mode identity is fixed to the auto-provisioned local account (`user@localhost`; `LOCAL_SESSION_*` constants in `service.py`, except the first name, which comes from `SystemConfig.local_session_first_name` — deploy-collected via `MIRA_LOCAL_SESSION_FIRST_NAME`, default `"Friend"`), created lazily by `GET /v0/auth/local/session` on first visit. `/signup`, `/magic-link`, `/verify`, and `/local/session` itself all 404 outside their intended mode: a stray second row would split data across identities. Do not re-open any of them under `single`.
- All Vault-backed auth configuration resolves lazily on first attribute access through `AuthConfig` (`config.py`); importing it performs no I/O. Non-Vault constants stay plain module values so `auth.session`/`auth.rate_limiter` can import the module in installs with no email transport. Failed Vault lookups are not cached — a transiently broken Vault is retried rather than pinning failure into the process.
- Raw auth tokens (session tokens, magic-link tokens, API tokens) are returned only at issuance. PostgreSQL and Valkey store SHA-256 hashes (`_hash_token`, `_token_digest`); a token can never be read back.
- `get_current_user()` (`api.py`) is the single FastAPI auth dependency and the place that calls `set_current_user_id()` / `set_current_user_data()`, establishing the context PostgreSQL RLS enforces downstream. Its credential ladder is a hard contract (see `### Credential ladder` below); `cns/api/AGENTS.md` cites this map for it.
- Session cookies are `SameSite=Lax` (`get_cookie_settings`) so cross-site magic-link clicks carry the session; browser writes rely on explicit CSRF tokens instead. `Secure` follows the mode: off under `single` (plain localhost HTTP where browsers reject Secure cookies), on under `multi`. The logout deletion (`api.py`) rebuilds its attributes from the same `get_cookie_settings` source, so a deletion can never drift from the set path — a mismatched `Secure` deletion is dropped by browsers and the stale revoked cookie survives logout.
- Session discipline in `database.py` is the security contract: pre-authentication reads (user lookup, magic-link CRUD, API-token hash validation) run on the BYPASSRLS admin session because no user context exists yet; post-authentication per-user token operations run on `get_session(user_id)` so RLS on `api_tokens` enforces ownership. With RLS on `users`/`magic_links`/`api_tokens`, using the wrong side does not error — the fail-closed `NULLIF` predicate yields silent zero-row results.
- `AccountProvisioner` (`provisioning.py`) is the minimal excision seam between account lifecycle inside `auth` and sidecar state outside it. `NullProvisioner` is the default and only implementation; its `delete` reaches `local_teardown`, which runs the eligibility-guarded `DELETE FROM users ... WHERE (unactivated member) OR (expired demo)` **first** on the admin session — eligibility lives in the DELETE itself, never in a preceding re-select — and only after a successful DELETE revokes sessions, clears the `UserDataManager` cache, and rmtrees `data/users/{id}`. A 0-row DELETE with the row still present means the account activated mid-GC and is skipped (returns True); a 0-row DELETE with the row gone raises. Accepted residual: a crash between the DELETE and the rmtree leaks an orphaned `data/users/{id}` dir the GC never revisits — deliberately not swept. Do not extend the seam with hooks, priorities, ordering, events, or registration.
- Email delivery goes through the `MailSender` seam (`email_service.py`); the only shipped backend is stdlib SMTP (`SmtpMailSender`). SMTP settings resolve from Vault only at send time (env vars never consulted at runtime — a missing Vault credential fails with setup guidance; nothing in `auth` may import an HTTP email gateway client, and `single`/`dev` installs boot and serve with no mailer at all (`get_mail_sender()` returns None; `_resolve_mailer` raises `email_not_configured`, which `request_magic_link` flattens to a generic `service_error`).
- The CSP header is gated behind `MIRA_CSP` (`security_middleware.py`) and off by default: `script-src 'self'` has no in-tree client that satisfies it (the `web/` UI that used inline script blocks and `onclick=` handlers has been removed), so it stays off by default. The other five security headers are always sent. Parsing is strict like `mode.py` — any value other than `off`/`strict` (including empty string) raises when the middleware stack is built, before the first response.

### Credential ladder

`get_current_user` resolves exactly one credential per request:

1. `Authorization: Bearer` header, when present (`HTTPBearer(auto_error=False)`) — never extends session TTL (`extend_activity=False`).
2. Otherwise the `session` cookie — extends TTL on validation.

A header token is validated first against Valkey sessions (`SessionData`), then against hashed API tokens in PostgreSQL (`APITokenContext`). A cookie token is session-only. Cookie-authenticated unsafe methods (`POST`/`PUT`/`PATCH`/`DELETE`, except paths ending `/auth/csrf`) must carry an `x-csrf-token` header validated against the session's Valkey CSRF record; missing/invalid is 403, everything else auth-failing is 401. On success the dependency sets the user context; `websocket_chat.py` reuses the same ladder for its first auth frame but implements it itself, since WebSockets cannot use FastAPI HTTP dependencies.

`get_current_session_user` sits on top: API-token contexts are rejected (403 `SESSION_REQUIRED`) for endpoints that manage sessions, tokens, and WebAuthn credentials. `get_current_user_for_pages` is the HTML-page variant: under `single` an unauthenticated page request 302-redirects to `/v0/auth/local/session` (which bootstraps the account), under `multi` it fails with the standard 401 envelope — mira-OSS ships no `/login/` page.

## Files

- `__init__.py` — Re-exports `get_current_user` only; no registration happens here (`main.py` imports `auth.api` directly and mounts the router).
- `api.py` — `/v0/auth` routes plus the `get_current_user` dependency (see `### Credential ladder`) and the page-redirect variant `get_current_user_for_pages`; `GET /local/session` bootstraps the single-mode local account. Response envelopes come from `cns/api/base.py` helpers wrapped by `create_auth_success_response`/`create_auth_error_response`. Every `async def` route/dependency here wraps its synchronous Valkey/Postgres service calls in `run_in_threadpool` — the shared event loop also schedules WebSocket frame sends, and blocking it on auth I/O trips the WS bridge's stall probe (`cns/api/AGENTS.md`); sync `def` routes need no wrap (Starlette threadpool). The `KNOWN, DELIBERATELY UNFIXED` comment above `get_current_user` claims the opposite — sync I/O on the event loop — and is made false by this wrapping; its only live point is the warning that converting the dependency to plain `def` would drop the contextvar mutations it installs. Consumers: every protected `cns/api/` route (`Depends(get_current_user)`), page dependencies in `main.py`.
- `service.py` — Magic-link request/verify, signup, session orchestration, API-token issue/validate/revoke, logout variants, cookie settings, and the single-mode bootstrap (`create_local_session`). Anti-enumeration is behavioral: a magic-link request for an unknown email sleeps a Gaussian-delayed fake send and returns success. `get_auth_service()` is the process-wide lazy singleton — deliberately no module-level instance, so importing `auth.service` never constructs it. Consumers: `api.py` (`Depends(get_auth_service)`), `cns/api/websocket_chat.py` and `cns/api/mcp.py` (ladder / auth gate), and the scheduler registry `utils/scheduled_tasks.py` (`SCHEDULED_TASK_MODULES` resolves `get_auth_service` lazily to call `register_cleanup_jobs`).
- `database.py` — `AuthDatabase`: user records, magic-link CRUD, API-token storage, and user creation (`create_user` inserts the user plus four seed memories in one transaction; `initialize_mira_account` creates the Continuum and welcome content). Session discipline per Rules. `create_user` performs no input-policy checks — public signup validation lives in `service.py` (plus the `SignupRequest.timezone` field validator in `api.py`, which normalizes/rejects via `validate_timezone` — an invalid timezone must never persist, it kills use-day jobs at read time), and the local bootstrap depends on being able to provision the non-routable `user@localhost`.
- `session.py` — `SessionManager`: hashed Valkey sessions (`session:<sha256>`) with idle timeout and absolute max lifetime, demo-subject expiry enforcement, CSRF tokens (`csrf:<sha256>`) — CSRF key TTL renewed with session on activity-extend; deleted on all expiry branches — and SCAN-based revoke-all / revoke-all-except-current traversal.
- `mode.py` — `auth_mode()`: the strict `MIRA_AUTH_MODE` parser described in Rules.
- `provisioning.py` — `AccountProvisioner` Protocol, `NullProvisioner`, and `local_teardown` (see Rules).
- `seed_lora.py` — `seed_lora_postgres(user_id)`: initializes `feedback_synthesis_tracking` via `FeedbackTracker` during account creation so the user-model pipeline has its state row.
- `account_gc.py` — Daily 03:00 UTC job deleting accounts that never logged in within 24h and expired demo subjects; the demo branch stays inert while nothing can mint a `subject_kind='demo'` row. The cross-user scan runs on the admin session (BYPASSRLS); deletion goes through the provisioner's `delete`. Registered by `service.py:register_cleanup_jobs`.
- `config.py` — Lazy Vault-backed `AuthConfig` plus hot-path constants (`MAGIC_LINK_EXPIRY`, session timeouts, rate-limit defaults). Import-time I/O-free by design (see Rules).
- `email_service.py` — `MailSender` Protocol + `SmtpMailSender` (stdlib `smtplib`). SMTP settings resolve from Vault `mira/services` fields only — runtime code never reads `MIRA_SMTP_*` env vars (env vars are a deploy-script input concern); a missing credential fails loudly with setup guidance. Used by magic-link delivery in `multi` mode, and by the pre-server POST gate: `utils/power_on_self_test.py` calls `get_mail_sender()` in `multi` mode and a `None` mailer raises there, parking the boot (`MIRA_AUTH_MODE=multi requires an email transport`).
- `rate_limiter.py` — `RateLimiter`: dual Valkey counters, email-keyed (5 per 5 min) and IP-keyed (10 per 5 min); raises on Valkey unavailability. Shared by signup, magic-link, and WebAuthn login (which rate-limits discoverable ceremonies per-IP under a `discoverable:{ip}` key).
- `webauthn_service.py` — Platform passkey (Touch ID / Face ID) challenges and credential management. Registration requests resident (discoverable) credentials; login supports an email-keyed ceremony and a discoverable ceremony (no email typed; user resolved from the credential's userHandle via an opaque one-time `challenge_id` stored in Valkey). Credential validation is classified by input origin: the webauthn library's `WebAuthnException` (malformed structure, wrong challenge, bad signature) and malformed `userHandle` decode are client input and raise `invalid_credential` with a generic message (specifics logged server-side, never leaked in the envelope); an origin/RP-ID mismatch instead indicts SERVER configuration (`self.origin` is `config.APP_URL`, `rp_id` derived from it) and raises `internal_error` (`_is_server_config_validation_error`); every other exception in the verify paths is a genuine server fault and raises `internal_error`. Credentials live in `users.webauthn_credentials` JSONB keyed by their base64url credential ID — the exact encoding browsers return in ceremonies. Registration/removal use guarded per-credential statements (`AuthDatabase.add_webauthn_credential`/`remove_webauthn_credential`) that check `rows_updated` — a zero-row update is a failure, never a silent success; there is no whole-column read-modify-write. Challenges are single-use, consumed atomically via GETDEL on retrieval (`getdel_json`). `sign_count`/`last_used_at` are updated by a single-statement `jsonb_set` UPDATE (`AuthDatabase.update_credential_sign_count`), not a read-modify-write of the whole column.
- `security_logger.py` — `security_logger` singleton: structured auth audit events with sanitized emails (partial-mask, never raw) and truncated user agents.
- `security_middleware.py` — `SecurityHeadersMiddleware`: five always-on headers, HTTPS-only HSTS, and the `MIRA_CSP`-gated CSP (see Rules). Consumed by `main.py` at middleware-stack construction.
- `types.py` — Shared Pydantic contracts: `UserRecord`, `UserProfile`, `SessionData`, `MagicLinkRecord`, `CookieSettings`, `APITokenContext`, `SubjectKind` (`member`/`demo`).
- `exceptions.py` — `AuthError(code, message, details)`; `api.py` maps codes to HTTP statuses per route (`rate_limit_exceeded`→429, `expired_token`→410, CSRF→403, WebAuthn-complete `internal_error`→500, else 401/400).

## Wiring

- Root-stack mount (our side's requirement): this directory registers nothing by itself — `auth/__init__.py` re-exports only, and the router and middleware take effect solely because the root application builder imports `auth.api` / `auth.security_middleware`, calls `app.include_router(auth_api.router, prefix="/v0/auth", tags=["auth"])`, and adds `SecurityHeadersMiddleware` via `app.add_middleware` while assembling the middleware stack. Page routes take `Depends(auth_api.get_current_user_for_pages)` from the same builder, inside its `if Path("web").exists()` gate — with no `web/` directory (mira-OSS ships none) no page route is registered, so `get_current_user_for_pages` has no consumer at all. Consequence of the requirement not being met: every auth route 404s, no security headers are emitted, and pages accept no authentication — all silently at the route level, not as an import error.
- Contextvar installation on `Depends`-protected routes is ours: `get_current_user` (`api.py`) and `get_current_user_for_pages` install `set_current_user_id()` / `set_current_user_data()` (`utils/user_context.py`) for every route that takes them as a dependency, and downstream RLS-scoped code depends on that context. It is the canonical HTTP installer, not the only one: `cns/api/federation.py` (Lattice delivery endpoint, token-authenticated, sets context from the payload's `to_user_id`) and `cns/api/trigger_rules.py` (re-sets from the dependency's `SessionData`) install context themselves, and non-HTTP paths (WebSocket first frame in `cns/api/websocket_chat.py`, background jobs and event handlers per root doctrine) set it explicitly. The contract is: no code path reaches RLS-scoped storage without installing context — a route that skips the dependency without installing it itself does not error, queries fail closed with silent zero-row results (RLS contract owned by `utils/AGENTS.md` and `clients/postgres_client.py`).
- Verified consumers of `get_current_user`: `cns/api/actions.py`, `cns/api/chat.py`, `cns/api/data.py`, `cns/api/files.py`, `cns/api/location.py`, `cns/api/tool_config.py`, `cns/api/trigger_rules.py`, `cns/api/update.py`, `cns/api/heartbeat_api.py`, each via `Depends(get_current_user)` (plus the DEBUG/INFO-gated `GET /dev/perf/summary` route registered by `utils/perf.py:register_perf_routes`). `cns/api/` cites this map for the ladder per its own map.
- WebSocket counterpart — the ladder is duplicated, not shared: `cns/api/websocket_chat.py:WebSocketChatHandler.authenticate` re-implements the same ladder for the first auth frame (frame token → `session` cookie → API token), calling the same `SessionManager.validate_session` / `AuthService.validate_api_token` and installing the same contextvars, because FastAPI HTTP dependencies do not apply to WebSocket frames. It is not dependency-coupled to `get_current_user`: a ladder change here (new credential rung, new context field) must change `authenticate()` in the same commit or the two surfaces drift silently — one accepts identities the other rejects.
- One ladder, both modes (session-stack identity unification): nothing in this directory branches request *authentication* on `auth_mode()` — both modes validate against the same Valkey session / hashed-API-token stack, and the credential ladder itself is mode-blind. Mode gates route *availability* (four sites in `api.py`: `/local/session` 404s outside `single`, `/signup` / `/magic-link` / `/verify` 404 under `single` — see Rules) plus two behavioral surfaces: the cookie `Secure` flag (`get_cookie_settings`) and the unauthenticated page-failure target (`_page_auth_failure` in `api.py`). Adding a mode-conditional credential rung reintroduces the split the unification removed.
- Account creation flow goes through `_initialize_account` (`service.py`): `initialize_mira_account` (continuum + welcome content) → `seed_lora_postgres` → provisioner — every path (signup, local-session bootstrap) takes it, so skipping `seed_lora_postgres` there breaks the user-model pipeline for that account. Signup failure after user creation triggers provisioner cleanup; `account_gc` provides teardown symmetry for abandoned signups. `AuthService.register_cleanup_jobs` registers the hourly magic-link cleanup and the daily account GC job.
- Outbound cross-directory imports: `api.py` wraps envelopes from `cns/api/base.py` helpers; `database.py` builds continuums via `cns/infrastructure/continuum_repository` / `continuum_pool` during account bootstrap and takes its sessions from `utils/database_session_manager.get_shared_session_manager` (admin vs `get_session(user_id)` split owned by this map's Rules); `session.py` stores sessions in Valkey via `clients/valkey_client.get_valkey`; `config.py` resolves Vault via `clients/vault_client.get_service_config`; `seed_lora.py` seeds through `cns/infrastructure/feedback_tracker.FeedbackTracker`.
- Client side: the browser client that called these `/v0/auth` endpoints (`web/assets/javascript/`) has been removed for rewrite; there is no in-tree caller today, so those `Calls:` edges have no counterpart map.
