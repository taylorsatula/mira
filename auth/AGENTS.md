# auth/ — passwordless identity and its admission surfaces: the credential ladder, sessions, CSRF, API tokens, passkeys, the account lifecycle, pre-auth limits and mail

## Files

- `api.py` — the `/v1/auth` router and the credential dependency the authenticated routers depend on. Open it before changing how a request proves who it is, or what a cookie carries.
- `service.py` — the `AuthService` facade every flow passes through: signup, magic link, local bootstrap, tokens, sessions, logout. Open it before changing an auth flow end to end.
- `database.py` — the auth repository: user rows, magic links, API tokens, passkey mutations, account bootstrap. Open it before changing any auth table read or write.
- `session.py` — Valkey session and CSRF storage. Open it before changing session lifetime, validation, extension, or revocation.
- `types.py` — the records that cross between api, service and database. Open it before changing a field on either side of that boundary.
- `mode.py` — the `single`/`multi` identity decision. Open it before a change that must apply to only one identity model.
- `config.py` — auth constants and the lazily-read Vault `APP_URL`. Open it before reading or adding a value this package configures.
- `provisioning.py` — the account-lifecycle seam and the local teardown. Open it before changing what deleting an account destroys.
- `account_gc.py` — the scheduled sweep that deletes abandoned signups and expired demos. Open it before changing which accounts are deletable.
- `seed_lora.py` — the feedback-tracking row every new account starts with. Open it before changing what a fresh account owes the user-model pipeline.
- `email_service.py` — the mail transport seam and the SMTP backend. Open it before changing how a magic link reaches an inbox, or where its settings come from.
- `rate_limiter.py` — Valkey fixed-window limiting on the pre-auth surfaces; `reset` is dead surface, so do not build on it. Open it when a signup or link request is refused for rate limits.
- `security_logger.py` — structured auth event logging with masked identifiers. Open it before adding a security event.
- `security_middleware.py` — the response security headers and the `MIRA_CSP` gate. Open it before changing a header, or before proposing a CSP posture.
- `webauthn_service.py` — passkey ceremonies and their failure taxonomy. Open it before touching a ceremony or a WebAuthn error class.
- `exceptions.py` — the one exception type, and the `code` string that crosses the HTTP boundary. Open it before adding an error code.
- `__init__.py` — package entry point; re-exports the credential dependency. Nothing lands here — import the submodule you need.

## Wiring

- Request identity: `api.get_current_user` → `service.AuthService.validate_session` → `session.SessionManager.validate_session`, with the API-token rung (`service.validate_api_token` → `database.get_api_token_by_hash`) reached only after a header-presented token failed session validation. Activity extension rides the cookie rung alone. Extending on a header token turns an issued token into a rolling browser session; running the token rung unconditionally accepts an auto-attached cookie string as a deliberately-presented credential.
- Ladder twins: `cns/api/websocket_chat.py:authenticate` and `cns/api/mcp.py:_AuthGate` resolve the same credential set for the WebSocket and MCP transports. A rung added or reordered here is a rung added or reordered in both, but the conditionals are not shared: the socket takes its credential from the auth frame or the cookie and runs the API-token rung on whichever it holds, while REST gates that rung on a header-presented token. Counterpart: `cns/api/AGENTS.md`.
- Dependency consumers: `cns/api` routers that resolve an identity take `get_current_user` from here and type their context from `auth.types` — `rg 'from auth.api import get_current_user'`; the families that run their own gate instead are `cns/api/AGENTS.md`'s Auth gate edge. The same dependency guards `/dev/perf/summary` in `utils/perf.py:register_perf_routes`. Counterpart: `cns/api/AGENTS.md`.
- Mount and page gate: `main.py` mounts `router` at `/v1/auth`, builds `SecurityHeadersMiddleware`, and gates the browser pages on `api.get_current_user_for_pages`. That gate's mode-dependent failure is the browser client's entry contract, so it moves in the same commit as the client. Counterpart: `ui/browser/AGENTS.md`.
- CSP posture: `security_middleware.STRICT_CONTENT_SECURITY_POLICY`'s `script-src 'self'` rejects every inline `<script>` block and inline event handler `ui/browser/` ships, which is why `MIRA_CSP` stays off by default. A page that adds one pushes the strict flip further out, and flipping the default before every inline block moves into `assets/` kills every page controller at load. Counterpart: `ui/browser/AGENTS.md`.
- CSRF token rotation: `session.SessionManager.generate_csrf_token` writes a brand-new token over the session's single `csrf:` record, and `validate_csrf_token` compares a presented token against that one stored value, so any write holding a token minted before the latest mint is refused `CSRF_INVALID` at 403. `api.get_csrf_token` must therefore return the replacement token in the same response that stored it; a mint that returns anything but the value it just wrote leaves the browser's single retry re-presenting the replaced token, and concurrent writes fail with no server-side record of the loop. Expiry answers `INVALID_TOKEN` at 401 from `api.get_current_user`, which is the status `api-client.js:_httpRequest` clears the stored token on, so a gate that reports a dead cookie as 400 or 403 leaves the client retrying with a credential the server rejects. Counterpart: `ui/browser/assets/javascript/AGENTS.md`.
- Vault read: `config.AuthConfig.APP_URL` is this tree's one runtime Vault read — `app_url` in `secret/mira/services`, seeded by the deploy scripts, normalized to origin form once and required (not at import) when a `WebAuthnService` is constructed. A seeded value carrying a path or trailing slash, or a renamed field, diverges passkey origin from magic-link targets and breaks both at once. Counterpart: `deploy/AGENTS.md`.
- Cleanup jobs: `utils.scheduled_tasks.SCHEDULED_TASK_MODULES` initializes `get_auth_service` and calls `AuthService.register_cleanup_jobs`, registering `auth_cleanup` and `account_garbage_collection`. Both IDs are boot-gate contract names, so renaming one fails the POST check; registration must go through the lazy factory, because a module-level service instance would make importing the scheduler registry depend on construction. Counterpart: `utils/AGENTS.md`.
- Valkey keyspace: this directory writes `session:`, `csrf:`, `rate_limit:` and `webauthn_challenge:`; `clients.valkey_client.BOOT_FLUSH_PRESERVE_PREFIXES` preserves the first three across a boot flush and not the fourth, so an in-flight passkey ceremony dies on restart while logins survive. Counterpart: `clients/AGENTS.md`.
- Boot mail gate: `utils.power_on_self_test` reads `auth.mode.auth_mode` and, under `multi`, requires `email_service.get_mail_sender` to return a transport, refusing boot with a remedy naming Vault `smtp_host`/`smtp_from`. Those field names and the mode set are boot-gate contract names. Counterpart: `utils/AGENTS.md`.
- Bootstrap and teardown cross out of `auth`: `database.initialize_mira_account` writes the continuum and its welcome content, `seed_lora.seed_lora_postgres` writes the `feedback_synthesis_tracking` row through `cns.infrastructure.feedback_tracker.FeedbackTracker.initialize_user` — an account without that row is unknown to the user-model pipeline, which reads it before it can synthesize anything — and `provisioning.local_teardown` clears the per-user SQLite manager cache and removes the data root that `utils/userdata_manager.py` builds. Counterparts: `cns/infrastructure/AGENTS.md`, `utils/AGENTS.md`.
- Schema and RLS: the `users`, `magic_links` and `api_tokens` DDL, and the fail-closed policy predicate that turns a wrongly-scoped query into zero rows instead of an error, live in `deploy/mira_service_schema.sql`. Counterpart: `deploy/AGENTS.md`.
- User data root: `provisioning.DATA_USERS_ROOT` is the one definition of the `<repo>/data/users` layout, and `tests/fixtures/probe_user.py` and `tests/fixtures/residue.py` carry a literal copy of it. A move of the constant lands in the same commit as that copy, otherwise the fixtures teardown removes nothing while their witness checks a path that never exists, and the probe passes with its debris still on disk. Counterpart: `tests/fixtures/AGENTS.md`.
- Token minting: the TUI bootstrap and the deploy VM tooling's scripted chain call `/v1/auth/local/session`, `/v1/auth/csrf` and `/v1/auth/api-tokens` — the routes the browser settings tab also drives. A shape change here breaks clients that share no code with this tree. Counterparts: `ui/tui/AGENTS.md`, `deploy/vm/AGENTS.md`.

## Rules

- A new identity surface gates inside its own handler with a bare 404, never a 403: an install that lacks the surface must not advertise it to an anonymous probe. Ungated, one unauthenticated GET creates a stray account row on a `multi` install, and one signup accepted under `single` splits one person's identity across two rows.
- Any route reachable with a session cookie and an unsafe HTTP method runs `_requires_cookie_csrf`. `CSRF_EXEMPT_PATH_SUFFIXES` exists for the one endpoint that mints the token and therefore cannot present one. A new cookie-write route that skips the check is cross-site forgeable — `samesite=lax` is not a CSRF defense: legacy browsers ignore it, a fresh cookie rides Chrome's Lax+POST grace window, and a same-site attacker forges the request regardless.
- Demo expiry is enforced wherever an expired demo could otherwise be admitted: `session.validate_session` on the session, `database.get_api_token_by_hash` on the API token, `account_gc.cleanup_unactivated_accounts` on the row. Links never reach a demo account at all — `service.request_magic_link` refuses every `demo` subject regardless of expiry — so `service.verify_magic_link` carries no expiry test and needs none. An admission path added without the check keeps an expired demo working.
- `provisioning.local_teardown`'s DELETE guard and `account_gc.cleanup_unactivated_accounts`' scan predicate are two halves of one rule. The guard re-verifies every mutable leg of the predicate (login state, demo expiry) and omits the immutable `created_at` term, because the same guarded DELETE also serves `create_user`'s provisioning-failure teardown for rows seconds old. Carrying `created_at` into the guard turns those teardowns into zero-row deletes that report success, leaving the failed-signup row behind permanently.
- `service.get_cookie_settings`' `secure` flag is mode-dependent, and a deletion carrying `Secure` over plain HTTP — a `single` install reached without TLS — is discarded by the browser (RFC 6265), leaving the revoked cookie alive in the client after logout. A delete site that hand-writes its attributes inherits that hole.
- Pre-auth surfaces answer identically whether or not the account exists — same envelope, and the send-time delay simulated rather than skipped, because response timing is the cheaper oracle to read. A new surface whose envelope or latency varies with account state is a user-enumeration bug, not a UX choice.

Elsewhere: this map does not own the HTTP error envelope, the database schema, the browser client's pages, or the scheduler. The envelope's body shapes and status mapping are `cns/api/base.py`; what each module implements is that module's own docstring, not restated here; and how a rule came to read as it does is `git log`. Every other destination this directory reaches is an edge — see `## Wiring` above.

## Account creation, from signup to the first message

The case that fixes the teardown Rule above, and the ordering every provisioning path inherits.

1. `api.signup` hands the request to `AuthService.create_user`, which canonicalizes the address with `normalize_email` and then validates format, profile names, and the IANA zone. All three raise before the rate limiter is charged, so a rejected signup costs the caller no quota.
2. `create_user` charges the dual rate limit, then `AuthDatabase.create_user` writes the user row and four seed memories in one admin-session transaction. One transaction because a memory insert failing after a committed row would leave an account with no profile memories, and nothing revisits it.
3. `_initialize_account` runs three steps in order: `initialize_mira_account` (continuum, then five welcome messages; why they commit one at a time is `auth/database.py`'s docstring), then `seed_lora_postgres`, then `provisioner.provision`.
4. A raise anywhere in step 3 unwinds to step 2's caller, which runs `provisioner.delete` → `local_teardown`. The eligibility-guarded DELETE runs before anything is revoked or removed: an account that activated between the GC snapshot and this call matches zero rows and is reported gone from the candidate set rather than deleted, and a teardown that fails propagates with the row intact and every destructive step unrun.
5. Only a fully initialized account gets a magic link. The email is sent before the link is stored, so a failed send stores nothing; only the token's sha256 is persisted, and the raw token exists in the delivered email and nowhere else.
6. Delivery failure is not creation failure. The handler converts `magic_link_delivery_failed` into a 201 telling the user the account exists, because the row was committed and is useful. Provisioning failure tears the account down; delivery failure never does.

Ordering invariants: validate before charging quota; commit the row before initializing it; guarded DELETE before every destructive teardown step; send before store.
