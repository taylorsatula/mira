## Rules

- Every `LTMemoryDB` method takes `user_id: Optional[str]` and resolves through `_resolve_user_id()` — explicit wins, ambient contextvar otherwise, `ValueError` ("Scheduled tasks must pass explicit user_id") when neither. `get_users_with_memory_enabled()` is the one admin-session (BYPASSRLS) method. A new method without the parameter works on the request path and raises or returns zero rows (RLS fails closed) from every scheduled job.
- `update_memory()` wraps only the `_JSONB_MEMORY_FIELDS` frozenset (`inbound_links`, `outbound_links`, `entity_links`, `annotations`) in `Jsonb()`; raw lists/dicts raise `cannot adapt type 'dict'` at the psycopg boundary — the curator's `merge_memories` died to this in the wild. A new JSONB column joins the frozenset in the same commit, or every `update_memory` write of it fails at the driver.
- Every parameter inside `jsonb_build_object`/`jsonb_build_array` (variadic jsonb) carries an explicit cast (`%(target_id_str)s::text`): Postgres cannot infer a parameter type from a variadic argument, so an untyped one fails the whole statement at PARSE time with `IndeterminateDatatype`, before any row is touched — production entity merges silently no-op'd this way on first observation.
- Activity-day snapshots: `store_memories()` stamps `activity_days_at_creation`/`activity_days_at_last_access` from `get_user_cumulative_activity_days()`; `update_access_stats()` re-stamps the latter from `u.cumulative_activity_days`; consolidation takes the minimum across sources. `scoring_formula.sql` decays over these deltas, never wall time. A store or access path that skips the stamp stores NULL — `COALESCE(…, 0)` is the snapshot fallback, so the memory scores as old as the account: newness fully decayed (the 15-activity-day grace), recency and access momentum collapsed, a fresh linkless memory near the 0.1 cold band instead of ~0.5.
- One formula, five entry points: `update_access_stats`, `apply_pin_boost`, `apply_mention_boost`, `bulk_recalculate_scores`, `recalculate_temporal_scores` all recalc through `_recalculate_importance_scores()`, which interpolates `_SCORING_FORMULA_SQL` — read once at `db_access` import from `scoring_formula.sql`, expecting aliases `m`/`u` and the `m.user_id = u.id` join. The two sweeps then auto-archive at `importance_score <= 0.001`; that threshold lives in `db_access`, not the formula file — retune one, check the other. A second formula spelling drifts per path.
- Archive is the delete; hygiene rides it: `archive_memory` → `_recount_entity_link_counts` inside the transaction (a recount of non-archived links, never a decrement) → `remove_dead_links` outside it (opens its own session). The two sweeps mirror this exactly. `link_count` counts only non-archived linked memories — an archive path that skips the recount inflates entity hub scores and the merge prompt's link counts.
- Links live only in the `inbound_links`/`outbound_links` JSONB and are written only through `create_links()`: bidirectional add-or-replace, one entry per counterparty UUID, both rows guarded `is_archived = FALSE` (a link onto an archived row silently no-ops). Callers repo-wide: `rg 'create_links'` → `tools/implementations/memory_tool.py` (curator `link_memories`) and `cns/services/segment_collapse_handler.py` (drain supersedes); consolidation's rewrite side is owned by `lt_memory/processing/AGENTS.md`. A direct UPDATE on the arrays writes one side and drifts.
- `get_or_create_entity` matches on name only — exact, then pg_trgm `> 0.3`; `entity_type` is stored metadata, never a match key (prevents "GPT-4o"-extracted-as-three-types fragmentation). `UNIQUE (user_id, name, entity_type)` spans archived rows, so creation runs `ON CONFLICT … DO UPDATE` resurrecting an archived slot; a plain INSERT violates on any previously-seen name. `merge_entities` rewrites memory `entity_links` source→target, recounts the target, zeroes and archives the source. `rg 'get_or_create_entity|link_memory_to_entity'` → only `persist_llm_entities` (`lt_memory/processing/AGENTS.md` owns that treatment).
- Encoder pairing: stored memories carry `encode_deep` (document encoding, applied at store time); queries carry `encode_realtime`. `find_similar_memories()` and `find_similar_for_dedup()` encode accordingly — the asymmetric model's two spaces do not mix, and a search or dedup surface that flips the encoder scores garbage similarity. Provider contract owned by `clients/AGENTS.md`.
- Fused results may carry `Memory.embedding = None` — the BM25 branch projects embedding as NULL and only vector-branch duplicates restore it. Never consume `embedding` on hybrid/fused-result paths. `Memory.similarity_score` is path-overloaded: raw cosine from `search_similar`, sigmoid-normalized RRF from fusion — a threshold tuned on one path lies on the other.
- Global-memory read contract: model-visible reads UNION personal `memories` (RLS via session) with `global_memories_runtime` — a security-barrier view over operator-curated `global_memories` (`can_read_global_memories()`; the runtime role is SELECT-only, curation happens out-of-band via psql, no app write path exists). Global rows synthesize defaults (`expires_at` NULL, `access_count`/`mention_count` 0, `annotations` `'[]'::jsonb`, `user_id` NULL) and tag `source='global'`; access tracking and debut boost skip them. Both UNION queries (`search_similar`, `HybridSearcher._bm25_search`) list columns explicitly: a new `memories` column lands in BOTH branches with a typed default in the global one, or every similarity/BM25 query fails at prepare time. DDL owned by `deploy/AGENTS.md` (`deploy/mira_service_schema.sql`).
- Every retrieval fan-out copies user context into its workers — `hybrid_search` (two searches) and `proactive.search_with_embedding` (two fetches on one pool sized `config.lt_memory.proactive_search_workers`) via `copy_context().run`. Root's thread-context doctrine, pinned at its load-bearing site: a new retrieval arm spawning without the copy fails closed to zero rows under RLS, indistinguishable from "no memories".
- `MAX_SURFACED_MEMORIES` (8), `MAX_PINNED_MEMORIES` (6), `MIN_FRESH_MEMORIES` (2) have no crash dialect and three-file blast radius: `rg 'MAX_SURFACED_MEMORIES'` → imported by `cns/services/orchestrator.py` (pinned+fresh merge budget) and `cns/services/subcortical.py` (retention cap, pressure warnings). `MAX_PINNED < MAX_SURFACED` is deliberate — the pinned cap binds while `MIN_FRESH` slots stay open; raising pinned above surfaced silently starves fresh discovery.
- Dead, callerless repo-wide — do not build on them: `apply_pin_boost` and `get_memories_by_segment_id` (`db_access.py`), `update_memory_embedding` (`vector_ops.py`), the `LTMemoryDB.transaction()` context manager. The pinned-boost pipeline is unwired end-to-end: `pinned_short_ids` is collected by extraction into `MemoryContextSnapshot` (`rg 'pinned_short_ids'` → collection sites and the TypedDict only) and consumed by nothing. Re-activation is a store-time consumer for those ids; until then extraction's "pinned importance boost" does not happen.

## Files

- `__init__.py` — package-root re-exports only (22 `__all__` names, services plus models); in-repo importers use `lt_memory.<submodule>` paths, never the root — the surface serves external/typed consumers.
- `db_access.py` — the storage gateway: every SQL against `memories`, `entities`, `global_memories_runtime` except two raw-read siblings — `hybrid_search.py` (`_bm25_search`, UNION over `memories` + `global_memories_runtime`) and `hub_discovery.py` (`entities` matching, lateral `memories`) run through `db.session_manager` directly — a table rename or RLS audit reaches them too. Entry: `_resolve_user_id`, `store_memories`, `get_memory`/`get_memories_by_ids`, `update_memory`, `archive_memory`, `search_similar`, `create_links`, `remove_dead_links`, `get_or_create_entity`, `link_memory_to_entity`, `merge_entities`, `find_similar_entity_pairs`, `update_access_stats`, `apply_mention_boost`, `bulk_recalculate_scores`, `recalculate_temporal_scores`, `update_last_tended`, `get_floor_candidates`, `get_users_with_memory_enabled`. Gotcha: `update_access_stats` refetches inside the same transaction — `get_memory` opens a second pooled connection and would miss the uncommitted UPDATE.
- `entity_merge.py` — background LLM entity dedup: pg_trgm pairs (threshold 0.6; calibrated 887 entities → ~408 pairs) → BFS connected components → one `fast`-route call (`entity_merge_system.txt`/`entity_merge_user.txt` via `load_prompt`) → deterministic `db.merge_entities` per source. Entry: `run_entity_merge_for_user`, `_build_merge_groups`, `_parse_merge_response`. Gotcha: three decision classes are skipped, never executed — unknown/hallucinated short ids, a canonical appearing in its own merge list (a self-merge archives the canonical hub through `merge_entities`), and targets archived earlier in the batch (merging into an archived row orphans the rewritten links).
- `factory.py` — construction and lifecycle: `get_lt_memory_factory()` module singleton (all four infra args required on first call, later calls take none; `force_new` cleans up and recreates, for tests); `_init_services()` builds in dependency order, `_service_init_order` drives `cleanup()` in reverse. Add a service: construct it there, append the order — a skipped append means its cleanup never runs. `on_memories_stored` starts None (Wiring).
- `hub_discovery.py` — the entity arm of surfacing: extracted names → matched entities (exact + lateral-join trigram best-match; two statements total regardless of name count) → per-entity capped memories (lateral top-N) → ranked by expansion cosine. Trust-the-extraction design: similarity ranks, never gates — `limit_per_entity` 15, `max_matched_entities` 5, trigram floor 0.3, `top_n` 20. Entry: `discover_hub_memories`.
- `hybrid_search.py` — RRF fusion of BM25 (`ts_rank` over `search_vector`, GIN) and vector (`search_similar`) arms, oversampled ×2, run on a two-worker pool with copied contexts; intent weights (recall 0.6/0.4, explore 0.3/0.7, exact 0.8/0.2, general 0.4/0.6), `RRF_K` 60, sigmoid k=1000 midpoint 0.009 spreading raw 0.007–0.016 to ~0.1–0.85. Entry: `hybrid_search`. Gotcha: RRF consumes ranks only — rescaling `ts_rank` or cosine changes nothing downstream; tune through the weights.
- `linking.py` — candidate discovery for the curator plus link traversal. `find_candidate_hints` runs three axes — vector (≥ 0.75, cap 20), entity co-occurrence (embedding floor 0.55), TF-IDF (≥ 0.20, cap 10) — and returns short ids with `discovery_signal`, never typed links; `traverse_related` walks outbound links (depth ≤ 3) with heal-on-read dead-link removal. Gotcha: `_tfidf_states` is a per-user dict on a process-global singleton; freshness = (active count, max write stamp) — a count-only check serves stale matrices through count-preserving churn; corpora under two documents or with empty vocabulary cache a disabled state that falls back to the other two axes, never raising into extraction storage.
- `models.py` — the Pydantic/TypedDict surface: `Memory`, `ExtractedMemory`, `MemoryLink`, `Entity`, `ProcessingChunk`, `PendingManualMemory` (Valkey queue payload), `MemoryDict` (surfacing output), `MemoryContextSnapshot` (extraction input), the 8-member `VALID_RELATIONSHIP_TYPES`. Gotcha: `similarity_score` is path-overloaded (raw cosine vs sigmoid-normalized RRF — see Rules), and `Memory._coerce_embedding` is the pgvector `Vector` → `list[float]` boundary a raw row would fail at.
- `proactive.py` — the surfacing service: two retrieval arms (hybrid similarity + hub discovery) run concurrently on one copied-context pool → merge with debut boost (personal only, < 2 entity links: +0.15 on activity days 0–6, trailing to day 10) and supersedes penalty (×0.3) → linked-memory traversal (depth 3) → link-type rerank (`MAX_LINKED_PER_PRIMARY` 2; conflicts 1.0 … shares_entity 0.4; importance inheritance weight 0.7) → `MemoryDict`. Entry: `search_with_embedding`. Gotcha: `_track_memory_access` skips `source='global'` and tolerate-logs personal failures — access tracking is enhancement and must never fail a search.
- `scoring_formula.sql` — the importance formula as an SQL expression fragment, not a runnable statement: loaded once by `_load_scoring_formula()` at `db_access` import, interpolated into the UPDATE in `_recalculate_importance_scores`. Expects aliases `m`/`u` plus the `m.user_id = u.id` join. Decay runs on activity days; `happens_at`/`expires_at` boosts and trailoffs run on calendar days. Constants documented in-file (baseline access rate 0.02, momentum 0.95, newness 2.0 over 15 days, recency 0.015, entity type weights).
- `vector_ops.py` — embeddings and similarity facade over the provider and `db`: `store_memories_with_embeddings` (encode_deep → `db.store_memories`), `find_similar_memories` (encode_realtime), `find_similar_for_dedup` (encode_deep, threshold 0.92), `find_similar_by_embedding` (raises on dimension mismatch against `embeddings_provider.dimensions` — the install's dimensionality is a hard contract), `find_similar_to_memory`, `hybrid_search` (composes `HybridSearcher`).
- `processing/` — the extraction and consolidation pipeline; `lt_memory/processing/AGENTS.md`.

## Importance, store to floor

One memory's score, birth to archive — the chain no single read shows:

1. Birth. Extraction always stores `DEFAULT_IMPORTANCE_SCORE` 0.5 regardless of the model's emitted `importance_score` — new memories "earn their keep" through behavior, never through the extractor's opinion. Browser create takes the operator's value; consolidation takes the median of its sources. `store_memories` stamps both activity-day snapshots at INSERT.
2. Touch. Every read bumps `access_count` and re-stamps activity days inside one transaction (`update_access_stats`); the curator's `touch` op adds `mention_count`. Both immediately recalculate through the formula. The stored column otherwise moves only via explicit `update_memory` writes — consolidation, links, annotations, merges.
3. Formula anatomy (`scoring_formula.sql`): value score = momentum-decayed access rate vs the 0.02 baseline (`access_count × 0.95^(days since last access) ÷ max(7, age)`, `LN(1 + rate/0.02) × 0.8`) + hub score (inbound links × 0.04 up to 10, diminishing after) + entity hub score (Σ entity `link_count` × type weight — PERSON 1.0, EVENT 0.9, ORG 0.8, PRODUCT 0.7, WORK_OF_ART 0.6, GPE/NORP/LAW 0.5, FAC 0.4, LANGUAGE 0.3, default 0.5 — linear to 50 weighted links, then log) + mention score (× 0.08 each up to 5, then log) + newness boost (2.0 → 0 over 15 activity days); all × recency (`1/(1 + days × 0.015)`, half-life ≈ 67 activity days) × temporal multiplier (upcoming: ≤ 1 day → 2.0, ≤ 7 → 1.5, ≤ 14 → 1.2; past: 0.8 → 0.4 over 45 days, floor 0.4) × expiration trailoff (1.0 → 0 across 5 days past `expires_at`; the outer CASE hard-zeroes anything further past); sigmoid centered at 2.0 maps the average memory to ~0.5.
4. Cold bands. Surfacing filters `min_importance` 0.1 — memories scoring 0.001–0.1 are cold: stored, invisible to search, still dedup-visible (`find_similar_for_dedup` floors at 0.001). The sweeps archive ≤ 0.001 only after a recalc, so the archive decision happens at sweep time, never at read time.
5. Read-time adjustments never persist. Debut boost, supersedes penalty, and link-type rerank live in `proactive._merge_memory_pools`/`_rerank_with_links` and change ranking only.
6. Floor. `get_floor_candidates` samples `importance_score < floor_threshold` among memories untended for `unseen_days` — or never tended (`last_tended_at IS NULL`) but created before that cutoff — at random, capped at `sample_size`. The curator decides; `update_last_tended` stamps exclusion. Score-abandoned memories never reach the floor — unless they enter the corpus already ≤ 0.001: browser create stores the operator's value verbatim (0.0 accepted) and the drain stores the queued score verbatim, while `bulk_recalculate_scores` selects `importance_score > 0.001` only and the temporal sweep sees in-window temporal rows only — such memories are never recalculated, never archived, and floor-eligible from birth.

Ordering invariants: snapshots before any recalc; access-stat recalc inside the access transaction (a second connection misses it); sweep archive only after the recalc it scores by.
