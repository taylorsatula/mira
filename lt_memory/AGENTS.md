# lt_memory/ — Long-term memory: storage, scoring, retrieval, linking, and entity services

## Rules

- `LTMemoryFactory` (`factory.py`) is the sole constructor for all services here — never instantiate `LTMemoryDB`, `VectorOps`, `LinkingService`, etc. directly. Access the singleton via `get_lt_memory_factory()`; the first call requires `session_manager`, `embeddings_provider`, `llm_provider`, and `continuum_repo` (all singletons are built during `main.py:lifespan` startup, single-threaded — not thread-safe during init). No config object is injected; algorithm tuning constants are module-level `UPPER_SNAKE_CASE` values in each service file.
- `on_memories_stored` on `LTMemoryFactory` is the seam between this package and `cns/`: it starts as `None` and is late-registered by `cns/services/segment_collapse_handler.py`; `store_and_tend_extraction()` (`lt_memory/processing/execution_strategy.py`) invokes it None-safe after storing. `lt_memory` never imports from `agents/` or `cns/` — any new cross-need goes through a callback seam, not an import.
- `db_access.py` loads `scoring_formula.sql` into `_SCORING_FORMULA_SQL` at import time and embeds it into every `UPDATE memories SET importance_score = ...` statement. The formula requires aliases `m` (memories) and `u` (users) joined via `m.user_id = u.id` — any query using `_recalculate_importance_scores` must supply the `FROM users u` join or the SQL breaks.
- Scoring-relevant writes must keep the activity-day snapshots coherent: `store_memories()` stamps `activity_days_at_creation`/`activity_days_at_last_access` from `get_user_cumulative_activity_days()`, and every access/boost path (`update_access_stats`, `apply_pin_boost`, `apply_mention_boost`) refreshes `activity_days_at_last_access` in the same statement. The decay math in `scoring_formula.sql` reads these snapshots — writing `access_count` without them silently corrupts scores.
- `ProactiveService.search_with_embedding()` runs its two retrieval pools on threads; each thread gets its own `contextvars.copy_context()` because a single Context object cannot be entered by two threads. Any new per-thread DB work in this package must copy the context the same way or RLS loses `app.current_user_id`.
- Global memories are searched side-by-side with personal ones via `UNION ALL` against `global_memories_runtime` in `db_access.search_similar()` and `hybrid_search._bm25_search()`, tagged `source='personal'|'global'` on the `Memory` model. These queries use explicit column lists (no `SELECT *`) — keep it that way when editing. Global rows are exempt from RLS by design.
- All shared types cross-used across files live in `models.py`; file-local types stay in their file. `ProcessingChunk.messages` stays `List[Any]` — Pydantic can't resolve TYPE_CHECKING-only imports at runtime.

## Files

- `models.py` — All Pydantic models and shared TypedDicts. Source of truth for `Memory` (including the `_coerce_embedding` pgvector→list boundary validator), `ExtractedMemory` (whose `_anchor_naive_temporal_fields` validator pins naive datetimes to UTC as a last-line backstop), `ExtractionResult`, `MemoryLink`, `Entity`, `ProcessingChunk`, `PendingManualMemory` (Valkey-queued manual memory from `tools/implementations/memory_tool.py`), and the cross-file TypedDicts (`MemoryLinkEntry`, `EntityLinkEntry`, `AnnotationEntry`, `MemoryDict`, `MemoryContextSnapshot`, `EntityPairRow`, etc.). Literal alias: `RelationshipType`.
- `db_access.py` — All SQL for memories, entities, and scoring: CRUD (`store_memories`, `get_memory`, `update_memory` — wraps the JSONB columns `inbound_links`/`outbound_links`/`entity_links`/`annotations` in `Jsonb()` for psycopg; raw lists/dicts raise `cannot adapt type 'dict'` at the driver), `archive_memory`), curator tending (`update_last_tended`, `get_floor_candidates` — random sample of low-importance memories not tended within the staleness window), search (`search_similar` vector UNION, `get_memories_paginated`, `get_memories_by_segment_id`), scoring (`_recalculate_importance_scores` via the loaded formula, `update_access_stats`, `apply_pin_boost`, `apply_mention_boost`, `bulk_recalculate_scores` with auto-archive below 0.001, `recalculate_temporal_scores` for the ±7/30-day event windows), link ops (`create_links` — one link per target UUID, replaces rather than duplicates; `remove_dead_links` for lazy cleanup), and entity ops (`get_or_create_entity` pg_trgm fuzzy matching, `link_memory_to_entity`, `merge_entities` — rewrites memory `entity_links`, bumps `link_count`, archives the loser). `_resolve_user_id()` falls back to the ambient contextvar and raises `ValueError` when neither is available. `get_users_with_memory_enabled()` is the one admin-session (RLS-bypassing) query. `Consumers:` every service in this package plus `lt_memory/processing/` (see `processing/AGENTS.md`).
- `scoring_formula.sql` — SQL expression for importance score recalculation, loaded by `db_access.py` at import time. Edit here, not inline. See the deep-dive below.
- `factory.py` — Builds all services in dependency order (`db` → `vector_ops` → `linking` → processing components incl. `create_execution_strategy` → `hub_discovery` → `proactive`) with reverse-order `cleanup()`. Owns `on_memories_stored` (see Rules) and the `get_lt_memory_factory()` singleton. `Consumers:` `main.py` startup, `utils/lt_memory_jobs.py`, and every external entry into this package.
- `vector_ops.py` — Embedding generation (mdbr-leaf-ir-asym, 768d) and vector search wrappers. Key contract: `find_similar_memories()` encodes queries with `encode_realtime()` while `find_similar_for_dedup()` uses `encode_deep()` — the asymmetric model has separate query/document spaces, so dedup (document-vs-document) must never switch to the query encoder. Owns `HybridSearcher` composition. Gotcha: `find_similar_memories()` references `self.vector_search_config`, which is never assigned — it raises `AttributeError` when called; use `find_similar_by_embedding()` or `hybrid_search()` instead.
- `hybrid_search.py` — BM25 (Postgres `search_vector` full-text, personal+global UNION) + vector search fused via Reciprocal Rank Fusion with intent-based weights (`recall`/`explore`/`exact`/`general`). Raw RRF scores (~0.007–0.016) are sigmoid-normalized (k=1000, midpoint 0.009) into a usable 0–1 range on `Memory.similarity_score`. Oversamples both legs 2× before fusion. Entry: `HybridSearcher.hybrid_search()` → `List[Memory]`. `Consumers:` `vector_ops.py` (`VectorOps.hybrid_search`), reached by `proactive.py`.
- `linking.py` — Typeless candidate discovery via three axes (vector similarity ≥ 0.75, entity co-occurrence with a 0.55 embedding-similarity floor to suppress common-entity noise, TF-IDF term overlap ≥ 0.20 for orphan memories). `find_candidate_hints(memory_id)` returns `CandidateRef`-shaped dicts (short id + `discovery_signal` + similarity, `bond` always empty) for the `MemoryCuratorAgent` — no typed links written; the agent classifies *how*, this code only finds *that*. Also `traverse_related()` for BFS link-graph traversal with heal-on-read dead-link cleanup (`db.remove_dead_links`). Per-user TF-IDF matrices are cached in `_tfidf_states`, keyed by the contextvar user id and invalidated when the active-memory count changes. `Consumers:` `proactive.py` (traversal), `lt_memory/processing/execution_strategy.py` (hints), `agents/implementations/memory_curator_agent.py` (hint consumer).
- `proactive.py` — Proactive surfacing for conversations: runs the hybrid-search similarity pool and `hub_discovery` pool in parallel threads (see Rules), merges with a debut boost (new personal memories <2 entity links get +0.15 trailing off over ~10 activity days) and a supersedes penalty (×0.3), attaches up to `MAX_LINKED_PER_PRIMARY=2` linked memories per primary via link rerank, then tracks access. Module constants `MAX_SURFACED_MEMORIES=8` / `MAX_PINNED_MEMORIES=6` / `MIN_FRESH_MEMORIES=2` are authoritative caps also imported by the orchestrator and subcortical layer. Entry: `search_with_embedding()` → `List[MemoryDict]`. `Consumers:` working-memory subcortical/orchestrator layer (conversation turn pipeline).
- `hub_discovery.py` — Entity-driven retrieval: pg_trgm fuzzy entity match (exact first, then trigram) → memories linked to matched entities (capped per entity, max 5 entities) → ranked by cosine similarity to the expansion embedding (ranking, not gating — the LLM's entity extraction is trusted). DB errors propagate from `_match_entities()`. Entry: `discover_hub_memories()`. `Consumers:` `proactive.py`.
- `entity_extraction.py` — spaCy NER (`en_core_web_lg`, parser/lemmatizer/textcat disabled) with type filtering (`ENTITY_TYPES`), verb-phrase rejection (`VERB_PREFIXES` catches spaCy misclassifications like "Built MIRA"), whitespace normalization, and rapidfuzz canonical clustering (`cluster_similar_entities`). Entries: `extract_entities()`, `extract_entities_with_types()` → `List[NamedEntity]`, `extract_entities_batch()`. Fails fast on missing spaCy model.
- `entity_merge.py` — Background entity dedup: pg_trgm pairs (`db.find_similar_entity_pairs`, threshold 0.6) → BFS connected-components grouping → single `model_config="fast"` LLM call (`entity_merge_system.txt`/`entity_merge_user.txt` prompts) judging which groups are one entity → deterministic `db.merge_entities` per decision. Hallucinated short IDs in the LLM response are rejected by `short_to_full` lookup. Entry: `run_entity_merge_for_user(user_id)`; use-day-gated scheduled job (`entity_merge_use_days`, registered in `utils/lt_memory_jobs.py`). Best-effort: per-merge failures logged, run continues.
- `__init__.py` — Public re-exports of the factory classes and all shared models/TypedDicts.
- `processing/` — Memory extraction pipeline and consolidation; see `processing/AGENTS.md` for the extraction flow, storage path (`store_and_tend_extraction()`), and temporal-field contract.

## Wiring

**Storage flow (cross-directory, strict order):** `cns/services/segment_collapse_handler.py` (or the sweep in `utils/lt_memory_jobs.py`) → `ExtractionOrchestrator.submit_segment_extraction()` (`processing/`) → `DirectExecutionStrategy` → `store_and_tend_extraction()` → `VectorOps.store_memories_with_embeddings()` + `db.create_links`/entity persistence + `LinkingService.find_candidate_hints` → `on_memories_stored` callback → `MemoryCuratorAgent` (owned by `agents/implementations/`, Mode Contract there). Component construction for this flow is owned end-to-end by `factory.py`; reordering construction layers breaks dependency wiring (each layer consumes the previous).

**Scheduled jobs:** `utils/lt_memory_jobs.py` (owner of scheduling) drives `entity_merge.run_entity_merge_for_user` (7 use-days) and the score-recalc paths (`db_access.bulk_recalculate_scores`, `recalculate_temporal_scores`) with explicit `set_current_user_id()` per user; the curator floor trigger samples via `db.get_floor_candidates`.

**Retrieval flow:** working-memory turn pipeline → `ProactiveService.search_with_embedding()` → parallel `VectorOps.hybrid_search()` (→ `HybridSearcher`) + `HubDiscoveryService.discover_hub_memories()` → merge/rerank → `MemoryDict` list; access tracking writes back through `db.update_access_stats` (which triggers score recalc).

## Importance Scoring Formula (`scoring_formula.sql`)

The importance score is a single SQL expression producing a value in [0, 1] via sigmoid transform ("earn your keep": new memories start at ~0.5 and must accumulate behavioral signals to stay relevant). `db_access._recalculate_importance_scores()` splices it into every score update; constants are documented in the file header (`BASELINE_ACCESS_RATE=0.02`, `SIGMOID_CENTER=2.0`, etc.).

Pipeline, in evaluation order:

1. **Expiration hard zero** — `expires_at` more than 5 calendar days in the past → `0.0` immediately.
2. **Value score** — `LN(1 + access_rate / 0.02) × 0.8`, where access_rate = `(access_count × 0.95^activity_days_since_last_access) / MAX(7, activity_days_since_creation)`. Momentum decay fades old accesses; the `MAX(7, ...)` floor prevents day-1 spikes.
3. **Hub score** — `0.04` per inbound link up to 10, then diminishing returns: `0.4 + (links−10)×0.02 / (1 + (links−10)×0.05)`.
4. **Entity hub score** — weighted sum over `entity_links`, weight = `entity.link_count × type_weight` (PERSON=1.0, EVENT=0.9, ORG=0.8, PRODUCT=0.7, WORK_OF_ART=0.6, GPE/NORP/LAW=0.5, FAC=0.4, LANGUAGE=0.3, default 0.5). Linear `×0.005` up to 50 weighted links, then `0.25 + LN(sum/50)×0.075`.
5. **Mention score** — `0.08` per mention up to 5, then `0.4 + LN(1 + (mentions−5))×0.1`. Explicit LLM references are the strongest behavioral signal.
6. **Newness boost** — `MAX(0, 2.0 − age_in_activity_days × 0.133)`: a 15-activity-day grace period before decay applies.
7. **Raw score** = value + hub + entity_hub + mention + newness.
8. **Recency boost** — `1 / (1 + activity_days_since_last_access × 0.015)`, half-life ~67 activity days.
9. **Temporal multiplier** (calendar-based, `happens_at`) — upcoming events: ≤1 day → 2.0, ≤7 → 1.5, ≤14 → 1.2; past events decay linearly 0.8 → 0.4 over 45 days, floored at 0.4.
10. **Expiration trailoff** (calendar-based) — linear 1.0 → 0.0 over 5 days after `expires_at`.
11. **Sigmoid** — `1 / (1 + EXP(−(raw × recency × temporal × trailoff − 2.0)))`, center 2.0 maps average memories to ~0.5; final `ROUND(..., 3)`.

Activity days (via `users.cumulative_activity_days` and the memory's stored snapshots) drive all decay math so vacations don't degrade scores; temporal events use calendar days because real-world deadlines don't pause.
