# lt_memory/processing/ — Memory extraction pipeline and consolidation

## Rules

- Memory extraction has exactly one execution path: `DirectExecutionStrategy.execute_extraction()` calls `LLMProvider.generate_response(model_config="batch")` synchronously per chunk and stores through `store_and_tend_extraction()`. Do not reintroduce a deferred/remote batch submission layer — `create_execution_strategy()` builds only `DirectExecutionStrategy` (`lt_memory/factory.py` wires it once at startup as `ExtractionOrchestrator.execution_strategy`).
- All LLM routing comes from `model_config='<route>'` on `generate_response()`. Extraction uses the `"batch"` route. Never pass model, endpoint, or API key explicitly.
- `store_and_tend_extraction()` (`execution_strategy.py`) is the single storage path for extraction output: stores memories with embeddings via `VectorOps.store_memories_with_embeddings`, persists LLM-extracted entities via `persist_llm_entities()` (the one sanctioned entity-linking treatment — the pending-manual drain in `cns/services/segment_collapse_handler.py` routes its links through the same function so the two store paths cannot diverge; owned by `cns/services/AGENTS.md`), builds candidate hints via `_build_candidate_hints()`, then invokes the `on_memories_stored` callback (seam contract owned by `lt_memory/AGENTS.md`, Rules). Do not duplicate any of this elsewhere.
- No typed links are written by extraction/storage code. The model's `related_memory_ids` + bonds flow to the `MemoryCuratorAgent` as `CandidateRef` hints (`discovery_signal: "extraction"`, merged with deterministic hints from `LinkingService.find_candidate_hints`) — not as edges. Typed `CandidateRef`/`NewMemory` shapes are owned by `agents/implementations/AGENTS.md` (`agents/implementations/memory_curator_agent.py`); `lt_memory` never imports from `agents/`.
- `MemoryProcessor` and `ExtractionEngine` are side-effect-free: pure data transformation and payload construction. Memory-storage writes live in `execution_strategy.py` and `consolidation_handler.py`; `orchestrator.py` writes only the boundary/retry metadata markers on the messages table.
- Model-supplied temporal fields (`happens_at`/`expires_at`) are the **user's local wall time**, never UTC instants. `MemoryProcessor.process_extraction_response()` resolves the timezone once per response via `_resolve_extraction_timezone()` (broad-except → `"UTC"`: extraction is a background durability path, not fail-loud) and parses each field through `_parse_model_temporal_field()` → `ensure_utc(parse_time_string(value, tz_name=...))`. Never let a raw naive string reach `ExtractedMemory`: a naive datetime binds to `timestamptz` under whatever Postgres `TimeZone` is configured (observed four-hour drift), and a `ValidationError` at construction aborts every memory in the segment batch — no per-memory catch exists upstream. An unparseable value logs the raw value, timezone, and parser reason, and the memory is stored without that field; text is never lost. Daylight-saving strictness belongs to model-facing scheduling tools, not here.
- `extract_unprocessed_segments()` (`orchestrator.py`) sets the user contextvar per user (`set_current_user_id` / `clear_user_context`) because it runs outside HTTP context on a scheduled sweep. `submit_segment_extraction()` itself does not set context — its callers must have it set (`cns/services/segment_collapse_handler.py` does; see `utils/user_context` doctrine in root AGENTS.md).
- The `referenced_memories` field in message metadata must contain **full UUIDs**, never short IDs: `_build_memory_context()` calls `UUID(ref_id)` on each value with no guard, so a `mem_XXXXXXXX` short form reaching it raises `ValueError` — in the sweep this is caught per-segment and logged (extraction for that segment never happens), and on the collapse-handler path it propagates and fails the collapse. The guarantee holds by construction: short IDs are resolved server-side by `memory_tool._touch()` (`tools/implementations/memory_tool.py`) before its `resolved_uuids` land in metadata via `cns/services/orchestrator.py`. Any new writer of `referenced_memories` must resolve through the same short-ID contract (owner: `utils/tag_parser.py`; root doctrine "Memory short IDs").

## Files

- `orchestrator.py` — Owns the segment extraction lifecycle: query the boundary message, load messages up to the next boundary, build a single `ProcessingChunk` (segments are natural units — no chunking), attach `memory_context_snapshot` via `_build_memory_context()`, execute through the strategy, and mark `memories_extracted=true` on the boundary row.
  - Keepsleeping heartbeat turns (`metadata.heartbeat` + `heartbeat_decision` predicate from `cns/services/heartbeat_service.py`) are filtered in Python during the load — an all-heartbeat segment is marked extracted with no memories instead of being retried by the sweep forever.
  - Entry points: `submit_segment_extraction()` (per-segment; raises `RuntimeError` when the boundary row is missing, returns `False` when the segment yields no messages — the collapse path turns that `False` into `RuntimeError`, the sweep leaves the segment for retry) and `extract_unprocessed_segments()` (calendar-based safety-net sweep at `jobs_config.extraction_retry_hours`, registered in `utils/lt_memory_jobs.py`; per-segment error isolation, retry capped by `ContinuumRepository.find_failed_extraction_segments` — the budget counts only content-caused failures (`EXTRACTION_MAX_CONTENT_FAILURES`); infrastructure/LLM outages are classified and never consume it, and budget exhaustion writes an `extraction_abandoned` marker so the exclusion is operator-visible).
  - An empty/degenerate extraction response raises `LLMResponseFormatError` — it is a FAILURE that leaves the segment unextracted for retry, never a successful zero-memory extraction. `Consumers:` `cns/services/segment_collapse_handler.py` (submit path), `utils/lt_memory_jobs.py` (sweep), `utils/power_on_self_test.py`.
- `execution_strategy.py` — Owns `DirectExecutionStrategy` and the `create_execution_strategy()` factory, plus module-level `store_and_tend_extraction()` / `persist_llm_entities()` / `_build_candidate_hints()`. `execute_extraction()` processes every chunk synchronously and returns `str` (`direct_<uuid>`), or raises `ValueError` when no chunk yielded a valid payload. `Consumers:` `lt_memory/factory.py`; `persist_llm_entities` is also consumed by the pending-manual drain (`cns/services/segment_collapse_handler.py`).
- `extraction_engine.py` — Owns `ExtractionPayload` construction: prompt loading (`config/prompts/loader.py:load_prompt` — fail-fast on missing files), bidirectional UUID shortening via `_build_identifier_maps()` (raises `RuntimeError` on short-ID collision), memory context retrieval from `ProcessingChunk.memory_context_snapshot` (DB fallback raises `ValueError` if any referenced memory is missing), and XML message formatting via `_format_chunk_for_extraction()` with `<meta>` memory attribution on assistant turns. File-local type: `ExtractionPayload`. `Consumers:` only within this directory (`execution_strategy.py`, `orchestrator.py`).
- `memory_processor.py` — Owns LLM response parsing: `json.loads` with `json_repair` fallback (`_parse_extraction_response`, raises `ValueError` if unparseable after repair), short→full UUID remapping with unresolved-ref dropping (`_remap_short_ids_to_full`), field validation/sanitization with in-place fixes (`_validate_extracted_memory`), model-supplied temporal-field parsing in the user's timezone (see Rules), and two-stage duplicate detection (`_is_duplicate_memory`: rapidfuzz ≥ 0.95 against context texts, then vector search at `DEDUP_SIMILARITY_THRESHOLD = 0.92` excluding cold-storage memories). `process_extraction_response(segment_id=...)` stamps every built `ExtractedMemory` with `source_segment_id` — the extraction provenance anchor `db_access.store_memories` persists. Module-level `sanitize_entity_list()` is the shared entity shape contract, also consumed by the pending-drain entity pass (`cns/services/segment_collapse_handler.py`). File-local types: `DuplicateCheckResult`, `RawMemoryDict`. `Consumers:` only within this directory (`execution_strategy.py`; `orchestrator.py` imports `LLMResponseFormatError` for its content-vs-infrastructure failure classifier) plus `sanitize_entity_list` from the drain.
- `consolidation_handler.py` — Owns memory merge execution: `execute_consolidation()` loads the full old-memory set (raises `ValueError` if any is missing), creates the consolidated memory with median importance and earliest source `source_segment_id`, transfers deduplicated inbound/outbound/entity link bundles, records the merge note as a `consolidation` annotation with `archived_source_ids`, rewrites `outbound_links` on memories that pointed at the old set and `inbound_links` on targets of the old set's outbound links (one pass, before the archive step), carries merged access/mention sums onto the new memory (`last_accessed` max, `activity_days_at_last_access` min), and archives the old memories. Pure business logic — no routing decisions, no LLM calls. `Consumers:` `tools/implementations/memory_tool.py` (agent-invoked `merge_memories`).
- `__init__.py` — Re-exports the seven names in `__all__` (`MemoryProcessor`, `ExtractionEngine`, `ExtractionPayload`, `DirectExecutionStrategy`, `create_execution_strategy`, `ConsolidationHandler`, `ExtractionOrchestrator`); in-repo callers import the submodules directly, not this package root.

## Wiring

**Extraction flow (strict order):**
`cns/services/segment_collapse_handler.py` (or the sweep) → `ExtractionOrchestrator.submit_segment_extraction()` → `DirectExecutionStrategy.execute_extraction()` → per chunk: `ExtractionEngine.build_extraction_payload()` → `generate_response(model_config="batch")` → `MemoryProcessor.process_extraction_response()` → `store_and_tend_extraction()` → `on_memories_stored` callback spawns `MemoryCuratorAgent` in integration mode. Extraction completes inline, so memories are durable before the user's next conversation. Reordering payload-build → parse → store breaks the `short_to_uuid` mapping contract between engine and processor.

**`segment_id` provenance:** `DirectExecutionStrategy` carries `str(chunk.segment_id)` from `ProcessingChunk` into `MemoryProcessor.process_extraction_response(segment_id=...)`, which stamps every built `ExtractedMemory` with `source_segment_id` so `db_access.store_memories` persists it — required for segment-scoped memory cleanup on session resume and for the curator work-item's source-segment record. The orchestrator defaults `segment_id` to `boundary_message_id` when boundary metadata lacks one. The pending-manual drain stamps the same field from its queue keys (owned by `cns/services/AGENTS.md`).

**Contextvar boundary:** the sweep sets user context per user; the collapse-handler path inherits HTTP context. `lt_memory/factory.py` owns all component construction for this directory (`create_execution_strategy`, `ConsolidationHandler`, `ExtractionOrchestrator`), and also owns the `on_memories_stored` callback slot (`None` until `cns` registers it; `store_and_tend_extraction()` is None-safe). `consolidation_handler.py` is constructed by the same factory and reached only through `tools/implementations/memory_tool.py` `merge_memories`, which resolves short IDs first — the short-ID contract above applies at that boundary too.

**Exception policy is positional:** the sweep wraps each segment and each user in log-and-continue isolation (background durability path — the model is off the call stack); the collapse-handler submit path propagates (`RuntimeError` from `submit_segment_extraction()` or a `False` return fails the collapse). Storage inside `execute_extraction()` propagates — a failed segment stays marked unextracted and is retried by the sweep; a storage failure is infra-class, so it never consumes the content-failure budget and the segment is retried until it succeeds.
