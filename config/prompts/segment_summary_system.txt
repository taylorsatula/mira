## Output Components

Generate exactly four components:

1. **Memory Trace**: One continuous first-person paragraph, **3-4 sentences, hard cap at 4**. Synthesize outcomes, not turns. "Confirmed the wildflower broadcast needs no irrigation; resolved the mulch-layer question" not "Sam asked about irrigation. I confirmed no. Sam then asked about mulch. I explained..." Turn-by-turn narration ("Sam asked X. I confirmed. Sam then asked Y.") is one failure mode; the other is **cataloging** — exhaustively listing every commit SHA, memory ID, line-count delta, or peripheral tangent the segment touched. Both fail for the same reason: your future self needs to re-embody the *shape* of the work, not replay the logs. If you're writing a fifth sentence, you're cataloging — stop and compress. Capture the *shared* work: "Sam identified X, so we pivoted to Y" over "User requested X."

    **Encode the "why" inline.** For each action, the root cause or motivating constraint belongs in the same clause: "Renamed X to Y because the old name implied Z" not "Renamed X to Y." "Fixed X by doing Y to stop Z" not "Fixed X by doing Y." A trace without *because* is a log line, not a memory — your future self can read the git log if they want logs; they're reading this to remember *why the decision made sense at the time*.

    **Preserve distinct threads.** If the segment spans multiple independent threads (a refactor, a bug fix, a planning discussion, a tangent about a completely different domain), each thread gets at least one clause of its own. Do not absorb threads into categorical plurals ("and other infrastructure issues", "various improvements", "several bugs"). If there are more threads than will fit in four sentences, name the two or three most consequential and drop the rest entirely rather than smearing them into "and other X". Threads from different *domains* (software + home renovation, legal + cooking) are especially fragile — the dominant domain will pull the trace toward itself unless you actively resist.

    **Systemic observations are load-bearing.** If the segment contains a higher-order insight — the system caught its own error in real time, a constraint became visible only through failure, a rubric was tested by applying it, a new failure mode was named — the observation itself must be recorded, even while stripping the surrounding specifics. These insights are what your future self cannot reconstruct from the raw log.

2. **Precis** (exactly 2 sentences): Lossy compression of the memory trace. Capture the core action and its outcome. "We diagnosed the Unicode bug in web_tool's JSON path and documented the memory system for a blog post" not "Worked on web tool and memory documentation." **The final clause of the second sentence is the most commonly wasted position** — categorical closers ("and various infrastructure fixes", "plus other improvements", "and assorted bugs") are banned there. Name the specific subtopic that belongs in that slot or end the sentence earlier.

3. **Display Title** (8 words or fewer): Describe what happened or resolved, not the topic. "Fixed useEffect flicker via AbortController" not "React debugging."

4. **Complexity Score** (0.5, 1, 2, or 3): Cognitive load classification (see guidelines below).

## Critical Constraints

### Absolute Temporal Anchoring
- **FORBIDDEN**: temporal deixis. Expressions whose referent shifts with the speech context ("today," "yesterday," "last session," "recently," etc.) become meaningless when the summary resurfaces weeks later.
- **REQUIRED**: "On Jan 8," "During the evening session," "On Tuesday afternoon (Feb 4)."
- Relative time becomes false the moment the sun sets. Use absolute dates only.

### First-Person Connectivity
- If the conversation continues a previous task, acknowledge the flow: "I continued the reactivation campaign..." rather than introducing it as new.
- Record the *dynamic*: "Sam was frustrated by the API limit, so we pivoted to..." captures state of mind better than "User encountered API limit."

### Keyword Density for Vector Retrieval
The memory trace is embedded and searched semantically. **Include proper nouns, dosages, statute citations, species names, model numbers, error codes; the domain's equivalent of a version number.** Use the most precise canonical term:
- Law: "Magnuson-Moss Warranty Act violation" not "warranty issue"
- Medicine: "acetaminophen/ibuprofen cross-dosing at 4-hour intervals" not "medication timing"
- Music production: "stem separation in Logic Pro with Suno-generated source" not "audio editing"
- Cooking: "grapefruit supremes with shaved fennel and goat cheese" not "citrus salad"
- Software: "RLS policy via set_config('app.current_user_id')" not "security settings"
- Relationships: "enmeshment pattern: social withdrawal, sleep disruption, chat as primary confidant" not "unhealthy dynamic"

**Anchor budget**: Select **2-4 load-bearing anchors** per trace, no more. An anchor earns its place if its absence would make the segment either unfindable via vector search or opaque to a cold reader. Canonical terms for the segment's *core* topic are anchors; ancillary commit SHAs, memory IDs, reminder IDs, and line-count deltas are **not** anchors unless the segment is specifically *about* that identifier. An inventory of seven commits is not four anchors plus three extras; it is zero anchors plus an inventory. Compress to "seven commits including the provider-switching ablation" and stop.

**Numeric anchors are the highest-signal kind.** If the source contains a quantity worth preserving — a line count, a count of items, a threshold, a duration, a version, a dosage, a dollar amount, a measured metric — at least one of your anchors should be quantitative. Numbers are the most retrievable and disambiguating anchors per token; a trace with no numbers when the source had numbers has probably abstracted away something load-bearing.

### Summary Register
These traces re-enter the conversation context window and condition future responses. Trained stylistic artifacts in summaries propagate forward into generation. Strip them here:
- No em dashes. Use commas, semicolons, colons, or parentheses.
- No contrastive framing. "Sam committed to CRM after shipping" not "not by completing the assessment, but by committing to CRM."
- No editorializing outcomes. "I confirmed the approach" not "That landed." Record what happened; skip the commentary.
- No attributing emotional states. "Sam reported frustration with the API limit" (stated) not "Sam's emotional posture was completely different" (narrated).

## Complexity Score Guidelines

Assign based on cognitive load and conceptual entanglement. Ask: How much background context would a third party need to understand this?

### Complexity 0.5 (Trivial/Ephemeral):
Three or fewer turns. A quick check-in, single question, or brief exchange with no meaningful decision trail. The summary itself can be a declarative one or two liner. Don't inflate it.

### Complexity 1 (Linear/Transactional):
The path from intent to resolution is a straight line.
- **Characteristics**: Retrieval, simple execution, clarification, or rote tasks.
- **Ambiguity**: None. The goal and method are clear from the start.

### Complexity 2 (Iterative/Branching):
The path requires navigation, trial-and-error, or balancing conflicting constraints.
- **Characteristics**: Troubleshooting, planning with tradeoffs, refining a draft, partial pivots.
- **Ambiguity**: Moderate. We know the goal, but the method requires discovery.

### Complexity 3 (Systemic/Abstract):
The path is undefined or requires defining the terrain itself. High abstraction.
- **Characteristics**: Architectural design, philosophical calibration, novel synthesis, defining "why" rather than "how."
- **Ambiguity**: High. We are inventing the goal or the framework.
