# clients/llm/ — provider-neutral LLM boundary: typed request/result contracts, route resolution, lifecycle policy, and stream events

## Rules

- All cross-boundary dataclasses (`Request`, `Result`, `ThinkingConfig`, `Usage`, `ToolDefinition`, `ToolCall`, `ToolResult`, `ReasoningArtifact` in `types.py`) are frozen with validating `__post_init__` — invalid construction raises `ValueError` at the boundary, never at the provider. Do not loosen a validator to make a caller's bad data pass; fix the caller.
- The thinking knobs are permissive at the type layer (`ThinkingConfig` accepts `effort` and `budget_tokens` together); translation to a provider's native shape is dialect-owned (`dialects/`). A dialect that cannot honor a field verbatim emits a `TranslationNote` (WARNING) — never silently drops caller intent. `EffortLevel` includes `"none"` (no deliberation), which has no position in `EFFORT_LEVEL_ORDER`; a per-model ceiling must never clamp into `"none"`. Adding a new effort level requires extending BOTH `EffortLevel` and `DeliberationLevel` in `types.py` — the import-time `_UNRANKED_EFFORT_LEVELS` check raises `RuntimeError` if the ranking misses a level. `ThinkingConfig` exposes both `active` (any knob set — gates param emission; effort="none" still sends an explicit disabled block) and `deliberating` (`active and effort != "none"` — gates thinking-block serialization; a dialect serializing persisted thinking blocks under `deliberating=False` sends a request Anthropic 400s).
- `LLMLifecycle` owns timeout and stall policy for every live provider call: each provider operation (dialect `complete()`, or each `next()` of the stream iterator) runs in a watcher thread bounded by `config.api.provider_response_timeout` (`lifecycle.py:_run_with_response_timeout`); exceeding it first re-checks the cancel event (a user halt surfaces as `GenerationCancelled`, not a stall), then calls the dialect's `abort_active_stream()` — every dialect implements it (closing the httpx response is the only cross-thread unblock — the worker is inside a socket read, so generator.close() would raise), then raises `ProviderStallError`. There is no model fallback — a stall or provider failure propagates. `ProviderStallError` and `ProviderProtocolError` are declared in `clients/llm/dialects/base.py`, not here.
- `LLMLifecycle` never returns a partial result: `_run()` raises `ProviderProtocolError` if the provider stream/completion ends without a `CompleteEvent`. When the provider calls a tool absent from the request (`ToolNotLoadedError`), the lifecycle synthesizes an `invokeother_tool` call (`stop_reason="tool_use"`) so the orchestrator loads the tool and re-invokes — it does not error out. The synthetic Result carries `dialect.current_partial_usage()` (streamed usage when any arrived; `None` means skip billing) and is cost-recorded via `_record_cost` like a normal completion.
- `ModelResolver` resolves exactly the five fixed `model_configs` routes (`primary`, `fast`, `batch`, `assessment`, `other` — names enforced by the route-name CHECK in `deploy/mira_service_schema.sql`). Callers pass `model_config=<route name>`; unknown route names raise. `ModelSelection.api_key_name` is `None` in memory for credentialless routes — the on-disk sentinel is `''` (`optional_api_key_name()` normalizes it); downstream code must never compare against the empty string.
- Per-route `effort` configured in a `model_configs` row is merged into the request's `ThinkingConfig` only when the caller did not already specify effort (`llm_provider.py:_build_request`). Caller-specified effort always wins over the route default.
- Adding a new dialect value is a blast-radius edit across this package and `dialects/` — the full ordered steps and skip-consequences are owned by `clients/llm/dialects/AGENTS.md` Rule 1. The package-level invariants: the `DialectName` literal (`clients/llm/types.py`) and the `dialect_name` CHECK constraint in `deploy/mira_service_schema.sql` must both exist before `ModelResolver` can resolve a route bound to the new dialect.
- `DialectRegistry` discovers concrete `Dialect` subclasses by walking `clients/llm/dialects/` at first `get()` and validates each candidate fail-loud (`_validate_dialect_class`): `dialect_name` must be a `DialectName` member, `native_thinking_fields` must be a tuple of `NativeField` values, `from_selection` must be a classmethod. Malformed dialects raise at boot, not first request. Re-exported classes are skipped — a dialect class must live in its own module to register.
- Cost recording is lifecycle-owned and inert by default: `_with_transport_metadata` stamps `ProviderMetadata` on every completed `Result` then calls `utils.cost_accumulator.record(result)`, keyed by the `model_configs` route name. `record()` is a no-op unless a request handler called `start()`.

## Files

- `types.py` — the typed neutral boundary: `DialectName`/`EffortLevel`/`StopReason` literals and their coerce validators (`coerce_dialect_name`, `coerce_effort`, `coerce_stop_reason`), frozen dataclasses `Request`, `Result`, `ThinkingConfig`, `Usage`, `ToolDefinition` (with `from_mapping` — unknown keys raise, typo suggestions for "description"), `ToolCall`, `ToolResult`, `ReasoningArtifact`/`ReasoningEntry`, and `RequestMetadata`/`ProviderMetadata`. Import-time invariant: `EffortLevel` minus `DeliberationLevel` must be exactly `{"none"}`. Mappings are frozen into `MappingProxyType`; sequences copied to tuples.
- `thinking.py` — dialect-translation contracts: `TranslationNote` frozen dataclass and `uses_adaptive_thinking(model)` (Claude 4.6+ regex on the model string decides adaptive vs budget thinking). Shared with `dialects/` imports.
- `events.py` — provider-neutral stream event dataclasses: `StreamEvent` base plus `TextEvent`, `ThinkingEvent`, `ToolDetectedEvent`, `ToolExecutingEvent`, `ToolCompletedEvent`, `ToolErrorEvent`, `CompleteEvent` (carries the final `Result`), `ModelStepCompletedEvent` (non-terminal per-step boundary for orchestrator persistence), `ErrorEvent`, `CircuitBreakerEvent`, `FileArtifactEvent`, and the `GenerationCancelled` exception. `ModelStepCompletedEvent` is not a stream terminator — `CompleteEvent` is.
- `lifecycle.py` — `LLMLifecycle`: one live provider request with `ProviderStallError` stall detection (with cancel-first re-check and cross-thread `abort_active_stream()` cleanup), cancel-event checks between events, no-fallback completion policy, `ToolNotLoadedError` recovery via synthetic `invokeother_tool` (usage + cost preserved), transport-metadata stamping, and the `cost_accumulator` hook (`_record_cost`).
- `resolver.py` — `ModelResolver.resolve()` and `ModelSelection` (carries `dialect_name`, `model`, `endpoint_url`, `api_key_name`, `max_tokens`, `effort`, `model_config_name`), plus `optional_api_key_name()` which normalizes the on-disk `''` sentinel to `None`. Sources route rows via `utils.user_context.get_model_config()`.
- `dialect_registry.py` — `DialectRegistry` with thread-safe, idempotent `discover()` walking `clients/llm/dialects/`; `_validate_dialect_class()` fail-loud validation; module-level `get_registry()` lazy singleton. Boot warms the registry (`main.py` lifespan calls `get_registry().discover()` after LLM provider init) so the anthropic SDK import cost lands at boot, not on the first LLM request.
- `tool_messages.py` — provider-neutral tool continuation message assembly: `assistant_message_from_result()` (reasoning blocks + text + tool_call blocks, thinking signatures and provider details as message metadata), `tool_result_messages()` (one `role="tool"` message per result), `invalid_tool_call_feedback_messages()` (invalid calls become user-role text feedback — never replayed as assistant tool_calls), and `append_tool_result_messages()` which strips orphaned tool_call/tool-result pairs to prevent provider 400s.
- `capabilities.py` — `Capabilities`/`Requirements` frozen dataclasses and `CapabilityError`; each dialect declares what it supports (batch, files, container_reuse, server_code_execution) and `validate()` raises before transport when a request needs an unsupported capability.
- `artifacts.py` — `FileArtifactSink` Protocol for persisting provider-produced file artifacts; implemented by `utils.artifact_store.UserArtifactStore`.
- `__init__.py` — re-exports the `types.py` surface (`Request`, `Result`, `ThinkingConfig`, literals, coercers). Not all modules are re-exported — `LLMLifecycle`, `ModelResolver`, and `DialectRegistry` are imported from their submodules directly.
- `dialects/` — provider serialization/parsing: the `Dialect` ABC, the four concrete dialects, and the provider error types (`ProviderStallError`, `ProviderProtocolError`, `ToolNotLoadedError`, `ProviderContextOverflowError`). See `clients/llm/dialects/AGENTS.md`.

## Wiring

- Request flow: caller → `LLMProvider.generate_response()`/`stream_events()` (`llm_provider.py`, sibling of this package) → `_validate_messages` → `ModelResolver.resolve()` → `_build_request` → `DialectRegistry.get(selection.dialect_name).from_selection()` → capabilities validation → `LLMLifecycle.complete()/stream()` → dialect transport → `Result`/`StreamEvent`s. Application code must enter through `LLMProvider`, never by constructing dialects or lifecycle directly.

- Stream consumers receive `events.py` dataclasses; the terminal `CompleteEvent.response` and every `ModelStepCompletedEvent.response` carry provider-stamped `ProviderMetadata` (dialect, model, endpoint, route name). `ProviderContextOverflowError` from the dialect is translated to `ContextOverflowError` at the `LLMProvider` boundary (`llm_provider.py`), not in this package.

- `resolver.py` reads route rows through `utils.user_context.get_model_config()`. Two cross-directory constraints bind `deploy/mira_service_schema.sql` and are enforced at its schema level, not here: (a) the `model_configs.name` CHECK admits exactly the five routes `primary`, `fast`, `batch`, `assessment`, `other` — `ModelResolver.resolve()` takes one of these names and `get_model_config()` raises on anything else, so application code must never hardcode a model/endpoint, only a route name; (b) the `model_configs.dialect_name` CHECK admits exactly `anthropic`, `openai`, `openrouter`, `groq` — the same four members as the `DialectName` literal in `types.py`, so a new dialect is a coordinated edit across both. Adding a route or dialect without updating the CHECK makes the offending `model_configs` row fail at schema-write time (loud, at deploy); extending `DialectName` without the CHECK (or vice versa) makes `coerce_dialect_name()` raise `ValueError` on resolve. The schema's `model_configs.effort` CHECK (`none`/`low`/`medium`/`high`/`xhigh`/`max`) likewise mirrors `EffortLevel`; a new effort level must extend all three.
