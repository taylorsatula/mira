# deploy/docker/scripts/ — container first-boot provisioning, the every-start database step, the health probe and restart unseal

## Files

- `container-setup.sh` — the TTY first-boot wizard, sourced into the entrypoint shell. Open it before adding a provisioning question or a provider to the menu.
- `healthcheck.sh` — the Docker HEALTHCHECK probe of the app's health route. Open it when a container reports unhealthy while the app is serving.
- `init-mira.sh` — the PID-1 entrypoint: first-boot gate, PostgreSQL and Vault provisioning, then `exec /init`. Open it before changing what a first boot writes or what a later start verifies.
- `mira-migrate.sh` — the every-start database step run, as the s6 `mira-migrate` oneshot. Open it before changing when a start refuses to proceed, or how an upgrade's backup is restored.
- `vault-unseal.sh` — restart-time unseal and root-token login, exec'd by the s6 `vault-init/up` oneshot. Open it when a start cannot reach an unsealed Vault.

## Wiring

- Container paths: the image COPYs the repo tree to `/opt/mira/app` and additionally places three scripts outside it — `/init-mira.sh`, `/opt/mira/container-setup.sh`, `/opt/mira/healthcheck.sh`; `vault-unseal.sh` and `mira-migrate.sh` are reached only at their in-repo paths. The repo tree itself is not bind-mounted, so editing the host tree changes no running container. Every helper `source` here is an absolute `/opt/mira/app/deploy/lib/...` path for the same reason the placements are explicit: a relative path resolves against the script's own directory and dies at container start. Counterpart: `deploy/AGENTS.md`.
- Boot chain: `init-mira.sh` provisioning → `exec /init` → s6 `user` bundle → `vault` → `vault-init` (`vault-unseal.sh`) → `mira-migrate` (`mira-migrate.sh`) → `mira`. The tree under `deploy/docker/s6-rc.d/` carries the ordering, one `dependencies.d/` entry per wait, so it enforces what this arrow chain means: reorder there and this line is stale, and reorder here alone and nothing moves. Provisioning finishes before `exec /init`, and the database step runs inside s6 rather than in the entrypoint, because PostgreSQL and an unsealed Vault exist only once s6 has started them; a step moved earlier waits on a service nothing has launched yet. Counterpart: `deploy/AGENTS.md`.
- Schema application: `init_postgresql` is an applier under `deploy/AGENTS.md`'s adopt-after-schema rule — `mira_service_schema.sql`, then `bootstrap_adopt.sql`, both under `ON_ERROR_STOP`. A new container applier that skips the adopt step leaves objects owned by the superuser, and the first `mira-migrate` step then fails as `mira_admin`. Counterpart: `deploy/AGENTS.md`.
- Database step: `mira-migrate.sh` → `scripts.migrate migrate`, then → `scripts.migrate restore "$STAMP"` when migrate exited 1 and this run's `/opt/mira/backups/<stamp>/manifest.json` is on disk. The exit code, the `restore` subcommand and the backup layout are one contract: renumbering the code (only `EXIT_STEP_FAILED` restores; refused and blocked exits do not) or renaming the subcommand leaves the container with a half-upgraded database, no restore, and `mira` never starting. Counterpart: `scripts/AGENTS.md`, which owns the CLI's subcommands, flags and exit codes.
- Sourced helpers: `deploy/lib/output.sh` (the `print_*` family) before `deploy/lib/services.sh` (`prefill_provider_model`) and before `deploy/lib/vault.sh` (`vault_initialize`); `vault.sh` sourced late, inside the Vault step; `deploy/lib/embedding_config.sh` (`resolve_embedding_schema_args`) only in the entrypoint. `output.sh` and `vault.sh` require `LOUD_MODE` set; both paths source their libraries first and assign `LOUD_MODE=false` immediately after, so neither has set it before the `source` lines run. `services.sh` requires `output.sh` sourced first and `OS` for its db and db_user checks, which only the wizard sets. Counterpart: `deploy/lib/AGENTS.md`.
- Health probe: `healthcheck.sh` → `GET /v1/api/health`, reading `.data.status` on the envelope and treating anything but `healthy` as a failure. Rename that field or the route path and every container reports unhealthy while the app serves normally. The route and its envelope are `cns/api/health.py`'s.
- First-boot inputs: `check_env_vars`, `setup_from_env_vars` and `init_vault`'s `MIRA_SMTP_*` block read the accepted env names, and that set is declared in `deploy/.env.example` — adding an input edits both in the same commit. The template lists no `MIRA_SMTP_*` entry today, so the six names the entrypoint accepts are documented nowhere an operator reads. Counterpart: `deploy/AGENTS.md`.
- Vault writes: `init_vault` writes `secret/mira/api_keys`, `secret/mira/database` and `secret/mira/services` on first boot only; the app reads them at runtime and the required-field set is its own manifest. A field added to the manifest needs a write here in the same commit, or a container install reports the gap and parks. Counterpart: `clients/AGENTS.md`.
- Database URL: `init_vault` percent-encodes the password and libpq is the single decoder (`clients/postgres_client.py:_parse_database_url`). Encode differently on either writer and the app authenticates with the literal `%XX` sequence. Counterpart: `clients/AGENTS.md`; the bare-metal twin is `deploy/postgresql.sh`.

## Rules

- First boot is keyed on `/opt/vault/init-keys.txt`, which only `vault_initialize` (`deploy/lib/vault.sh`) creates — nothing here writes it. Provisioning is first-boot-only, so a start where the key exists and `/var/lib/postgresql/17/main/postgresql.conf` does not aborts in `init-mira.sh:main`: the pgdata volume was lost or never mounted, and re-running initdb would quietly create a new database while the surviving Vault still describes the old one. Replacing that abort with re-provisioning is the failure it prevents.
- A sixth route seeded in `deploy/mira_service_schema.sql` keeps its seed endpoint and key name, because `init_postgresql` rewrites the five route names it knows to the collected provider — the new route fails at the first LLM call, so adding one edits that UPDATE in the same commit. A Vault key no route names is a defect, which is why no container route ends up naming `anthropic_key`. An empty model name aborts with guidance instead of installing routes that cannot resolve. Same mechanism as the bare-metal `deploy/postgresql.sh` rewrites, different bindings.
- Adding a provider is four coordinated edits: the menu arm in `container-setup.sh` (endpoint and key prefix), its model-defaulting `case` — a separate block on the same provider name, and a provider missing there has no verified default, so the wizard falls back to a free-text model prompt while the entrypoint's empty-model guard aborts an env-var install outright — the endpoint arm plus its model-defaulting arm in `init-mira.sh:setup_from_env_vars`, and the `prefill_provider_model` call site (pre-key for providers whose models list needs no key, post-key for the ones that do). A provider missing from the env-var endpoint arm falls to the `*)` default and binds Lunaroute's endpoint with the new provider's key; auth fails at the first LLM call. `prefill_provider_model` leaves the model unset when the provider does not serve the suggestion — that unset value is the fail-fast, so never replace it with a hardcoded default.
- `/opt/mira/systemone.env` is a start-path contract across four sites: written here in `init_vault` when a System One token was collected, written on bare metal by `deploy/finalize.sh`, sourced by the s6 `mira` runner with `MIRA_INJECTION_SCREEN_ENABLED` defaulting to 0, and mapped onto config fields by `config/config_manager.py`. All four move in one commit. Rename the variables at this site only and this container's install goes dark — the runner re-exports the old names at their default and the mapper still reads them — while bare-metal installs keep the screen on. `/opt/mira` is image-ephemeral, so a recreate against persisted Vault volumes skips provisioning entirely and the runner's default leaves the screen off. Non-secret values only; the token lives in Vault.

Elsewhere: this directory owns what a container does before and around the app, not the image that places these scripts, the supervision tree's own service files, or what the app does with the state provisioned here. The schema's contents are the SQL files' own; the required-field set a Vault check compares against is `rg 'REQUIRED_SECRET_MANIFEST'`; how a given step or provider arm came to exist is in `git log`. Every other destination this directory reaches is an edge — see `## Wiring` above.

## First boot, from `docker run` to the first served turn

The case that decides most of the Rules above, since every state the app needs is created here exactly once.

1. `/init-mira.sh` runs as PID 1. `is_first_boot` finds no `/opt/vault/init-keys.txt`, so `main` picks a path: with stdin and stdout both TTYs it sources `container-setup.sh`, which exports `CONFIG_*` and returns; otherwise `check_env_vars` enforces the one required variable and `setup_from_env_vars` fills the same exports.
2. `init_postgresql` fixes pgdata ownership, runs initdb when the cluster is absent, starts PostgreSQL temporarily, creates the two roles and `mira_service` behind existence guards, applies the schema and `deploy/bootstrap_adopt.sql` under `ON_ERROR_STOP`, refuses an empty model name, then rewrites all five routes. The guards are what let a boot that crashed mid-schema resume; the schema's own emptiness guard is what still stops a half-applied one.
3. `init_vault` starts Vault temporarily, calls `vault_initialize` — which writes `init-keys.txt` and the AppRole credential files — then puts the three secret paths and, when a token was collected, `systemone.env`. It stops Vault again. From here the first-boot gate reads "configured" for as long as the `/opt/vault` volume survives.
4. Both temporary servers are down, and the entrypoint fixes ownership on the volume mountpoints, which come up root-owned while the app runs as `mira` and PostgreSQL runs as `postgres`. Then `exec /init` replaces PID 1 with s6-overlay.
5. s6 starts `vault`; `vault-init` waits for it to answer and execs `vault-unseal.sh`, which finds the persisted unseal key, unseals, and logs in with the root token. `mira-migrate` waits for that unseal and for PostgreSQL, then runs the step runner with this run's backup stamp. It runs on a first boot too, over a schema `init_postgresql` has already applied.
6. `mira` waits again, reads the AppRole files `vault_initialize` wrote, sources `systemone.env` if it survived, and execs the app. Every credential it reads was written in step 3 under a name something in the tree still uses — which is why a renamed Vault field is a boot-time failure here rather than a later surprise.
