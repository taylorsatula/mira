# deploy/docker/scripts/ — bootstrap and supervision scripts for the MIRA Docker container

## Rules

- Scripts execute in-container under baked absolute paths, not their repo-relative paths. `deploy/docker/Dockerfile` maps `init-mira.sh` → `/init-mira.sh` (ENTRYPOINT), `container-setup.sh` → `/opt/mira/container-setup.sh`, `healthcheck.sh` → `/opt/mira/healthcheck.sh` (HEALTHCHECK), but `vault-unseal.sh` → `/opt/mira/app/deploy/docker/scripts/vault-unseal.sh` (in-tree location, referenced by `deploy/docker/s6-rc.d/vault-init/up`). Editing a script here does not change a running container until the image is rebuilt; also mind that the same Dockerfile COPY lines are the single source of the path mapping.
- `vault-unseal.sh` must not use `set -e`: `vault status` exits 2 when the vault is sealed, which is the expected "needs unseal" signal the script branches on. Adding `set -e` there turns normal sealed startup into a crash loop. Conversely `healthcheck.sh` and `init-mira.sh` DO use `set -e`; in `healthcheck.sh` the curl fallback (`|| echo '{"data":{"status":"error"}}'`) is what keeps a dead API from killing the check before it can exit 1 deliberately.
- First-boot detection is keyed on `/opt/vault/init-keys.txt`: absent → setup wizard, present → skip straight to `exec /init` (s6). `init-mira.sh:is_first_boot()` is the only gate; `vault-unseal.sh` independently refuses to run without the same file, so any change to where Vault init keys are stored must update both.
- The wizard and the entrypoint communicate through `CONFIG_*` environment variables. `container-setup.sh` is SOURCED (not executed) by `init-mira.sh:main` when a TTY is attached, so its `export CONFIG_*` statements must survive; a new credential must be collected and exported in `container-setup.sh`, and stored by the `vault kv put secret/mira/api_keys` / `secret/mira/database` / `secret/mira/services` calls in `init-mira.sh:init_vault` — skipping the Vault write means the key never reaches the running app. Non-interactive mode bypasses the wizard entirely: `init-mira.sh:check_env_vars` requires `MIRA_ANTHROPIC_KEY` and `MIRA_PROVIDER_KEY`, and `setup_from_env_vars` derives the same `CONFIG_*` values from `MIRA_*` variables with its own duplicated provider-endpoint table.
- The `model_configs` rewrite in `init_postgresql` runs on every provider path (Groq included) and retargets all five routes (`primary`, `fast`, `batch`, `assessment`, `other`) in one UPDATE: `dialect_name='openai'`, the collected `CONFIG_PROVIDER_ENDPOINT`/`CONFIG_PROVIDER_MODEL`, and `api_key_name='subcortical_key'` — the seeded `primary` row ships with an empty key name (the unauthenticated llama-server) and would 401 against the collected provider. It requires `CONFIG_PROVIDER_MODEL` to be non-empty (hard `exit 1` otherwise; the guard covers Groq too). `effort`/`max_tokens` stay as seeded.
- Model defaulting is a live check, never a hardcoded fallback: `prefill_provider_model` (`deploy/lib/services.sh`) queries the provider's models-list endpoint (chat-completions URL with the suffix swapped for `/models`, Bearer with the collected key when present) and prefills the suggested model only when the list confirms it; on a miss or a failed request it leaves `CONFIG_PROVIDER_MODEL` unset with a pointer to the provider's site, and the empty-model guard above aborts the install. Call sites: the wizard's OpenRouter model prompt (public endpoint, so it works before the key is collected), the wizard's post-key Groq check (step 2b), and `setup_from_env_vars` for Groq/OpenRouter in non-interactive mode.
- `init_vault` writes the provider key under `subcortical_key` only — after the container rewrite every `model_configs` row names it. `provider_key` is a bare-metal-installer concern (`deploy/postgresql.sh`, `deploy/python.sh`; `deploy/finalize.sh` reads it, and finalize.sh is sourced only by bare-metal `deploy/deploy.sh`, never inside the container). Do not add a `provider_key` write back to `init_vault`.
- The database password sentinel `changethisifdeployingpwd` appears in three coupled places: the wizard default, `setup_from_env_vars` default, and the `CREATE ROLE mira_admin/mira_dbuser ... PASSWORD` provisioning in `init_postgresql`. Roles are created with that literal because `pg_hba.conf` uses `scram-sha-256`; a passwordless role could never authenticate the `postgresql://` URLs stored in Vault. Changing the default requires touching all of them plus the `ALTER ROLE` conditional.
- `init_postgresql` is restart-safe by design: roles/database creation is guarded (`IF NOT EXISTS`, `createdb` only if missing) so a first boot that crashed before schema application resumes cleanly, while a crash mid-schema still fails fast on the schema's own emptiness guard. Do not replace the guards with unconditional DDL.
- Both `container-setup.sh` and `init-mira.sh` source `deploy/lib/output.sh` and `deploy/lib/services.sh` (plus `deploy/lib/vault.sh` inside `init_vault`) via in-container paths; the print helpers (`print_header`, `print_error`, etc.) and `vault_initialize` live there, not here.

## Files

- `container-setup.sh` — interactive first-boot wizard (Anthropic key, optional batch key, generic provider selection with endpoint/key-prefix table, provider model prompt — OpenRouter's default confirmed live against the public models list, Groq's model confirmed after key entry via `prefill_provider_model` — optional Kagi key, DB password). Sourced, never executed. Exports the `CONFIG_*` set consumed by `init-mira.sh`. Hardcodes `CONFIG_OFFLINE_MODE="no"`; on user rejection it re-execs itself via `exec /opt/mira/container-setup.sh`. Consumers: `deploy/docker/Dockerfile` (COPY), `init-mira.sh` (source).
- `init-mira.sh` — container ENTRYPOINT. Owns first-boot detection (`is_first_boot`, `has_tty`: both stdin and stdout must be TTYs), non-interactive env-var configuration (`check_env_vars`, `setup_from_env_vars` with live model prefill for Groq/OpenRouter), PostgreSQL provisioning (`init_postgresql`: initdb, pg_hba.conf, roles/db, schema via `deploy/mira_service_schema.sql`, all-five-routes model_configs rewrite, password override), Vault initialization (`init_vault`: temp server, `vault_initialize`, all three `vault kv put` payloads, optional `MIRA_SMTP_*` persistence), and the `/opt/mira/app/data` ownership fixup (volume mountpoints come up root-owned; the app writes as mira) — run on EVERY start, first boot or not, before `exec /init`. Consumers: `deploy/docker/Dockerfile` (ENTRYPOINT).
- `healthcheck.sh` — Docker HEALTHCHECK probe; curls `http://localhost:1993/v0/api/health`, exits 0 only when `.data.status == "healthy"`. Consumers: `deploy/docker/Dockerfile` (HEALTHCHECK).
- `vault-unseal.sh` — s6 oneshot body for `deploy/docker/s6-rc.d/vault-init/up`: waits are handled by the `up` wrapper, this script checks seal status, unseals with `Unseal Key 1` from `/opt/vault/init-keys.txt`, and logs in with the initial root token. Deliberately no `set -e` (see Rules). Consumers: `deploy/docker/s6-rc.d/vault-init/up`.

## Wiring

- First-boot flow order: `init-mira.sh` (ENTRYPOINT) → interactive: source `container-setup.sh`, or non-interactive: env vars → `init_postgresql` → `init_vault` → `exec /init` (s6-overlay). Reordering breaks everything: Postgres must be provisioned before the model_configs rewrite (which retargets all five routes on every provider path), and `init_vault` stores the DB URLs that embed the password chosen earlier.
- On container (re)start after first boot, s6 runs `vault-init` (oneshot, depends on the `vault` longrun) whose `up` polls `http://127.0.0.1:8200/v1/sys/health` up to 30s and then execs `vault-unseal.sh`. The `mira` longrun depends on `vault-init` and re-checks unseal itself (60s poll of `sys/health`, exit 1 on timeout) before reading `/opt/vault/role-id.txt` and `/opt/vault/secret-id.txt` and exporting them as `VAULT_ROLE_ID`/`VAULT_SECRET_ID` for the app. Those files are written once by `vault_initialize` in `deploy/lib/vault.sh` during first boot; a first boot that crashes before `vault_initialize` returns leaves them missing, and on every subsequent start `mira/run` fails loudly (exit 1) rather than silently degrading.
- The s6 dependency chain is `mira` → (`postgresql`, `valkey`, `vault-init`) and `vault-init` → `vault`; membership in the `user` bundle (`deploy/docker/s6-rc.d/user/contents.d/*`) is what starts everything. Adding a service that reads Vault secrets requires both a `dependencies.d/vault-init` entry and a `contents.d` line, or s6 starts it before Vault is unsealed and its run script fails.
- The Vault credential chain binds `vault-unseal.sh` to the post-unseal consumer: `vault-unseal.sh` authenticates with the initial root token from `/opt/vault/init-keys.txt`; the app itself never sees that token — it authenticates via the AppRole env vars `mira/run` exports. `vault_initialize` (in `deploy/lib/vault.sh`) creates the `mira` AppRole, the `mira-policy` policy scoped to `secret/*`, and writes the role-id/secret-id files.
- Shared libraries live outside this directory: `deploy/lib/output.sh` (print helpers, ANSI palette, requires `LOUD_MODE` set — both `init-mira.sh` and `container-setup.sh` set `LOUD_MODE=false` at top level after sourcing), `deploy/lib/services.sh` (requires `OS` set — `container-setup.sh` sets `OS`/`DISTRO`; `init-mira.sh` sources it but does not set `OS`), `deploy/lib/vault.sh` (requires output.sh and services.sh sourced first — satisfied by the source order in both files). Docs `docs/MANUAL_INSTALL.md` and `docs/OFFLINE_MODELS.md` do not reference these scripts (verified by grep), so this map is the only documentation of the Docker bootstrap contract.
