# deploy/docker/scripts/ — container bootstrap and supervision scripts: first-boot provisioning, the health probe, restart-time unseal

Elsewhere: s6 service tree, Dockerfile/image layers, volume topology — `deploy/AGENTS.md` · sourced helper contracts (`print_*`, `vault_initialize`, `resolve_embedding_schema_args`) — `deploy/lib/AGENTS.md` · schema contents and seeding — `deploy/AGENTS.md` (`deploy/mira_service_schema.sql`) · health-endpoint semantics — `cns/api/AGENTS.md` (`cns/api/health.py`) · injection-screen mechanism — `utils/AGENTS.md` (`utils/untrusted_content.py`); its config keys — `config/AGENTS.md` · bare-metal install flow — `deploy/AGENTS.md` (`deploy/config.sh`, `deploy/postgresql.sh`, `deploy/finalize.sh`) · how a wizard step or provider arm was introduced — `git log`.

## Rules

- First boot is keyed on `/opt/vault/init-keys.txt`, written only by `vault_initialize` (`deploy/lib/vault.sh`) — nothing in this directory creates it, so the gate's meaning lives outside these files. Provisioning (`init-mira.sh:init_postgresql`) is first-boot-only: a start where the key exists but `/var/lib/postgresql/17/main/postgresql.conf` is missing aborts in `init-mira.sh:main`, because the pgdata volume was lost or never mounted and re-running initdb would silently discard the database the surviving Vault describes. Never replace that abort with re-provisioning.
- One key, one model, five routes: `init_postgresql` rewrites the five seeded `model_configs` routes by name (`WHERE name IN ('primary','fast','batch','assessment','other')`) to the collected provider with `api_key_name = 'subcortical_key'` — a sixth route seeded in the schema keeps its seed endpoint and credential and fails at the first LLM call; adding one updates this UPDATE in the same commit. The schema seeds `primary` against `provider_key` (`deploy/mira_service_schema.sql`) — the bare-metal chat-tier credential this script never stores — and after the rewrite no route names `anthropic_key`; a Vault field without a reader is a defect. An empty `CONFIG_PROVIDER_MODEL` aborts with guidance rather than installing routes that cannot resolve. A new credential lands with its reader in the same commit: `systemone_key` is written only when a token was collected — the screen's remote provider reads it, and a screened install without it raises at first gated sidebar dispatch; with no token the screen stays off and external content is structurally wrapped (fail-closed either way).
- Adding a provider touches `container-setup.sh` twice plus `init-mira.sh`: the menu arm (endpoint, key prefix) and the model-prompt case (example model — a separate `case "$CONFIG_PROVIDER_NAME"` block; a default missing there soft-fails the wizard and env-var installs abort on the empty-model guard), the endpoint case in `init-mira.sh:setup_from_env_vars` (with its model-defaulting case), and the `prefill_provider_model` call sites (OpenRouter pre-key, Groq/Lunaroute post-key). A provider missing from the env-var case falls to the `*)` arm and silently binds Lunaroute's endpoint with the new provider's key; auth fails at the first LLM call. Model defaults are verified live by `prefill_provider_model` (`deploy/lib/services.sh`), which leaves `CONFIG_PROVIDER_MODEL` unset on a miss — never replace that with a hardcoded default.
- `/opt/mira/systemone.env` is a start-path contract across four sites: written here on first boot when a System One token was collected (`init-mira.sh:init_vault`), written on bare metal by `deploy/finalize.sh` (systemd `EnvironmentFile=`), sourced by `deploy/docker/s6-rc.d/mira/run` with `MIRA_INJECTION_SCREEN_ENABLED` defaulting 0; the app maps the variables in `config/config_manager.py`. A variable renamed in one site only leaves the others speaking the old name — rename just the env-file write here and this container's own install goes dark (`mira/run` re-exports the old name, default 0, and the mapper still reads it) while untouched bare-metal installs keep the screen on; all four sites move in one commit. Non-secret values only — the token lives in Vault.
- `MIRA_SMTP_*` is a first-boot input, never a runtime one: `init_vault` persists the values to `secret/mira/services`, and the mail sender reads Vault only (`auth/email_service.py`) — setting the vars on an existing container does nothing; the live remedy is `vault kv patch secret/mira/services smtp_host=... smtp_from=...`. The values are assembled as a bash array handed to `vault kv put`, never eval-rejoined — eval keeps the built-in quotes and word-splits a value on spaces, seeding a mangled relay credential.

## Files

- `container-setup.sh` — interactive first-boot wizard (TTY installs): provider menu, key-prefix validation, Kagi / DB-password / System One steps, summary, `CONFIG_*` exports consumed by `init-mira.sh`. Gotcha: sourced into the PID-1 shell — never `exec` it (replaces the entrypoint, ends the container) and never bare `exit`; the cancel path re-sources itself and `return`s so accepted exports unwind to `init-mira.sh`.
- `healthcheck.sh` — the Docker HEALTHCHECK probe: `GET http://localhost:1993/v0/api/health`, pass iff `.data.status` is `"healthy"` (envelope owned by `cns/api/AGENTS.md`, `cns/api/base.py`); an unhealthy response or dead socket yields no `data` and exits 1.
- `init-mira.sh` — PID-1 entrypoint: first-boot gate, TTY-vs-env-var dispatch (`MIRA_PROVIDER_KEY` the only required var), `init_postgresql` (roles `mira_admin` BYPASSRLS + `mira_dbuser`, `mira_service` DB, schema via `EMBEDDING_SCHEMA_ARGS`, the five-route rewrite, custom-password ALTERs), `init_vault` (`vault_initialize`, `secret/mira/api_keys|database|services` writes, `systemone.env`), every-start chowns for root-owned volume mountpoints, `exec /init` handoff. Entry: `main`, `is_first_boot`, `has_tty`, `check_env_vars` (the `MIRA_PROVIDER_KEY`-only-required contract), `init_postgresql`, `init_vault`, `setup_from_env_vars`. Gotcha: `systemone.env` is written only inside `init_vault` (first boot) and `/opt/mira` is image-ephemeral — a docker recreate with surviving Vault volumes skips provisioning and `mira/run`'s default turns the screen off; `deploy/docker/s6-rc.d/mira/run`'s comment says the gate re-provisions the file, and no code path does.
- `vault-unseal.sh` — restart-time unseal + root-token login, exec'd by `deploy/docker/s6-rc.d/vault-init/up` (Vault comes up sealed on every container start; the key persists on the `/opt/vault` volume, the seal state does not). Extracts `Unseal Key 1` / `Initial Root Token` from `/opt/vault/init-keys.txt`. Gotcha: no `set -e` by design — `vault status` exits 2 when sealed, the expected branch; adding `set -e` kills every sealed restart.

## Wiring

- Image placement (counterpart: `deploy/AGENTS.md`, `deploy/docker/Dockerfile`): `init-mira.sh` → `/init-mira.sh` (ENTRYPOINT), `container-setup.sh` → `/opt/mira/container-setup.sh`, `healthcheck.sh` → `/opt/mira/healthcheck.sh` (HEALTHCHECK CMD), `vault-unseal.sh` → `/opt/mira/app/deploy/docker/scripts/vault-unseal.sh` — the in-tree path `vault-init/up` execs; repo root → `/opt/mira/app`, so the sourced helpers and schema resolve under `/opt/mira/app/deploy/`.
- Boot chain: `/init-mira.sh` → provisioning → every-start chowns → `exec /init` → s6 `user` bundle: `vault` → `vault-init` (oneshot: waits for Vault HTTP, execs `vault-unseal.sh`) → `mira` (depends on postgresql, valkey, vault-init; waits for unsealed Vault, sources `systemone.env`, reads `/opt/vault/role-id.txt`/`secret-id.txt` written by `vault_initialize`, execs `main.py` as mira). Ordering: provisioning precedes `exec /init` — the longruns assume roles, schema, and Vault entries exist. Counterpart: `deploy/AGENTS.md`.
- Sourced helpers (counterpart: `deploy/lib/AGENTS.md`): `deploy/lib/output.sh` (print family, colors), `deploy/lib/services.sh` (`prefill_provider_model`; requires output.sh first), `deploy/lib/embedding_config.sh` (`resolve_embedding_schema_args` → `EMBEDDING_SCHEMA_ARGS`; container always `local` — the image ships the model), `deploy/lib/vault.sh` (`vault_initialize`; requires output.sh + services.sh + `LOUD_MODE`, which both entry scripts set false).
- Schema application (counterpart: `deploy/AGENTS.md`): `init_postgresql` provisions roles and `mira_service` before applying `deploy/mira_service_schema.sql` under `ON_ERROR_STOP` — the schema assumes both exist and targets an empty database; a first boot crashed mid-schema resumes at the role/DB guard, then fails fast on the schema's emptiness guard.
- Health probe: `healthcheck.sh` → `GET /v0/api/health` (`cns/api/health.py`, mounted at `/v0/api` in `main.py`); Docker reports the container healthy only while the app answers `data.status = "healthy"` (counterpart `deploy/AGENTS.md` — its Health-polls Wiring edge names this gate; envelope semantics owned by `cns/api/AGENTS.md`).
- Bare-metal mirrors (counterpart: `deploy/AGENTS.md`): route rewrite ↔ `deploy/postgresql.sh` (`OFFLINE_SQL`/`CHAT_SQL` — same UPDATE mechanism, different bindings; bare metal keeps `primary` on `provider_key`); DB-password URL percent-encoding is a two-writer contract (reader `clients/postgres_client.py:_parse_database_url`, libpq the single decoder) — encode differently on either writer and the app authenticates with the literal `%XX` sequence as the password; unseal logic ↔ `deploy/vault.sh`'s systemd `vault-unseal.service`; `systemone.env` ↔ `deploy/finalize.sh`.
- Vault entries written here, read by the app (counterparts: `clients/AGENTS.md`, `auth/AGENTS.md`): `secret/mira/api_keys` (`subcortical_key`, `kagi_api_key`, optional `systemone_key`), `secret/mira/database` (`admin_url`/`service_url`/`username`/`password`), `secret/mira/services` (`app_url` — required by WebAuthn (`auth/config.py`), `valkey_url`, `userdata_encryption_key`, `diagnostics_token`, optional `smtp_*`).
