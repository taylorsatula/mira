# deploy/lib/ — the sourced bash function libraries the host install phases, the updater, the standalone database tool, and the container bootstrap share

## Files

- `output.sh` — the palette and the print/run family the install, update, and container chains render through. Open it before adding a line of output or a command a deploy script runs.
- `repo_identity.sh` — the bash reader of `deploy/GITHUB_REPO`. Open it before adding a fetch site or changing anything that names the repository.
- `services.sh` — host mechanics whose correct spelling differs per platform and per service manager. Open it before hand-rolling a port check, a timeout, a hash, an elevation call, a launchd reload, or a PostgreSQL/Valkey lookup.
- `vault.sh` — the Vault initialize/reconcile state machine and the put policy every host-install credential write goes through. Open it before writing, moving, or backing up a secret.
- `config_file.sh` — the flat-YAML `--config` parser and its mapping onto the interview's `CONFIG_*`/`STATUS_*` state. Open it before adding a config key or changing what an existing key means.
- `context_window_config.sh` — resolves the chat model's context window from the endpoint's models list and derives the compaction trigger from it. Open it when an install resolves no window or a trigger looks wrong.
- `embedding_config.sh` — builds the five psql variables the schema needs to size the embedding space. Open it before changing how an embedding model or its dimensions reach the schema.
- `systemone_config.sh` — the reachability probe for the injection screen's System One model. Open it when that model, endpoint, or wire contract changes.
- `provenance.sh` — building the release artifact, and naming the commit a tree came from. Open it before cutting a release or changing how an install learns its provenance.
- `venv_stamp.sh` — the venv build stamp, so an update rebuilds a venv only when its inputs changed. Open it when an update rebuilds too much or too little, or when the comparison changes.
- `state_preserve.sh` — the one definition of the host-local state a code clear keeps, and of what a clear destroys. Open it before touching the preserve set, the install exclude, or the clear itself.
- `custom_export.sh` — saves the operator's own changes out of the install tree before a code clear, and classifies each against the incoming release when the caller names one. Open it before changing what an update saves, how the delta is computed, how a saved file is classified, or what the save notice says.
- `host_artifacts.sh` — generators for the files MIRA installs outside its code tree. Open it before changing an installed file that both a fresh install and every update write.

## Wiring

- Install chain: `deploy/deploy.sh` sources `output.sh` → `repo_identity.sh` → `services.sh` → `provenance.sh` → `venv_stamp.sh` → `state_preserve.sh` → `custom_export.sh` → `host_artifacts.sh` → `vault.sh` → `embedding_config.sh` → `context_window_config.sh` → `systemone_config.sh`, then the phase scripts, whose `Requires:` headers bind what they may call. `output.sh` must come first (every other lib prints and runs through it), `services.sh` before `provenance.sh`, `venv_stamp.sh`, `custom_export.sh`, `host_artifacts.sh`, and `vault.sh` (the last two reach `resolve_pg_unit`, `resolve_valkey_unit`, and `check_exists`), `repo_identity.sh` before `provenance.sh` and `host_artifacts.sh`, and `state_preserve.sh` before `custom_export.sh`; a lib sourced ahead of a function it calls fails at call time under `set -e`, not at parse time. Counterpart: `deploy/AGENTS.md`.
- Interview: `deploy/config.sh` sources `config_file.sh` on the `--config` path, and it is the only definition of `is_lunaroute_full_service`, which `apply_yaml_config`'s key-reuse arms call. A second sourcer of `config_file.sh` must supply that function itself, or those arms fail at call time — after elevation has already prompted. Counterpart: `deploy/AGENTS.md`.
- Update chain: `deploy/update.sh` sources the same set minus `vault.sh` and the three probe libs, then runs `export_custom_build` → `move_code_aside` → overlay → the `update <tag> @ <sha>` commit → `install_host_file`. The export must precede the aside move, because it reads the operator's files out of the live tree and the aside move is what takes them away; the unit and wrapper rewrite must follow the overlay, because it is generated from the new tree. Counterpart: `deploy/AGENTS.md`.
- Container chain: `deploy/docker/scripts/container-setup.sh` and `init-mira.sh` source these libraries by absolute `/opt/mira/app/deploy/lib/` path inside the released container tree, and `init-mira.sh` sources `vault.sh` late, inside its Vault step rather than at the top. Counterpart: `deploy/docker/scripts/AGENTS.md`.
- Vault seam: `vault_initialize` materializes `/opt/vault/role-id.txt` and `/opt/vault/secret-id.txt`; `deploy/finalize.sh` bakes them into the service environment and `deploy/vault.sh` re-syncs an existing unit when a re-run rotates them. The app-side consumer is `clients/vault_client.py`; counterpart: `clients/AGENTS.md`.
- Probe edges: `resolve_embedding_schema_args` and `probe_systemone` call `clients/embeddings_provider.py:describe_for_installer` and `clients/systemone_client.py:describe_for_installer`. A change to either side of either contract breaks fresh installs, so both sides move in one commit. Counterpart: `clients/AGENTS.md`.
- Embedding arg convergence: `resolve_embedding_schema_args` and `tests/fixtures/scratch_db.py:_embedding_args` both drive `clients/embeddings_provider.py:describe_for_installer` with `["describe", "local"]` and both turn its `<model> <dimensions>` line into the schema's five `embedding_*` psql variables, so a return-shape change is one commit across the producer and both consumers. Neither consumer may move alone: `read -r EMBEDDING_MODEL EMBEDDING_DIMENSIONS <<< "$described"` absorbs every token past the second into `EMBEDDING_DIMENSIONS`, and the `''|*[!0-9]*` case then refuses a value the endpoint did report, while the fixture's `model, dimensions = describe_for_installer(...).split()` unpacks and raises there. Counterpart: `tests/fixtures/AGENTS.md`.
- Window env chain: `resolve_context_window` imports no app code — it fetches the endpoint's models list with the install venv's interpreter — and its one edge across the boundary is a variable-name pair: `deploy/finalize.sh` writes `MIRA_CONTEXT_WINDOW_TOKENS` and `MIRA_COMPACTION_TRIGGER_TOKENS`, and `config/config_manager.py:API_INT_ENVIRONMENT_FIELDS` maps them onto `ApiConfig`. A rename is writer, mapper, and container default in one commit. Counterpart: `deploy/AGENTS.md`, which owns that env chain.
- Vault backup stamp: `deploy/postgresql.sh` defines `MIRA_LEGACY_STAMP` and initializes `MIRA_VAULT_BACKUPS` before its first `vault_put_with_backup` call, and `vault.sh` defaults neither. A second caller that skips them writes `..._legacy_` with an empty stamp, so every run's backup collides on one key. Counterpart: `deploy/AGENTS.md`.
- Install exclude: `write_install_exclude` emits the literal top-level names the running agent must never delete — `tools/implementations/bash_tool.py:_load_app_tree` reads them out of `.git/info/exclude` — so a name added to the heredoc widens what the agent may delete and a name removed from it narrows the protection. `deploy/AGENTS.md` owns that install-identity edge.
- TUI runner dependency: `ui/tui/migrate.py` builds its child env with `bash -c 'source deploy/lib/output.sh && source deploy/lib/services.sh && pg_bindir'`, so renaming or moving `pg_bindir` leaves `mira migrate` and `mira status` running with an empty path prepend instead of reporting a runner error. Counterpart: `ui/tui/AGENTS.md`.
- Elevation seam: `services.sh:seam_mode` and `utils/schema_migrations.py:superuser_prefix` compute the same three-way choice of how this host runs a command as the PostgreSQL superuser, and they change in one commit — a one-sided edit leaves shell and Python taking different arms on the hosts that use the edited one, surfacing as a refused backup. Counterpart: `utils/AGENTS.md`.
- Official-commit grammar: `custom_export.sh:MIRA_OFFICIAL_SUBJECT_ERE` and `ui/tui/migrate.py:OFFICIAL_SUBJECT_RE` are two spellings of the subject `provenance.sh:official_commit_message` writes. A divergence makes the two disagree about which commits are official, which moves the export's baseline. Counterpart: `ui/tui/AGENTS.md`.
- Palette export: `deploy/config.sh` and the phase scripts bake `STATUS_*` strings and status lines from `CHECKMARK` / `WARNING` / `DIM` / `RESET`, so renaming a palette constant in `output.sh` breaks rendering everywhere it is baked. Counterpart: `deploy/AGENTS.md`.

## Rules

- Adding a library takes the file here plus a `source` line in every host family that calls it — `deploy/deploy.sh` (host install), `deploy/update.sh` (updater), `deploy/deploy_database.sh` (standalone database provisioning), and the container scripts, which use absolute paths. A missing `source` line is `command not found` at the first call, mid-install, after elevation has already prompted.
- These libraries must all run on macOS's bash 3.2 — only `config_file.sh`'s header states that locally for itself, and no single file states it for the family — and a bash-4ism does not fail at parse time: the file sources clean and `${var,,}` dies `bad substitution` at first call, while `declare -A` degrades to indexed-array semantics with no error at all. `yaml_store`'s `eval`-generated `YAML_*` variables exist for this reason.
- `deploy/GITHUB_REPO` is the one spelling of the repository; `repo_identity.sh:mira_github_repo` and `utils/release_identity.py:GITHUB_REPO` read it and fail loud when it is missing or empty. Exactly two sites may spell it literally, because each runs before any checkout exists: root `install.sh` and `deploy/deploy.sh`'s bootstrap clone. A third literal at a fetch site keeps fetching from the old name after a rename; `provenance.sh:build_release_artifact` refuses to build a release either of the two disagrees with.
- Vault writes preserve what a previous install left. `vault_put_with_backup` covers every host-install secret except `secret/mira/database`, which uses `vault_put_if_not_exists` because a re-run at the sentinel password leaves the roles holding their previous password. Two blocks may write bare: `deploy/postgresql.sh`'s changed-password block (the legacy copy and the write) and the three first-boot writes in `deploy/docker/scripts/init-mira.sh`, where a fresh container has nothing to preserve. Any other bare `vault kv put` in the deploy tree discards the operator's only credential with no backup.
- The three install-time probes share one shape, which no single file states: the entry is the install venv's python — app code for the two `describe_for_installer` probes, an inline models-list fetch for the context window — a bearer token goes in on stdin rather than argv where `ps` would expose it, the output variables stay unset on failure with the reason on stderr, and the caller owns fatality (`deploy/postgresql.sh` aborts on embedding and System One failure; `deploy/finalize.sh` falls back for the context window). A probe that invents its own default instead ships an unverified value.
- Adding a `--config` key is six ordered edits in `config_file.sh` plus its consumers, each miss failing differently: the `case` whitelist in `parse_yaml_config` (else `Unknown config key` aborts), the required-keys loop and the `deploy/deploy-config.example.yml` line it corresponds to (else the abort names the missing key), the `__SET_ME__` placeholder loop (else the install aborts at parse time, after `deploy.sh` has already prompted for sudo), enum and conditional validation, the `apply_yaml_config` arm that turns the `YAML_*` value into `CONFIG_*`/`STATUS_*` — needed only for the keys a later phase reaches that way, since `overwrite_existing` and `stop_occupied_ports` have no arm and `deploy/config.sh` reads `$YAML_*` directly — and the same value from `deploy/config.sh`'s interview, because later phases cannot tell the two paths apart. A key with neither an arm nor a direct `YAML_<key>` reader parses, validates, and silently changes nothing. `anthropic_batch_key` is the whitelist-only case: no required-keys entry, no template line, no reader, so it is accepted and dropped.
- `state_preserve.sh` is the one definition of what a clear keeps and what it destroys, and nothing enforces that its two spellings agree: `MIRA_PRESERVE_NAMES` is read by `is_preserved_name`, `clear_code_preserving_state`, and `list_cleared_files` (through `_cleared_top_level_names`), while `write_install_exclude` writes its slash-anchored entries as a heredoc and never reads the array. A new preserve name is therefore two hand edits, and a name added to only one side fails one way or the other: in the exclude but not the array, it is protected from the agent and then deleted by the next clear — the operator's data gone at update time; in the array but not the exclude, the clear keeps it and the agent may still delete it. `list_cleared_files` is what `custom_export.sh` computes the operator's delta from, so a name it omits is a file the save never copies.
- `CONTEXT_WINDOW_COMPACTION_FRACTION_NUM`/`_DEN` here and the fallback arithmetic in `deploy/finalize.sh` are two spellings of one fraction. Change both in one commit, or an install that resolved its window and one that fell back trip live compaction at different points.

Elsewhere: this map does not own install-phase order, the application code these helpers configure, or the runtime consumers of the secrets they write. The interview that produces the same `CONFIG_*` state a `--config` file does is `deploy/config.sh`; the shape any helper took, and why, is `git log`. Every directory it reaches is an edge, and `## Wiring` above carries each one.

## Vault across a re-run

An install on a host that already runs MIRA lands on a Vault holding the previous install's credentials, and the three-way split between the helpers here is what keeps the operator's data reachable.

1. `vault_is_initialized` keys on `/opt/vault/init-keys.txt`. Present, and `vault_initialize` takes its reconcile half: unseal, log in with the root token from that file, enable KV2 / AppRole / policy only where they are missing, and re-derive the role-id and secret-id files only when they are absent — a rotated id would otherwise be written over a unit that still references the old one.
2. `deploy/postgresql.sh` decides the database write. A re-run that left the password at the sentinel default skips `ALTER USER`, so `vault_put_if_not_exists` must leave `secret/mira/database` alone: the roles still hold the previous custom password and the entry has to stay in step with them. A changed password goes through that script's direct-put block instead, which copies the old entry to its own `date +%Y%m%d%H%M%S`-stamped legacy key before writing and running `ALTER USER`.
3. Every other host-install entry goes through `vault_put_with_backup`, whose ordering is the safety mechanism: reachability of Vault first, existing value copied verbatim, path appended to `MIRA_VAULT_BACKUPS`, new values written, and an abort on any failed copy. Because `vault kv put` replaces the whole secret, the caller must pass every field worth keeping — which is why `deploy/postgresql.sh` reads `userdata_encryption_key` back out of Vault before rewriting `secret/mira/services`, since rotating that key leaves every per-user encrypted SQLite database unreadable.
4. One `MIRA_LEGACY_STAMP` — defined, with `MIRA_VAULT_BACKUPS`, in `deploy/postgresql.sh` before its first `vault_put_with_backup` call, because the library defaults neither — names one moment across all the `vault_put_with_backup` copies and the renamed-aside `mira_service_old_*` database; `deploy/finalize.sh` reports both at the end of the run, and each copy is recoverable with `vault kv get`. The changed-password legacy entry stands outside that stamp and outside `MIRA_VAULT_BACKUPS`, so `howtoaccess.txt` is its only report channel.
