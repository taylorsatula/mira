# deploy/lib/ — sourced bash helper libraries for the installer, updater, and container scripts: output, elevation, service and port management, the Vault state machine, install-time model probes

Elsewhere: install-phase order and which step calls which helper — `deploy/AGENTS.md` and the `deploy/*.sh` phase scripts · interview questions producing `CONFIG_*` — `deploy/config.sh` · the app's Vault client and runtime secret reads — `clients/AGENTS.md` (`clients/vault_client.py`) · env-var → config-field mapping — `config/AGENTS.md` (`config/config_manager.py`) · container first-boot flow — `deploy/docker/scripts/AGENTS.md` · how anything here got its shape — `git log`.

## Rules

- Every file here is a sourced function library — no main, no top-level execution; the four non-probe files state their sourcer guarantees in a `Requires:` header, and the three probe libs are self-contained — stderr only, no `output.sh` dependency. Load order is a chain: `output.sh` first, then `services.sh` (calls `print_*`, reads `OS`), then `vault.sh` (calls `print_*`, `run_with_status`, `check_exists`, reads `LOUD_MODE`). A new lib needs a `source` line in every host family that calls it — `deploy/deploy.sh` (host install), `deploy/update.sh` (updater), `deploy/deploy_database.sh` (standalone DB provisioning), the container scripts (absolute `/opt/mira/app/deploy/lib/` paths) — else its functions are `command not found` at call time.
- `LOUD_MODE` — set by `deploy/deploy.sh`'s `--loud`, default false — is the one verbosity switch: `run_quiet`, `run_with_status`, `show_progress`, and `install_python_package` branch on it, and `vault_extract_credential`'s init-keys debug dump is stderr-gated on it. Route new output through the `print_*`/`run_*` family — a helper that prints or runs commands bare floods the default quiet install and `--loud` stops meaning anything.
- Elevation is captured once by `acquire_sudo`: password read once into a 0700/0600 `SUDO_ASKPASS` temp helper (removed on exit, never an env var), a `sudo()` wrapper (`command sudo -A`) exported via `export -f sudo`, `MIRA_SUDO_READY` short-circuiting re-entry — because Homebrew clears the sudo ticket on every touchpoint (observed live on brew 7.0.7, per the comment in `acquire_sudo`). Every later sudo call rides the wrapper, and each brew-adjacent phase re-establishes with `ensure_sudo` (`deploy/dependencies.sh`, `deploy/postgresql.sh`) — a bare `sudo -n` right after a brew command fails and re-prompts, breaking unattended installs.
- `port_probe_status` is the single sanctioned port check (ladder lsof → ss → netstat; probing with lsof alone fails on stock Debian/Fedora images where only ss is guaranteed). Its return 2 means indeterminate — fail loud on it, never treat as free; treating 2 as free installs onto an occupied port.
- Vault writes preserve what a previous install left: `vault_put_with_backup` for every host-install secret except the database; `vault_put_if_not_exists` reserved for `secret/mira/database` (a re-run at the sentinel password skips the `ALTER USER` block, so the roles keep the previous custom password and the entry must survive untouched — `deploy/postgresql.sh` owns the reason). Two sanctioned direct-put sites exist: `deploy/postgresql.sh`'s changed-password database block and the container first-boot writes in `deploy/docker/scripts/init-mira.sh` (a fresh container has nothing to preserve). A failed preservation step aborts the install — replacing the operator's only credential with no backup is unrecoverable; any other bare `vault kv put` in the deploy tree is a defect (`rg 'vault kv put'`).
- Stay bash-3.x-safe — the floor `config_file.sh`'s header states for macOS; `yaml_store` writes `eval`-generated `YAML_*` variables instead of arrays for exactly this. A bash-4ism does not fail at parse time: bash 3.2 sources the file clean, then `${var,,}` dies `bad substitution` at first call — mid-install under `set -e` — and `declare -A` degrades to indexed-array semantics (silently wrong behavior, no abort); a parse-clean source proves nothing.
- Install-time probes share one shape: entry through the install venv's python (`describe_for_installer` in `clients/embeddings_provider.py` / `clients/systemone_client.py`, or an inline urllib probe), bearer tokens on stdin — never argv, where `ps` exposes them — and on failure the output variables stay unset, the reason goes to stderr, return 1; the caller owns fatality (`deploy/postgresql.sh` aborts on embedding/System One failure, `deploy/finalize.sh` falls back for the context window). A probe that invents its own default ships an unverified value — a wrong `EMBEDDING_DIMENSIONS` sizes every vector column in `deploy/mira_service_schema.sql` permanently.
- Adding a `--config` key is six ordered edits in `config_file.sh`, each miss failing differently: (1) the `case` whitelist in `parse_yaml_config` — else `Unknown config key` aborts; (2) the required-keys loop (the template `deploy/deploy-config.example.yml` ships one line per key) — else the abort names the missing key; (3) the `__SET_ME__` placeholder loop — aborts the install at parse time, after `deploy.sh`'s `acquire_sudo` has already prompted (elevation precedes the config parse); (4) enum/conditional validation; (5) the `CONFIG_*`/`STATUS_*` mapping in `apply_yaml_config` — an unmapped key parses, then silently does nothing, because later phases read only `CONFIG_*`; (6) the template line. The interview in `deploy/config.sh` must produce the same `CONFIG_*` value — later phases cannot tell the two paths apart.
- `CONTEXT_WINDOW_COMPACTION_FRACTION_NUM`/`_DEN` (8/10) and the fallback arithmetic in `deploy/finalize.sh` (`CONTEXT_WINDOW_TOKENS * 8 / 10`) are two spellings of the live-compaction fraction — change both in one commit or resolved-window installs and fallback installs trip compaction at different points.

## Files

- `output.sh` — the ANSI palette and display family the sourced deploy scripts render through (`deploy/deploy_database.sh` is the exception: bare `echo` with its own glyphs, sources no lib but `embedding_config.sh`). Entry: `RESET`/`DIM`/`BOLD` + color vars, `CHECKMARK`/`ARROW`/`WARNING`/`ERROR`, `print_header`…`print_info`, `run_quiet`, `run_with_status`, `show_progress`. Gotcha: `show_progress` takes a backgrounded PID (`$!`), not a command — the caller manages the `&` itself (`deploy/python.sh` pattern).
- `services.sh` — host mechanics. Entry: `port_probe_status`, `acquire_sudo`/`ensure_sudo`, `launchd_reload_agent` (bootout → settle-wait → bootstrap+enable; the one sanctioned launchd path), `resolve_pg_unit`/`resolve_valkey_unit` (existence-probed via `systemctl cat`, never distro-named — a wrong `Requires=` makes systemd refuse `mira.service`), `check_exists`, `start_service`/`stop_service`, `cpu_count`, `install_python_package`, `prefill_provider_model` (verifies a suggested model against the provider's models list; leaves `CONFIG_PROVIDER_MODEL` unset on doubt). `check_exists package` and `install_python_package` run relative `venv/bin/pip3` — valid only with cwd = the install dir (`deploy/python.sh` cd's first). Gotcha: dead branches, do not build on — `write_file_if_changed` (zero callers; the only `rg 'write_file_if_changed'` hit is its own definition), `check_exists` types `dir`/`command`/`db`/`db_user`, `stop_service`'s `pid_file`, `start_service`'s `background`.
- `vault.sh` — the Vault state machine and put policy. Entry: `vault_initialize` (full init vs reconcile, selected by `vault_is_initialized` = `/opt/vault/init-keys.txt` present), `vault_is_sealed` (`vault status`: 0 unsealed, 2 sealed, any other failure assumed sealed — the safe direction), `vault_unseal`, `vault_authenticate`, `vault_approle_exists`, `vault_extract_credential`, `vault_put_if_not_exists`, `vault_put_with_backup`, `vault_copy_secret` (verbatim field copy through the HTTP API — values never pass a shell). Gotcha: `vault_extract_credential` under `LOUD_MODE` cats the whole init-keys file — root token and unseal keys — to stderr; `--loud` on a shared terminal leaks them.
- `config_file.sh` — the `--config` path: flat-YAML parser (whitelist, required, placeholder, enum validation) plus `apply_yaml_config` mapping onto the interview's `CONFIG_*`/`STATUS_*` state. Entry: `parse_yaml_config`, `apply_yaml_config`, `yaml_fail`, `yaml_store`. Gotcha: not self-contained — `apply_yaml_config` calls `is_lunaroute_full_service`, defined in the sourcer `deploy/config.sh`; sourced into any other host, the key-reuse branches fail.
- `context_window_config.sh` — resolves the chat model's context window from the endpoint's models list (inline urllib probe through the venv python; accepts `context_window`/`context_length`/`max_input_tokens`), sets `CONTEXT_WINDOW_TOKENS` + `COMPACTION_TRIGGER_TOKENS`. Returns 1 with the reason on stderr; the `CONTEXT_WINDOW_FALLBACK_TOKENS` (200000, matching the `ApiConfig` default) is applied by `deploy/finalize.sh`, never here.
- `embedding_config.sh` — builds the five psql variables the fresh-install schema demands (`EMBEDDING_SCHEMA_ARGS`: provider, model, endpoint_url, api_key_name, dimensions); model and vector length come from the app — `clients/embeddings_provider.py:describe_for_installer` (local returns literals, remote embeds one probe text and reads the returned width). `EMBEDDING_VAULT_KEY_NAME` (`embeddings_key`) names the Vault key for the remote bearer; local leaves it empty — no Vault entry. Gotcha: `deploy/mira_service_schema.sql` refuses to run without the variables and its `RAISE EXCEPTION` names this file as their builder.
- `systemone_config.sh` — reachability probe for the injection screen's System One model, through the app's own wire contract (`clients/systemone_client.py:describe_for_installer`: one Noul question, typed `[0, 1]` answer validated). Sets no psql variables — System One is app-config only, nothing stored. `SYSTEMONE_VAULT_KEY_NAME` (`systemone_key`). Gotcha: the probe exists so an enabled-but-broken screen cannot park MIRA's boot gate on every start (`utils/power_on_self_test.py` `_check_injection_screen`).

## Wiring

- Host install: `deploy/deploy.sh` sources `output.sh` → `services.sh` → `vault.sh` → the three probe libs in one block, then sources the phase scripts (`config.sh`, `preflight.sh`, `dependencies.sh`, `python.sh`, `vault.sh`, `postgresql.sh`, `finalize.sh`) whose `Requires:` headers bind those guarantees. Lazy edge: `deploy/config.sh` sources `config_file.sh` only when `--config` was given. The updater (`deploy/update.sh`) sources `output.sh` + `services.sh` only — vault and probe helpers are undefined in the update path.
- Container flow: `deploy/docker/scripts/container-setup.sh` and `init-mira.sh` source these libs by absolute `/opt/mira/app/deploy/lib/` paths (the released tree inside the container); `init-mira.sh` sources `vault.sh` late, inside its Vault step. Counterpart: `deploy/docker/scripts/AGENTS.md`.
- Elevation chain: `acquire_sudo` runs at install start (`deploy/deploy.sh`; `deploy/preflight.sh` self-acquires when run standalone) → brew-adjacent phases call `ensure_sudo` (`deploy/dependencies.sh`, `deploy/postgresql.sh`).
- Vault seam to the runtime: `vault_initialize` materializes `/opt/vault/role-id.txt` + `/opt/vault/secret-id.txt`; `deploy/finalize.sh` reads them into the service environment (`VAULT_ROLE_ID`/`VAULT_SECRET_ID`) and `deploy/vault.sh` re-seeds the systemd unit when a re-run rotates them. The app-side AppRole consumer is `clients/vault_client.py` (`clients/AGENTS.md`); root owns the doctrine.
- Stamp and backup flow: `deploy/postgresql.sh` defines `MIRA_LEGACY_STAMP` + `MIRA_VAULT_BACKUPS` and makes every host-install put call; `vault_put_with_backup` appends the backup paths; `deploy/finalize.sh` reports them at install end beside the renamed-aside database note — the stamp covers the `vault_put_with_backup` copies and the rename; the changed-password legacy copy (`DB_LEGACY_KEY`, its own `date +%Y%m%d%H%M%S` stamp) never joins `MIRA_VAULT_BACKUPS` — `howtoaccess.txt` is its only report channel.
- Probe edges are bilateral with app code — a signature change on either side breaks installs, same commit: `resolve_embedding_schema_args` ↔ `clients/embeddings_provider.py:describe_for_installer` (also driving `tests/fixtures/scratch_db.py:_embedding_args`, the fixture leg — counterpart `tests/fixtures/AGENTS.md`) · `probe_systemone` ↔ `clients/systemone_client.py:describe_for_installer` (both Python entries document their lib caller in their docstrings); schema consumption `deploy/mira_service_schema.sql`. Structural callers, re-derive with the greps: `rg 'resolve_embedding_schema_args'` → `deploy/postgresql.sh`, `deploy/deploy_database.sh`, `deploy/docker/scripts/init-mira.sh` · `rg 'probe_systemone'` → `deploy/postgresql.sh` · `rg 'resolve_context_window'` → `deploy/finalize.sh` · `rg 'prefill_provider_model'` → the container scripts only · `rg 'port_probe_status'` → `deploy/config.sh`, `deploy/update.sh` · `rg 'launchd_reload_agent'` → `deploy/vault.sh`, `deploy/update.sh`, `deploy/finalize.sh`.
- Context-window chain: `resolve_context_window` → `CONTEXT_WINDOW_TOKENS`/`COMPACTION_TRIGGER_TOKENS` → env keys `MIRA_CONTEXT_WINDOW_TOKENS`/`MIRA_COMPACTION_TRIGGER_TOKENS` written by `deploy/finalize.sh` → mapped onto `ApiConfig.context_window_tokens`/`compaction_trigger_tokens` by `config/config_manager.py` (field defaults `config/config.py`; the trigger is read by live compaction). Env mapping owned by `config/AGENTS.md`.
- The palette is a shared export: `deploy/config.sh` bakes `STATUS_*` strings from `CHECKMARK`/`WARNING`/`DIM`/`RESET` at interview time — renaming a palette constant breaks phase-script rendering everywhere; `rg 'CHECKMARK'` for the set.

## Vault across a re-run

An install on a host that already runs MIRA lands on a Vault holding the previous install's credentials, and the flow is built so nothing of the operator's is lost. `vault_is_initialized` keys on `/opt/vault/init-keys.txt`; the file's presence selects `vault_initialize`'s reconcile half — unseal if sealed (`vault status` exits 2 sealed, 0 unsealed, any other failure treated as sealed, the safe direction), authenticate with the root token from the same file, enable KV2/AppRole/policy only where missing, and re-derive `/opt/vault/role-id.txt` and `/opt/vault/secret-id.txt` only when the files are absent.

Writes then split three ways for the database secret. A re-run that leaves `db_password` at the sentinel default skips the `ALTER USER` block entirely, so the database roles still hold the previous custom password, and `vault_put_if_not_exists` leaves `secret/mira/database` untouched to stay in step with them. A changed password takes `deploy/postgresql.sh`'s direct-put block: reachability proven first (`vault kv get` exits 2 both for no-value and for an unreachable Vault — an unreadable secret must never read as absent), the old entry copied field-by-field to `DB_LEGACY_KEY` (`secret/mira/database_legacy_$(date +%Y%m%d%H%M%S)` — a fresh stamp of its own, not `MIRA_LEGACY_STAMP`) with an abort if the copy fails, and only then the primary written and `ALTER USER` run, so Vault and PostgreSQL move from the same new value. Every other host-install path (`secret/mira/api_keys`, `secret/mira/services`) goes through `vault_put_with_backup`, whose internal ordering is the safety mechanism: reachability first, existing value copied verbatim to `${secret_path}_legacy_${MIRA_LEGACY_STAMP}` through `vault_copy_secret`'s HTTP JSON rewrite (values never pass a shell — newlines, quotes, backticks, `$` in a credential survive byte-identical), path recorded in `MIRA_VAULT_BACKUPS`, new values written; a failed copy aborts the install. `vault kv put` replaces the whole secret, so the caller must pass every field worth keeping — `deploy/postgresql.sh` reads `userdata_encryption_key` back out of Vault before rewriting `secret/mira/services`, because rotating that Fernet key would leave the per-user encrypted SQLite data unreadable (`utils/userdata_manager.py`).

One `MIRA_LEGACY_STAMP` names one moment in time across the `vault_put_with_backup` legacy copies and the renamed-aside `mira_service_old_*` database — `deploy/finalize.sh` reports both at the end, each backup recoverable verbatim via `vault kv get ${backup}`. The changed-password preserve stands outside both: its key carries a fresh `date +%Y%m%d%H%M%S` stamp, it never joins `MIRA_VAULT_BACKUPS`, and `howtoaccess.txt` is its only report channel.
