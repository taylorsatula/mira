# deploy/lib/ — shared bash helper functions sourced by every deploy script

All seven files are libraries: they are `source`d, never executed directly. There is no `__init__`-style entry point — `deploy.sh` sources six in fixed order (`output.sh` → `services.sh` → `vault.sh` → `embedding_config.sh` → `context_window_config.sh` → `systemone_config.sh`), and `deploy/docker/scripts/` re-sources them from `/opt/mira/app/deploy/lib/` inside the container (`vault.sh` only in `init-mira.sh`, sourced later in the flow, not at the top). `config_file.sh` is sourced conditionally by `config.sh` (only under `deploy.sh --config`).

## Rules

- Source order matters: `services.sh` calls `print_info`/`run_with_status` from `output.sh`, and `deploy/lib/vault.sh` calls functions from both. Sourcing `vault.sh` or `services.sh` before `output.sh` leaves functions undefined at call time. The `deploy/lib/vault.sh` header states "Requires: lib/output.sh and lib/services.sh sourced first".
- `LOUD_MODE` must be set before any lib function runs. `run_quiet`, `run_with_status`, `show_progress`, `install_python_package`, and `vault_extract_credential` all branch on it; it is initialized by each entry script that branches on it: `deploy.sh` (`LOUD_MODE=false` default, `--loud` sets true), `update.sh` (`${LOUD_MODE:-false}`, so an inherited value wins), and both docker scripts (`LOUD_MODE=false`); `deploy_database.sh` sources only `embedding_config.sh`, which never branches on it.
- `check_exists package` uses the relative path `venv/bin/pip3`, so it only works when the caller's CWD is the MIRA app root (the post-clone deploy context). Running it from elsewhere silently reports "not installed".
- Vault failure semantics in `deploy/lib/vault.sh` are encode-by-exit-code: `vault status` exit 0 = unsealed, 2 = sealed, other = error. `vault_is_sealed` treats errors as sealed (safe default). Do not "fix" the inverted-looking mapping.
- `vault_put_if_not_exists` preserves existing secrets — it skips the write if the path already exists, and calls `exit 1` (not `return 1`) when the write fails. Callers run it at top level; it is not safe inside a subshell where `exit` would not abort the script.
- `vault_extract_credential` prints the credential on stdout and debug output on stderr, so command substitution like `ROOT_TOKEN=$(vault_extract_credential "Initial Root Token")` (as in `finalize.sh`) captures only the value.

## Files

- `output.sh` — ANSI-colored print helpers (`print_header`, `print_step`, `print_success`, `print_warning`, `print_error`, `print_info`), command wrappers (`run_quiet`, `run_with_status`), and the background-job spinner `show_progress PID MSG`. Also defines the full color/element variable palette (`RESET`, `DIM`, `BOLD`, `GRAY`, `BLUE`, `GREEN`, `YELLOW`, `RED`, `CYAN`, `CHECKMARK`, `ARROW`, `WARNING`, `ERROR`) that other scripts interpolate directly in `echo -e` — the color codes are literal escape strings, so they only render inside `echo -e`/`printf '%b'`, not plain `echo`. Consumed by: every `deploy/*.sh` except the standalone `deploy/deploy_database.sh` (plain `echo`; it sources only `lib/embedding_config.sh`), plus `deploy/docker/scripts/container-setup.sh` and `deploy/docker/scripts/init-mira.sh`.
- `config_file.sh` — `--config` support: `parse_yaml_config` (flat `key: value` YAML, zero dependencies, bash 3.x safe; aborts on unknown/duplicate/missing keys, unfilled `__SET_ME__` placeholders, bad enums, mode-dependent empty fields; an empty `systemone_api_key` is allowed only for a lunaroute endpoint) and `apply_yaml_config` (maps `YAML_*` onto the interview's exact `CONFIG_*`/`STATUS_*` semantics — an empty subcortical/embeddings/System One key is filled from the chat key on the lunaroute gateway — and exports `MIRA_LLAMA_MAIN_URL`/`MIRA_LLAMA_SMALL_URL` for `postgresql.sh`'s offline SQL). Requires `output.sh` for `print_error`, and `apply_yaml_config` also calls `is_lunaroute_full_service` (defined in `deploy/config.sh`, the only sourcer, so it must be defined before `config_file.sh` runs). The key whitelist and required-key list here are the `--config` contract — see the parity Rule in `deploy/AGENTS.md`. Consumers: `deploy/config.sh` (only when `CONFIG_FILE` is set).
- `embedding_config.sh` — `resolve_embedding_schema_args PYTHON APP_DIR PROVIDER ENDPOINT MODEL API_KEY`: asks the app (`clients/embeddings_provider.py:describe_for_installer`, via `python -c` from `APP_DIR`) for the model and vector length — a live `/v1/embeddings` probe for `remote`, token passed on stdin — then sets `EMBEDDING_SCHEMA_ARGS` (the five `-v embedding_*=` psql arguments `deploy/mira_service_schema.sql` requires), `EMBEDDING_MODEL`, and `EMBEDDING_DIMENSIONS`; returns 1 with the reason on stderr. `EMBEDDING_VAULT_KEY_NAME` (`embeddings_key`) is the Vault field name the row's `api_key_name` points at. Needs a Python with MIRA's requirements (not sentence-transformers). Consumers: `deploy/postgresql.sh`, `deploy/deploy_database.sh`, `deploy/docker/scripts/init-mira.sh`.
- `context_window_config.sh` — `resolve_context_window PYTHON ENDPOINT MODEL API_KEY`: reads the chosen chat model's context window from the chat endpoint's models list (`GET <endpoint minus /chat/completions>/models`, token piped on stdin) and sets `CONTEXT_WINDOW_TOKENS` plus `COMPACTION_TRIGGER_TOKENS` at 80% of it (`CONTEXT_WINDOW_COMPACTION_FRACTION_NUM/DEN`). Sets **no psql variables** — the window is an app-config fact, not a schema one. Returns 1 with the reason on stderr and applies no fallback itself; `deploy/finalize.sh` owns the fallback (`CONTEXT_WINDOW_FALLBACK_TOKENS`) and writes both values into `/opt/mira/systemone.env`. Consumer: `deploy/finalize.sh`.
- `systemone_config.sh` — `probe_systemone PYTHON APP_DIR PROVIDER ENDPOINT MODEL API_KEY`: proves the injection screen's System One model answers before the install commits, by asking the app (`clients/systemone_client.py:describe_for_installer`, via `python -c` from `APP_DIR`) to run one Noul probe — token piped on stdin for `remote`, no Authorization header for `local`; returns 1 with the reason on stderr. Sets **no psql variables**: System One has no schema artifact (the deliberate divergence from `embedding_config.sh` — judgments are ephemeral, nothing is stored). `SYSTEMONE_VAULT_KEY_NAME` (`systemone_key`) is the Vault field name `deploy/postgresql.sh` Step 14 seeds for `remote` and `config.systemone.api_key_name` points at. Consumer: `deploy/postgresql.sh`.
- `services.sh` — idempotent system helpers: `port_probe_status PORT` (the ONE port-occupancy probe: lsof→ss→netstat ladder, 0=occupied/1=free/2=indeterminate — callers fail loud on 2; a clean minimal Linux often has only `ss`, stock macOS only `lsof`; call it as `cmd || rc=$?` — a free port returns 1 and a bare call trips `set -e`), `resolve_pg_unit`/`resolve_valkey_unit` (existence-based systemd unit-name resolvers — PGDG ships `postgresql-17.service`, Debian/Arch `postgresql.service`; Ubuntu/Debian ship `valkey-server.service`, Fedora/Arch `valkey.service`; a wrong name in `Requires=` or a stop call is a silent no-op or a refused unit), `cpu_count` (nproc → sysctl hw.ncpu; stock macOS has no nproc), `acquire_sudo` (one-time elevation capture at install start: `sudo -k` then probe, so the answer is "is this account NOPASSWD?" rather than "is a ticket still valid?"; NOPASSWD returns silently, else the password is read once and handed to a 0700 `SUDO_ASKPASS` helper in a temp dir removed on exit, and a `sudo()` wrapper adds `-A` so every later call — including after a Homebrew-cleared ticket — re-primes with no prompt) and `ensure_sudo` (silent re-prime after a cleared ticket; tty → fall back to a prompt, no tty → fail loud with the two real options — Homebrew CLEARS the credential ticket, observed live on brew 7.0.7), `launchd_reload_agent PLIST` (the ONE launchd load path: bootout → wait for teardown to settle → bootstrap + enable; bootstrapping during an in-flight bootout fails with "Bootstrap failed: 5: Input/output error"), `check_exists TYPE TARGET` (types: file, dir, command, package, db, db_user, service_systemctl, service_brew), `start_service` (systemctl/brew; its `background` branch is an unimplemented stub that errors) and `stop_service` (systemctl/brew/pid_file/port — the port variant shares the lsof→ss pid ladder), `write_file_if_changed`, `install_python_package`, `prefill_provider_model SUGGESTED` (live models-list check for the OpenAI-compatible provider being configured — derives `<endpoint>/models` from `CONFIG_PROVIDER_ENDPOINT`, sends the collected `CONFIG_PROVIDER_KEY` as Bearer when set, prefills `CONFIG_PROVIDER_MODEL` only when the provider's list confirms the model; requires output.sh sourced plus `CONFIG_PROVIDER_ENDPOINT`/`KEY`/`NAME` in scope). `db`/`db_user` checks require the `OS` variable (linux uses `sudo -u postgres psql`, else plain `psql`). Consumers: every `deploy/*.sh` except the standalone `deploy/deploy_database.sh` — `preflight.sh`'s header declares only `output.sh`, but it calls `acquire_sudo` from `services.sh` (deploy.sh sources services.sh before the phases, so the function is in scope) — plus both docker scripts.
- `vault.sh` — HashiCorp Vault lifecycle: `vault_is_initialized`, `vault_is_sealed`, `vault_extract_credential`, `vault_unseal`, `vault_authenticate`, `vault_approle_exists`, `vault_initialize`, `vault_put_with_backup`, `vault_copy_secret`, `vault_put_if_not_exists`. Hardcodes `/opt/vault/` paths (`init-keys.txt`, `role-id.txt`, `secret-id.txt`), the `mira-policy` AppRole policy (KV2 at `secret/`, TTL 1h/max 4h), and single-key-shares init (`-key-shares=1 -key-threshold=1`). `vault_initialize` is idempotent: on an initialized Vault it repairs unseal/auth/engine/AppRole state rather than re-initializing. `vault_put_with_backup` is the default writer for every entry but the database: a previous value is copied verbatim to `<path>_legacy_${MIRA_LEGACY_STAMP}` by `vault_copy_secret` (KV v2 HTTP API via stdlib `python3` — the CLI has no copy and no field-agnostic put; only the FIRST path segment is the mount, so `secret/mira/api_keys` is API path `secret/data/mira/api_keys`), then the new values are written to the primary path. It checks exit codes rather than trusting them: `vault kv get` answers 2 both for "no value" and for an unreachable Vault, so `vault status` is checked first and any other get failure aborts — treating an unreadable existing secret as absent would overwrite it with no backup, and a failed backup aborts for the same reason. Backup paths accumulate in `MIRA_VAULT_BACKUPS` for `finalize.sh`. `vault_put_if_not_exists` is reserved for `secret/mira/database` (comment states why). Consumers: `deploy.sh`, `deploy/vault.sh`, `deploy/postgresql.sh`, `deploy/finalize.sh` (`vault_extract_credential`), `deploy/docker/scripts/init-mira.sh` (`vault_initialize`).

## Wiring

- `deploy.sh` sources six in order `output.sh` → `services.sh` → `vault.sh` → `embedding_config.sh` → `context_window_config.sh` → `systemone_config.sh`, then orchestrates the script chain (`config.sh`, `preflight.sh`, `dependencies.sh`, `python.sh`, `vault.sh`, `postgresql.sh`, `finalize.sh`), each of which re-declares its own lib requirements in its header. The lib files themselves are stateless beyond the sourced-in variables.
- `config.sh` sources `config_file.sh` only when `CONFIG_FILE` is set (deploy.sh `--config`); it needs `output.sh`'s `print_error` and runs before any interactive prompt so validation failures surface before the sudo ask. The container scripts never source it — Docker bootstrap has its own wizard/env-var flow.
- In the container, `deploy/docker/scripts/init-mira.sh` and `container-setup.sh` source the same lib files from `/opt/mira/app/deploy/lib/` — `output.sh`/`services.sh` at the top of both, `vault.sh` only in `init-mira.sh` (before its `vault_initialize` call). Any lib change therefore ships into the image — there is no separate container lib copy to keep in sync.
- `install_python_package` (services.sh) depends on `show_progress` (output.sh) for its quiet-mode spinner; `vault_unseal`/`vault_authenticate` depend on `vault_extract_credential` and `run_with_status`. These are intra-directory edges only; the cross-script orchestration flow is owned by `deploy.sh`.

## Vault state machine

`vault_initialize` implements a two-branch state repair with an ordering constraint worth knowing before editing:

- Initialized path: unseal → authenticate → ensure KV2 engine (`secret/`) → ensure AppRole `mira` with `mira-policy` → ensure `/opt/vault/role-id.txt` and `/opt/vault/secret-id.txt` exist (each written only if missing).
- Fresh path: `vault operator init -key-shares=1 -key-threshold=1 > /opt/vault/init-keys.txt` (chmod 600) → then the same sequence, but writing role-id/secret-id unconditionally.

The unseal key and root token are read by `grep ... | awk '{print $NF}'` from `init-keys.txt`, which is why that file is the single source of Vault credentials for the whole deploy (`finalize.sh` re-extracts them later via two `vault_extract_credential` calls — "Initial Root Token" and "Unseal Key 1" — for the credential dump; the AppRole files `role-id.txt`/`secret-id.txt` are a separate mechanism read by `finalize.sh`'s systemd block and the macOS `run.sh` launcher). If the init output format or file path changes, `vault_extract_credential`, `vault_unseal`, `vault_authenticate`, and `finalize.sh`'s credential dump all break together.
