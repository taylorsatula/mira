# deploy/ — host-metal install pipeline, in-place updater, and container images over one fresh-install database contract

Elsewhere: sourced helper contracts, the Vault put policy, install-time probe shape, the add-a-`--config`-key recipe — `deploy/lib/AGENTS.md` · container first-boot gate, wizard, health probe, restart unseal — `deploy/docker/scripts/AGENTS.md` · VM modes, transports, sarcophagus restore — `deploy/vm/AGENTS.md` · the runtime Vault client and the AppRole read — `clients/AGENTS.md` (`clients/vault_client.py`) · env-var→config-field mapping — `config/AGENTS.md` (`config/config_manager.py`) · the health route and envelope — `cns/api/AGENTS.md` · the restart latch behind exit 75 — `utils/AGENTS.md` (`utils/self_restart.py`) · how a scar was learned — `git log`.

## Rules

- `deploy/deploy.sh:RELEASE_TAG` is the single source of truth for the release the installer deploys; both fetch sites pin to it — the bootstrap clone and `deploy/python.sh`'s release-asset download (`rg 'RELEASE_TAG'`). Cut a release by moving the constant, tagging, building and attaching the asset, publishing (`deploy/RELEASE.md`); root `install.sh` resolves the newest published release from GitHub's `releases/latest` redirect and hands off to that tag's `deploy/deploy.sh`. Consequence: an unreleased `RELEASE_TAG` (or a release without its asset) on main fails the installer at the fetch sites, and the reported `VERSION` always comes from the tagged tree — move the constant without tagging and installs report a version nothing serves.
- The `model_configs` rows seeded in `mira_service_schema.sql` ARE the deployment defaults — five routes at the lunaroute gateway, `primary` on `provider_key`, the aux four on `subcortical_key`; every departure is applied as UPDATEs against the live database after the schema apply (`deploy/postgresql.sh` `CHAT_SQL`/`SUB_SQL` hosted, `OFFLINE_SQL` offline; the container rewrite is owned by `deploy/docker/scripts/AGENTS.md`), never a per-install edit of the schema file. Empty `chat_model` aborts in `deploy/lib/config_file.sh` and again at Step 13 — `chat_endpoint` required in openai chat mode only (Step 13's anthropic branch hardcodes the endpoint); both run after `acquire_sudo`, so a headless `--config` install with a bad file dies at the elevation step before the validation can name the problem.; the aux rewrite fires only on departure from the lunaroute defaults, so a default install keeps `batch`'s `glm-5.3-flash-background` variant — a serving a single subcortical model cannot express. Consequence: a string-patched schema reverts on the next tagged deploy and installs lunaroute routes under another provider's key names — auth fails at the first LLM call.
- `mira_service_schema.sql` is deliberately not a migration: it creates no roles, no database, no compat DDL, and its precondition guard aborts on a non-empty target; its only non-baseline DDL is the step ledger `schema_migrations` + its `GRANT SELECT` to `mira_dbuser`, inside the `-- BEGIN/END GENERATED LEDGER DDL` sentinels (no RLS — `utils/power_on_self_test.py:_check_postgres_rls` must not expect it). `mira_admin` (BYPASSRLS, never CREATEDB) + `mira_dbuser` and the empty `mira_service` database (owned by `mira_admin`) are provisioned by tooling first (`deploy/postgresql.sh` Step 13, `deploy/deploy_database.sh`, container `init-mira.sh`), and every applier runs `bootstrap_adopt.sql` immediately after the schema, so all later database steps (`deploy/migrations/`, owned by `deploy/migrations/AGENTS.md`) run as `mira_admin` with no superuser. An install over a populated `mira_service` is a migration attempt, not an automatic rename: the database stays in place while `deploy/postgresql.sh` classifies it with the runner's `migrate --plan` (read-only) at the script's end — a shape this release knows (a `BASELINE` origin row) is printed verbatim with one typed OK, then carried forward in place by `migrate` (backup first, the interview's model routes applied, `MIRA_DATA_CARRIED` for finalize's note; a failed run leaves the database as the steps left it with the restore command and never installs fresh over it — rerunning resumes); a refused shape, a declined OK, or an unattended install (`--config`) falls back to `keep_database_aside` — renamed aside as `mira_service_old_${MIRA_LEGACY_STAMP}`, never dropped — then `apply_fresh_schema_and_bootstrap` + `apply_model_config_routes`. Vault entries a re-run replaces are copied aside before the write (policy owned by `deploy/lib/AGENTS.md`), and `deploy/finalize.sh` reports either the carried-forward success or the renamed database plus the Vault backup list at install end. Consequence: a re-install over an unknown shape always starts from an empty schema with the operator's data intact aside; treating the schema as upgradeable still defeats the emptiness guard and migrates nothing.
- Runtime-written state under `/opt/mira/app` must land under a slash-anchored excluded name — the exclude (`/data/ /venv/ /.env /logs/ /scratch/ /run.sh` plus the `/venv*/` `/tui-venv*/` globs and unanchored junk) and the code-clear preserve set are each one definition in `deploy/lib/state_preserve.sh` (contract owned by `deploy/lib/AGENTS.md`), shared by `deploy/python.sh` and `deploy/update.sh`; `.git` is preserved and never excluded. `tools/implementations/bash_tool.py:_load_app_tree` reads the exclude's literal entries as the top-level undeletable set (reader owned by `tools/implementations/AGENTS.md`). Consequence: a runtime write outside the excluded names reads as the operator's own change — `mira update` copies it to the Desktop export on every update and bash_tool treats it as deletable.
- `deploy/update.sh` never leaves an install between versions. The positional contract `<tree> <tag> [flags]` and the `MIRA_APP_DIR`/`MIRA_TUI_VENV`/`NIGHTLY`/`NIGHTLY_SHA` env are fixed — an installed pre-mechanism updater invokes the new tree's script with exactly these; `--rebuild-venvs-only` is the dedicated venv-rebuild fast path (no release fetch, no code swap, no database steps, no consent gate — it rebuilds both venvs from the installed tree, extras re-detected from the old venvs, stamps written last). Order: update lock (an update-level `mkdir` lock at `<parent>/.update-in-progress` acquired before any phase work — two updaters at once destroyed each other's venvs and left the install unbootable; a second updater waits 120 s then refuses exit 3 with nothing changed, a dead holder's lock is taken over by an atomic mv that re-verifies the pid (a cross-account holder is NEVER taken over — kill -0 cannot prove another user's holder dead, so the waiter refuses instead; the lockdir is mode 755 so every account can read the holder's pid/uid), an account that cannot write the lock's parent at all refuses exit 1 with that truth — never the held-lock message (a second-account update on an install-owner-owned `/opt/mira` otherwise waited 120 s being told a nonexistent update was running), and the holder releases it as the LAST action of its exit trap so the minutes-long rollback stays serialized) → preflight (tree shape, version no-op unless `NIGHTLY`, a non-git or baseline-less install refused — a git dubious-ownership refusal on a second account gets its own message naming the `git config --global --add safe.directory` remedy, because the .git is present and merely untrusted, and a really missing .git keeps the reinstall message — the release SHA resolved) → extras detection → stamp-gated venv builds while the server runs → consent (the release's own runner computes `migrate --plan` read-only; a refusal, no terminal, or no superuser seam (`deploy/lib/services.sh:seam_mode`, owned by `deploy/lib/AGENTS.md`) exits 3 with nothing changed — the no-seam refusal is platform-aware (Darwin names the not-a-superuser cause and the account that must run it; Linux keeps the terminal/password remedy) — anything that changes the database needs Y) → one `acquire_sudo` (Linux; macOS only when `/usr/local/bin/mira` is not writable) → stop → save (custom-build export + venv drift; failure restarts the old service with nothing changed) → swap rebuilt venvs + TOAST refresh → `move_code_aside` + overlay + `update <tag> @ <sha>` commit + `mira` wrapper and (Linux) systemd unit rewrite when their bytes differ (`deploy/lib/host_artifacts.sh`) → durability barrier (`run_with_status … sync` — everything above was page-cache-only, and a power cut inside the minutes-long database phase below left zero-byte program files that destroyed every recovery path) → phase 6.5 `scripts.migrate migrate --stamp <STAMP>` on the new code (the runner backs up to `<parent>/backups/<STAMP>/` before its first change), then `scripts.migrate reconcile` (drops `MIRA_*` settings nothing reads — `utils/env_reconcile.py`) → restart + 600 s health poll for the new `VERSION` + `status --json` at the release head → drop asides. A supervisor-less install (no systemd unit, no launchd plist) starts via `${APP_DIR}/run.sh` detached — `start_mira_service`/`start_command` carry those arms, and the port-kill stop still finds it — and the success-path aside cleanup is non-fatal (a failed `rm -rf` warns and preserves the aside; a completed update is never reported failed). The database phases (3.5 plan, 6.5 migrate/reconcile, 7 status) refuse on a non-canonical `MIRA_APP_DIR` — the connection target is the host's Vault AppRole, which no `MIRA_*` override scopes, so a throwaway root can never touch the host install's database (the twin guard lives in `ui/tui/migrate.py`). Any exit after the stop that is not success runs `on_exit`: stop the new version, `restore_database` from this run's backup with the NEW code (only it knows the new steps) — a failed restore leaves MIRA stopped with the runner's printed commands — then code back from the aside, HEAD reset with `update-ref`, the saved `.git/index` restored, TOAST shim, swapped venvs, the settings file, and the old `mira` wrapper and unit put back (filesystem state, not flags, decides each venv undo), old version restarted and health-polled. Consequence: a step inserted after the stop without its undo in `rollback_install` leaves the install half-updated on that step's failure; a step inserted before the stop needs no undo. update.sh's own header restates this phase list for by-hand invokers, who see no maps — a phase change updates both in the same commit.
- torch, sentence-transformers, and the playwright package are deliberately absent from `requirements.txt` (the "not listed here" block): `deploy/python.sh` installs them gated on config (`CONFIG_EMBEDDING_PROVIDER=local`, `CONFIG_INSTALL_PLAYWRIGHT=yes`), `deploy/docker/Dockerfile.base` installs all three unconditionally (an image has no config gate), and `deploy/update.sh` redetects the choice from the old venv — the only record of it the updater can read (nothing else on disk says the install pulled them). Consequence: moving one into `requirements.txt` drags PyTorch onto every remote-embedding install; forgetting an installer site makes the next update silently strip the extra from that install class.
- Vault and MIRA each land on a supervised, auto-unsealed start path on both supervisors, systemd and launchd in parity: `deploy/vault.sh` writes `vault.service` (Restart=on-failure) / `com.mira.vault` (RunAtLoad+KeepAlive) plus `vault-unseal.service` (oneshot, After+Requires vault) / `com.mira.vault.unseal` on every host; `deploy/finalize.sh` adds `mira.service` (Restart=on-failure — the exit-75 respawn, mechanism owned by `utils/AGENTS.md`) when opted in / `com.mira.app` (KeepAlive SuccessfulExit=false) always on macOS. launchd has no ordering, so the bounded waits live inside the generated artifacts (`/opt/vault/unseal.sh` 60 s, `run.sh`'s seal-status poll). Stopping is `bootout`, never kill — KeepAlive resurrects a killed process mid-swap. Consequence: a bare backgrounded process survives neither logout nor reboot while the install still reports the service running.
- An installer input exists in both spellings or neither: the `deploy/config.sh` interview question and the `deploy-config.example.yml` key, plus its `parse_yaml_config` whitelist/required/placeholder/mapping edits — the six-step recipe owned by `deploy/lib/AGENTS.md`. Later phases read only `CONFIG_*`; `""` is the interview's Enter-to-skip, so the install proceeds on `PLACEHOLDER_*` values and the final banner explains the Vault fixup. Vestigial exception: `anthropic_batch_key` sits in the whitelist only — no interview question, no template key, absent from the required/placeholder loops, mapped by nothing (`CONFIG_ANTHROPIC_BATCH_KEY` only ever holds placeholders; no phase reads it) — a real batch key is accepted and silently dropped; do not build on it. Consequence: an interview-only input is unreachable for unattended `--config` installs; a YAML-only key silently diverges from every interactive install.

## Files

- `deploy.sh` — entry point: flag parse (`--loud`, `--config`, `--local` — cwd captured at parse time, before any phase cd's), `RELEASE_TAG`, bootstrap clone when `lib/output.sh` is absent (the curl'd-standalone case), then `acquire_sudo` and the phase sourcing chain (Wiring). Every phase is sourced, never executed — its `Requires:`/`Sets:` header is the contract, and `set -e` means a phase failure aborts before later phases run half-fed.
- `config.sh` — the interview and pre-flight: OS/DISTRO detection, 10 GB disk floor, existing-install class-aware prompt (`YAML_overwrite_existing` under `--config`): a tree carrying `deploy/update.sh` is named a REINSTALL with the `mira update` steer, a pre-floor tree a MIGRATION; both state the preservation facts (database renamed aside if not carried forward, never deleted; Vault entries copied aside; per-user data kept), port sweep 1993/8200/6379/5432 via `port_probe_status` with occupied-port stops (`resolve_pg_unit`/`resolve_valkey_unit` on Linux; launchd bootout for Vault on macOS), then the interview: offline-llama branch, LunaRoute one-key shortcut (`is_lunaroute_full_service` — one key covers chat/subcortical/embeddings/System One), Kagi, embeddings, injection screen, DB password, name, timezone (`detect_system_timezone` mirrors `utils/timezone_utils.py`'s `get_default_timezone`), Playwright, supervision. Sets `CONFIG_*`/`STATUS_*`/`OS`/`DISTRO`. Gotcha: `--config` applies before OS detection, so the macOS patch after detection re-forces `CONFIG_INSTALL_SYSTEMD="no"` — move it and `--config` on macOS desyncs from the interview.
- `preflight.sh` — validation display, root refusal, `acquire_sudo` (no-op when deploy.sh captured it; self-acquiring standalone), background sudo keepalive re-priming every 60 s.
- `dependencies.sh` — system packages per distro, plus llama.cpp for offline mode (`CONFIG_BUILD_LLAMA_CPP=no` skips the build for a remote llama-server). Sets `PYTHON_VER` (3.12 floor); `require_pg_floor 17` after the distro chain mechanically enforces the PostgreSQL floor (Arch installs an unpinned `postgresql`, so its major is only checked, never pinned). Distro pins with teeth: Debian asks `valkey-server` never `valkey` (Ubuntu ships no metapackage), pins `postgresql-17*` and never an unversioned `postgresql-contrib` (it resolves to the distro major, whose auto-created cluster races port 5432); Fedora requires 41+ and x86_64 (PGDG publishes nothing else). Gotcha: data-dir and `pg_hba` guards must stay `sudo test`/`sudo grep` — postgres-owned 0700 dirs make unprivileged tests read false; that exact bug left the Fedora scram edits dead code. Every distro branch also installs `acl`: the update's backup grants the postgres user read of its dump with `setfacl` (`utils/schema_migrations.py:take_backup`) and refuses to start the upgrade without the tool.
- `python.sh` — app install and Python env: on a reinstall over an install repo, the custom-build export (`export_custom_build`, aborting before the clear on failure) then `clear_code_preserving_state --sudo`; the release asset (`mira-<version>.tar.gz`, `RELEASE_COMMIT` asserted 40-hex — a missing asset is fatal, the auto-archive is never fetched) or the `--local` tree; the install git repo (init, `write_install_exclude`, `install <tag> @ <sha>` commit — SHA from `resolve_local_sha` for `--local`, else `RELEASE_COMMIT`, else `resolve_release_sha`; all three failing is fatal); venv + TOAST `.pth` + build stamp written LAST (after the optional-extras install — a stamp naming unwritten extras would lie), Step 5b TUI venv at `/opt/mira/tui-venv` + stamp (outside `/opt/mira/app`, so code clears never touch it; `deploy/finalize.sh` wires `/usr/local/bin/mira` onto it), local embedding-model download, Playwright gated on config. Gotcha: Chromium presence is decided by `playwright install chromium` itself (build-specific, idempotent) — a directory-existence pre-check skipped the download for a stale cached build.
- `vault.sh` — Steps 8–11: Vault binary (Linux: pinned zip + persistent SELinux labels via `semanage`+`restorecon`, never `chcon`; macOS: brew verify), `/opt/vault` layout, `vault.hcl`, service supervision (Rule above), wait-ready, `vault_initialize` (owned by `deploy/lib/AGENTS.md`), AppRole re-sync into an existing `mira.service` (sed on its `Environment` lines when a re-run rotates ids), unseal script + supervision — macOS: `/opt/vault/unseal.sh` user-owned (launchd runs it as the user); Linux: `/usr/local/sbin/mira-unseal.sh` root-owned 700 via `install(1)` (the root oneshot must not exec from the MIRA_USER-owned `/opt/vault` — a dir owner can replace any entry; Fedora: labeled `bin_t` by a local fcontext rule — services cannot exec the path's default type; sarcophagus stages/restores it with the units — `deploy/vm/AGENTS.md`). Sets `VAULT_ADDR`.
- `postgresql.sh` — Steps 12–14: macOS keg-only client PATH prepend (one resolver, every later psql call); readiness wait; role provisioning at the sentinel password (roles always carry one — the URLs stored in Vault present a password under scram; `mira_admin` gets BYPASSRLS); existing-database classification with the rename-aside fallback (Rule); embedding resolve + System One probe (gated on `CONFIG_INJECTION_SCREEN=yes` — an enabled-but-broken screen would park the boot gate, `utils/power_on_self_test.py`); schema apply under `ON_ERROR_STOP` with the psql tail printed on failure; `bootstrap_adopt.sql`; after Step 14, `scripts.migrate migrate` (stamps the fresh install at the release head; fatal on nonzero); route rewrites (Rule); custom-password block (URL password percent-encoded — a two-writer contract with the container's, reader `clients/postgres_client.py:_parse_database_url`; legacy copy at `DB_LEGACY_KEY` before the primary store, `howtoaccess.txt` after it, ALTER pair last — an ALTER failure aborts with the roles still on the old password while `secret/mira/database` already holds the new one: the running app reads the new password and fails auth, and the legacy copy is the recovery path); Step 14 Vault writes (Wiring). Gotcha: the changed-password legacy copy keys on its own `date +%Y%m%d%H%M%S` — not `MIRA_LEGACY_STAMP` — and never joins `MIRA_VAULT_BACKUPS`, so `deploy/finalize.sh`'s kept-credentials list omits it; only the install-time print and `howtoaccess.txt` name it.
- `finalize.sh` — supervision and handoff: context-window resolve through `deploy/lib/context_window_config.sh` (the 200000 fallback is applied here, never in the lib; compaction trigger at 80%); `/opt/mira/systemone.env` (non-secret values only — timezone, name, window vars, screen + System One); `mira.service` from `deploy/lib/host_artifacts.sh:render_mira_unit` (resolved `Requires=` units, AppRole env, `Restart=on-failure` for exit 75; `deploy/update.sh` regenerates it from the same generator); `run.sh` launcher for macOS and declined-systemd Linux (PATH for launchd's minimal env, 120 s seal-status wait); `com.mira.app` LaunchAgent + 600 s health poll; `/usr/local/bin/mira` from `deploy/lib/host_artifacts.sh:render_mira_cli` (the generator `deploy/update.sh` rewrites it from); one-time credential dump `~/MIRA_credentials.txt`; cleanup; `/opt/vault` hardening; degraded-mode banner (missing subcortical key = every-turn extraction no-ops); legacy-stamp reporting. Gotcha: `run.sh` sources `systemone.env` under `set -a` — systemd's `EnvironmentFile=` exports natively, a plain `.` does not; without it the app never sees the vars and the boot gate parks.
- `update.sh` — the machine half of `mira update` (executed by `ui/tui/update.py`; hand-runnable as `bash <release-tree>/deploy/update.sh <tree> <tag> [--rebuild-venvs] [--rebuild-venvs-only] [--adopt-drifted]`; exit 0 updated/cancelled, 1 failed and put back (or parked), 3 needs a terminal or the operator's decision or another update holds the lock — all three leave nothing changed): phase order and the rollback contract are the in-place-update Rule above; log at `<app>/logs/update-<STAMP>.log`. Gotcha: service control applies only to the canonical root `/opt/mira/app` — `MIRA_APP_DIR`/`MIRA_TUI_VENV` overrides point at a throwaway root so verification never stops the real install. The standalone commands' service stop/start (`mira restore`, the parked-service start after `migrate`) is the TUI twin — `ui/tui/AGENTS.md`.
- `GITHUB_REPO` — the repository spelling (`owner/name`), one line; readers and the one-spelling rule owned by `deploy/lib/AGENTS.md`.
- `deploy_database.sh` — standalone executable for a hand-provisioned fresh PostgreSQL; never called by `deploy.sh`: superuser detect, existing-DB refusal, role/DB provisioning + schema apply through `deploy/lib/embedding_config.sh` (`MIRA_PYTHON`, `MIRA_EMBEDDING_*`; bearer tokens read interactively), verification queries. Gotcha: writes no Vault entries — it prints the manual `vault kv put` steps and the `scripts.migrate migrate` run instead.
- `mira_service_schema.sql` — the fresh-install database contract — psql is the only applier (the `\if`/`\set` guard block aborts under a raw SQL client; `tests/fixtures/scratch_db.py` routes here on that failure): five psql embedding variables (the guard names `deploy/lib/embedding_config.sh` as their builder), emptiness precondition, seeds for `model_configs`/`usage_pricing` (NULL prices fall through to `utils/cost_accumulator.py` fallbacks)/`embedding_config` (singleton, UPDATE/DELETE refused once any vector exists — the model and dimensions are permanent for the install), `users` with the `provision_baseline_persona` trigger (a user row without Persona revision 1 cannot exist, local-session bootstrap included), `heartbeat_armed_users` (dispatcher presence only; briefs live in per-user SQLite), per-table RLS policies keyed to `app.current_user_id`, least-privilege grants (`global_memories` revoked from the runtime role — reads go through the `global_memories_runtime` security-barrier view), `active_user_identity`/`resolve_active_user_identity` for cross-user domaindoc lookups. Gotcha: the seed rows are the deployment defaults — reconfigure via the Step-13 UPDATEs, never by editing this file.
- `bootstrap_adopt.sql` — the ownership bootstrap: creates the ledger (`CREATE TABLE IF NOT EXISTS`, same generated sentinels as the schema), transfers every non-extension table/view/sequence/function in `public` to `mira_admin`, `GRANT CREATE ON SCHEMA public`; idempotent, stamps nothing. Superuser only, through psql. Callers: `rg 'bootstrap_adopt.sql' deploy tests utils`. Gotcha: extension members stay with the superuser — moving them breaks `ALTER EXTENSION UPDATE` and dump/restore.
- `mira_blog_schema.sql` — standalone `mira_blog` posts schema (mira_blog_owner/reader/writer roles, `posts` table, default privileges). No in-repo caller; operator-run psql against a separately created database — do not build on it.
- `prepopulate_new_user.sql` — operator psql tool seeding orientation messages + starter memories for an existing user (`-v user_id/user_email/user_name/user_timezone/current_focus`); the `user_id` value rides a session `SET` because psql never interpolates `:'var'` inside dollar-quoted bodies. No in-repo caller.
- `_mira_log_levels.py` — TOAST (60) registration, zero deps; installed into site-packages with a `mira-log-levels.pth` auto-import by `deploy/python.sh`, `deploy/update.sh`, and `deploy/docker/Dockerfile.base`; `utils/logging_config.py` re-registers idempotently as the bare-checkout fallback (counterpart `utils/AGENTS.md`).
- `.env.example` — container first-boot env template: `MIRA_PROVIDER_KEY` the only required var; provider name/endpoint/model, Kagi, System One, DB password optional; no `MIRA_SMTP_*` lines ship — the first-boot SMTP inputs are owned by `deploy/docker/scripts/AGENTS.md`. Nothing loads it — copy into `docker run`; the reader is `init-mira.sh`'s env-var mode (`deploy/docker/scripts/AGENTS.md`).
- `deploy-config.example.yml` — the `--config` template: every key required (deleting a line aborts), `""` = skip, `__SET_ME__` aborts at parse time (after `acquire_sudo` has run), flat `key: value` only; the header documents the comment/quote rules. Must stay in step with the parser's key list — recipe owned by `deploy/lib/AGENTS.md`.
- `RELEASE.md` — the release procedure: move `RELEASE_TAG`, tag, build the asset with `build_release_artifact` and attach it (the only payload installs and updates fetch), publish; the provenance commit shapes; the update summary, the release gate (a–e) and its checklist — including `scripts.migrate generate`; manual recovery from the asset (`mira-<version>/`).
- `HOW_TO_MIGRATE_OLD_INSTALLS.txt` — the agent-run migration runbook: acceptable old-data forms, survey→plan→port→verify method with STOP gates, RLS/vector/end-to-end verification, the operator paste-prompt. Scoped to pre-2.0 installs (a major crossing — a reinstall, never `mira update`); `deploy/finalize.sh`'s renamed-database note points here.
- `docker/Dockerfile` — thin application layer over `mira-base` (rebuilds in seconds): `MIRA_REVISION` build arg → `org.opencontainers.image.revision` label and `/opt/mira/image-build.txt` (falls back to the tree's `RELEASE_COMMIT`), code copy, s6 tree, config files, script placement (`init-mira.sh` → `/init-mira.sh` ENTRYPOINT; `vault-unseal.sh` → `/opt/mira/app/deploy/docker/scripts/vault-unseal.sh`, the path `vault-init/up` execs), HEALTHCHECK, six persistent volumes (pgdata, `/opt/vault`, valkey, HF model cache, `/opt/mira/app/data` — anchored by `utils/userdata_manager.py:base_dir` — and `/opt/mira/backups`, the step runner's pre-upgrade backups). Gotcha: a bare `VOLUME` is anonymous — each persists across recreation only under the named `-v` mount the README's `docker run` lines carry; a run without `-v mira-backups:/opt/mira/backups` loses every backup with the container.
- `docker/Dockerfile.base` — the heavy base, rebuilt only when requirements move: two stages (builder: venv + requirements + torch + sentence-transformers + playwright + TOAST `.pth` + embedding-model cache; runtime: PGDG postgresql-17 + pgvector + valkey + Playwright Chromium deps + s6-overlay + Vault + `acl` (the container is the fourth `acl` install branch — the three distro branches in `dependencies.sh` plus this image; the root seam makes every container backup take `take_backup`'s setfacl path, reason owned by the `dependencies.sh` bullet above), `mira` user, ubuntu 24.04). Gotcha: `PLAYWRIGHT_BROWSERS_PATH=/home/mira/.cache/ms-playwright` must stay set in the runtime image — build-time install and the s6 service (HOME=/home/mira) must resolve the same browsers dir, else launch fails with "Executable doesn't exist".
- `docker/config/valkey.conf` — container Valkey: loopback bind, RDB snapshots, 256mb `allkeys-lru`, `daemonize no` for s6; AOF off.
- `docker/config/vault.hcl` — container Vault: file storage under `/opt/vault/data`, loopback listener, `disable_mlock` (container), ui on.
- `docker/s6-rc.d/` — the supervision tree (boot-chain semantics owned by `deploy/docker/scripts/AGENTS.md`): `user` bundle → `postgresql`/`valkey`/`vault` longruns + `vault-init` oneshot → `mira-migrate` oneshot (database steps before every start; a failure restores and keeps `mira` down) → `mira` longrun (waits unsealed, AppRole files, sources `systemone.env`, `MIRA_INJECTION_SCREEN_ENABLED` defaulting 0, execs `main.py` as mira). Gotcha: `mira/run` is bash; the other `run` scripts are execlineb — do not mix dialects in one service.
- `docker/scripts/` — container bootstrap and supervision scripts; own map: `deploy/docker/scripts/AGENTS.md`.
- `migrations/` — the database step chain carrying an installed `mira_service` forward; own map: `deploy/migrations/AGENTS.md`.
- `lib/` — sourced bash helper libraries (output, elevation, services, Vault state machine, install-time probes); own map: `deploy/lib/AGENTS.md`.
- `vm/` — VM spin-up, dev-build deploy, sarcophagus restore toolkit; own map: `deploy/vm/AGENTS.md`.

## Wiring

- Host-install flow: `deploy.sh` → `acquire_sudo` → `config.sh` (interview, or `--config` through `deploy/lib/config_file.sh`) → `preflight.sh` → `dependencies.sh` (sets `PYTHON_VER`) → `python.sh` (sets `MIRA_USER`/`MIRA_GROUP`; installs to `/opt/mira/app`) → `vault.sh` (needs `MIRA_USER`; initializes Vault) → `postgresql.sh` (needs an initialized Vault for the Step-14 writes; sets `MIRA_LEGACY_STAMP`/`MIRA_VAULT_BACKUPS`/`MIRA_PREVIOUS_DB`) → `finalize.sh` (reports the stamps; writes the service). All sourced into one shell under `set -e`; a phase sourced outside deploy.sh dies on its `Requires:` guards (`: "${VAR:?}"`) — every phase except `config.sh`, whose header names its requirements but enforces none at runtime.
- Installer entry (counterpart root `AGENTS.md`): root `install.sh` resolves the newest published release from the `releases/latest` redirect (`MIRA_RELEASE_TAG` pins), clones the tag — never raw-curls `deploy/deploy.sh` (the raw per-ref cache serves a stale file after a republish) — and hands off with stdin reattached to `/dev/tty`, forwarding `--config/--loud/--local`.
- Update handoff (counterpart `ui/tui/AGENTS.md`): `ui/tui/update.py` resolves the release and downloads its asset, then execs the release's own `deploy/update.sh <tree> <tag> [--rebuild-venvs] [--adopt-drifted]` (the `--rebuild-venvs-only` fast path execs it against the installed tree with no release fetch); shared env contract `MIRA_APP_DIR`/`MIRA_TUI_VENV`/`NIGHTLY`/`NIGHTLY_SHA`/`LOUD_MODE`; the TUI owns resolution, `deploy/update.sh` owns everything that touches the install.
- Install-time probes (counterpart `clients/AGENTS.md`; mechanics owned by `deploy/lib/AGENTS.md`): `deploy/postgresql.sh` verifies both the embedding model and the System One endpoint through `clients/embeddings_provider.py:describe_for_installer` and `clients/systemone_client.py:describe_for_installer` before the install commits; `deploy_database.sh` probes the embedding model only (its System One token is collected unverified) — a signature change on either side breaks fresh installs in the same commit; `EMBEDDING_SCHEMA_ARGS` parameterizes the installer's schema-apply sites (`rg 'resolve_embedding_schema_args'`); the fourth apply site is `tests/fixtures/scratch_db.py`, which builds its own `-v` args through `describe_for_installer` directly, and whose `_ROLES` mirror Step 13's role creation (same names, `BYPASSRLS` on `mira_admin`, minus passwords) — counterpart `tests/fixtures/AGENTS.md`.
- Health polls (counterpart `cns/api/AGENTS.md`): `deploy/finalize.sh` (first start — the 600 s `GET /v1/api/health` poll is the macOS launchd path only; the Linux systemd branch verifies with `systemctl is-active` and never hits the endpoint), `deploy/update.sh` (post-swap — status AND the new `VERSION`) — both polls print a `still waiting (waiting N more seconds)` countdown after the first 30 s and every 60 s after, so a parked boot reads as bounded waiting, not a silent hang — and the container HEALTHCHECK gate on `GET /v1/api/health` answering `"status":"healthy"` in the data envelope.
- AppRole seam (writer mechanics owned by `deploy/lib/AGENTS.md`; reader `clients/AGENTS.md`): `deploy/vault.sh` calls `vault_initialize` (materializes `/opt/vault/role-id.txt` + `secret-id.txt`), `deploy/finalize.sh` bakes them into `mira.service` or `run.sh` exports them, and `deploy/vault.sh` re-syncs an existing unit when a re-run rotates them; the app fails fast without `VAULT_ROLE_ID`/`VAULT_SECRET_ID`.
- Install-tree identity (counterpart `tools/implementations/AGENTS.md`): `deploy/python.sh` writes `.git/info/exclude` (via `deploy/lib/state_preserve.sh:write_install_exclude`) and the `install <tag> @ <sha>` commit; `deploy/update.sh` rewrites the exclude, exports the operator's changes, and records `update <tag> @ <sha>` — the newest such commit is the baseline the next export diffs against (`deploy/lib/custom_export.sh:official_baseline_commit`), and `ui/tui/migrate.py:run_status` reports against it; `tools/implementations/bash_tool.py:_load_app_tree` reads the exclude as the undeletable set — the exclude's format and anchoring change with its reader in one commit.
- Install-time env chain (counterpart `config/AGENTS.md`; container start path owned by `deploy/docker/scripts/AGENTS.md`): `deploy/finalize.sh` writes `/opt/mira/systemone.env` (`MIRA_TIMEZONE`, `MIRA_LOCAL_SESSION_FIRST_NAME`, `MIRA_CONTEXT_WINDOW_TOKENS`, `MIRA_COMPACTION_TRIGGER_TOKENS`, `MIRA_INJECTION_SCREEN_ENABLED`, `MIRA_SYSTEMONE_PROVIDER/ENDPOINT/MODEL`) → systemd `EnvironmentFile=` / `run.sh` `set -a` / s6 `mira/run`; `config/config_manager.py` maps each onto its field. A renamed var is writer + mapper + container default in one commit; on update, the old name is dropped from the file by `scripts.migrate reconcile` once nothing in the tree mentions it, and the new name's default applies until a step sets it.
- Vault layout (counterparts `clients/AGENTS.md`, `auth/AGENTS.md`; container entry list owned by `deploy/docker/scripts/AGENTS.md`): `deploy/postgresql.sh` Step 14 writes `secret/mira/api_keys` (`anthropic_key`, `provider_key`, `subcortical_key`, `kagi_api_key`, embedding/System One keys per config), `secret/mira/database` (put-if-not-exists — reason owned by `deploy/lib/AGENTS.md`), `secret/mira/services` (`app_url` — required by WebAuthn (`auth/config.py`), `valkey_url`, `userdata_encryption_key`, `diagnostics_token`, optional `smtp_*` — read only from Vault at runtime by `auth/email_service.py`). Reader set: `rg 'get_service_config'`.
- Dev-VM handoff (counterpart `deploy/vm/AGENTS.md`): `deploy/vm/oneshot.sh` phase 4 runs `deploy/deploy.sh --config ~/deploy-config.yml --local --loud` from the pushed worktree — `--local` installs from the invocation cwd, so the push precedes; dev configs carry `""` placeholder keys that park the POST gate until inject restores a real Vault.
- Counterparts: operator docs under `docs/` describe the install and update mechanics owned here ↔ `docs/AGENTS.md`; the schema DDL/RLS/view are consumed by `lt_memory` ↔ `lt_memory/AGENTS.md`.
