# deploy/ — host-metal and Docker deployment tooling for a fresh MIRA install

## Rules

- `deploy.sh` orchestrates a fixed seven-phase chain by sourcing each phase script in one shell (`config.sh` → `preflight.sh` → `dependencies.sh` → `python.sh` → `vault.sh` → `postgresql.sh` → `finalize.sh`), so every phase shares one variable scope: `CONFIG_*`/`STATUS_*` are initialized in `config.sh`, `OS`/`DISTRO` in `config.sh`, `PYTHON_VER` in `dependencies.sh`, `MIRA_USER`/`MIRA_GROUP` in `python.sh`, and each later phase guards this with a `: "${VAR:?...}"` check naming the phase that must run first. A new phase script must be both added to the chain in `deploy.sh` and given its variable-contract header; sourcing it in the wrong order fails at the guard.
- There is no in-place upgrade path: 2.0 installs `mira_service_schema.sql` into an empty database only, and the schema itself aborts (`RAISE EXCEPTION` in its `$schema_precondition$` block) if the target has any tables. Data salvage from 1.x is manual `pg_dump` work. Do not add migration DDL to the schema file; the docs/ map records that `MANUAL_INSTALL.md` still advertises a nonexistent `--migrate` flag.
- The database sentinel password `changethisifdeployingpwd` is created by `postgresql.sh` (`ROLE_SQL`) and `deploy_database.sh` and later replaced by `ALTER USER ... WITH PASSWORD` in `postgresql.sh` when `CONFIG_DB_PASSWORD` differs. On a changed password the re-run PRESERVES the old Vault entry under a timestamped `secret/mira/database_legacy_*` key and writes `/opt/vault/howtoaccess.txt` (mode 600) documenting both entries before updating the primary key — overwriting a Vault entry in place risks irreparable lockout. The `ALTER USER` pairs run as `if`-conditions — `set -e` does not abort inside an if-condition, so a password failure reaches the warning branch and the installer continues instead of dying before it can report. Roles must be created WITH a password because `pg_hba.conf` uses scram-sha-256 on every supported platform; the Vault URLs stored in Step 14 embed it — percent-encoded (`postgresql.sh` Step 14 and `deploy/docker/scripts/init-mira.sh`); the app side decodes through libpq (`clients/AGENTS.md`). The Docker bootstrap has its own copy of this contract (owned by `deploy/docker/scripts/AGENTS.md`).
- `mira_service_schema.sql` seeds every `model_configs` route at the lunaroute gateway — the deployment defaults: `primary` = `glm-5.3` under `provider_key`, `fast`/`batch`/`assessment`/`other` = the `glm-5.3-flash` family under `subcortical_key` (`batch` gets the `-background` variant). No deploy script string-patches the schema file: `postgresql.sh` rewrites the seeded rows with UPDATEs AFTER application in both modes — `OFFLINE_SQL` for offline installs, and for hosted installs the chat-tier rewrite of `primary` (from `CONFIG_CHAT_PROVIDER_TYPE`/`CONFIG_CHAT_MODEL`/`CONFIG_CHAT_ENDPOINT`, fail-fast on an empty model) plus the subcortical rewrite of the four aux routes (skipped when endpoint and model both equal the lunaroute defaults, so `batch` keeps its `-background` variant on a default install). Changing a seeded value is therefore safe for the deploy chain, but the subcortical skip-check literals in `postgresql.sh` (`DEF_SUB_ENDPOINT`/`DEF_SUB_MODEL`) must be updated in the same commit or default installs start rewriting `batch` too.
- Offline mode routes are split by capability: `postgresql.sh`'s `OFFLINE_SQL` points `primary`/`batch`/`assessment` at the main llama-server URL (default port 3090) and `fast`/`other` at the small one (port 3092), with `api_key_name` cleared to `''` (empty string = no credential required). The `3090`/`3092` endpoint contract is cited by `docs/OFFLINE_MODELS.md` (see `docs/AGENTS.md`).
- `dependencies.sh` declares `LLAMA_MAIN_PORT=8080`/`LLAMA_SMALL_PORT=8081` inside the offline branch but never uses them; the real ports everywhere else are 3090/3092. Treat the 8080/8081 assignments as dead code, not as a competing port contract.
- `vault.sh` writes `/opt/vault/init-keys.txt` (via `deploy/lib/vault.sh`'s `vault_initialize`) and later phases re-read it: `finalize.sh` extracts the root token and unseal key for the credential dump, and the auto-unseal script `/opt/vault/unseal.sh` greps `Unseal Key 1` from it. `deploy/lib/vault.sh` owns the file format and paths.
- The documented Docker builds use the repo root as context, so only the root `.dockerignore` applies — a file at `deploy/docker/.dockerignore` is inert (Docker reads `<context>/.dockerignore` or a `<Dockerfile>.dockerignore` sidecar). The root file's `**/`-prefixed junk patterns (`**/__pycache__`, `**/*.pyc`, `**/*.log`) are required because bare `*` patterns match root-level paths only; moving the file away from the root, or flattening the prefixes, silently bakes `.git`, `scratch/`, and any stray host credential files into the image.
- Both install paths — the interactive interview and `deploy.sh --config <file>` — must produce identical `CONFIG_*` semantics. Adding a new install choice is a coordinated five-file edit in one commit: the interview block in `config.sh`, the key whitelist + required-key list + `apply_yaml_config` mapping in `deploy/lib/config_file.sh`, the template line in `deploy-config.example.yml`, and the summary's `STATUS_*` rendering. Skipping the parser piece makes `--config` silently produce a different install than the interview.
- A package commented out of the root `requirements.txt` optional block is invisible to `Dockerfile.base`, which installs from that file and has no `CONFIG_*` gate of any kind. Where a later `RUN` invokes the package's CLI, the builder stage must `pip install` it explicitly — `playwright` is installed that way because the runtime stage unconditionally runs `playwright install chromium`. `deploy/python.sh` is the only path that honours `CONFIG_INSTALL_PLAYWRIGHT`, and it gates the pip package and the browser together in Step 7 so the two cannot disagree.
- Deployment docs alignment: `docs/AGENTS.md` cites `deploy/deploy.sh`, `deploy/vault.sh`, `deploy/postgresql.sh`, `deploy/mira_service_schema.sql`, and `deploy/deploy_database.sh` as verified anchors for `docs/MANUAL_INSTALL.md` and the offline docs. Renaming or removing any of these files requires updating `docs/MANUAL_INSTALL.md` and the `docs/AGENTS.md` citation list in the same change.

## Files

- `deploy.sh` — orchestrator and only directly-executed script here. Standalone-bootstrap: if `lib/output.sh` is missing it clones the repo to `/tmp/mira-install-$$` and re-execs itself; parses `--loud` into `LOUD_MODE`, `--local` into `LOCAL_SOURCE` plus the cwd captured as `LOCAL_SOURCE_DIR` (consumed by `python.sh`; unknown flags abort); sources the three lib files in fixed order (`output.sh` → `services.sh` → `vault.sh`), then sources each phase in sequence. Consumers: end users (`./deploy/deploy.sh`), `docs/MANUAL_INSTALL.md`.
- `config.sh` — configuration gathering, interview or config-file. Variable initialization for all `CONFIG_*`/`STATUS_*` plus `SYSTEM_TIMEZONE` (from `detect_system_timezone`, the same `/etc/timezone`/`/etc/localtime` read `utils/timezone_utils.py:get_default_timezone` does); when `CONFIG_FILE` is set (deploy.sh `--config`), sources `deploy/lib/config_file.sh`, parses + applies it, and skips every interactive prompt (`overwrite_existing`/`stop_occupied_ports` answer the two mid-flow prompts; macOS systemd N/A parity is re-applied after OS detection). Interview mode: disk-space and `/opt/mira/app` overwrite checks, `OS`/`DISTRO` detection (linux-debian/fedora, macos), port 1993/8200/6379/5432 occupancy check with per-service stop prompts, LLM provider interview (offline llama-server vs OpenAI-compatible — the default, prefilled with the lunaroute endpoint and `glm-5.3` — vs Anthropic), subcortical endpoint (default lunaroute `glm-5.3-flash`), optional Kagi key, embeddings (local, or remote endpoint/model/key), DB password, timezone (empty resolves to `SYSTEM_TIMEZONE` before the summary, so `finalize.sh` always writes a concrete name into the unit), Playwright and systemd opt-ins, and the configuration summary. Must be sourced, not executed.
- `deploy-config.example.yml` — the `--config` template: one flat `key: value` line per install choice, secrets shipped as `__SET_ME__` placeholders. Every key is required; leaving `__SET_ME__` aborts before sudo; `""` means the interview's Enter-to-skip semantics. Consumed by: end users (copied to `deploy-config.yml`), `deploy/lib/config_file.sh` (contract).
- `preflight.sh` — final validation before unattended install: re-verifies `OS`/`DISTRO`, refuses running as root, probes elevation with `sudo -n true` and only falls back to a tty-prompt `sudo -v` when a password is needed (`sudo -v` alone aborts headless installs even with NOPASSWD sudo), then starts the sudo-keepalive background loop (Linux). Sourced.
- `dependencies.sh` — system packages per platform (apt with PGDG repo, dnf with PGDG + Fedora-41 floor + pg_hba scram rewrite + cluster init, brew with the redis/valkey formula-conflict unlink workaround); sets `PYTHON_VER`. The apt branch installs `valkey-server`, not `valkey`: Ubuntu splits the package and ships no `valkey` metapackage (only Debian/Fedora do), so asking apt for `valkey` aborts Step 1 on Ubuntu LTS. Offline mode also sets up llama.cpp (`build_llama_cpp: no` from the config file skips the source build entirely — remote llama-server installs have nothing to compile locally; interview mode defaults to build) and creates `/opt/mira/models`. Sourced.
- `python.sh` — Python verification (3.12 floor), MIRA code install to `/opt/mira/app` — wget of the main-branch tarball, or, under `--local`, the invocation-cwd checkout with untracked runtime junk excluded (tarball parity), venv creation, requirements, the `_mira_log_levels.py` .pth install, and — only when `CONFIG_EMBEDDING_PROVIDER` is `local` — the PyTorch CPU wheel and sentence-transformers (neither is in `requirements.txt`) plus the embedding model (`MongoDB/mdbr-leaf-ir-asym`) cache check/download, Playwright pip package + Chromium (both inside the Step 7 `CONFIG_INSTALL_PLAYWRIGHT` gate). Route configuration is NOT done here — `postgresql.sh` owns it (see Rules). Sets `MIRA_USER`/`MIRA_GROUP`/`PYTHON_CMD`. Sourced.
- `vault.sh` — Vault 1.18.3 binary install (Linux arch-mapped, SELinux `chcon` on Fedora), `/opt/vault/{data,config,logs}` layout, `vault.hcl`, systemd `vault.service` (Linux) or background process with `vault.pid` (macOS), readiness poll, `vault_initialize` call, credential sync into an existing `mira.service`, and the `/opt/vault/unseal.sh` auto-unseal unit. Exports `VAULT_ADDR`. Sourced.
- `postgresql.sh` — macOS service starts; Linux starts the distro-correct unit first if `pg_isready` fails (a re-run's occupied-port stop otherwise orphans it), then `pg_isready` readiness poll, role/database provisioning (`mira_admin` BYPASSRLS + `mira_dbuser`, sentinel password), embedding resolution (`resolve_embedding_schema_args` from `deploy/lib/embedding_config.sh` against the venv — a failed remote probe exits the install), schema application as superuser with those psql variables, the post-application `model_configs` route rewrite in both modes (offline `OFFLINE_SQL`; hosted chat-tier + subcortical UPDATEs, see Rules), custom-password `ALTER USER`, and Step 14 Vault writes: `secret/mira/api_keys` (provider-conditional field set plus optional `kagi_api_key` and, for a remote embedding endpoint with a key, `embeddings_key`), `secret/mira/database` (admin/service URLs, username, password), `secret/mira/services` (`app_url`, `valkey_url`, generated `userdata_encryption_key` and `diagnostics_token`, optional `MIRA_SMTP_*` fields). Sourced.
- `finalize.sh` — systemd `mira.service` (Linux, opt-in; reads `/opt/vault/role-id.txt`/`secret-id.txt`; resolves the Valkey unit name by detecting what the host ships — `valkey-server.service` on Ubuntu, `valkey.service` on Fedora — because a wrong name in `Requires=` makes systemd refuse to start the unit; carries `Environment="MIRA_TIMEZONE=$CONFIG_TIMEZONE"` so the app's `SystemConfig.timezone` comes from the install choice), macOS `run.sh` launcher (exports `VAULT_*` — without it `main.py` crashes at import), one-time credential dump to `~/MIRA_credentials.txt`, pip-cache and `/tmp` cleanup, final status/next-steps output including the degraded-mode banner when `CONFIG_SUBCORTICAL_API_KEY` is still `PLACEHOLDER_SET_THIS_LATER`, and `/opt/vault` permission hardening (700/600). Sourced.
- `deploy_database.sh` — standalone (not part of the `deploy.sh` chain) database-only installer for an existing machine: superuser detection, refuses an existing `mira_service`, provisions the same roles/database, resolves embedding variables (local default; `MIRA_EMBEDDING_PROVIDER=remote` + `MIRA_EMBEDDING_ENDPOINT`/`MIRA_EMBEDDING_MODEL`, token read from the terminal; `MIRA_PYTHON` must carry MIRA's requirements), applies the schema, and prints verification queries plus manual Vault-setup next steps. Uses the sentinel password without a custom-password override path.
- `mira_service_schema.sql` — fresh-install database contract: empty-database precondition, extensions (pgcrypto, vector, pg_trgm), `model_configs` (exactly five routes: `primary`, `fast`, `batch`, `assessment`, `other`) and `usage_pricing` seeds, `embedding_config` (one row from five `embedding_*` psql variables that also size every `vector(...)` column; a leading `\if` guard fails the apply before any DDL when one is missing; lock trigger `embedding_config_locked_once_vectors_exist`), tables for users/auth/continuum/messages/memories/entities/persona/feedback/sharing/federation, RLS policies on `mira_dbuser`, least-privilege grants, and `REVOKE ALL ON global_memories FROM mira_dbuser` (runtime reads go through the `global_memories_runtime` security-barrier view). Consumers: `postgresql.sh`, `deploy_database.sh`, `deploy/docker/scripts/init-mira.sh` (all three build the embedding variables through `deploy/lib/embedding_config.sh`); its `model_configs` seed values are the lunaroute deployment defaults rewritten post-application by `postgresql.sh` (see Rules). A raw client (psycopg `execute` of the file) cannot apply it — psql variables and `\if` are psql features.
- `mira_blog_schema.sql` — separate `mira_blog` database schema (posts table, `mira_blog_owner`/`mira_blog_reader`/`mira_blog_writer` role split). Not referenced by any deploy script; run manually.
- `prepopulate_new_user.sql` — seeds a new user's continuum bootstrap messages (beginning-of-conversation marker, active segment sentinel, intake system messages) and initial memories. Parameterized via psql `-v user_id/user_email/user_name/user_timezone/current_focus`; run as `mira_admin` against `mira_service` after the user and continuum rows exist. psql never interpolates `:'var'` inside a dollar-quoted `DO` body, so `user_id` is hoisted via a plain `SET mira.user_id = :'user_id';` statement that the block reads back with `current_setting` — keep that shape; inlining `:'user_id'` into the DO body reintroduces a syntax error at the guard.
- `_mira_log_levels.py` — registers the `TOAST` log level (value 60) on `logging.Logger`. Copied into venv site-packages by `python.sh` (and into the Docker image by `Dockerfile.base`) with a `mira-log-levels.pth` auto-import hook so it loads before any application code. Consumers: `python.sh`, `deploy/docker/Dockerfile.base`.
- `RELEASE.md` — runbook for switching `python.sh` from the main-branch tarball to a tagged release tarball when cutting a stable release. Current; matches the note left in `python.sh`.
- `lib/` — shared bash helper libraries sourced by every deploy script. See `deploy/lib/AGENTS.md` (owns source-order, `LOUD_MODE`, and Vault state-machine rules).
- `vm/` — VM spin-up + instance-sarcophagus toolkit (one-shot deploy/restore over local libvirt, remote `--host`, or plain-ssh `--ip`). See `deploy/vm/AGENTS.md` (owns modes, transport gotchas, and the sarcophagus contract).
- `docker/` — Docker image build and in-container bootstrap. See `deploy/docker/scripts/AGENTS.md` for the per-script bootstrap contract; directory-level build/supervision topology is below.

## Wiring

- Phase order in `deploy.sh` is load-bearing: `config.sh` collects inputs (and parses `deploy/lib/config_file.sh` under `--config`) → `preflight.sh` validates elevation and starts the sudo keepalive → `dependencies.sh` installs packages and detects `PYTHON_VER` → `python.sh` installs the app (needs nothing from later phases) → `vault.sh` installs/starts Vault and runs `vault_initialize` → `postgresql.sh` provisions roles, applies the schema, rewrites the `model_configs` routes for the install mode, and writes every credential into Vault → `finalize.sh` consumes the AppRole credential files for systemd and the credential dump. Route rewriting happens after schema application in BOTH modes (offline `OFFLINE_SQL` and the hosted chat/subcortical UPDATEs are owned by `postgresql.sh`); Vault credential storage must precede `finalize.sh`'s credential-file reads.
- `deploy/mira_service_schema.sql` is coupled to the app layer in three places, each owned elsewhere: the `vector(...)` columns and the `embedding_config` row are sized from one `embedding_dimensions` psql variable (owning statement in `clients/AGENTS.md`); the `model_configs.name` CHECK admits exactly the five fixed routes `primary`/`fast`/`batch`/`assessment`/`other` that `ModelResolver` resolves (owning statement in `clients/llm/AGENTS.md`); and the `model_configs.dialect_name` CHECK domain is the same four members as the `DialectName` literal, so dialect additions are a blast-radius edit (owning statement in `clients/llm/dialects/AGENTS.md`). Changing any of these from the schema side breaks the LLM/embeddings layer silently — e.g. a widened CHECK lets a route row carry a dialect no registered class implements, which surfaces only as a runtime resolve failure, not a crash at deploy.
- `deploy_database.sh` is an independent entry point, not a phase: it re-implements the role-provisioning and schema-application steps of `postgresql.sh` for bare-database setups and must be kept consistent with `postgresql.sh` when the `ROLE_SQL` or schema-precondition contract changes.
- Docker image topology: `Dockerfile.base` builds the heavy layer (Python venv, ML model cache, Playwright, PostgreSQL 17 + pgvector, Valkey, Vault 1.18.3, s6-overlay 3.2.0.0); `Dockerfile` layers only the app onto it. `Dockerfile` COPY mappings: repo root → `/opt/mira/app/`, `deploy/docker/s6-rc.d/` → `/etc/s6-overlay/s6-rc.d/`, `deploy/docker/config/vault.hcl` → `/opt/vault/config/vault.hcl`, `deploy/docker/config/valkey.conf` → `/etc/valkey/valkey.conf`, and the four script mappings listed in the child map.
- Docker data persistence: the `Dockerfile` `VOLUME` list covers `/var/lib/postgresql/17/main`, `/opt/vault`, `/var/lib/valkey`, `/home/mira/.cache/huggingface`, and `/opt/mira/app/data` — the last is per-user storage (`userdata.db`, artifacts, imagegen outputs) anchored by `utils/userdata_manager.py:base_dir` plus the `Path("data/users")` call sites (`utils/artifact_store.py`, `cns/services/subcortical.py`); dropping it destroys user data on container recreation. Volume mountpoints come up root-owned, so `init-mira.sh` `chown`s `/opt/mira/app/data` to mira on every start (the same reason `init_vault` chowns `/opt/vault`).
- Docker Playwright browser path: `Dockerfile.base` sets `ENV PLAYWRIGHT_BROWSERS_PATH=/home/mira/.cache/ms-playwright` before the `playwright install chromium` RUN; the s6 `mira/run` service runs as mira with `HOME=/home/mira`, and `utils/playwright_service.py` launches Chromium with no explicit executable_path. Removing the ENV separates the install location (`/root/.cache/ms-playwright`) from the runtime lookup and Chromium fails to launch at first use. The `playwright` package that provides this CLI is `pip install`ed explicitly in the builder stage, not inherited from `requirements.txt`.
- s6 service set: `user/contents.d` bundles `mira`, `postgresql`, `valkey`, `vault`, `vault-init`. `mira/dependencies.d` requires `postgresql`, `valkey`, `vault-init`; `vault-init/up` polls Vault health then execs `vault-unseal.sh` (child-map contract), so unseal completes before `mira/run` — which additionally polls unsealed status for up to 60s and reads `/opt/vault/role-id.txt`/`secret-id.txt` — starts the app as the `mira` user with `HOME`/`HF_HOME` set for the cached embedding model.
