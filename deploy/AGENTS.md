# deploy/ — host install pipeline, in-place updater, and container images built on one fresh-install database contract

## Files

- `deploy.sh` — the installer entry point: flag parsing, `RELEASE_TAG`, the standalone bootstrap clone, then sourcing every phase in order. Open it before adding, reordering, or deleting a phase.
- `config.sh` — the interview (or the `--config` YAML apply) plus disk, OS, and port pre-flight. Open it before changing what an install asks for or how an answer is defaulted.
- `preflight.sh` — the pre-interview gate: unsupported-distro refusal, root refusal, and the elevation capture for hosts where it was not taken yet. Open it before changing which platforms an install accepts or when the sudo prompt appears.
- `dependencies.sh` — system packages per distro, the PostgreSQL floor, and the optional llama.cpp build. Open it before adding a package a later phase or Chromium needs.
- `python.sh` — lands the code tree from the release asset or `--local`, records the install commit, builds the server and TUI venvs, fetches the embedding model. Open it before changing what an install puts in `/opt/mira/app` or how a venv is built.
- `vault.sh` — Vault binary, config, supervision, initialization, AppRole sync, auto-unseal. Open it before changing how Vault starts or how the app's AppRole reaches the service.
- `postgresql.sh` — the install's whole relationship with the database: provisioning, the fresh-or-existing decision, and every write that issues into PostgreSQL or Vault. Open it before changing what an install writes into the database or Vault.
- `finalize.sh` — the start path and the end-of-install report: one env file, one supervisor artifact per platform, and the notes that tell the operator what happened to their data. Open it before changing how an installed MIRA starts or what the operator is told at the end.
- `update.sh` — the machine half of `mira update`: every phase that touches an installed tree. Open it before changing any in-place update behavior.
- `deploy_database.sh` — standalone operator tool for a hand-provisioned PostgreSQL; `deploy.sh` never calls it. Open it before creating `mira_service` outside an install.
- `mira_service_schema.sql` — the fresh-install database contract. Open it before adding a table, policy, grant, or seed row.
- `bootstrap_adopt.sql` — hands object ownership to `mira_admin` and creates the step ledger. Open it before changing who owns database objects.
- `mira_blog_schema.sql` — a separate blog schema no MIRA code reads. Open it only if an operator asks about `mira_blog`; do not build on it.
- `prepopulate_new_user.sql` — operator psql tool seeding orientation messages and starter memories for an existing user; no in-repo caller. Open it when an operator wants a user's first conversation pre-seeded; it assumes the continuum already exists and fails loudly when it does not.
- `_mira_log_levels.py` — the TOAST level, installed into site-packages behind a `.pth` auto-import. Open it before adding or moving a log level.
- `GITHUB_REPO` — the repository spelling `owner/name`, one line and too thin to earn a header. Open it before changing a repository URL anywhere.
- `.env.example` — the container first-boot env template. Open it before adding an env var a container install accepts.
- `deploy-config.example.yml` — the `--config` template, every key required. Open it before adding an installer input.
- `RELEASE.md` — the release procedure, the provenance commit shapes, and the release gate. Open it before cutting a release.
- `HOW_TO_MIGRATE_OLD_INSTALLS.txt` — the agent-run runbook for porting pre-2.0 data by hand. Open it when an install kept a database aside and the operator wants that data forward.
- `docker/Dockerfile` — the thin application layer over `mira-base`: code copy, s6 tree, entrypoint, HEALTHCHECK, volume list. Open it before changing what a container build includes or which paths persist.
- `docker/Dockerfile.base` — the heavy half of the container image: every system package and Python package a container starts with. Open it when a dependency or system package moves, or when a container needs something the thin layer cannot supply.
- `docker/config/valkey.conf` — the container's Valkey config. Open it before changing how a container caches or persists.
- `docker/config/vault.hcl` — the container's Vault config. Open it before changing container Vault storage or its listener.
- `docker/s6-rc.d/` — the container supervision tree: longruns, oneshots, boot dependencies. Open it before changing container start order.
- `lib/` — sourced bash helpers (output, elevation, services, Vault, provenance, state preservation, install-time probes); its own map.
- `migrations/` — the database step chain that carries an installed database forward; its own map.
- `docker/scripts/` — container bootstrap and supervision scripts; its own map.
- `vm/` — VM spin-up, dev-build deploy, and sarcophagus restore; its own map.

## Wiring

- Install chain: `deploy.sh` → `config.sh` → `preflight.sh` → `dependencies.sh` → `python.sh` → `vault.sh` → `postgresql.sh` → `finalize.sh`, every phase sourced into one shell under `set -e`. Each phase's own `Requires:` guard kills the install when it is sourced out of order — `PYTHON_VER` comes from `dependencies.sh`, `MIRA_USER` from `python.sh` — and `config.sh` names its requirements but enforces none. Vault readiness is a different guard class, enforced per write by `deploy/lib/vault.sh:vault_put_with_backup`, which refuses before overwriting an existing secret; no phase header covers it.
- Installer entry: root `install.sh` resolves the newest published release from GitHub's `releases/latest` redirect and clones that tag; `deploy.sh` clones its own `RELEASE_TAG` when run standalone (no `deploy/lib/output.sh` beside it), and `python.sh`'s release-asset download fetches that same exported constant, so both fetch sites follow one tag. Counterpart: `AGENTS.md` (repo root).
- Update handoff: `ui/tui/update.py` resolves the release and downloads its asset, then runs `bash <release-tree>/deploy/update.sh <tree> <tag>` with `MIRA_APP_DIR`, `MIRA_TUI_VENV`, `NIGHTLY`, `NIGHTLY_SHA`. `update.sh` reads `LOUD_MODE` with a false default and no TUI path sets it, so verbose update output requires exporting it before `mira update`. The TUI owns resolution, this script owns everything that touches the install, and the exit code returns unchanged. Counterpart: `ui/tui/AGENTS.md`.
- Plan handoff: `scripts/migrate.py`'s `--plan` writes the human-readable plan, then `MIRA_PLAN_BEGIN`, the machine plan, `MIRA_PLAN_END`; `update.sh` splits that stream on the marker pair and `postgresql.sh:carry_existing_data_forward` reads the same output. The JSON block is emitted even when the command refuses with exit 2 — drop it and both readers take the transcript as unreadable, so the updater reports it could not read the database and the installer sees a non-empty `refusals` list and sends the database down `keep_database_aside`. A marker rename changes both sides in one commit. Counterpart: `scripts/AGENTS.md`.
- Service-file generators: `finalize.sh` renders `mira.service` and the `mira` wrapper from `deploy/lib/host_artifacts.sh:render_mira_unit` and `render_mira_cli`; `update.sh` renders both from the same generators and rewrites them only when the bytes differ. A hand-edited unit is discarded on the next update — change the generator, not the file.
- AppRole seam: `vault.sh:vault_initialize` materializes `/opt/vault/role-id.txt` and `secret-id.txt`, `finalize.sh` bakes them into the unit or exports them from `run.sh`, and `update.sh` reads them for the step runner — the one read outside the generators, and why the step runner fails rather than running unauthenticated. The writer mechanics and the app-side reader are `deploy/lib/AGENTS.md`'s. Counterpart: `clients/AGENTS.md` (the app-side reader, which fails fast without them).
- Install-time env chain: `finalize.sh` writes `/opt/mira/systemone.env` → systemd `EnvironmentFile=` / `run.sh` under `set -a` / the container's s6 `mira/run` → `config/config_manager.py` maps each var onto its field. The container's writer is `deploy/docker/scripts/init-mira.sh:init_vault` on first boot, not `finalize.sh`. A renamed var is writer, mapper, and container default in one commit: the s6 `mira/run` applies `MIRA_INJECTION_SCREEN_ENABLED:-0` where the two host start paths apply no default, so a var renamed in the host writers alone leaves containers reading the old name. Counterparts: `config/AGENTS.md`, `deploy/docker/scripts/AGENTS.md`.
- Vault layout: `postgresql.sh` Step 14 writes `secret/mira/api_keys`, `secret/mira/database`, and `secret/mira/services` (whose `app_url` WebAuthn requires); the runtime reads them at startup only. Counterparts: `clients/AGENTS.md`, `auth/AGENTS.md`.
- Install identity: `python.sh` writes `.git/info/exclude` and the `install <tag> @ <sha>` commit; `update.sh` writes `update <tag> @ <sha>`. The newest such commit is what `deploy/lib/custom_export.sh:official_baseline_commit` diffs for the operator's own changes. The subject shape has one writer, `deploy/lib/provenance.sh:official_commit_message`, and two matchers that move in one commit: `custom_export.sh:MIRA_OFFICIAL_SUBJECT_ERE` in shell and `ui/tui/migrate.py:OFFICIAL_SUBJECT_RE` in Python — edit one alone and `mira restore`'s baseline detection keeps matching the old shape. The exclude's literal entries are the top-level names `tools/implementations/bash_tool.py:_load_app_tree` refuses to delete, generated by `deploy/lib/state_preserve.sh:write_install_exclude`. Counterparts: `deploy/lib/AGENTS.md`, `ui/tui/AGENTS.md`.
- Install-time probes: the enforcing callers are `deploy/lib/embedding_config.sh:resolve_embedding_schema_args` and `deploy/lib/systemone_config.sh:probe_systemone`, whose contracts, shared shape, and failure policy are `deploy/lib/AGENTS.md`'s. What this map owns is the order `postgresql.sh` imposes: both probes run before its first `apply_fresh_schema_and_bootstrap` call, so a probe failure never leaves a half-provisioned database.
- Dev-VM handoff: `deploy/vm/oneshot.sh` runs `deploy/deploy.sh --config … --local --loud` from the pushed worktree, and `--local` installs the invocation cwd, so the push precedes the install. Counterpart: `deploy/vm/AGENTS.md`.
- Generated ledger DDL: `utils/schema_migrations.py:ledger_ddl` owns the ledger's columns and writes the sentinel block in both `mira_service_schema.sql` and `bootstrap_adopt.sql`; `python -m scripts.migrate generate` regenerates them. A hand-edit to either block is overwritten on the next generate and diverges fresh installs from upgraded ones. Counterparts: `utils/AGENTS.md`, `scripts/AGENTS.md`.
- Elevation twin: how this host runs a command as the PostgreSQL superuser is computed twice, by `deploy/lib/services.sh:seam_mode` and `utils/schema_migrations.py:superuser_prefix`, and `update.sh` renders its own elevation sentence from `seam_mode`. The two change in one commit, or shell and Python take different arms on the host whose arm was edited. Counterpart: `utils/AGENTS.md`.
- Probe fixture: `tests/fixtures/scratch_db.py:scratch_database` reproduces this directory's database contract in-process, provisioning `_ROLES` from `deploy/postgresql.sh:ROLE_SQL`'s names and privileges and then applying `mira_service_schema.sql` before `bootstrap_adopt.sql` through psql. The roles must exist before the schema apply on both sides, because the header's precondition list names `mira_admin` and `mira_dbuser` and the GRANTs to them fail without the roles, and `bootstrap_adopt.sql` must follow the schema, because its `schema_migrations` table would otherwise be a public BASE TABLE when the `$schema_precondition$` block counts the target's tables and the apply stops with `requires an empty target database`. A role renamed or re-privileged in `ROLE_SQL` alone leaves the fixture raising at its apply before any of the probe's own checks run, and an order flipped in `apply_fresh_schema_and_bootstrap` alone leaves the fixture certifying an install sequence no release performs. Counterpart: `tests/fixtures/AGENTS.md`.
- Schema consumers: this directory's DDL, RLS policies, and `global_memories_runtime` view are what `lt_memory` queries. Counterpart: `lt_memory/AGENTS.md`.
- Operator docs: `docs/` describes the install and update mechanics owned here. Counterpart: `docs/AGENTS.md`.

## Rules

- Every applier runs `bootstrap_adopt.sql` immediately after `mira_service_schema.sql` — `rg 'bootstrap_adopt.sql'` lists them. A new applier that skips it leaves objects owned by the superuser, and the first database step then fails as `mira_admin`.
- Every database structure change is two edits in one commit: the change in `mira_service_schema.sql` for fresh installs, and a numbered step under `deploy/migrations/` for installed databases (`deploy/migrations/AGENTS.md` owns the step contract). One without the other leaves fresh and upgraded installs at different structures, and `scripts.migrate generate`'s convergence gate prints DO NOT PUBLISH instead of an asset.
- Every install-time database write lands in every branch that creates a database: `apply_fresh_schema_and_bootstrap`, `apply_model_config_routes`, and `record_install_steps` run together on the top-level fresh path and again on each branch of `carry_existing_data_forward` that starts a database fresh, `keep_database_aside` among them, while the in-place carry-forward branch calls `apply_model_config_routes` alone. A write added to one branch leaves that install class missing it with nothing failing.
- An installer input ships in both spellings or neither: the `config.sh` question and the `deploy-config.example.yml` key, plus whatever the parser needs — the six-step recipe in `deploy/lib/AGENTS.md` lists every file. Vestigial exception: `anthropic_batch_key` is accepted by `parse_yaml_config`'s whitelist and echoed into `CONFIG_ANTHROPIC_BATCH_KEY` with a placeholder value, but no interview question collects it, `deploy-config.example.yml` has no line for it, and no phase reads the variable — so a real batch key is accepted and silently dropped. `deploy/vm/deploy-config-dev-vm.yml` carries a stray `anthropic_batch_key: ""` line, which is a template key for a dev VM only. An interview-only input is unreachable for an unattended `--config` install.
- `deploy.sh` calls `acquire_sudo` before sourcing `config.sh`, so a malformed `--config` file costs the operator a password prompt before it is rejected. Two source comments claim otherwise — the rules header in `deploy-config.example.yml` and the `--config` block comment in `deploy/config.sh` — and both describe the parser, not the install's order.
- `update.sh`'s header is the phase contract a by-hand invoker reads (they load no maps), and `rollback_install` is its other half. A step inserted after the service stops needs its undo there; a step inserted before the stop needs none. Without that undo the step's failure leaves the install half-updated instead of put back, so a phase change edits the header, `rollback_install`, and this rule in one commit.
- Any new `update.sh` phase that touches the database must carry the same non-canonical-root refusal the plan, migrate, and status phases carry: the connection target is the host's Vault AppRole, which no `MIRA_APP_DIR` override scopes, so a throwaway root would otherwise read and change the real install's database. The twin guard is `ui/tui/migrate.py`.
- torch, sentence-transformers, and the playwright package are deliberately absent from `requirements.txt`: `python.sh` installs them gated on config, `docker/Dockerfile.base` installs all three unconditionally (an image has no config gate), and `update.sh` re-detects the choice from the live venv, the only record of it. Moving one into `requirements.txt` drags PyTorch onto every remote-embedding install; forgetting an installer site makes the next update silently strip that extra from that install class.
- Runtime-written state under `/opt/mira/app` must land under a slash-anchored excluded name, defined once in `deploy/lib/state_preserve.sh` and shared by `python.sh` and `update.sh`. A write outside those names reads as the operator's own change: the next `mira update` exports it to the Desktop and bash_tool treats it as deletable.
- Vault and MIRA each land on a supervised, auto-unsealed start path on both supervisors: `vault.sh` writes `vault.service` + `vault-unseal.service` or `com.mira.vault` + `com.mira.vault.unseal`, `finalize.sh` writes `mira.service` or `com.mira.app`. launchd has no ordering, so every bounded wait lives inside the generated artifacts rather than in a unit dependency, and a launchd service is stopped with `bootout`, never killed — KeepAlive resurrects a killed process mid-swap.

Elsewhere: this map owns the order of the phases, the edges between them, and the database contract they share; it does not own what any single phase does inside itself, nor how an image layer is assembled. Nor does it own what the sourced helpers do, what a database step contains, or how a container's supervision tree boots. How a rule here was learned is `git log`; each phase script's header states the variables it requires and sets. Every other destination this directory reaches is an edge — see `## Wiring` above.

## An install over a populated database

The one path no single script shows: `/opt/mira/app` and `mira_service` already exist.

1. `config.sh` classifies the existing tree before the interview — one carrying `deploy/update.sh` is a REINSTALL (it is steered to `mira update`), an older one a MIGRATION. The classification only chooses the wording; nothing touches the database yet.
2. `postgresql.sh` provisions the roles, creates `mira_service` when absent, and counts public base tables. Zero sends it down the fresh path: schema, `bootstrap_adopt.sql`, model-route UPDATEs, then `scripts.migrate migrate` to stamp the ledger at the release head.
3. Non-zero leaves the database untouched and calls `carry_existing_data_forward`, which runs the release's own runner as `migrate --plan --report-marker`, read-only. A shape this release does not recognize, a declined offer, and a session with no terminal all reach the same branch: `keep_database_aside` renames the database to `mira_service_old_<stamp>`, creates a fresh one, and the fresh path runs.
4. A shape the release does recognize is printed verbatim and needs one typed Y. That is the only place an install changes a populated database, and the reason an unattended `--config` install never carries data forward.
5. On Y the runner migrates in place after taking its own backup, and `apply_model_config_routes` writes the interview's answers to the five routes of whichever database the install landed on. `MIRA_DATA_CARRIED=yes` records that.
6. `finalize.sh` reads those flags and prints one of three notes: data carried forward, the previous database's new name plus `HOW_TO_MIGRATE_OLD_INSTALLS.txt`, or the Vault entries copied aside. A failed migration exits before `finalize.sh` with the restore command and leaves the database as the steps left it, so rerunning resumes.
