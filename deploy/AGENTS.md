# deploy/ — host-metal and Docker deployment tooling for a fresh MIRA install

## Rules

- `deploy.sh` orchestrates a fixed seven-phase chain by sourcing each phase script in one shell (`config.sh` → `preflight.sh` → `dependencies.sh` → `python.sh` → `vault.sh` → `postgresql.sh` → `finalize.sh`), so every phase shares one variable scope: `CONFIG_*`/`STATUS_*` are initialized in `config.sh`, `OS`/`DISTRO` in `config.sh`, `PYTHON_VER` in `dependencies.sh`, `MIRA_USER`/`MIRA_GROUP` in `python.sh`, and each later phase guards this with a `: "${VAR:?...}"` check naming the phase that must run first. A new phase script must be both added to the chain in `deploy.sh` and given its variable-contract header; sourcing it in the wrong order fails at the guard.
- In-place update vs. the greenfield database: `mira update` (TUI subcommand `tui/update.py` → this directory's `update.sh`) updates non-breaking releases in place — code, venvs, restart — while the database stays greenfield: `mira_service_schema.sql` installs into an empty database only, and the schema itself aborts (`RAISE EXCEPTION` in its `$schema_precondition$` block) if the target has any tables. A release carrying `BREAKING.md` at the repo root is breaking (any schema change is breaking by definition); `mira update` refuses it and prints the manual path — reinstall via `install.sh` (old DB renamed aside, Vault credentials preserved), then agent-run history import (`HOW_TO_MIGRATE_OLD_INSTALLS.txt`, the `working_memory/skills/hosted-recovery` runbook). The updater never migrates data and never touches the DB. Do not add migration DDL to the schema file; the docs' `--migrate` references were removed in the v2release-census fix wave.
- The database sentinel password `changethisifdeployingpwd` is created by `postgresql.sh` (`ROLE_SQL`) and `deploy_database.sh` and later replaced by `ALTER USER ... WITH PASSWORD` in `postgresql.sh` when `CONFIG_DB_PASSWORD` differs. On a changed password the re-run PRESERVES the old Vault entry under a timestamped `secret/mira/database_legacy_*` key and writes `/opt/vault/howtoaccess.txt` (mode 600) documenting both entries before updating the primary key — overwriting a Vault entry in place risks irreparable lockout. Every other Step 14 entry (`secret/mira/api_keys`, `secret/mira/services`) goes through `vault_put_with_backup`: the previous value is copied verbatim to `<path>_legacy_<MIRA_LEGACY_STAMP>` and only then overwritten with the new install's values, so a re-run's new keys take effect while the old ones stay recoverable; `userdata_encryption_key` is carried forward unchanged (rotating it leaves encrypted user data unreadable) and an unreachable Vault aborts rather than regenerate it. The `ALTER USER` pairs run as `if`-conditions — `set -e` does not abort inside an if-condition, so a password failure reaches the explicit error report and its `exit 1` instead of aborting silently before the operator sees why; the install aborts rather than continue, because Step 14 would otherwise store a password the roles never received. Roles must be created WITH a password because every Linux target's `pg_hba.conf` uses scram-sha-256 for TCP connections (Homebrew's macOS pg_hba defaults to `trust` for localhost — the password rides in the URL but is not challenged there); the Vault URLs stored in Step 14 embed it — percent-encoded (`postgresql.sh` Step 14 and `deploy/docker/scripts/init-mira.sh`); the app side decodes through libpq (`clients/AGENTS.md`). The Docker bootstrap has its own copy of this contract (owned by `deploy/docker/scripts/AGENTS.md`).
- `mira_service_schema.sql` seeds every `model_configs` route at the lunaroute gateway — the deployment defaults: `primary` = `glm-5.3` under `provider_key`, `fast`/`batch`/`assessment`/`other` = the `glm-5.3-flash` family under `subcortical_key` (`batch` gets the `-background` variant). No deploy script string-patches the schema file: `postgresql.sh` rewrites the seeded rows with UPDATEs AFTER application in both modes — `OFFLINE_SQL` for offline installs, and for hosted installs the chat-tier rewrite of `primary` (from `CONFIG_CHAT_PROVIDER_TYPE`/`CONFIG_CHAT_MODEL`/`CONFIG_CHAT_ENDPOINT`, fail-fast on an empty model) plus the subcortical rewrite of the four aux routes (skipped when endpoint and model both equal the lunaroute defaults, so `batch` keeps its `-background` variant on a default install). Changing a seeded value is therefore safe for the deploy chain, but the subcortical skip-check literals in `postgresql.sh` (`DEF_SUB_ENDPOINT`/`DEF_SUB_MODEL`) must be updated in the same commit or default installs start rewriting `batch` too. A default (lunaroute) config leaves the seed untouched and any departure is applied live — a staging-copy refresh needs no patch. `chat_provider_type` takes `openai` (any OpenAI-compatible endpoint) or `anthropic`; the old value `generic` is gone (breaking, no alias). Installation is code: it gets a smoke run before release, same as any handler.
- Offline mode routes are split by capability: `postgresql.sh`'s `OFFLINE_SQL` points `primary`/`batch`/`assessment` at the main llama-server URL (default port 3090) and `fast`/`other` at the small one (port 3092), with `api_key_name` cleared to `''` (empty string = no credential required). The `3090`/`3092` endpoint contract is cited by `docs/OFFLINE_MODELS.md` (see `docs/AGENTS.md`).
- `dependencies.sh` declares `LLAMA_MAIN_PORT=8080`/`LLAMA_SMALL_PORT=8081` inside the offline branch but never uses them; the real ports everywhere else are 3090/3092. Treat the 8080/8081 assignments as dead code, not as a competing port contract.
- `vault.sh` writes `/opt/vault/init-keys.txt` (via `deploy/lib/vault.sh`'s `vault_initialize`) and later phases re-read it: `finalize.sh` extracts the root token and unseal key for the credential dump, and the auto-unseal script `/opt/vault/unseal.sh` greps `Unseal Key 1` from it. `deploy/lib/vault.sh` owns the file format and paths.
- The documented Docker builds use the repo root as context, so only the root `.dockerignore` applies — a file at `deploy/docker/.dockerignore` is inert (Docker reads `<context>/.dockerignore` or a `<Dockerfile>.dockerignore` sidecar). The root file's `**/`-prefixed junk patterns (`**/__pycache__`, `**/*.pyc`, `**/*.log`) are required because bare `*` patterns match root-level paths only; moving the file away from the root, or flattening the prefixes, silently bakes `.git`, `scratch/`, and stray host files into the image. The gitignored credential paths (`.env`, `**/.env` incl. `deploy/.env`, `.vault_env`, `.vault_keys`, `vault_data/`) are excluded in a Credentials section — keep every new gitignored credential path mirrored there, or the repo-root build bakes it into `mira:latest`.
- Both install paths — the interactive interview and `deploy.sh --config <file>` — must produce identical `CONFIG_*` semantics. Adding a new install choice is a coordinated five-file edit in one commit: the interview block in `config.sh`, the key whitelist + required-key list + `apply_yaml_config` mapping in `deploy/lib/config_file.sh`, the template line in `deploy-config.example.yml`, and the summary's `STATUS_*` rendering. Skipping the parser piece makes `--config` silently produce a different install than the interview. The injection screen rides this mechanism as five keys (`injection_screen`, `systemone_provider`, `systemone_endpoint`, `systemone_model`, `systemone_api_key`): enabled screens require a provider/endpoint/model and a `remote` key (both paths reuse the chat key on a lunaroute endpoint — no fallback otherwise, the M16 fix), and a disabled screen requires all four `systemone_*` empty, because it probes and seeds nothing.
- A package commented out of the root `requirements.txt` optional block is invisible to `Dockerfile.base`, which installs from that file and has no `CONFIG_*` gate of any kind. Where a later `RUN` invokes the package's CLI, the builder stage must `pip install` it explicitly — `playwright` is installed that way because the runtime stage unconditionally runs `playwright install chromium`. `deploy/python.sh` is the only path that honours `CONFIG_INSTALL_PLAYWRIGHT`, and it gates the pip package and the browser together in Step 7 so the two cannot disagree.
- Deployment docs alignment: `docs/AGENTS.md` cites `deploy/deploy.sh`, `deploy/vault.sh`, `deploy/postgresql.sh`, and `deploy/mira_service_schema.sql` as verified anchors for `docs/MANUAL_INSTALL.md` and the offline docs. Renaming or removing any of these files requires updating `docs/MANUAL_INSTALL.md` and the `docs/AGENTS.md` citation list in the same change.

## Files

- `deploy.sh` — orchestrator and only directly-executed script here. Standalone-bootstrap: if `lib/output.sh` is missing it clones the repo to `/tmp/mira-install-$$` and re-execs itself; parses `--loud` into `LOUD_MODE`, `--local` into `LOCAL_SOURCE` plus the invocation cwd captured as `LOCAL_SOURCE_DIR` (run `--local` from the repo root; consumed by `python.sh`; unknown flags abort); sources the six lib files in fixed order (`output.sh` → `services.sh` → `vault.sh` → `embedding_config.sh` → `context_window_config.sh` → `systemone_config.sh`), calls `acquire_sudo` (lib/services.sh — elevation captured once for the whole run), then sources each phase in sequence. Consumers: end users (`./deploy/deploy.sh`), the root `install.sh` entrypoint (which fetches the newest release's `deploy.sh` and hands off), `docs/MANUAL_INSTALL.md`.
- `config.sh` — configuration gathering, interview or config-file. Variable initialization for all `CONFIG_*`/`STATUS_*` plus `SYSTEM_TIMEZONE` (from `detect_system_timezone`, the same `/etc/timezone`/`/etc/localtime` read `utils/timezone_utils.py:get_default_timezone` does); when `CONFIG_FILE` is set (deploy.sh `--config`), sources `deploy/lib/config_file.sh`, parses + applies it, and skips every interactive prompt (`overwrite_existing`/`stop_occupied_ports` answer the two mid-flow prompts; macOS systemd N/A parity is re-applied after OS detection). Interview mode: disk-space and `/opt/mira/app` overwrite checks, `OS`/`DISTRO` detection (linux-debian/fedora/arch — `ID` then `ID_LIKE` from `/etc/os-release`; macos), port 1993/8200/6379/5432 occupancy check via `port_probe_status` (lib/services.sh — lsof→ss→netstat ladder; a clean minimal Linux often has only `ss`) with per-service stop prompts (the valkey/postgres systemd stops resolve unit names through `resolve_valkey_unit`/`resolve_pg_unit`), LLM provider decision tree — a LunaRoute shortcut first (`LUNAROUTE_MODE=yes`: unlimited API usage for a flat fee, one key prefills chat `glm-5.3`, subcortical `glm-5.3-flash`, embeddings `emb-qwen3`, and the System One `djev` screen, then skips those four prompts) else offline llama-server vs OpenAI-compatible (the default, prefilled with the lunaroute endpoint and `glm-5.3`) vs Anthropic, subcortical endpoint (default lunaroute `glm-5.3-flash`), optional Kagi key, embeddings (default remote: lunaroute endpoint, `emb-qwen3`; local under `offline_mode: yes` or on request), injection screen (default no under `offline_mode: yes` — air-gapped has no djev — yes otherwise; when yes: provider/endpoint/model, defaulting to the lunaroute `djev` gateway, and a key for `remote` only when the endpoint is not lunaroute), DB password, the user's first name (default `Friend`; `user_name` in the yml, empty resolves to `Friend` before the summary so `finalize.sh` always writes a concrete name), timezone (empty resolves to `SYSTEM_TIMEZONE` before the summary, so `finalize.sh` always writes a concrete name into the unit), Playwright and systemd opt-ins, and the configuration summary. A lunaroute endpoint reuses the chat key for subcortical, embeddings, and System One rather than re-prompting (`is_lunaroute_full_service`). Must be sourced, not executed.
- `deploy-config.example.yml` — the `--config` template: one flat `key: value` line per install choice, secrets shipped as `__SET_ME__` placeholders. Every key is required; leaving `__SET_ME__` aborts during config parsing — which runs after `deploy.sh`'s `acquire_sudo`, not before it. `""` means the interview's Enter-to-skip semantics. Debt (code defect, do not "fix" the template without resolving the key): `config_file.sh` requires `anthropic_batch_key`, which the shipped template omits — a faithful copy aborts with a missing-key error (`deploy/vm/deploy-config-dev-vm.yml` carries it) — and the key maps to `CONFIG_ANTHROPIC_BATCH_KEY`, which no phase ever reads. Consumed by: end users (copied to `deploy-config.yml`), `deploy/lib/config_file.sh` (contract).
- `.env.example` — template for the container's non-interactive first-boot env vars (`MIRA_PROVIDER_KEY` required; `MIRA_PROVIDER_NAME`/`ENDPOINT`/`MODEL`, `MIRA_KAGI_KEY`, `MIRA_SYSTEMONE_API_KEY`, `MIRA_DB_PASSWORD` optional), the set `deploy/docker/scripts/init-mira.sh:check_env_vars`/`setup_from_env_vars` reads. No script reads this file and `docker run` does not load it — pass the vars with `-e`/`--env-file`; the root `.dockerignore` Development-files block excludes it from the image.
- `HOW_TO_MIGRATE_OLD_INSTALLS.txt` — operator handoff for salvaging user data from a 1.x / old-schema install into a fresh greenfield instance: the salvage doctrine's agent-run counterpart to the manual-`pg_dump` posture above. Carries a fill-in-the-brackets prompt the operator pastes into their own agent (survey both schemas read-only, plan with STOP gates, never copy vectors across embedding models, stage-then-load with count parity, live RLS + recall verification, drop-and-report for no-analog fields).
- `preflight.sh` — final validation before unattended install: re-verifies `OS`/`DISTRO` (debian/fedora/arch accepted), refuses running as root, calls `acquire_sudo` (a no-op when `deploy.sh` already captured elevation; it self-acquires for a standalone run, and a headless session with neither passwordless sudo nor a tty exits with the two real options), then starts the sudo-keepalive background loop on every platform — the loop re-primes a Homebrew-cleared ticket silently through `SUDO_ASKPASS` (`acquire_sudo`/`ensure_sudo` in `deploy/lib/AGENTS.md`). Sourced.
- `dependencies.sh` — system packages per platform (apt with PGDG repo keyed on `/etc/os-release` `VERSION_CODENAME` — not `lsb_release`, absent on minimal images — and `DEBIAN_FRONTEND=noninteractive`; dnf with PGDG + Fedora-41 floor + x86_64-only gate (PGDG publishes no aarch64 Fedora repos) + non-interactive PGDG GPG key import (`rpm --import`, dnf5 otherwise prompts at first makecache) + cluster init + pg_hba rewrite; pacman with full `-Syu` first (Arch forbids partial upgrades; the distro's CURRENT postgresql major is used — 18.6 verified live, schema floor is 14 — not a pinned 17) + initdb-as-postgres (the Arch package does not initialize the cluster; `sudo -u postgres initdb --locale C.UTF-8`) + the same host-lines-only pg_hba rewrite (Arch initdb defaults every line to trust); brew with the redis/valkey formula-conflict unlink workaround and non-interactive env (`NONINTERACTIVE`, `HOMEBREW_NO_INSTALLED_DEPENDENTS_CHECK`, `HOMEBREW_NO_INSTALL_UPGRADE` — brew 7 otherwise prompts to upgrade UNRELATED installed packages mid-deploy) ending in `ensure_sudo`); sets `PYTHON_VER`. The pg_hba rewrite touches ONLY the `host` (TCP) lines → scram-sha-256; the `local` (unix-socket) lines keep their initdb defaults (peer/ident/trust) because every `sudo -u postgres psql` provisioning call authenticates through them — rewriting local lines locks the deploy out of its own database. All pg_hba/cluster guards run through `sudo test`/`sudo grep`: the data dirs are 0700 postgres, and unprivileged guards silently evaluate false (they made the Fedora block dead code and re-ran initdb on every redeploy). The apt branch installs `valkey-server`, not `valkey`: Ubuntu splits the package and ships no `valkey` metapackage (Debian/Fedora/Arch package it as `valkey-server`/`valkey`/`valkey`), so asking apt for `valkey` aborts Step 1 on Ubuntu LTS. Offline mode also sets up llama.cpp (`build_llama_cpp: no` from the config file skips the source build entirely — remote llama-server installs have nothing to compile locally; interview mode defaults to build) and creates `/opt/mira/models`. Sourced.
- `python.sh` — Python verification (3.12 floor; macOS keg paths probed), MIRA code install to `/opt/mira/app` — the target's previous code is cleared first (every top-level entry except `venv`/`.env`/`data`/`logs`/`.git`, the host-local state the payload never contains — `data/` is per-user storage, `venv/` is reused below, `.git` holds install history and stashed edits) so a retired module left by an overlay cannot park the POST gate; uncommitted changes in an existing tree are stashed first (MIRA edits that never went through a restart — kept, never deleted); then wget of the pinned tag tarball (`RELEASE_TAG`, exported by `deploy.sh`), or, under `--local`, the invocation-cwd checkout with untracked runtime junk excluded (tarball parity), then the tree is recorded as a git commit (`git init` on first install — git is a declared dependency on every platform — repo-local `user.name`/`user.email`, `.git/info/exclude` written from the heredoc here: the single source of the untracked set, which `tools/implementations/bash_tool.py:_load_app_tree` reads back as the top-level names bash refuses to delete; state-carrying entries are slash-anchored so git ignores them at top level only, matching bash_tool's protection — a depth-matched ignore would leave a nested same-named dir invisible to git yet deletable; every runtime write under the tree must land under one of these entries or the tree reads as dirty), venv creation (pip upgraded to current), requirements, the `_mira_log_levels.py` .pth install, and — only when `CONFIG_EMBEDDING_PROVIDER` is `local` — the PyTorch CPU wheel and sentence-transformers (neither is in `requirements.txt`) plus the embedding model (`MongoDB/mdbr-leaf-ir-asym`) cache check/download, Playwright pip package + Chromium (both inside the Step 7 `CONFIG_INSTALL_PLAYWRIGHT` gate; `playwright install chromium` runs UNCONDITIONALLY — it is build-specific and idempotent, while a cache-directory pre-check is build-agnostic and a stale cache from an older Playwright silently leaves the browser unlaunchable; `playwright install-deps` runs only on the debian family — upstream is apt-only, Fedora/Arch get the Chromium libs from the Step 1 package set, live-proven by a headless launch on both). Route configuration is NOT done here — `postgresql.sh` owns it (see Rules). Sets `MIRA_USER`/`MIRA_GROUP` (whoami + `id -gn` on every platform — the macOS arm used to hardcode `staff`)/`PYTHON_CMD`. Step 5b builds the TUI client venv at `/opt/mira/tui-venv` from `tui/requirements.txt` (separate from the server venv: the TUI pins pydantic where the server's is unpinned; outside `/opt/mira/app` so Step 3's code-clear never touches it) — `finalize.sh` Step 15d wires `/usr/local/bin/mira` onto it. Sourced.
- `vault.sh` — Vault 1.18.3 binary install (Linux arch-mapped; macOS uses the brew formula), persistent SELinux labeling on Fedora via `semanage fcontext`+`restorecon` (`chcon` was ephemeral — any relabel reverted it; `policycoreutils-python-utils` comes from the dnf branch), `/opt/vault/{data,config,logs}` layout, `vault.hcl`, systemd `vault.service` (Linux) or the launchd `com.mira.vault` LaunchAgent (macOS — RunAtLoad+KeepAlive, loaded through `launchd_reload_agent`; the old background-process+`vault.pid` path survived neither logout nor reboot), readiness poll, `vault_initialize` call, credential sync into an existing `mira.service`, and the `/opt/vault/unseal.sh` auto-unseal (one script on every platform: bounded 60 s wait for the server, idempotent — unseals only when sealed, PATH-prefixed for launchd's minimal env) wired as `vault-unseal.service` (Linux) or the `com.mira.vault.unseal` LaunchAgent (macOS). Exports `VAULT_ADDR`. Sourced.
- `postgresql.sh` — macOS service starts behind a one-time `PG_BINDIR=$(brew --prefix postgresql@17)/bin` PATH prepend (the keg is keg-only: bare `psql`/`createdb` are NOT symlinked into `/opt/homebrew/bin`, and every later phase shares this shell's PATH) and `ensure_sudo` after the brew-service calls; Linux starts the distro-correct unit first if `pg_isready` fails (a re-run's occupied-port stop otherwise orphans it), then `pg_isready` readiness poll, role/database provisioning (`mira_admin` BYPASSRLS + `mira_dbuser`, sentinel password), embedding resolution (`resolve_embedding_schema_args` from `deploy/lib/embedding_config.sh` against the venv — a failed remote probe exits the install), injection-screen probe (`probe_systemone` from `deploy/lib/systemone_config.sh`, gated on `CONFIG_INJECTION_SCREEN=yes` — an endpoint that does not answer exits the install with guidance; a disabled screen probes nothing), an empty-database check that renames a populated `mira_service` aside as `mira_service_old_<stamp>` (never dropped) before creating a fresh one (`MIRA_PREVIOUS_DB` carries the kept name to `finalize.sh`), schema application as superuser with those psql variables (stdout+stderr captured; the schema's refusal message prints on failure), the post-application `model_configs` route rewrite in both modes (offline `OFFLINE_SQL`; hosted chat-tier + subcortical UPDATEs, see Rules), custom-password `ALTER USER`, and Step 14 Vault writes: `secret/mira/api_keys` (provider-conditional field set plus optional `kagi_api_key`, for a remote embedding endpoint with a key `embeddings_key`, and — when `CONFIG_INJECTION_SCREEN=yes` and `CONFIG_SYSTEMONE_PROVIDER=remote` — `systemone_key` from `CONFIG_SYSTEMONE_API_KEY`; local and disabled installs seed nothing), `secret/mira/database` (admin/service URLs, username, password — preserve-only), and `secret/mira/services` (`app_url`, `valkey_url`, `userdata_encryption_key` carried forward from the existing entry and generated only when absent, `diagnostics_token` likewise, optional `MIRA_SMTP_*` fields). `api_keys` and `services` are written with `vault_put_with_backup` — previous value copied to `*_legacy_<stamp>` first — and `MIRA_LEGACY_STAMP` is shared with the database rename-aside above. Sourced.
- `finalize.sh` — writes `/opt/mira/systemone.env` (mode 600, `$MIRA_USER`; non-secret only — `MIRA_TIMEZONE` from the install choice and `MIRA_LOCAL_SESSION_FIRST_NAME` from the user-name choice (the app maps them to `SystemConfig.timezone` and `SystemConfig.local_session_first_name`; config.sh collects both and this file is where they reach the app — neither is an inline unit `Environment=` line; the name is consumed by `create_local_session` for the local account's first name and orientation content), `MIRA_CONTEXT_WINDOW_TOKENS` and `MIRA_COMPACTION_TRIGGER_TOKENS` (resolved from the chosen chat endpoint's models list, 80% of the reported window, via `deploy/lib/context_window_config.sh` — fallback to the app-side defaults with a warning when the endpoint reports nothing), `MIRA_INJECTION_SCREEN_ENABLED` plus, when enabled, `MIRA_SYSTEMONE_PROVIDER/ENDPOINT/MODEL`; the bearer token lives in Vault): the ONE mechanism carrying install-time env into every start path — the systemd unit's `EnvironmentFile=`, the Step 15b launcher's `set -a` source (a plain `.` sets shell variables only — python never saw them and the boot gate parked), and the container's s6 `mira/run` source the same file. Then: systemd `mira.service` (Linux, opt-in; reads `/opt/vault/role-id.txt`/`secret-id.txt`; dependency unit names come from `resolve_pg_unit`/`resolve_valkey_unit` in lib/services.sh — a wrong name in `Requires=` makes systemd refuse to start the unit), macOS `run.sh` launcher PLUS the Step 15b2 `com.mira.app` LaunchAgent (RunAtLoad + KeepAlive-on-failed-exit, loaded via `launchd_reload_agent`, health-polled up to 600 s when `start_mira_now: yes` — macOS honors that flag; `CONFIG_INSTALL_SYSTEMD` stays `no` there by construction, so the Step 15 systemd banner is OS-gated — reporting "user opted out" there was false, the operator opted in to the LaunchAgent), and the same launcher for Linux installs without systemd (both `CONFIG_INSTALL_SYSTEMD` = `no` and the failed-install case) — run.sh exports `VAULT_*`, sources `/opt/mira/systemone.env` with `set -a`, PATH-prefixes for launchd, and waits bounded (120 s) for Vault to be up AND unsealed before starting the server (launchd has no agent ordering; a sealed Vault parks the POST gate); without `VAULT_*` `main.py` crashes at import, one-time credential dump to `~/MIRA_credentials.txt` (includes `systemone_key` for enabled remote screens), pip-cache and `/tmp` cleanup, final status/next-steps output including the `Injection Scr:` banner line and the degraded-mode banner when `CONFIG_SUBCORTICAL_API_KEY` is still `PLACEHOLDER_SET_THIS_LATER`, a kept-database warning when `MIRA_PREVIOUS_DB` is set (names the renamed database and points at `deploy/HOW_TO_MIGRATE_OLD_INSTALLS.txt`), and a kept-credentials note listing every `MIRA_VAULT_BACKUPS` path, and `/opt/vault` permission hardening (700/600). Step 15d writes `/usr/local/bin/mira` (755): a wrapper setting `PYTHONPATH=/opt/mira/app` and execing `/opt/mira/tui-venv/bin/python3 -P -m tui "$@"` (the `-P` stops `-m`'s cwd prepend from shadowing the installed tree when `mira` is run from inside a checkout), so the deployed TUI chat client runs as `mira` from any directory (venv from python.sh Step 5b; client side owned by `tui/AGENTS.md`). Sourced.
- `deploy_database.sh` — standalone (not part of the `deploy.sh` chain) database-only installer for an existing machine: superuser detection, refuses an existing `mira_service`, provisions the same roles/database, resolves embedding variables (local default; `MIRA_EMBEDDING_PROVIDER=remote` + `MIRA_EMBEDDING_ENDPOINT`/`MIRA_EMBEDDING_MODEL`, token read from the terminal; `MIRA_PYTHON` must carry MIRA's requirements), applies the schema, and prints verification queries plus manual Vault-setup next steps. Uses the sentinel password without a custom-password override path.
- `mira_service_schema.sql` — fresh-install database contract: empty-database precondition, extensions (pgcrypto, vector, pg_trgm), `model_configs` (exactly five routes: `primary`, `fast`, `batch`, `assessment`, `other`) and `usage_pricing` seeds, `embedding_config` (one row from five `embedding_*` psql variables that also size every `vector(...)` column; a leading `\if` guard fails the apply before any DDL when one is missing; lock trigger `embedding_config_locked_once_vectors_exist`), tables for users/auth/continuum/messages/memories/entities/persona/feedback/sharing/federation, RLS policies on `mira_dbuser`, least-privilege grants, and `REVOKE ALL ON global_memories FROM mira_dbuser` (runtime reads go through the `global_memories_runtime` security-barrier view). Consumers: `postgresql.sh`, `deploy_database.sh`, `deploy/docker/scripts/init-mira.sh` (all three build the embedding variables through `deploy/lib/embedding_config.sh`), and `tests/fixtures/scratch_db.py` (applies the shipped schema to throwaway probe databases via psql); its `model_configs` seed values are the lunaroute deployment defaults rewritten post-application by `postgresql.sh` (see Rules). A raw client (psycopg `execute` of the file) cannot apply it — psql variables and `\if` are psql features.
- `mira_blog_schema.sql` — separate `mira_blog` database schema (posts table, `mira_blog_owner`/`mira_blog_reader`/`mira_blog_writer` role split). Not referenced by any deploy script; run manually.
- `prepopulate_new_user.sql` — seeds a new user's continuum bootstrap messages (beginning-of-conversation marker, active segment sentinel, intake system messages) and initial memories. Parameterized via psql `-v user_id/user_email/user_name/user_timezone/current_focus`; run as `mira_admin` against `mira_service` after the user and continuum rows exist. psql never interpolates `:'var'` inside a dollar-quoted `DO` body, so `user_id` is hoisted via a plain `SET mira.user_id = :'user_id';` statement that the block reads back with `current_setting` — keep that shape; inlining `:'user_id'` into the DO body reintroduces a syntax error at the guard.
- `_mira_log_levels.py` — registers the `TOAST` log level (value 60) on `logging.Logger`. Copied into venv site-packages by `python.sh` (and into the Docker image by `Dockerfile.base`) with a `mira-log-levels.pth` auto-import hook so it loads before any application code. Consumers: `python.sh`, `deploy/docker/Dockerfile.base`.
- `update.sh` — the machine half of `mira update`, executed (not sourced) by `tui/update.py` against a downloaded release tree (`update.sh <release-tree> <tag>`); also runnable by hand. No sudo: `/opt/mira` is user-owned and the command runs as that user (Linux `systemctl` control is attempted via `sudo -n` and aborts before touching anything when it fails). Sequence: preflight (trees, versions differ, no `BREAKING.md` — re-checked here so direct invocation cannot bypass the TUI's gate) → read the OLD venv for extras the rebuild must reproduce (torch, sentence-transformers, playwright — they ride install-time choices, not `requirements.txt`; the browser cache lives outside the venv) → build `venv.new`/`tui-venv.new` from the new tree's requirement files plus the TOAST `.pth` hook (`python.sh` Step 5 parity) while the service still runs → stop the service (macOS: `launchctl bootout`, not kill — an unloaded agent cannot KeepAlive-restart onto a half-swapped tree; Linux: `systemctl stop`) → move the old venvs aside and swap the new ones in (same-volume `mv`, instant, kept as `*.pre-update-<stamp>` until health passes) → code swap (stash uncommitted edits, clear top-level except `venv`/`.env`/`data`/`logs`/`.git` AND `run.sh` — finalize.sh generates it into the tree at install time, so a plain preserve-set clear would delete the very launcher com.mira.app runs — overlay the new tree, commit `update <tag>`) → restart (`launchd_reload_agent`/`systemctl start`) → health-poll ≤600 s on `/v0/api/health` reporting the new `VERSION`. Service management and health-poll apply ONLY to the canonical root `/opt/mira/app` (`MIRA_APP_DIR` override ⇒ a probe's throwaway root never stops or starts the real service). On failure the aside venvs are kept and rollback commands printed; v1 never auto-rolls back. `MIRA_APP_DIR`/`MIRA_TUI_VENV` env overrides exist so verification probes run the real flow against a throwaway root.
- `RELEASE.md` — the release runbook: `RELEASE_TAG` in `deploy/deploy.sh` is the switch (moving it + tagging + publishing cuts a release), and the `BREAKING.md` contract lives here — add it at the repo root in the same commit as the breaking change, remove it in the first release that is safe again; `mira update` refuses a tree that carries it (presence is the entire contract). Current; matches the note left in `python.sh`.
- `lib/` — shared bash helper libraries sourced by every deploy script. See `deploy/lib/AGENTS.md` (owns source-order, `LOUD_MODE`, and Vault state-machine rules).
- `vm/` — VM spin-up + instance-sarcophagus toolkit (one-shot deploy/restore over local libvirt, remote `--host`, or plain-ssh `--ip`). See `deploy/vm/AGENTS.md` (owns modes, transport gotchas, and the sarcophagus contract).
- `docker/` — Docker image build and in-container bootstrap. See `deploy/docker/scripts/AGENTS.md` for the per-script bootstrap contract; directory-level build/supervision topology is below.

## Wiring

- Phase order in `deploy.sh` is load-bearing: `config.sh` collects inputs (and parses `deploy/lib/config_file.sh` under `--config`) → `preflight.sh` validates elevation and starts the sudo keepalive → `dependencies.sh` installs packages and detects `PYTHON_VER` → `python.sh` installs the app (needs nothing from later phases) → `vault.sh` installs/starts Vault and runs `vault_initialize` → `postgresql.sh` provisions roles, applies the schema, rewrites the `model_configs` routes for the install mode, and writes every credential into Vault → `finalize.sh` consumes the AppRole credential files for systemd and the credential dump. Route rewriting happens after schema application in BOTH modes (offline `OFFLINE_SQL` and the hosted chat/subcortical UPDATEs are owned by `postgresql.sh`); Vault credential storage must precede `finalize.sh`'s credential-file reads.
- `deploy/mira_service_schema.sql` is coupled to the app layer in three places, each owned elsewhere: the `vector(...)` columns and the `embedding_config` row are sized from one `embedding_dimensions` psql variable (owning statement in `clients/AGENTS.md`); the `model_configs.name` CHECK admits exactly the five fixed routes `primary`/`fast`/`batch`/`assessment`/`other` that `ModelResolver` resolves (owning statement in `clients/llm/AGENTS.md`); and the `model_configs.dialect_name` CHECK domain is the same four members as the `DialectName` literal, so dialect additions are a blast-radius edit (owning statement in `clients/llm/dialects/AGENTS.md`). Changing any of these from the schema side breaks the LLM/embeddings layer silently — e.g. a widened CHECK lets a route row carry a dialect no registered class implements, which surfaces only as a runtime resolve failure, not a crash at deploy.
- `deploy_database.sh` is an independent entry point, not a phase: it re-implements the role-provisioning and schema-application steps of `postgresql.sh` for bare-database setups and must be kept consistent with `postgresql.sh` when the `ROLE_SQL` or schema-precondition contract changes.
- Docker image topology: `Dockerfile.base` builds the heavy layer (Python venv, ML model cache, Playwright, PostgreSQL 17 + pgvector, Valkey, Vault 1.18.3, s6-overlay 3.2.0.0); `Dockerfile` layers only the app onto it. `Dockerfile` COPY mappings: repo root → `/opt/mira/app/`, `deploy/docker/s6-rc.d/` → `/etc/s6-overlay/s6-rc.d/`, `deploy/docker/config/vault.hcl` → `/opt/vault/config/vault.hcl`, `deploy/docker/config/valkey.conf` → `/etc/valkey/valkey.conf`, and the four script mappings listed in the child map.
- Docker data persistence: the `Dockerfile` `VOLUME` list covers `/var/lib/postgresql/17/main`, `/opt/vault`, `/var/lib/valkey`, `/home/mira/.cache/huggingface`, and `/opt/mira/app/data` — the last is per-user storage (`userdata.db`, artifacts, imagegen outputs) anchored by `utils/userdata_manager.py:base_dir` plus the `Path("data/users")` call sites (`utils/artifact_store.py`, `cns/services/subcortical.py`); dropping it destroys user data on container recreation. The documented `docker run` commands mount all four state volumes by name (`mira-pgdata`, `mira-data`, `mira-userdata`, `mira-valkey`); `init-mira.sh` aborts loudly when Vault is initialized but pgdata is empty (lost/unnamed postgres volume) instead of crash-looping, and chowns `/var/lib/postgresql` on every start. Volume mountpoints come up root-owned, so `init-mira.sh` `chown`s `/opt/mira/app/data` to mira on every start (the same reason `init_vault` chowns `/opt/vault`).
- Docker Playwright browser path: `Dockerfile.base` sets `ENV PLAYWRIGHT_BROWSERS_PATH=/home/mira/.cache/ms-playwright` before the `playwright install chromium` RUN; the s6 `mira/run` service runs as mira with `HOME=/home/mira`, and `utils/playwright_service.py` launches Chromium with no explicit executable_path. Removing the ENV separates the install location (`/root/.cache/ms-playwright`) from the runtime lookup and Chromium fails to launch at first use. The `playwright` package that provides this CLI is `pip install`ed explicitly in the builder stage, not inherited from `requirements.txt`.
- s6 service set: `user/contents.d` bundles `mira`, `postgresql`, `valkey`, `vault`, `vault-init`. `mira/dependencies.d` requires `postgresql`, `valkey`, `vault-init`; `vault-init/up` polls Vault health then execs `vault-unseal.sh` (child-map contract), so unseal completes before `mira/run` — which additionally polls unsealed status for up to 60s and reads `/opt/vault/role-id.txt`/`secret-id.txt` — starts the app as the `mira` user with `HOME`/`HF_HOME` set for the cached embedding model.
