# deploy/vm/ — VM spawn, dev-build deploy, and sealed instance snapshot/restore toolkit

## Files

- `README.md` — the operator manual. Open it before running a bring-up end to end; it carries the command sequences this toolkit was validated with.
- `base-vm.xml` — the libvirt domain skeleton, rendered with `__DOMAIN__` and `__DISK__` at define time. Open it before changing a spawned VM's shape, resources, or devices.
- `deploy-config-dev-vm.yml` — the deploy answer file oneshot pushes as `~/deploy-config.yml`, with `""` in every secret field. Open it before changing which models, endpoints, or feature switches a spawned dev VM deploys with.
- `extract-stage-vm.sh` — the in-VM half of extract: stages every sarcophagus member under `/tmp/sarc-v2` and self-checks its checksums. Open it before changing what a sarcophagus contains or how one member is captured.
- `extract.sh` — the seal driver, caller-side. Open it before changing the seal order or the sealed directory.
- `inject-restore-vm.sh` — the in-VM half of restore: re-gate, stop mira, then replace app code, Postgres, user data, Vault, credentials, and units. Open it before changing restore order or what gets remapped for a differently-named VM user.
- `inject.sh` — the restore driver: verify the sarcophagus, quiesce mira, push, run `inject-restore-vm.sh`, then verify facts and health. Open it before changing what a restore checks or what it refuses.
- `lib.sh` — the substrate every driver sources, never executes. Open it before adding a transport, a flag, or a gate.
- `make-base-template.sh` — EXPERIMENTAL builder for the frozen base template oneshot clones; not yet exercised end to end. Open it only when a base template has to be rebuilt.
- `oneshot.sh` — the end-to-end driver, printing numbered phases 0 preflight through 6 inject-and-verify. Open it before any full bring-up, or to find which phase one failed in.
- `talktomira.sh` — one-shot chat probe: resolves the VM's address, then scripts session → csrf → api-tokens → chat and prints the reply. Open it to confirm a restored instance answers, or as the reference for scripting that chain.
- `vm-exec.sh` — thin CLI over `vmexec`: one root command in the VM through the guest agent. Open it for a one-off in-VM command without ssh.

## Wiring

- Deploy handoff: `oneshot.sh` phase 4 → `deploy/deploy.sh --config ~/deploy-config.yml --local --loud`, run from the pushed `~/mira`. `--local` installs from the invocation cwd, so the push must precede the phase, and the phase drops `mira_service` first because the deploy is greenfield-only. Counterpart: `deploy/AGENTS.md`.
- Parked gate: `deploy-config-dev-vm.yml`'s `""` keys leave the service active but unbound, so health arrives only after inject installs a Vault carrying real routes. A config holding real `chat_api_key` and `subcortical_api_key` is the exception — `deploy/postgresql.sh` seeds them into Vault and the instance comes up healthy with live model routes and no inject. Read a parked gate as a failure and you rebuild a VM for nothing. Counterpart: `deploy/AGENTS.md`.
- Auth chain: `talktomira.sh` scripts session → csrf → api-tokens → bearer chat; `ui/tui/login.py` scripts the same chain, so a route or envelope change reaches every scripter in one commit. Counterparts: `auth/AGENTS.md`, `ui/tui/AGENTS.md`.

## Rules

- Transport split: `vmssh` runs a command with `ssh -n`, `vmstream` streams without it. Flipped, ssh swallows the caller's read-loop stdin or the producer dies of SIGPIPE mid-transfer. A heredoc that is itself the stdin (`talktomira.sh`'s remote block) is the one sanctioned exception.
- The `--host` path re-parses through a second shell: ssh joins its arguments and the remote shell splits them again. `VIRSH` and `oneshot.sh:hostfs` `%q`-escape every argument for that reason; an unescaped inner quote reaches `virsh` as broken JSON and the guest call never starts.
- Every driver owns its own argument loop, assigns common flags through `set_common`, and calls `finish_flags` once after parsing. `IS_LIBVIRT` cannot be settled when `lib.sh` is sourced, because `--ip` selects the mode; a driver that reaches a transport before `finish_flags` drives a plain-ssh VM through libvirt calls, then fails with an error that names neither the flag nor the mode.
- Every stop, drop, and restore is gated and then re-gated: `turn_lock_gate` on the caller, then the in-VM scan at `inject-restore-vm.sh` step 0, because turns start in the gap between them. Skipped, an in-flight turn's HTTP call dies mid-generation after hanging for its full timeout, and the turn is lost. `turn_lock_gate` scans the `user_lock:*` keyspace that `UserRequestLock` in `utils/distributed_lock.py` mints per turn; a prefix change there empties the scan, and the gate passes a turn it was meant to wait on.
- A sarcophagus is write-once and manifest-gated: `extract.sh` refuses an existing destination and `resolve_sarc` runs `sha256sum -c` on every resolution, directory or bare name. `README-RESTORE.md` is written after the manifest, so it sits outside manifest coverage: edit the placeholder header into a real orientation without regenerating, since regenerating anyway pulls the README into the manifest and every later header edit then fails `resolve_sarc`. Regenerate `MANIFEST.sha256` only when a covered member changed, and add a row to the lineage table in the host lineage dir's `AGENTS.md` either way. Leaving the placeholder makes every later restore check run against a header that says nothing about the instance.
- In `--host` mode the sealed directory lands on the caller, not the host: sync it to the host's lineage root and verify `MANIFEST.sha256` at both ends before destroying the VM it came from, or that destruction orphans the only copy.
- Three drivers gate on the literal `"status":"healthy"` from `/v1/api/health` (`extract.sh`, `inject.sh`, `inject-restore-vm.sh`). An envelope change in `cns/api/health.py` has to reach all three in the same commit; missed, every extract and inject halts on `FATAL: mira not healthy`, which reads exactly like an unhealthy instance.
- Every key `deploy/lib/config_file.sh` requires is a line in `deploy-config-dev-vm.yml`, or the bring-up dies at `oneshot.sh` phase 4 with `Config file is missing required key`. An installer input added on the `deploy/` side is a dev-VM change too.
- `talktomira.sh` sources no `lib.sh`, so none of the transport split, `JUMP` handling, or `VM_DOMAIN` default reaches it: it carries its own `MIRA_HOST`/`MIRA_DOMAIN` defaults and its own `virsh domifaddr` call. Moving a default in `lib.sh` leaves this probe pointing at `ubuntu_vm`.
- The valkey unit name is probed, never assumed: `inject-restore-vm.sh`'s inline detection must stay identical to `deploy/lib/services.sh:resolve_valkey_unit`. On drift a restored `valkey.conf` lands on a distro whose unit name the detection misses, and valkey keeps running the previous config with nothing reporting it.
- `vault-unseal.service` execs `/usr/local/sbin/mira-unseal.sh`, a path `deploy/vault.sh:274` installs and `deploy/vault.sh:296` writes into the unit's `ExecStart=`; the script lives outside `/opt/vault`, so `extract-stage-vm.sh` stages it alongside the unit and `inject-restore-vm.sh` root-installs it. Moving the install target or renaming the script strands both capture halves; staged without the script, a restored unit points at a missing file and vault never unseals.

Elsewhere: this map routes the toolkit, not the system it deploys or the state it carries. The deployed-instance quickbook lives on the reference host, out of tree, and the root map owns that pointer; the sarcophagus lineage table is the `AGENTS.md` of the host's `mira_instance_snapshots` dir, which `README.md` locates; the validated command recipes and scar narratives are `README.md`; how a scar was learned is `git log`. Every other destination this directory reaches is an edge — see `## Wiring` above.

## Sarcophagus lifecycle, extract to verified restore

1. `extract.sh` resolves the VM's address, requires `/v1/api/health` to answer healthy, scans for an in-flight turn, then bootstraps ssh.
2. `extract-stage-vm.sh` stages as `$VM_USER` in `/tmp/sarc-v2`: `pg_dump -Fc` behind a TOC entry-count gate, per-database sqlite `.backup()` snapshots, vault and app-code tars, home members, systemd units plus `valkey.conf` through `sudo -n cat`, system-info, then `SHA256SUMS`.
3. The snapshots must replace the copied live files before the tar runs. Tarring a live WAL seals a torn database that passes every later checksum, which is why this ordering has no substitute.
4. Pull to the caller's `--snap-dir`, then compare the caller's bytes against the VM's `SHA256SUMS`, then run `PRAGMA integrity_check` on every database inside `data-users.tar.gz`. `MANIFEST.sha256` is generated after parity, integrity, and `SNAPSHOT-FACTS.txt`, and excludes itself; `README-RESTORE.md` is written after the manifest, so it is not manifest-covered.
5. `inject.sh` calls `resolve_sarc` unconditionally (idempotent for the absolute path oneshot hands in), refuses a payload missing any member, gates and stops mira, pushes to `/tmp/inject-sarc`.
6. `inject-restore-vm.sh` runs its own steps 0-10 in order: re-gate → stop mira → overlay app code (untar removes nothing, so deletions survive a restore) → terminate backends, drop and recreate `mira_service`, `pg_restore --no-owner` → replace `data` wholesale and chown it to `$VM_USER` → stop vault, replace `/opt/vault`, start vault and its unseal unit → remap credentials and unit `User=`/`Group=` → restart valkey while mira is still down → reinstall `requirements.txt` into the venv behind a warn-not-abort drift guard → start mira → poll health to 300 s.
7. `inject.sh` walks `SNAPSHOT-FACTS.txt`, comparing only `pg_*`, `sqlite_*`, and `mira_version`, and finishes on a health check. App INFO lines never reach the journal, so a passing restore is verified through the database and the API, not through `journalctl`.
