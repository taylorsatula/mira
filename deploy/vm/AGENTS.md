# deploy/vm/ — VM spin-up, dev-build deploy, and sarcophagus restore toolkit

Elsewhere: install mechanics, phase scripts, Step 13/14 route rewrites and key seeding — `deploy/AGENTS.md` · auth/chat/health routes and response envelopes — `auth/AGENTS.md`, `cns/api/AGENTS.md` · `user_lock:{user_id}` minting, TTL, release semantics — `utils/AGENTS.md` (`distributed_lock.py`) · the scripted auth chain's TUI twin — `ui/tui/AGENTS.md` (`login.py`) · deployed-instance quickbook and the sarcophagus lineage table — the host's $SNAPSHOTS/AGENTS.md, an out-of-tree host path (pointer owned by root AGENTS.md) · gotcha narratives and validated command recipes — `README.md` · how a behavior was learned — `git log`.

## Rules

- Transport split: `vmssh` (ssh -n) for command execution, `vmstream` (no -n) for pipe/stream transfers — flipped, ssh eats the caller's read-loop stdin or the producer SIGPIPEs mid-transfer. One sanctioned exception: a heredoc IS the stdin (`talktomira.sh`'s remote block). Every new transport follows the split (`lib.sh`).
- The `--host` path re-parses through an extra ssh shell hop (ssh joins args, the remote shell splits again) — `%q`-escape every argument in `lib.sh:VIRSH` and `oneshot.sh:hostfs`; unescaped inner quotes get eaten and virsh receives broken JSON — `{execute:guest-ping}` is the malformed result.
- Driver flag contract: a shared parser cannot consume positional args (a bash function gets a copy of `$@`; its shifts never reach the caller), so every driver owns its argument loop, assigns common flags through `lib.sh:set_common`, and calls `lib.sh:finish_flags` after parsing — mode can be selected by flags (`--ip`), so `IS_LIBVIRT` cannot be finalized at source time. A driver using lib.sh transports before `finish_flags` runs libvirt transports against a plain-ssh VM — the one reachable ordering failure (`set_common`'s `ip)` assigns `VMIP` but never clears it, so flag parsing cannot flip a libvirt run the other way).
- Never stop, drop, flush, restart, or restore with a MIRA turn in flight: gate first — `lib.sh:turn_lock_gate` (oneshot phases 1 and 4, extract preflight, inject quiesce) plus the in-VM re-gate at `inject-restore-vm.sh` step 0 (time passes between the caller gate and payload landing). Key: `user_lock:{user_id}` in Valkey, minted per turn by `UserRequestLock` (lock doc owned by `utils/AGENTS.md`); empty scan output = safe. Skipped, an in-flight turn's HTTP call — blocked up to 900 s — dies mid-generation.
- A sarcophagus (sealed, checksummed, append-only instance snapshot: `postgres/mira_service.dump`, `data-users.tar.gz`, `app-code.tar.gz`, `vault.tar.gz`, `home-ubuntu.tar.gz`, `systemd/`, `system-info/`, `SNAPSHOT-FACTS.txt`, `README-RESTORE.md`, `MANIFEST.sha256`) is write-once: `extract.sh` refuses an existing destination, edits after sealing require regenerating `MANIFEST.sha256` and saying so, and `lib.sh:resolve_sarc` manifest-gates unconditionally — resolved directories and bare names alike — so an unverified payload never reaches a VM.
- `""`-keyed deploy configs park the pre-server POST gate by design: the service comes up active-but-unbound and health arrives from inject (the sarcophagus's Vault carries the real keys). Read a parked gate as a deploy failure and you rebuild for nothing. A config carrying real `chat_api_key`/`subcortical_api_key` is the exception — `deploy/postgresql.sh` Step 14 seeds them into Vault (`provider_key`/`subcortical_key` in openai chat mode; anthropic mode stores `anthropic_key`/`subcortical_key` only — `chat_api_key` unused there) and Step 13 rewrites the routes (anthropic mode rewrites `primary` to `anthropic_key`), so a no-inject deploy runs healthy with live model routes (quickstart D; mechanism owned by `deploy/AGENTS.md`).
- Post-seal obligations, all before destroying the source VM: in `--host` mode the sarcophagus materializes on the caller only — sync it to the host lineage dir and verify `MANIFEST.sha256` on both ends; then replace the placeholder `README-RESTORE.md` header with a real orientation (delta vs the previous sarcophagus), regenerate the manifest, and add a row to the lineage table in the host dir's AGENTS.md. Skip the sync and the VM's destruction orphans the only copy; keep the placeholder and every future restore check runs against an unreadable lineage.

## Files

- `README.md` — operator manual: the three modes, quickstarts A–D, the sarcophagus contract, validated curl recipes for talking to the instance, the fourteen gotchas, and the reference-host deployment (canonical domain, template, sarcophagus paths; the host-side `bin/deploy-only.sh` deploy-only driver). Trust: verified against this directory's source; one overstatement — the "common flags (all scripts)" list includes `--source`/`--config`, which are oneshot-only (extract/inject/vm-exec reject them).
- `base-vm.xml` — domain skeleton; rendered by sed over `__DOMAIN__`/`__DISK__` at define time (oneshot spawn, make-base-template's builder). Gotcha: x86_64-pinned (`arch='x86_64'`, `pc-q35-10.2`, `/usr/bin/qemu-system-x86_64`) — `make-base-template.sh --arch arm64` builds an arm64 disk this skeleton cannot boot; dynamic apparmor/dac labels are reference-host leftovers that libvirt rewrites at define.
- `deploy-config-dev-vm.yml` — the `""`-keyed dev config oneshot pushes as `~/deploy-config.yml`; keys track `deploy/deploy-config.example.yml` (one drift: the dev config also carries the vestigial `anthropic_batch_key` — whitelist-only, never required, mapped to nothing; do not build on it); no secrets by design (inject replaces the Vault wholesale); `injection_screen: no` because a remote System One endpoint requires an explicit key. Gotcha: the mandatory set is `deploy/lib/config_file.sh`'s required-keys loop, which differs from both yml files — a whitelist key absent from that loop (the batch key) can be removed without aborting.
- `extract.sh` — seal driver: health + turn gates, stage via `extract-stage-vm.sh`, pull to the caller's `--snap-dir`, VM↔caller byte parity, caller-side sqlite integrity, `SNAPSHOT-FACTS.txt`, manifest, placeholder `README-RESTORE.md`. Gotcha: the `ssh_dir_copy` guard branch is a vestigial no-op (`if … then :; fi` — both arms fall through to the same scp); dead, nothing re-activates it, do not build on it.
- `extract-stage-vm.sh` — in-VM staging under `/tmp/sarc-v2`: `pg_dump -Fc` with a TOC gate (≥20 TABLE DATA), sqlite `.backup()` snapshots replacing the copied live dbs (wal/shm dropped — never tar a live WAL), vault tar, app-code tar (venv/data/pycache excluded), systemd units plus `valkey.conf` through `sudo -n cat` with a loud completeness check (units + conf +, when the host carries it, `/usr/local/sbin/mira-unseal.sh` — the root-exec'd unseal script lives outside `/opt/vault` and must travel with its unit), home members, system-info, `SHA256SUMS` self-check. Gotcha: `home-ubuntu.tar.gz` is the contractual filename regardless of `$VM_USER` — `inject-restore-vm.sh` reads that literal.
- `inject.sh` — restore driver: unconditional `resolve_sarc`, payload-presence loop, quiesce (gate → stop), push, delegate to `inject-restore-vm.sh`, fact-verify loop, health check. Gotcha: the verify loop silently skips unrecognized fact keys — `continuum_id`/`user_id` are written for orientation and never verified; a mistyped fact key verifies nothing.
- `inject-restore-vm.sh` — in-VM restore: re-gate, stop, app-code overlay (untar removes nothing), postgres drop + recreate + `pg_restore --no-owner`, data wholesale replace + chown to `$VM_USER`, Vault wholesale replace + the staged `mira-unseal.sh` root-installed to `/usr/local/sbin` when present (pre-relocation captures carry the script inside `vault.tar.gz`) + unseal restart, credential remap (captured authorized_keys deliberately not restored), unit `User=` remap (mira/vault only — distro units keep their own user), valkey restart when a conf staged, venv drift guard, start, ≤300 s health poll. Gotcha: the comment citing `deploy/finalize.sh:66-69` for unit detection is stale — the live twin is `deploy/lib/services.sh:resolve_valkey_unit`.
- `lib.sh` — the shared substrate (source it, never execute): config defaults + env overrides, transports (`VIRSH`, `vmssh`/`vmstream`, `vmcp_from`/`vmcp_to`, `vmexec`), `vmip` (domifaddr → guest-agent fallback; DHCP re-leases every spawned MAC), `wait_guest_agent`, `bootstrap_ssh`, `turn_lock_gate`, `resolve_sarc`, `bootstrap_ip`, `set_common`/`finish_flags`. Gotcha: `vmexec` is the keyless root bootstrap primitive (guest-agent, works before any ssh key exists) — a template without qemu-guest-agent kills every libvirt phase at bootstrap.
- `make-base-template.sh` — EXPERIMENTAL cloud-image template builder, not yet exercised end-to-end (the reference template was built by hand): cloud-init seed (user + pubkey + NOPASSWD + guest-agent), 20G disk, freeze after shutdown. Gotcha: the local-only guard runs before `finish_flags`, so `--ip` slips past it and dies later at the first `VIRSH` call with a confusing error.
- `oneshot.sh` — the whole point, phases 0–6: preflight (checkout + config + sarc) → spawn (template clone `--reflink=auto`, define from skeleton; `--fresh` gated: turn lock, shutdown, refusal when the live disk IS the template, old disk kept as `<disk>.pre-oneshot-<ts>`) → ssh bootstrap → push worktree + config → deploy (turn gate, stop, terminate backends, DROP DATABASE — greenfield-only) under a nohup `/tmp/deploy.exit` poll with a 60-min cap → service poll (active = process up, not bound) → inject + verify. Gotcha: phase 6 hands inject an already-resolved abs path and inject re-runs `resolve_sarc` on it — idempotent by design; do not remove the double manifest gate.
- `talktomira.sh` — one-liner chat probe, the one caller-side driver not built on `lib.sh` (its remote block runs on the libvirt host — `ssh "$HOST" … 'bash -s'` — curling the VM's API at the resolved IP; no payload is pushed into the VM, unlike extract/inject; `MIRA_HOST` required, no default): domifaddr IP resolve, base64 message through two shell layers, remote block does session → csrf → api-tokens → `/v0/api/chat` with `--max-time 900`. Gotcha: no `ssh -n` here — the heredoc IS stdin, the sanctioned exception to the transport split.
- `vm-exec.sh` — thin CLI for `vmexec` (root via guest-agent); refuses plain-ssh mode — no agent there, use `ssh … 'sudo -n …'`.

## Wiring

- Deploy handoff (counterpart `deploy/AGENTS.md`): oneshot phase 4 runs `deploy/deploy.sh --config ~/deploy-config.yml --local --loud` from the pushed worktree — invocation-cwd semantics, exclusion list in `deploy/python.sh` (`.git, venv, __pycache__, *.pyc, .env, .claude, .DS_Store, data, logs, scratch`; parity with the release asset). Config keys track `deploy/deploy-config.example.yml` (plus the vestigial `anthropic_batch_key`); validation gates in `deploy/lib/config_file.sh` (empty `chat_model` aborts after `acquire_sudo` and again at Step 13 — `chat_endpoint` required in openai chat mode only); placeholder-vs-real-key behavior per Rules above.
- Valkey unit twin: `inject-restore-vm.sh`'s inline detection (Ubuntu `valkey-server.service`, Fedora `valkey.service`) must stay identical to `deploy/lib/services.sh:resolve_valkey_unit` — same-commit on drift, or a restored conf lands on a distro the detection misses (counterpart `deploy/AGENTS.md`).
- Turn-gate key (counterpart `utils/AGENTS.md`): `turn_lock_gate` scans `user_lock:*` — minted per turn by `UserRequestLock` (`utils/distributed_lock.py`), acquired on both transports (`cns/api/websocket_chat.py`, `cns/api/chat.py`; counterpart `cns/api/AGENTS.md`).
- Auth-chain mirrors (counterparts `auth/AGENTS.md`, `cns/api/AGENTS.md`, `ui/tui/AGENTS.md`): session → csrf → api-tokens → chat, scripted here by `talktomira.sh` and the README curl recipe, in the TUI by `ui/tui/login.py`; `ui/tui/app.py` first-run guidance points at `talktomira.sh` as the reference implementation. Scripted surfaces: `rg 'v0/auth/local/session'`. A route change updates every scripter in the same commit. Cookie-auth POSTs need `X-CSRF-Token`; Bearer does not; never shrink `--max-time`.
- Sarcophagus consumers: none in-repo outside this directory (`rg 'SNAPSHOT-FACTS'` → this dir only); the second home and the lineage table live on the host (quickbook pointer owned by root AGENTS.md).

## Sarcophagus lifecycle, extract to verified restore

1. `extract.sh` preflight: resolve IP, `GET /v0/api/health` must answer `"status":"healthy"`, turn gate, ssh bootstrap. The gates narrow the window, they do not close it: pg_dump is transactional (consistent as of its snapshot), each sqlite gets a per-db consistent `.backup()`, vault storage is quiescent since provision — cross-store consistency is only as good as the quiesce.
2. `extract-stage-vm.sh` stages `/tmp/sarc-v2` as `$VM_USER` (sudo -n for postgres/valkey): dump + TOC gate, staged sqlite snapshots replace the copied live dbs, vault/app/home/system tars, units via sudo with the loud completeness check (a silent gap ships an incomplete sarcophagus), system-info, `SHA256SUMS` self-check.
3. Pull to the caller's `--snap-dir` (`--host` mode: the caller machine), then VM↔caller byte parity against the streamed `SHA256SUMS`.
4. Caller-side integrity: `PRAGMA integrity_check` on every db inside `data-users.tar.gz` — a torn snapshot never seals.
5. `SNAPSHOT-FACTS.txt`: `mira_version`, `pg_*` counts (users, messages, memories, api_tokens, model_configs, tables), `continuum_id`, `user_id`, `sqlite_domaindocs`. The verify contract: inject's loop consumes `pg_*`/`sqlite_*`/`mira_version`; the rest orient operators, never verified.
6. `MANIFEST.sha256` is generated last (excluding itself) and self-checked — any post-seal edit invalidates it; the regen contract is Rule 5's, the obligations Rule 7's.
7. Restore: `resolve_sarc` (manifest + facts gate; remote bare names pull from the host's snap dir), payload-presence loop, quiesce, push, then `inject-restore-vm.sh`: re-gate (a turn may have started since the caller gate) → stop → overlay app code → postgres drop/recreate/`--no-owner` → data wholesale + chown → vault stop → replace → start (+ unseal) → credentials remap → unit remap + valkey restart (mira still stopped, nothing depends on valkey mid-restart) → venv drift guard → start → health poll.
8. `inject.sh` verifies facts and health; its failure branch prints a `vmssh journalctl` pointer — the tail is printed only by `inject-restore-vm.sh`'s health-poll failure (whose exit 1 kills inject.sh under `set -e` before the verify loop) — app INFO never reaches the journal (WARNING+ only), so verify via DB/API.

Ordering invariants: the sqlite snapshots must replace the staged live copies before the tar — tarring the live WAL is the torn-copy alternative; the manifest seals only after parity and integrity; vault must be stopped before its storage is replaced (a running vault rewrites storage mid-copy); data chown and unit remap precede mira's start (root-owned sqlite hits `readonly database`; units run mira as `$VM_USER`); the valkey restart happens only while mira is stopped. ACCEPTED-RESIDUAL: a standalone inject of a bf85d1c+ sarcophagus into a host not redeployed first (old-shape unit, no `/usr/local/sbin/mira-unseal.sh`) aborts at the unseal start — the oneshot toolchain always redeploys at the captured revision before phase 6 inject, which is what keeps the vintage matrix consistent.
