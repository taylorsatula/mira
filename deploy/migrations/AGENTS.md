# deploy/migrations/ — the step chain that carries an installed MIRA to head, and the fingerprints a release is classified against

## Files

- `V0001__widen_segment_sentinel_uniqueness.sql` — the index swap that made a paused message count as a live segment boundary. Open it before changing what makes a message a live boundary, or before writing a step that must refuse bad existing data.
- `V0002__drop_keepsleeping_turn_index.sql` — one `DROP INDEX IF EXISTS` and nothing else. Open it when you want the smallest step that still satisfies the header contract.
- `V0003__create_heartbeat_armed_users.sql` — the table the heartbeat dispatcher reads to find armed users. Open it before changing how a user's wake time is stored or queried.
- `R__usage_pricing.sql` — the price keys MIRA ships, inserted only when absent. Open it before adding or changing a price row that MIRA itself supplies.
- `BASELINE` — generated: one row per supported starting release, then one row per versioned step of the newest release's walk. Open it when an update refuses with `ADOPTION_DRIFT` ("structure matches no BASELINE row"), when `baseline_fingerprints` raises its append-only `ValueError`, or at a release cut.
- `HEAD_FINGERPRINT.json` — generated: the whole structure at head, as the drift report diff's right-hand side. Open it when a drift report lists a table, policy, or grant and you need to know what head expects.

## Wiring

- Authoring: a structural change lands as two edits in one commit — the DDL in `deploy/mira_service_schema.sql` and its numbered step here. `python3 -m scripts.migrate generate` first rewrites the generated ledger DDL in `deploy/mira_service_schema.sql` and `deploy/bootstrap_adopt.sql`, then builds the two fingerprints from every release in `SCHEMA_ORIGINS` plus the whole chain on throwaway databases; when one does not reach exactly the schema file's structure it prints `DO NOT PUBLISH` and leaves `BASELINE` + `HEAD_FINGERPRINT.json` unwritten, with the ledger-DDL rewrite already on disk. Counterpart: `deploy/AGENTS.md`.
- Boot gate: `utils/power_on_self_test.py:_check_schema_revision` rediscovers this chain at every start and refuses to serve unless the ledger's highest revision equals the tree's last step, so adding a step here takes every install that has not run it offline. Counterpart: `utils/AGENTS.md`.
- Runner: this directory holds the step files, and everything the runner reads out of them is `utils/schema_migrations.py`. That file owns the filename grammar, the leading header block, ordering, lint, and the ledger write. A step whose name or header breaks that grammar is refused when the chain is discovered, so an authoring slip fails loudly on every install instead of being skipped as an unknown file. Counterpart: `utils/AGENTS.md`.
- Regeneration: `python3 -m scripts.migrate generate` calls `utils/schema_migrations.py:write_baseline`, which writes `BASELINE` and `HEAD_FINGERPRINT.json` together. `read_head_fingerprint` refuses a pair whose hashes disagree, so a hand-edited file or a half-finished regeneration refuses every later run instead of reporting drift to the operator. Counterpart: `utils/AGENTS.md`.

## Rules

- Adding a step is one commit of four things: the same DDL in `deploy/mira_service_schema.sql`; a `V<NNNN>__<slug>.sql` for a database step, or a `V<NNNN>__<slug>.py` for a store step, with a number that is the next dense one above the chain's head; a header carrying `-- store:` and a plain-English `-- notice:` (a `.py` step declares the same fields as capitalized module literals — `STORE`, `NOTICE`, `REQUIRES_OPERATOR_INPUT`, `DIALECT_TWINS`, `EXPAND_CONTRACT` — and defines `up(ctx)`, after which an optional `verify(ctx)` runs); and a `python3 -m scripts.migrate generate` run committed whole — the regenerated `BASELINE` + `HEAD_FINGERPRINT.json` and whatever ledger-DDL rewrite it left in `deploy/bootstrap_adopt.sql`. A schema edit without its step ships two different structures for one release, which `generate` refuses; a step without its schema edit fails the same check in the other direction; committing the fingerprints without the ledger-DDL rewrite ships a fresh install a ledger table that differs from an upgraded one; a skipped regeneration ships a chain no installed database can be classified against. A step that needs a typed value from the operator declares `-- REQUIRES_OPERATOR_INPUT:` with the prompt, so a run with no terminal stops before changing anything.
- A step that drops or renames a table or column carries `-- expand-contract: contract-for V<NNNN>` naming the release that added the replacement, and a step that changes the `dialect_name` CHECK carries `-- dialect-twins: DialectName, DIALECT_NAMES` while `clients/llm/types.py:DialectName` moves in the same commit. `utils/schema_migrations.py:lint_steps` refuses either step at artifact build — the header is a declaration, never a comment a reader can skip.
- A merged step is immutable, byte for byte, comments included: the ledger's `checksum` column holds the file's sha256 from the run that applied it, and a merged step can already be on other people's databases. Editing one makes every install that already ran it refuse its next update as `CHECKSUM_MISMATCH`; the repair is always a new step.
- A repeatable step re-runs whenever its bytes change, so it must converge MIRA's own rows without touching the operator's: an edited row is their override, so it is never deleted and never overwritten. `BASELINE` records no row for a repeatable step, so structure written in one appears on upgraded installs and never on fresh ones, with nothing in the convergence check to catch it.
- `utils/schema_migrations.py:MIGRATION_ADVISORY_KEY` is the runner's alone. Any other MIRA code taking that advisory lock blocks or is blocked by an in-flight upgrade, and neither side reports why.
- A step for `vault`, `env`, or `valkey` must put no structure-changing SQL in its `.sql` body: `run_step` executes any `.sql` body against the database whatever store the header declares, while `baseline_fingerprints` skips the step and repeats the previous fingerprint — so DDL in such a step reaches upgraded installs only, and no check reports it. Adjacent identical rows in `BASELINE` are the correct output, not a half-finished regeneration.

Elsewhere: this map does not own what a step runs through, nor the fresh-install schema the steps must mirror. The plain-English authoring rules, the notice's banned words, and the operator-recovery table are `docs/MAINTAINER_UPGRADE_GUIDE.md`; the release gate rows and the release cut checklist are `deploy/RELEASE.md`; why a step exists and why it was shaped that way is `git log`. Every other destination this directory reaches is an edge — see `## Wiring` above.

## One step, from merge to a refused update

The case that decides the immutability rule above, traced through every file it touches.

1. The commit carries the schema edit and `V0004__<slug>.sql`. The artifact build runs `scripts.migrate lint`; a banned construct stops the release here, before any user sees the tag.
2. Nightly installs fetch the next nightly and run `migrate` on it. The step runs inside the runner's transaction, and its ledger row is written last, carrying `revision`, `store`, and the file's sha256 in `checksum`. A crash between the DDL and the row leaves no row, so the rerun repeats the step rather than skipping it.
3. The release cut regenerates `BASELINE`: the walk over the newest origin grows a `revision=0004` line holding the structure the database had after the step. `baseline_fingerprints` refuses to write a result that changes or drops an existing line, which is what keeps old rows meaningful for old installs.
4. Stable installs pick the step up at their next `mira update`, after a backup. The boot guard `utils/power_on_self_test.py:_check_schema_revision` then compares the ledger's highest revision against this tree's last step at every start: an install holding the file but not the row refuses as behind, and one that ran a newer nightly refuses as ahead. Both failures are visible before the server serves a request.
5. Someone later edits that step — a typo in its notice is enough. The file's sha256 changes, the ledger row still holds the old one, and every install that ran it refuses its next update as `CHECKSUM_MISMATCH` with the state of that part of the data unknowable. That is the whole reason a step ships once.
