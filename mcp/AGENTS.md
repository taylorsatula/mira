# mcp/ — agent-facing check-in client: the pi `talkto_mira` extension and the twin contracts binding it to MIRA's server-side check-in surface

Elsewhere: the chat turn itself (auth, per-user lock, validation, commit, restart hook) — `cns/api/AGENTS.md` (`chat.py`) · the server-side MCP endpoint's mechanics (`_AuthGate`, mount gate, session-manager lifespan) — `cns/api/AGENTS.md` (`mcp.py`) · the endpoint store's writing side and `--login` token minting — `ui/tui/AGENTS.md` (`endpoints.py`, `login.py`) · pi's extension API (`ExtensionAPI`, `registerTool`, TypeBox) — the pi harness's own docs, out of tree; usage in the file · when the "may be extracted into long-term memory" promise resolves (collapse-time, post-commit — never within the call) — `lt_memory/processing/AGENTS.md` · how a feature was built — `git log`.

## Rules

- Both check-in surfaces — this extension and `cns/api/mcp.py:check_in` — are thin riders over `POST /v1/api/chat`; no turn logic lives in either: auth, the per-user lock, validation, and commit are the server's (`cns/api/chat.py`), and memory extraction plus every other post-commit effect rides the server's turn, never client code. `cns/api/mcp.py`'s module docstring assigns this design contract to this map. Turn behavior added to a check-in client (retries, prompt prep, memory handling) forks the one turn path — a check-in stops being "a real turn" and drifts from the WS/TUI clients.
- The model-facing text is a byte-identical twin: `DESCRIPTION` ≡ `cns/api/mcp.py:_CHECK_IN_DESCRIPTION`. `READ_TIMEOUT_MS` (600_000 ms) pairs with `_CHAT_READ_TIMEOUT_S` (600.0 s) — neither value bounds a legal turn (the server's lock TTL derives from `(MAX_LOCAL_TOOL_CALLS_PER_TURN + 1) * max(api.timeout, provider_response_timeout) * 2`, `cns/api/chat.py:_HTTP_TURN_LOCK_TTL_SECONDS`), so both state the realistic-turn ceiling. `execute`'s seven error rows (timeout, abort, unreachable, malformed-success, busy, rejected-token, generic-HTTP) pair semantically with `_check_in`'s six ToolError rows — the abort row is pi-client-only (no server twin); the generic-HTTP row pairs with `_check_in`'s status row. Any change lands in both files in the same commit — drift means the two surfaces teach different tools to the models reaching them.
- The description's attachment literals are calibrated against server validators: image set + 5 MB (`cns/api/chat.py:SUPPORTED_IMAGE_FORMATS`/`MAX_IMAGE_SIZE_MB`), document set + 32 MB (`utils/document_processing.py:SUPPORTED_DOCUMENT_FORMATS`/`MAX_DOCUMENT_SIZE_MB`), one image or document per message (`ChatRequest.validate_attachment_exclusion`). A limit change re-derives the description in both twins, or the tool teaches attachments the server rejects with a 400 after the payload upload.
- The busy row is the one sanctioned transcription: `cns/api/mcp.py` imports `cns/api/chat.py:_BUSY_REJECTION_MESSAGE`, TypeScript cannot — `execute` matches the hardcoded substring `"already in progress"`. An edit to `_BUSY_REJECTION_MESSAGE` keeps that substring, or the pi busy row dies silently: the model sees the generic `HTTP 400` row instead of wait-and-retry guidance. Grep before merging: `rg 'already in progress'`.
- Client abandonment is not server cancellation, and the timeout/abort rows are contracts, not boilerplate: the abort signal and `READ_TIMEOUT_MS` sever only pi's wait. `cns/api/chat.py` stages the accepted message before model work and commits it even on turn failure; the per-user lock holds until the handler ends; an immediate retry bounces with the busy row. Rewording the rows into "failed, retry now" or adding cancel semantics promises behavior that does not exist.
- `resolveEndpoint()` reads only `active`, `endpoints[active].base_url`, and `endpoints[active].api_key` from the TUI endpoint store at ~/.config/mira-tui/config.json; the format is owned by `ui/tui/endpoints.py` (reciprocal one-liner in `ui/tui/AGENTS.md`); `history_fetch` and `include_thinking` are ignored here. A format change updates both readers in the same commit, or the TUI keeps working while every `talkto_mira` call dies at `resolveEndpoint` with the unreadable-store error.
- The reply rides raw to the calling model — MIRA's own composed turn output, not ingested external content; the root's untrusted-content boundary governs what MIRA ingests, not what it emits. Wrapping the reply double-treats MIRA's voice as hostile data.
- No repo code imports, mounts, or installs this file: `rg 'talkto_mira'` returns the extension, the twin citations, and the root registry row, nothing else. The runtime consumer is pi (the file imports `@earendil-works/pi-coding-agent`), which loads extensions from ~/.pi/agent/extensions/ at startup and refuses registration on TypeScript errors; deployment is placing the file there by hand. Editing the repo file changes a running pi only via its deployed copy — test against the deployed pi, not the repo.

## Files

- `talkto_mira.ts` — the pi extension registering the `talkto_mira` tool (`pi.registerTool`: name, label, `DESCRIPTION`, promptSnippet, promptGuidelines, TypeBox params `message`/`image`/`image_type`/`document`/`document_type`). Entry: `execute` (the seven error rows; body always carries all five chat keys, null defaults — `include_thinking`/`show_cost` stay server-default False, reply text only), `resolveEndpoint` (store reader; every failure names the `python3 -m ui.tui --login` remedy), `READ_TIMEOUT_MS`. Gotcha: a message past `cns/api/chat.py`'s HTTP-only `MAX_TEXT_MESSAGE_LENGTH` (20 000 chars) returns HTTP 200 whose `data.response` is MIRA's size-limit rejection (`rejected: true`, ignored by the row) — reads as a normal reply, and the rejection itself persists an assistant message in MIRA's history.

## Wiring

- Call flow: pi model → `talkto_mira` → `resolveEndpoint` → `POST {base_url}/v1/api/chat` (Bearer api_key, five-key JSON) → the `cns/api/chat.py` turn → envelope per `cns/api/base.py` (`{success, data}` / `{success, error{code,message}}`) → `execute`'s rows. A `ChatRequest` key or envelope-shape change updates the TS body/parser in the same commit. Counterpart: `cns/api/AGENTS.md`; the mount is unconditional in `main.py` — the pi path needs no flag, unlike `/v1/mcp`'s `config.system.mcp_enabled` gate.
- Server-side twin: `cns/api/mcp.py:check_in` exposes the same turn to non-pi MCP clients — opt-in (`MIRA_MCP_ENABLED`, strict 0/1, default off), lazy SDK import, `_AuthGate` rejecting before protocol handling — twins per Rules above; gate, mount, and lifespan owned by `cns/api/AGENTS.md`.
- Credential chain: `python3 -m ui.tui --login` (flow owned by `ui/tui/AGENTS.md`, `login.py`) mints the api_key → the endpoint store (writer `ui/tui/endpoints.py`) → `resolveEndpoint()` — the 401/403 and store-error rows name the mint step as remedy.
- Turn boundary: a check-in is a gauge-registered turn — `cns/api/chat.py` calls `enter_turn`/`exit_turn`/`trigger_restart_if_pending` at the boundary, and `utils/self_restart.py`'s header names chat.py as the check-in's ride — an in-flight check-in holds a pending `restart_mira` restart; mechanism owned by `utils/AGENTS.md`.
