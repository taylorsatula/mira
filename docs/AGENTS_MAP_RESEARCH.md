# AGENTS_MAP_RESEARCH.md — research pointers behind the map system's design law

The `maintaining-agentsmd-maps` skill states the law; this file holds the pointers to the work each rule rests on. Read before amending the law or its cull, convergence, bilateral, or register rules: check the grounding before changing the rule. Pointers, not summaries — the one-line "→" note names the design element a source produced. Nothing here is operator documentation.

## Culling and slot discipline

- Carroll, *The Nurnberg Funnel* (1990); *Minimalism Beyond the Nurnberg Funnel* (MIT Press, 1998; https://mitpress.mit.edu/9780262512954/minimalism-beyond-the-nurnberg-funnel) — task-anchored documentation; the explicit warning that minimalism is disciplined task-orientation, not brevity, and careless cutting strands the reader → the cull test is arrival-task-shaped, not line-count-shaped; task-support is never cut to reach a size.
- Information Foraging Theory — Pirolli & Card, "Information Foraging" (*Psychological Review*, 1999; overview: https://en.wikipedia.org/wiki/Information_foraging); applied to software work: Robillard & DeLine, "An IFT Perspective on Tools for Debugging, Refactoring, and Reuse Tasks" (TOSEM 2012; https://dl.acm.org/doi/10.1145/2430545.2430551) — information scent and patch-residence economics; content that never changes the forager's next decision is overhead → consequence-or-cut; Entry symbols as scent; "true but decision-inert" as the deletion class.
- "A Test of Time: Predicting the Sustainable Success of Online Collaboration in Wikipedia" (PNAS Nexus 2024; https://arxiv.org/abs/2410.19150); edit-longevity studies (https://arxiv.org/abs/1206.2517) — document quality is not self-sustaining; it holds only through continuous curator attention, and curation works only when deletion is a demand-side criterion enforced per-touch → slot eviction rows in the trigger table; deletion pressure at write time, not sweep time.
- Matuschak, "Evergreen notes" (https://notes.andymatuschak.org/z5E5QawiXCMbtNtupvxeoEX) — atomic, concept-oriented notes; "note maintenance approximates spaced repetition"; the notes-as-bucket anti-pattern and the no-accumulation problem → card atomicity (the giant-bullet cure); concept-orientation (state the concept, never the source); per-touch maintenance.
- Uddin & Robillard, "How API Documentation Fails" (IEEE Software 2015; https://www.cs.mcgill.ca/~martin/papers/ieeesw2015.pdf); "Automatic Detection of Five API Documentation Smells" (https://arxiv.org/abs/2102.08486); Maalej & Robillard, "Patterns of Knowledge in API Reference Documentation" (https://www.cs.mcgill.ca/~martin/papers/tse2013a.pdf) — the classic blockers are ambiguity, incompleteness, incorrectness; verbosity is not a top failure class → the diagnosis that this corpus's accuracy machinery (trigger table, same-commit) already solved the classic problem, leaving attention cost as the actual enemy.
- Drawing revision control in capital projects (https://www.aodocs.com/blog/drawing-revision-control-capital-projects) — superseded sets are pulled from circulation, not annotated beside the new → delete-don't-annotate (corpus-native doctrine, independently corroborated).

## Demand model and section shape

- Diátaxis — Procida (https://diataxis.fr) — documentation modes answer different reader intents, and content serving two intents serves neither; improve from the inside, one step at a time; never create empty structures → Rules/Files/Wiring/one-deep-dive as jobs, not categories; restructure-don't-binary-delete; the arrival-task demand model as an authoring instrument.
- IFT, again — harness-injected maps delete the within-map navigation problem: the whole map is already in context, so enumerations of what a reader might have come for route nothing → the shipped `Arrivals:` header was cut; the demand model stays spec-side.
- Karpathy's LLM-wiki pattern (https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f); "Retrieval as Reasoning" / LLM-Wiki (https://arxiv.org/abs/2605.25480) — agent-native knowledge as a compiled, linked, self-evolving structure; evolvability defined as "self-corrects over time rather than silently degrading" → the map corpus as the agent-era instantiation of the concept; maintenance named as the frontier.

## Wiring and reciprocity

- NASA Systems Engineering Handbook (SP-2016-6105 Rev 2), §6.3 Interface Management and §6.5 Configuration Management (https://www.nasa.gov/reference/6-3-interface-management/ ; https://www.nasa.gov/reference/6-5-configuration-management/); NASA-STD-0005, endorsing SAE/EIA-649B (https://standards.nasa.gov/standard/NASA/NASA-STD-0005) — CM exists to ensure "consistency between the product and information about the product"; identification, control, accounting, verification/audit; change control requires cross-impact assessment → the trigger table (control + identification), the audits (verification), same-commit doctrine (corpus-native, corroborated).
- Interface Control Document doctrine — "Stop ICDs Going Stale" (https://tandem.inc/resources/guides/interface-control-document-guide-stop-icds-going-stale); NASA RP-1370, "Training Manual for Elements of Interface Definition and Control" (https://ntrs.nasa.gov/citations/19970018043); NTRS 20100015497, "Project Interface Requirements Process Including Shuttle Lessons Learned" (https://ntrs.nasa.gov/citations/20100015497) — interface docs are bilateral contracts at a mating plane; "if a parameter does not cross that boundary, it does not belong in the document"; internal specs dumped into interface docs rot first and bloat everything; unilateral change is void → Wiring admission (boundary-crossing facts and ordering constraints only); counterpart citations; the bilateral same-commit rule.
- MBSE — CMU SEI (https://www.sei.cmu.edu/blog/introduction-model-based-systems-engineering-mbse/); Northrop Grumman (https://www.northropgrumman.com/who-we-are/the-facts/digital-transformation/finding-a-single-source-of-truth-with-model-based-systems-engineering); https://en.wikipedia.org/wiki/Model-based_systems_engineering ; the generated-diagram school (https://dev.to/libme/the-architecture-diagram-in-your-wiki-is-lying-how-to-generate-one-from-the-code-instead-5cc8) — hand-maintained parallel documents are the losing battle; derive every view from one model; a doc that is a function of the source can only be wrong when the code is → derivation over transcription: named greps replace transcribed consumer lists; the DEAD-GREP audit.
- As-built vs as-designed drift (https://vidyatec.com/blog/as-built-vs-as-designed-detecting-divergences-in-complex-environments/); "The Real Reason Architecture Diagrams Go Stale" (https://dev.to/erajasekar/the-real-reason-architecture-diagrams-go-stale-35ok) — drift accumulates through small, individually-legitimate changes with no reconciliation step → per-touch reconciliation (audits at commit time); the reverse-edge sweep's code→map direction as the high-yield check.

## Ancestry — pre-AI equivalents, and what carried forward

- IBM Program Logic Manuals (the LY-numbered System Logic Library volumes for OS/360 and descendants); Brooks, *The Mythical Man-Month* (1975) — the documentary hypothesis: the manual is the design medium → map-first authoring for new mechanisms (spec carry-forward).
- Parnas — "On the Criteria To Be Used in Decomposing Systems into Modules" (CACM 1972); the module guide and module "secrets" ("The Modular Structure of Complex Systems") → Files routing cards: a card names what a file owns/hides in one phrase; a card that cannot name its secret is a summary.
- Parnas & Clements, "A Rational Design Process: How and Why to Fake It" (IEEE TSE, 1986) — document the design as though it had been produced rationally: present tense, no archaeology → the incident-narration ban; maps say what IS.
- HIPO (IBM, 1970s) — layered overview→detail packets → the ancestor chain (root → directory map → files) as the zoom levels.
- Lions, *Commentary on the UNIX 6th Edition Source Code* (1977) — one real path traced end-to-end teaches a mechanism better than an exhaustive catalog → traced-path deep-dives (first used in `lt_memory/processing/AGENTS.md`).
- Unit Development Folders (Tracz, IEEE Software, 1980s) — per-unit living folders → one map per directory.
- DOD-STD-2167A (1988), MIL-STD-498, IEEE 1016 *Software Design Descriptions* — the SDD's views and the Data Item Descriptions → Wiring's ancestors; DIDs → the spec's slot contracts.
- Data dictionary practice → one-home rule and defined terms.
- Wirelist/schematic pairing → raw connection data vs. derived views (the grep convention's hardware form).
- OWNERS/CODEOWNERS files (Chromium-era) — machine-consulted per-path governance documents → harness-consulted per-directory maps.
- Knuth, Literate Programming (1984) — documentation and code as one artifact under one maintenance regime → docs-as-code, the corpus's default.

## Native to this medium — no external source

- Harness-injection economics: every retained token is re-paid on each file read in the subtree; the reader never chooses to load; nothing is skimmable; no usage analytics exist, so all cull judgment is predictive (operator observation, this codebase's delivery model).
- The same-commit trigger table and the anchor audits pre-date this research pass and are corpus-native; the CM literature corroborates them.
- The register (`REGISTER.md`) is corpus-native; the research here only confirmed its two-setting structure.
- Internal evidence that motivated the write-time teeth: the corpus's own git history — per-commit net-positive growth with deletion firing only on dead referents, and corpus-wide sweeps that reorganized without subtracting. Sweeps change the artifact; only a spec change changes the mechanism.
