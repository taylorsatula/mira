# docs/ — operator-facing documentation

## Rules

- A path printed in a doc here must exist in the repo and describe the current workflow — one sanctioned exception: release-time artifacts named by contract, e.g. `BREAKING.md` (exists only in breaking release trees, owned by `deploy/AGENTS.md`). Keep deployment docs aligned with the `deploy/` scripts they cite. Verified examples: `deploy/deploy.sh`, `deploy/vault.sh`, `deploy/postgresql.sh`, `deploy/mira_service_schema.sql` (cited by MANUAL_INSTALL.md) and the `3090`/`3092` endpoint contract (cited by OFFLINE_MODELS.md; owned by `deploy/AGENTS.md` — `deploy/config.sh:CONFIG_LLAMA_MAIN_MODEL`/`CONFIG_LLAMA_SMALL_MODEL`, `deploy/postgresql.sh:LLAMA_MAIN_URL`/`LLAMA_SMALL_URL`).
- `MANUAL_INSTALL.md` is current as of the v2release-census fix wave: the dead `--migrate` tail was replaced with the no-upgrade-path statement matching `deploy/AGENTS.md`. One stale sentence remains (debt): it says the Docker container cannot provision the Vault key and the operator must seed Vault manually, but the interactive wizard (`deploy/docker/scripts/container-setup.sh` step 4) collects the System One bearer token and `deploy/docker/scripts/init-mira.sh` provisions it — `setup_from_env_vars` reads `MIRA_SYSTEMONE_API_KEY` in non-interactive mode, and `init_vault` writes `systemone_key` to Vault and `/opt/mira/systemone.env`. Fix the sentence or delete it.
- `UPGRADE_PATH.md` (repo root, unimplemented design guide) is co-owned by this map and `deploy/AGENTS.md` for its design-only status and the no-upgrade-path doctrine: it describes a possible future, never a commitment; releases never migrate the database in place — a schema change is breaking, `mira update` refuses it, and the manual path is reinstall + agent-run history import (`deploy/HOW_TO_MIGRATE_OLD_INSTALLS.txt`).
- These files are read when the automated installer cannot continue or when an operator must prepare external resources; keep them as operational checklists, not design essays.
- `docs/` holds three kinds of file: operator documentation for the host-metal install and offline model flow (`MANUAL_INSTALL.md`, `OFFLINE_MODELS.md`, `SEGMENT_SYSTEM.md`), process authorities that other maps cite (`AGENTS_MAP_SPEC.md` for map shape, `REGISTER.md` for writing register), and one-off process material with no standing authority (`MAPPING_PASS_JUMPSTART.md`, consumed at the start of a first mapping pass and historical afterward). Docker bootstrap is owned by `deploy/docker/scripts/AGENTS.md`; that map's claim that `MANUAL_INSTALL.md` and `OFFLINE_MODELS.md` reference no `deploy/docker/scripts/` files holds (grep-verified).

## Files

- `MANUAL_INSTALL.md` — Manual setup checklist for platforms the installer rejects (the automated matrix is macOS/brew, Debian-family/apt, Fedora-family/dnf x86_64, Arch-family/pacman): required services (PostgreSQL 17 + pgvector, Valkey, Vault, Python ≥3.12 — installer prefers the newest of 3.12–3.14), the Arch manual-initdb note (the pacman package does not initialize the cluster), default ports (1993/8200/6379/5432), venv + local-embedding stack (PyTorch CPU + sentence-transformers; skipped for a remote endpoint) + Playwright setup, schema load with the `deploy/lib/embedding_config.sh` variables, run command. Current except the Docker injection-screen sentence (see ## Rules).
- `OFFLINE_MODELS.md` — Offline/local LLM preparation: endpoints (`localhost:3090` main, `localhost:3092` small), model storage (`/opt/mira/models/`), llama-server log paths, startup checklist. Current — endpoint/port/log claims match `deploy/config.sh`, `deploy/postgresql.sh`, `deploy/finalize.sh`.
- `SEGMENT_SYSTEM.md` — Segment lifecycle overview: active segment, live context compaction vs segment collapse (`SegmentCollapseHandler`, sentinel messages, `messages.segment_embedding`, sized by the install's embedding model). Current; matches `cns/services/segment_collapse_handler.py` and `deploy/mira_service_schema.sql`. Conceptual overview, not an operator checklist.
- `GLOSSARY.md` — one-sentence definitions of codebase-specific terms (segment, sentinel, subcortical, trinket, route, probe verdicts, and similar), each pointing at its owning map. Agent-facing reference: read it when a term in a user message or tool result has no obvious meaning. Add an entry in the same commit as any new term that appears in a map, prompt name, config field, or file name.
- `AGENTS_MAP_SPEC.md` — the full AGENTS.md map specification: shape, authoring rules, cross-map reciprocity, the complete maintenance trigger table, and the run-before-committing anchor audits. Root `AGENTS.md` carries the map registry, the high-frequency obligations, and points here; this file is the authority.
- `REGISTER.md` — the house writing register for agent-written text: skills, agent definitions, `AGENTS.md` maps, docs, commit messages, model-facing prompts. Names the register (**cablese directive**), states the one rule (delete only what the reader can reconstruct), and carries the delete/keep tables, the three-layer compression floors, the person and obligation conventions, the two settings, and the before-saving checklist. Read it into context before writing or editing any file a model will read; it is self-contained and needs no other document. Not operator documentation — no install or runtime surface.
- `MAPPING_PASS_JUMPSTART.md` — one-off kickoff brief for the agent swarm running a project's first mapping pass under `AGENTS_MAP_SPEC.md`: swarm shape (editors/verifiers/arbiters funnel), the failure classes verifiers must hunt by name, and the latent-bug byproduct policy. Distilled from the 2026-09 regeneration pass's git history (commits cited in the file). Consumed at pass start; after the pass closes it is a historical record — no maintenance trigger fires on it.
